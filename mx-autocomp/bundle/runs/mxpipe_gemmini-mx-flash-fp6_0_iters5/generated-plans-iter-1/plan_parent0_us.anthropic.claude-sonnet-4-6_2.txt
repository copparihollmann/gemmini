# Optimization Plan: Hoist Redundant Operations Out of Loops

## Strategy: #2 — Hoist redundant operations out of loops

## Analysis of the Current Code

Looking at the baseline code, the outer loop is `for(int t=0; t<NT; t++)`, and inside this loop there are **two hardware matmul blocks** (QK^T and PV). Each iteration performs:

### Block 1 (QK^T: Q × KT → S1):
- `gemmini_flush(0)` — **unnecessarily called every iteration**
- `gemmini_extended3_config_ex(...)` — **same arguments every iteration**
- `gemmini_mx_load_scales(...Q_scales_row..., 0)` — **Q scales never change across `t`**; Q is fixed, yet it's reloaded every iteration of the `t` loop

### Block 2 (PV: P × V → O):
- `gemmini_flush(0)` — **unnecessarily called every iteration**
- `gemmini_extended3_config_ex(...)` — **same arguments every iteration**
- `gemmini_config_st(...)` — **same stride every iteration**

## Specific Changes

### 1. Hoist `gemmini_flush(0)` before the `t` loop
Both blocks call `gemmini_flush(0)` on every iteration. A flush only needs to happen once at initialization to clear stale state. Move both `gemmini_flush(0)` calls to before the `for(int t=0; t<NT; t++)` loop, and remove them from inside the loop. This eliminates `2*NT` flush operations down to 2.

### 2. Hoist `gemmini_extended3_config_ex(...)` before the `t` loop
Both calls to `gemmini_extended3_config_ex` use **identical arguments** (`WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 1, 1, 3, 1`) and never change across iterations. These configure persistent hardware state (format, dataflow, strides). Issue them once before the `t` loop. This eliminates `2*NT` config instructions down to 2.

### 3. Hoist `gemmini_mx_load_scales(...Q_scales_row..., 0)` for Block 1
Q is the query matrix — it is **fixed across all `t` iterations** (the `t` loop iterates over KV sequence blocks, not Q). The Q scale factors `Q_scales_row` never change. Move this single `gemmini_mx_load_scales` call to before the `t` loop. This eliminates `NT-1` redundant scale-load operations. **Important:** The KT scales (`KTsc`) do change each `t` iteration and must remain inside the loop.

### 4. Hoist `gemmini_config_st(...)` calls where stride is constant
- Block 1: `gemmini_config_st((BT/BF16_PER_WORD)*sizeof(out_t))` — same every `t`; hoist before the loop
- Block 2: `gemmini_config_st((ATT_D/BF16_PER_WORD)*sizeof(out_t))` — same every `t`; these two have different strides so they cannot both be hoisted to one place before the loop, but Block 2's can be noted as invariant. Since Block 1 and Block 2 alternate within the loop and use different strides, hoist Block 1's config_st before the loop and re-issue Block 2's config_st once per iteration just before Block 2 begins (it was already there — but Block 1's re-issue is the redundant one to eliminate).

### 5. Hoist Q MVIN before the `t` loop
Q tiles are loaded in Block 1's mvin loops (`gemmini_extended_mvin` over `i,k` for Q_hw`). Since Q never changes across `t`, these mvin operations load the **same data to the same scratchpad addresses** every iteration. Hoist the Q mvin loop (including its `gemmini_config_ld`) to before the `t` loop so Q tiles are loaded once into scratchpad at `a_base=0` and remain there. **Constraint check:** the scratchpad layout for Block 1 uses `ab=0` (A tiles) and `bb=BANK_NUM*BANK_ROWS - tk*tj*DIM` (B tiles for KT). With `ti=ATT_S/DIM/2=4`, `tk=ATT_D/DIM=4`, `tj=BT/DIM/2`, Q occupies `ti*tk*DIM = 4*4*16 = 256` rows at the bottom. KT tiles sit at the top. As long as `256 + tk*tj*DIM ≤ 8192`, the layout is valid. After hoisting Q mvin, Block 1 inside the loop only needs to mvin KT tiles (which change every `t`).

## Summary of Changes

| Operation | Before | After |
|-----------|--------|-------|
| `gemmini_flush` | 2×NT calls | 2 calls (before loop) |
| `gemmini_extended3_config_ex` (Block 1) | NT calls | 1 call (before loop) |
| `gemmini_extended3_config_ex` (Block 2) | NT calls | 1 call (before loop) |
| `gemmini_mx_load_scales(Q_scales_row, -, 0)` | NT calls | 1 call (before loop) |
| `gemmini_config_st` (Block 1) | NT calls | 1 call (before loop) |
| Q tile mvin loop | NT × ti×tk mvin calls | 1× ti×tk mvin calls (before loop) |
| KT scale build + load | NT calls (unchanged) | NT calls (must remain) |
| KT tile mvin | NT calls (unchanged) | NT calls (must remain) |

The `gemmini_mxquant_config_mvout` calls **cannot** be hoisted because they reference tile-count-specific bounds and `scale_factors` that are consumed per-iteration — they remain inside the loop. Similarly, KT and V scale loads change per-`t` and must stay inside.

This plan focuses purely on hoisting redundant, iteration-invariant setup operations out of the `t` loop, directly reducing instruction count and accelerator stall cycles by eliminating `O(NT)` redundant configuration and data-load instructions.
