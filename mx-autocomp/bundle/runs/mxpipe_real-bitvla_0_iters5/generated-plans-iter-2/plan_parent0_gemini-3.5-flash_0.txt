An elegant and highly effective optimization plan to reduce the execution latency of the MX-Gemmini matmul kernel.

### Optimization Plan: Cache Reused Data in Local Memory (Strategy 1)

**Analysis of Inefficient Data Caching in the Baseline:**
In the baseline code, the weight matrix $B$ is loaded into the scratchpad via nested loops. However, the loop order is structured as `j` (outer) and `k` (inner):
```c
for (int j = 0; j < tiles_J; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin((void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + j * DIM), ...);
```
For each fixed column tile `j`, the inner loop steps through row tiles `k`. This results in:
1. **Non-contiguous DRAM Accesses:** The DRAM source pointer leaps by `DIM * MATMUL_N` bytes in every inner iteration, completely breaking spatial locality and failing to utilize the memory controller's burst capabilities.
2. **Non-contiguous Scratchpad Writes:** The destination address `b_base + (k * tiles_J + j) * DIM` jumps by `tiles_J * DIM` rows in each iteration, which leads to strided and inefficient scratchpad writing.

**Optimization Strategy:**
We will apply **Strategy 1** to maximize the local caching efficiency of the stationary $B$ matrix. By swapping the loop nest of $B$ to `k` (outer) and `j` (inner), we align the DMA data transfers with both the layout of DRAM and the scratchpad structure:
1. **Contiguous DRAM Striding:** For a fixed `k`, incrementing `j` accesses memory sequentially (increasing by `DIM` bytes per iteration).
2. **Contiguous Scratchpad Allocation:** As `j` increases, the destination address `b_base + (k * tiles_J + j) * DIM` increments contiguously by exactly `DIM` rows (16 rows) in the local memory.
This dramatically increases DMA efficiency, exploits hardware prefetching, and reduces CPU-to-coprocessor instruction overhead.

### Modified C Code

```c
// Optimized MX matmul kernel (32x256x256, fp8:e4m3).
void solution(void) {
  // 1. Configure execution format and strides
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);

  // 2. Load scale factors into scale-factor memories
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // 3. MVIN A tiles: sequential loading along K is already contiguous
  gemmini_config_ld(MATMUL_K * sizeof(elem_t));      // A rows: stride K
  for (int i = 0; i < tiles_I; i++) {
    for (int k = 0; k < tiles_K; k++) {
      gemmini_extended_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM),
                            a_base + (i * tiles_K + k) * DIM, DIM, DIM);
    }
  }

  // 4. MVIN B tiles: loop swapped to (k, j) to ensure contiguous DRAM reads and contiguous scratchpad writes
  gemmini_config_ld(MATMUL_N * sizeof(elem_t));      // B rows: stride N
  for (int k = 0; k < tiles_K; k++) {
    for (int j = 0; j < tiles_J; j++) {
      gemmini_extended_mvin((void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + j * DIM),
                            b_base + (k * tiles_J + j) * DIM, DIM, DIM);
    }
  }

  // 5. Configure store and MX-quantization bounds
  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);

  // 6. Execute high-performance fused weight-stationary matmul loop
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, PAD_I, PAD_J, PAD_K, a_base, BANK_NUM * BANK_ROWS, 0,
                       SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);

  // 7. Drain output results from SMEM and synchronize
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, REAL_M * MATMUL_N);
  gemmini_fence();
}
```
