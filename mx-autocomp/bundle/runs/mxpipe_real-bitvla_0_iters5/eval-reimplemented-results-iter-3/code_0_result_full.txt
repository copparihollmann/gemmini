### Explanation of the Strategy

In the baseline implementation, both matrix $A$ and matrix $B$ are loaded using the default `gemmini_extended_mvin` instruction, which maps to DMA Port 0. This serializes all memory transfers because the RISC-V host CPU queues all DMA requests in a single hardware queue.

However, the Gemmini hardware architecture features **three independent DMA channels/ports** (`mvin`, `mvin2`, and `mvin3`) that can process memory transfers in parallel. 

By applying this strategy:
1. We configure **DMA Port 0** specifically for the layout and stride of Matrix $A$.
2. We configure **DMA Port 1** specifically for the layout and stride of Matrix $B$ using `gemmini_extended3_config_ld` with `id = 1`.
3. We replace B's loading calls with `gemmini_extended_mvin2`, which maps to DMA Port 1.
4. We **interleave the dispatch of A and B tile transfers** in a single outer loop over the $K$ dimension. 

This interleaving fills both hardware DMA queues simultaneously. The Gemmini memory controller can then overlap the DRAM access latencies of both ports in parallel, maximizing memory bandwidth utilization and eliminating the serialization bottleneck.
