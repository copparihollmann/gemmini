### Optimization Plan: Pipelined Output Transfers via Double-Buffered Accumulator and Scratchpad (Strategy 3)

We will implement **Strategy 3: pipeline `gemmini_mx_read_smem` reads with next-tile mvin to overlap output transfer and input loading**. This approach significantly reduces execution time by keeping the Gemmini systolic array fed with compute instructions while output transfers run asynchronously in the background.

#### 1. Inefficiencies in the Baseline Code:
- **Sequential Execution**: Compute and data transfer are entirely serialized. The CPU waits for the whole matmul to finish, then blocks during `gemmini_mx_read_smem` and the final fence.
- **High Instruction Overhead**: B-tiles are loaded individually, resulting in $16 \times 16 = 256$ independent `gemmini_extended_mvin` instructions. Since `MAX_BLOCK_LEN = 4`, we can load up to 4 contiguous tiles of size `DIM` at once.
- **Zero Scratchpad/Accumulator Overlap**: The hardware resources are single-buffered, meaning new data cannot be loaded until the current computation and transfer are completely done.

#### 2. Key Optimization Strategies:
- **Tiling along $J$**: We will divide `tiles_J` (16) into blocks of size `J_TILE = 4`. This splits the computation into 4 blocks of $32 \times 64 \times 256$.
- **Contiguous Block MVIN**: For each block of $J$, we will load the weights $B$ using block-based `mvin` with columns of width `4 * DIM = 64`. This reduces the number of load instructions for $B$ from 256 to 64. Similarly, we will load $A$ using 4-tile wide blocks.
- **Double-Buffered Scratchpad**: We will split the upper scratchpad region into two buffers for $B$ (`b_bases[2] = {7168, 6144}`).
- **Double-Buffered Accumulator/SMEM**: Since each block needs only $32 \times 64$ output elements, it occupies exactly 128 rows of the accumulator. We can perfectly double-buffer `SPAD_DEST` (`spad_dests[2] = {0, 128}`) to completely eliminate write-after-read hazards.
- **Three-Stage Software Pipeline**: We will construct a loop with stage indicators:
  - **Stage 1 (Load)**: Load $B$ for block `b` into scratchpad buffer `b % 2`.
  - **Stage 2 (Compute)**: Execute the weight-stationary gemmini loop for block `b-1` writing to `spad_dests[(b-1) % 2]`.
  - **Stage 3 (Store)**: Asynchronously stream results of block `b-2` from `spad_dests[(b-2) % 2]` in SMEM to DRAM.
- **CPU Reconstruction**: Because the slices are non-contiguous in the final row-major DRAM buffers, each block of `gemmini_mx_read_smem` and scale-factor writes will output to contiguous temporary DRAM buffers (`C_temp` and `scale_factors_temp`). At the end of the kernel (after the `gemmini_fence()`), the CPU will assemble the final non-contiguous outputs, adding negligible overhead.
