### Method Explanation

In the baseline implementation, the entire $M \times N \times K$ matrix multiplication is executed in a single monolithic hardware loop. However, this has several inefficiencies:
1. **Accumulator Constraint Violation:** The accumulator single-buffer capacity is $256$ rows. With `tiles_I = 2` and `tiles_J = 16`, the total accumulator space required is $2 \times 16 \times 16 = 512$ rows, which exceeds the limit and could cause structural hazards or out-of-bounds corruption.
2. **Lack of Double Buffering:** The scratchpad is $256\text{ KB}$ ($8192$ rows) and is completely single-buffered, meaning the compute unit sits idle while new inputs are loaded, and the DMA engine sits idle during computation.

By tiling the $M$ dimension (using $I$-tiling) in software into two blocks of size $\text{tiles\_I\_block} = 1$:
1. **Weight-Stationary B-Reuse:** The $B$ matrix (weights) is shared across the entire $M$ dimension. We load the entire $B$ matrix into the top of the scratchpad *once* at the beginning and keep it stationary. We completely avoid reloading B for the second block, saving 50% of the weight DMA transfers.
2. **Double-Buffered A-Pipelining:** We partition the scratchpad to double-buffer the $A$ matrix inputs. While the first block ($i=0$) is computing, we concurrently stream the $A$ matrix inputs for the second block ($i=1$) into the second scratchpad buffer. 
3. **Hardware Queue Overlap:** Because the RISC-V coprocessor execution is non-blocking, we can interleave the memory loads (`gemmini_extended_mvin`) and the output drain (`gemmini_mx_read_smem`) of block 0 with the compute phase (`gemmini_loop_ws_spad`) of block 1, maximizing hardware execution pipeline overlap.

### Scratchpad Memory Layout
- **B (Weight-Stationary):** rows `4096` to `8191`
- **A Buffer 0 (Block 0):** rows `0` to `255`
- **A Buffer 1 (Block 1):** rows `256` to `511`

This layout is completely non-overlapping and safely fits within the $8192$-row scratchpad.
