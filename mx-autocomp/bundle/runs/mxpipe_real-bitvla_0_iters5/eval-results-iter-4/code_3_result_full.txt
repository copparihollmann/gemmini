### Strategy Explanation

In the baseline implementation, both matrix A and matrix B are loaded into the scratchpad sequentially using the same `gemmini_extended_mvin` instruction (which uses the default load controller `id=0`). This creates two severe performance bottlenecks:
1. **Serialization of Data Movement**: Since both matrices use the same DMA port, the hardware cannot overlap the loading of A and B. The memory transfer of B cannot start until the transfer of A is completely finished.
2. **Redundant Configuration Overhead**: The host CPU must repeatedly reconfigure the DMA stride (`gemmini_config_ld`) between `MATMUL_K` and `MATMUL_N` because the same load controller is shared.

**Our Optimization**: 
We configure two separate hardware load controllers: `id=0` for matrix A (stride `MATMUL_K`) and `id=1` for matrix B (stride `MATMUL_N`). We then load matrix A using `gemmini_extended_mvin` (port 0) and matrix B using `gemmini_extended_mvin2` (port 1). 

Furthermore, we restructure the loops to use `k` as the outermost loop. In each step, we interleave the loading of the $k$-th column of A tiles with the $k$-th row of B tiles. This maximizes the utilization of both hardware DMA engines simultaneously and completely eliminates all redundant stride reconfiguration instructions.
