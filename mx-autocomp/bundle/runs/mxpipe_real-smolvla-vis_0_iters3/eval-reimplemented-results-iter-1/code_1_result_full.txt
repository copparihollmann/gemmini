### Key Observation

The output array `C_hw` is row-major with `OUT_COLS / BF16_PER_WORD` words per row. The MX shared memory stores the output block in row-major order with an in-smem row stride of `BLK` BF16 elements. The DRAM destination `C_hw[i0*BLK + r][(j0*BLK)/BF16_PER_WORD]` is contiguous across rows **only if** the smem row stride matches the DRAM row stride.

### When Full Consolidation Is Possible

If `BLK == OUT_COLS` (i.e., the block covers the full output width), then consecutive smem rows map to consecutive DRAM rows with no gap — a single `gemmini_mx_read_smem` call suffices for the entire `mrows × ncols` block.

When `BLK < OUT_COLS`, the DRAM rows have stride `OUT_COLS` BF16 elements but smem rows have stride `BLK` — so per-row calls are needed **unless** we use the full-width case. However, we can still reduce call count by reading full rows (all `BLK` columns including padding columns), if the output buffer has contiguous row layout and we cap reads to `ncols`.

### Concrete Change

Replace the per-row loop with a **single** `gemmini_mx_read_smem` call when the output rows in `C_hw` are contiguous in memory (i.e., `ncols == BLK` and `mrows == BLK`, or more generally when the smem layout is stride-compatible with DRAM).

For the general case, consolidate to read `mrows` full rows at once when `ncols == BLK` (full-width column block), and keep per-row calls only when `ncols < BLK` (partial last column block). Since `BLK` divides `REAL_N` evenly (except possibly the last block), most blocks will have `ncols == BLK`.

Specifically:
- **When `ncols == BLK`** (full column block, which is the common case): issue a single `gemmini_mx_read_smem(&C_hw[i0*BLK][j0*BLK/BF16_PER_WORD], SPAD_DEST*16, mrows * BLK)` — one DMA transfer for the entire `mrows × BLK` contiguous region.
- **When `ncols < BLK`** (partial last column block): keep the per-row loop (required since smem stride `BLK` ≠ DRAM stride `OUT_COLS`... but actually even here, if `BLK == ncols` they're the same; otherwise fall back to per-row).

The single call eliminates up to `BLK - 1` RoCC instructions per output block and removes the loop overhead entirely for full blocks, directly reducing accelerator command latency.
