## Analysis of the Inefficiency

In the original code, there are two consecutive `gemmini_fence()` calls before `gemmini_mx_read_smem` in the SPIKE_SIM path:

```c

  gemmini_poll_until_ready();
#endif
gemmini_fence();

#ifdef SPIKE_SIM
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
#else
  ...
#endif
```

On the SPIKE_SIM path (which is the target for optimization), this compiles to:
```c
gemmini_fence();
// poll_until_ready is compiled out
gemmini_fence();
gemmini_mx_read_smem(...);
```

Two back-to-back `gemmini_fence()` instructions provide no additional ordering guarantee over a single `gemmini_fence()`. A fence is a full memory barrier — once the first fence completes, all preceding accelerator operations are drained. Issuing a second fence immediately after the first one simply re-checks an already-empty queue, adding unnecessary overhead (each `asm volatile("fence")` is a serializing instruction that stalls the CPU pipeline until the RoCC coprocessor acknowledges the barrier). This contributes to the measured latency of 853 cycles.

## Proposed Change

Remove the first `gemmini_fence()` (and the dead `#ifndef SPIKE_SIM gemmini_poll_until_ready() #endif` block) before `gemmini_mx_read_smem`, leaving exactly one `gemmini_fence()` after `gemmini_mx_read_smem` as required by Rule 9.

The correct ordering remains:
1. `gemmini_loop_ws_spad` (compute)
2. `gemmini_mx_read_smem` (drain results to DRAM)
3. `gemmini_fence()` (single barrier before host reads output)
