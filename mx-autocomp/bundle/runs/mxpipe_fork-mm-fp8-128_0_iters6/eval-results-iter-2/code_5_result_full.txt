## Analysis of the Current Code

The current code uses:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```

The `lut_update_granularity` parameter is set to **1**, meaning the output LUT refreshes after every single output tile during the requantization post-pass. For a 128×128 matmul with `tiles_I = 8`, `tiles_J = 8`, `tiles_K = 8`, there are 64 output tiles — and with G=1, the requantizer re-runs a LUT refresh 64 times unnecessarily.

## The Strategy

**Strategy 9 + Strategy 5 (tune `lut_update_granularity`):** Increase `lut_update_granularity` G to `tiles_J` (or the full `tiles_I * tiles_J`) so the LUT refreshes at most once per row-of-tiles (or once for the entire output), amortizing the refresh overhead across all J-tiles within each I-row. Since all output tiles share the same BF16 output format (out_mx_fmt=3) and the same quantization target throughout the entire matmul, there is no correctness reason to refresh the LUT more frequently than once.

## Specific Change

Replace:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```
With:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_J);
```

Setting `G = tiles_J = MATMUL_N / DIM` means the LUT updates once per row of output tiles rather than once per tile. This reduces LUT refresh overhead by a factor of `tiles_J` (8× for the 128×128 case).

## Why This Is Safe

The output format is BF16 (`out_mx_fmt=3`) and the same scale factors and quantization mapping apply uniformly to all output tiles. The LUT state does not change meaningfully between tiles — refreshing it on every tile is redundant overhead. The `lut_update_granularity` field controls performance, not correctness, when the LUT contents are identical for all tiles sharing the same weight format.
