## Analysis

Looking at the code, I need to identify the key inefficiency to address with a single strategy.

**Key observation:** In every iteration of the outer `t` loop (0 to N_TILES-1), **step 1 (Q @ KT)** loads Q tiles into the scratchpad from scratch:
- `tiles_I * tiles_K = (ATT_S/DIM) * (ATT_D/DIM) = 8 * 4 = 32` mvin calls per tile iteration
- Q (`Q_in`) is **invariant across all N_TILES iterations** — it never changes
- These 32 mvin calls are completely redundant for tiles t=1 through N_TILES-1

**Strategy 13** directly addresses this: *reuse the Q scratchpad tiles across all N_TILES iterations of the outer loop by loading Q into the scratchpad once before the tile loop.*

## Plan

### What to change

**Before the `for (int t = 0; t < N_TILES; t++)` loop:**

1. Compute `tiles_I = ATT_S/DIM`, `tiles_K = ATT_D/DIM` for the Q@KT matmul.
2. Fix `a_base = 0` for Q tiles.
3. Issue `gemmini_config_ld(ATT_D * sizeof(elem_t))` once.
4. Issue all `tiles_I * tiles_K = 32` `gemmini_extended_mvin` calls to load Q tiles into `a_base + (i*tiles_K + k)*DIM` in the scratchpad.

**Inside the `for (int t = 0; t < N_TILES; t++)` loop, in step 1:**

- Remove the `gemmini_config_ld(ATT_D * sizeof(elem_t))` and the entire Q mvin double-loop (the `for (int i ...) for (int k ...)` block that loads `Q_in` tiles).
- Keep everything else (flush, config_ex, load_scales, KT mvin, config_st, mxquant_config_mvout, loop_ws_spad, read_smem, fence) unchanged.

### Why this is safe

- Q tiles occupy rows `[0, tiles_I * tiles_K * DIM) = [0, 512)` in the scratchpad. B tiles (`KT`) are placed at `b_base = 8192 - tiles_K * tiles_J * DIM = 8192 - 4*4*16 = 8192 - 256 = 7936`, so there is no overlap.
- The scratchpad is not flushed between tile iterations (only `gemmini_flush(0)` resets hardware state, but scratchpad data persists — however, `gemmini_flush` **does** flush the command queue, not scratchpad contents; scratchpad rows are not cleared by flush).
- Q tiles at `a_base=0` remain valid across all iterations since nothing overwrites rows 0–511.
- This saves `32 mvin calls × N_TILES` total mvin instructions.

### Scratchpad capacity check

For Q@KT: `(tiles_I*tiles_K + tiles_J*tiles_K)*DIM = (32 + 16)*16 = 768 rows ≤ 8192`. Safe.

For P@V (step 3): `tiles_K=BT/DIM=4`, `tiles_J=ATT_D/DIM=4`, `tiles_I=ATT_S/DIM=8`. `(32 + 16)*16 = 768 rows ≤ 8192`. Safe and unchanged.

### Summary of code changes

1. Add a pre-loop Q-load block (with `gemmini_config_ld` and the Q mvin loops) before `for (int t = 0; t < N_TILES; t++)`.
2. Delete the Q `gemmini_config_ld` and Q mvin loops from inside the step-1 block, keeping the KT config_ld and mvin loops, and all subsequent instructions, unchanged.
