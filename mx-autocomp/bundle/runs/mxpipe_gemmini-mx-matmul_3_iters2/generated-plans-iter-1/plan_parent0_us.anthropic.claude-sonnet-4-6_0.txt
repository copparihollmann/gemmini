## Analysis of the Original Code

The original code has this structure:
1. Configure execution
2. Load scales (A and B)
3. Load all A tiles into scratchpad
4. Load all B tiles into scratchpad
5. Configure mvout
6. Execute `gemmini_loop_ws_spad`
7. Read results + fence

The key inefficiency I'm focusing on: **`lut_update_granularity` is set to `1`**, meaning the requantizer refreshes its LUT after every single tile operation. For a 128×128×256 matmul with `tiles_K = K/DIM = 256/16 = 16`, `tiles_I = 128/16 = 8`, `tiles_J = 128/16 = 8`, this causes 8×8×16 = 1024 unnecessary LUT refreshes when they could be amortized.

## Strategy Selection

**Strategy 11: Increase `lut_update_granularity` to `tiles_K` (or its maximum allowed value) in `gemmini_mxquant_config_mvout`.**

## Plan

### What the parameter does
In `gemmini_mxquant_config_mvout`, the `lut_update_granularity` parameter `G` controls how often the requantizer refreshes its output LUT during the fused hardware loop. Currently it is set to `1`, meaning the LUT is refreshed after every individual tile step — the most expensive possible setting.

### What to change
The `lut_update_granularity` argument in the `gemmini_mxquant_config_mvout` call should be changed from `1` to `tiles_K` (which equals `MATMUL_K / DIM = 256 / 16 = 16`).

Setting `G = tiles_K` means the LUT is only refreshed once per complete K-sweep for each (I, J) output tile pair, rather than once per individual K-tile step. Since all K-tiles within a single output tile accumulate into the same C location, a single LUT refresh per output tile is sufficient for correctness — the requantization only needs to run once the full dot product across K is complete.

### Specific code change
In the `gemmini_mxquant_config_mvout` call, change:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```
to:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_K);
```

### Why this is correct and safe
- The matmul uses `ex_accumulate = false` and `gemmini_loop_ws_spad` handles full K accumulation internally in hardware. The requantization post-pass runs after the full K sweep for each (I, J) pair, so the LUT only needs to be valid at that point — not at every K step.
- No other parameters change; scales, formats, tile counts, scratchpad layout, and output destination remain identical.
- The output remains bit-exact BF16 because the requantization computation itself is unchanged; only the refresh frequency of the LUT lookup table is reduced from once-per-K-tile to once-per-output-tile.
- This reduces LUT refresh overhead by a factor of `tiles_K = 16`, directly cutting requantizer setup cost inside the hardware loop from 1024 refreshes down to 64 (one per output tile pair).
