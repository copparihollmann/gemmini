## Selected Strategy: **Loop Reordering and Restructuring (Strategy 2) — specifically, batching mvin commands using `MAX_BLOCK_LEN=4`**

### Inefficiency Identified

Each `gemmini_extended_mvin` call transfers exactly one `DIM×DIM = 16×16` tile. However, the hardware supports `MAX_BLOCK_LEN=4`, meaning a single mvin command can transfer up to **4 consecutive DIM-row tiles** at once. The baseline never exploits this — it issues one command per tile, incurring 4× the instruction overhead.

The key insight is: `gemmini_extended_mvin(dram_ptr, spad_addr, cols, rows)` can use `cols = len*DIM` (up to `4*16=64` columns) and `rows = DIM` to transfer `len` consecutive tiles in one shot — **but only when the tiles are contiguous in both DRAM and scratchpad**.

### Plan

**For A tiles:** For a fixed `i`, iterating over `k = 0..tiles_K-1`, the DRAM addresses are `A_in + i*DIM*MATMUL_K + k*DIM` — stride `DIM` bytes in the K dimension. These are **not** contiguous in DRAM (they are strided by `MATMUL_K` bytes per row, not packed). So blocking consecutive k-tiles for A requires contiguous rows in DRAM, which holds since each row of A_in has `MATMUL_K` elements, so tile `(i,k)` starts at byte offset `i*DIM*MATMUL_K + k*DIM` — adjacent k-tiles within a row differ by `DIM` bytes, but the rows within a tile span `DIM` rows of A, each row `MATMUL_K` bytes wide. Within one `(i,k)` tile the DIM rows are contiguous with stride `MATMUL_K`. A block-mvin of length `L` means `cols = L*DIM, rows = DIM`, transferring a `DIM × (L*DIM)` block — this works when tiles along K are adjacent in DRAM columns (they are, since K is the inner dim of A).

Actually, re-reading: `gemmini_extended_mvin(dram_addr, spad_addr, cols, rows)` sends a `cols×rows` block. For A, each tile is `DIM cols × DIM rows`. To batch `L` consecutive k-tiles for the same i-tile, we'd set `cols = L*DIM, rows = DIM`… but that only works if the tiles are laid out as a single fat row in DRAM, which they're not (they span `DIM` DRAM rows).

The correct batching pattern: for a fixed `i` and consecutive `k` values, A_in DRAM rows are contiguous (stride `MATMUL_K`), but the mvin stride is already set to `MATMUL_K`. The mvin reads `rows=DIM` rows, each `cols` bytes. To batch two k-tiles: `cols=2*DIM, rows=DIM` from `A_in + i*DIM*MATMUL_K + k*DIM`. This reads a `2*DIM × DIM` submatrix — which IS exactly two adjacent k-tiles in A (since k runs along columns, cols=K direction). ✓

Similarly for B: tile `(k,j)` is at `B_in + k*DIM*MATMUL_N + j*DIM`. For fixed `k`, consecutive `j` tiles differ by `DIM` columns — batch with `cols=L*DIM, rows=DIM`. ✓ For fixed `j`, consecutive `k` tiles differ by `DIM` rows — batch with `cols=DIM, rows=L*DIM` — but the scratchpad layout `b_base + (k*tiles_J + j)*DIM` is not contiguous across k either.

**Practical batching strategy:**

- **A mvin**: For each `i`, loop over `k` in batches of `L=4` (MAX_BLOCK_LEN). Issue one mvin with `cols=L*DIM, rows=DIM`, DRAM ptr at `A_in + i*DIM*MATMUL_K + k*DIM`, spad at `a_base + (i*tiles_K + k)*DIM`. The spad addresses `a_base + (i*tiles_K+k)*DIM` through `a_base + (i*tiles_K+k+L-1)*DIM` are consecutive. ✓. `tiles_K=16` is divisible by 4.

- **B mvin**: For each `k`, loop over `j` in batches of `L=4`. Issue one mvin with `cols=L*DIM, rows=DIM`, DRAM ptr at `B_in + k*DIM*MATMUL_N + j*DIM`, spad at `b_base + (k*tiles_J + j)*DIM`. ✓. `tiles_J=8` is divisible by 4.

This reduces A-mvin commands from 128 → 32 and B-mvin commands from 128 → 32, for a total of 64 vs. 256 — a **4× reduction in DMA instruction count**.
