## Analysis of the Current Code

The current code has `gemmini_flush(0)` and `gemmini_extended3_config_ex(...)` **inside** the outer `i0 × j0` double loop. Since the MX format fields (`WEIGHT_STATIONARY`, `act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`) are completely invariant across all `(i0, j0)` iterations, this means the configuration instruction is re-issued `BLOCKS_M × BLOCKS_N` times unnecessarily. Each invocation of `gemmini_extended3_config_ex` and `gemmini_flush` adds overhead that compounds across every block iteration.

## Strategy: Hoist `gemmini_extended3_config_ex` (and `gemmini_flush`) Outside All Loops

### Plan

**Step 1:** Remove `gemmini_flush(0)` and `gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0)` from inside the `i0`/`j0` loop body.

**Step 2:** Place a single `gemmini_flush(0)` call at the very top of `solution()`, before any loop, to reset accelerator state once.

**Step 3:** Place a single `gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0)` call immediately after `gemmini_flush(0)`, also outside all loops.

**Step 4:** Leave everything else inside the loop unchanged — `gemmini_mx_load_scales`, `gemmini_config_ld`, mvin loops, `gemmini_config_st`, `gemmini_mxquant_config_mvout`, `gemmini_loop_ws_spad`, `gemmini_mx_read_smem`, and `gemmini_fence()` all remain per-block because they depend on `(i0, j0)`-specific data (scale subsets, DRAM tile pointers, padding dimensions, output destinations).

**Step 5:** The programming model sequence rule (config_ex → load_scales → mvin → mxquant_config_mvout → loop_ws_spad → read_smem → fence) is preserved: `config_ex` is still issued before the first `mx_load_scales`, because config_ex is now at the top of the function, which executes before any loop iteration reaches `mx_load_scales`.

### Why This Is Valid

- The format fields `WEIGHT_STATIONARY`, `act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`, `A_stride=1`, `C_stride=1`, transposes=false, `set_only_strides=false` do not change between any `(i0, j0)` pair — they are compile-time constants.
- `gemmini_extended3_config_ex` sets persistent hardware state that remains valid until overwritten. Since no other instruction in the loop changes these fields, issuing it once at the start is semantically identical to issuing it every iteration.
- `gemmini_flush(0)` is a one-time reset; re-flushing every block iteration is wasteful and unnecessary once the accelerator is already in a clean state.
- The savings scale as `O(BLOCKS_M × BLOCKS_N)`: with `BLOCKS_M = REAL_M / BLK` and `BLOCKS_N = REAL_N / BLK`, even moderate matrix sizes yield dozens of eliminated config+flush pairs.
