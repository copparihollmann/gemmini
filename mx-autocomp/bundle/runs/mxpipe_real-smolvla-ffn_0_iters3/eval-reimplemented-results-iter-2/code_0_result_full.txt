### Why this works

- The `memcpy` for `(i0_next, j0_next)` executes on the CPU immediately after `gemmini_mx_load_scales` for the current block is enqueued. At this point, the accelerator's command queue begins processing the scale DMA *and* will then process the upcoming mvin commands. The CPU's memcpy work (which populates `A_s[nxt]`/`B_s[nxt]`) runs in parallel with all of that accelerator activity.
- By the time the next loop iteration begins and calls `gemmini_mx_load_scales(A_s[cur], ...)` (where `cur` is the swapped `nxt`), the staging is already complete — eliminating the blocking memcpy from the critical path.
- The programming model order (`config_ex` → `load_scales` → `mvin` → `mxquant_config_mvout` → `loop_ws_spad` → `read_smem` → `fence`) is fully preserved within each iteration, since the prefetch memcpy only writes to the *next* buffer and does not issue any accelerator instructions.
- Double-buffering requires 2× the scale buffer memory, but scale buffers are tiny (`BLK × GK` bytes each), so this is negligible.
