## Analysis

Looking at the original code, I identify the key inefficiency targeted by **strategy 3**:

### Problem in the Original Code

The output readout uses a **per-row loop**:
```c
for (int r = 0; r < mrows; r++)
    gemmini_mx_read_smem(&C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
                         SPAD_DEST * 16 + r * BLK, ncols);
gemmini_fence();
```

This issues `mrows` separate `gemmini_mx_read_smem` instructions (up to BLK calls per block). For full blocks where `mrows == BLK` and `ncols == BLK`, the entire output fits contiguously in smem and could be read in a single call. The per-row dispatch adds unnecessary instruction overhead.

Additionally, for full blocks there's no padding computation needed and no conditional branching on `pad_i`/`pad_j`.

## Plan: Strategy 3 — Fast Path / Slow Path Split

### Specific Changes

1. **Split the i0/j0 loop body** into two cases:
   - **Fast path**: when `mrows == BLK && ncols == BLK` (i.e., `pad_i == 0 && pad_j == 0`), it's a full BLK×BLK block. Here we replace the per-row `gemmini_mx_read_smem` loop with a **single** `gemmini_mx_read_smem` call for the entire block: `gemmini_mx_read_smem(&C_hw[i0*BLK][j0*BLK/BF16_PER_WORD], SPAD_DEST*16, BLK*BLK)`. This works because the smem layout for a full BLK×BLK output is a contiguous region of `BLK*BLK` BF16 values starting at `SPAD_DEST*16`, so one DMA covers the entire block.

   - **Slow path**: when `mrows < BLK || ncols < BLK` (boundary blocks), keep the existing per-row loop with the `ncols`-truncated reads, unchanged in logic.

2. **Eliminate the `pad_i`/`pad_j` branch overhead** in the fast path — no need to compute or pass `pad_i`/`pad_j` as they are known to be zero. Pass `0, 0` directly to `gemmini_loop_ws_spad`.

3. **Keep both paths using the same programming model sequence** (config_ex → load_scales → mvin → config_mvout → loop_ws_spad → read_smem → fence), as required by rule 6.

4. **No changes to tiling, scratchpad layout, scale loading, or mvin logic** — those remain identical between fast and slow paths.

### Why This Helps

For the problem dimensions (50×256×512), `REAL_M=50`, `REAL_N=256`, `BLK` divides N evenly (256/BLK is integer), so most j0 blocks are full-width. Only the last i0 block (if 50 is not a multiple of BLK) is partial. The fast path eliminates `BLK - 1` redundant `gemmini_mx_read_smem` instruction dispatches per full block, replacing them with a single call. This reduces instruction count and associated synchronization overhead in the dominant case.
