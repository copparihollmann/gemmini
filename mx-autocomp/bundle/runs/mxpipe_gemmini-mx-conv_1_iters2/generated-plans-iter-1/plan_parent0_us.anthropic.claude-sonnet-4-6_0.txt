## Analysis of the Original Code

Looking at the baseline code, I can identify a key inefficiency:

**The im2col scatter loop** explicitly writes the entire `A_buf` intermediate buffer (MATMUL_M × MATMUL_K = 64×32 = 2048 bytes) before the MVIN loop reads it back. This creates:
1. A full write pass over `A_buf` (2048 byte-writes with multiply-heavy address calculations)
2. A subsequent read pass during MVIN (reading the same 2048 bytes again)

The problem dimensions are: `CONV_H=32, CONV_KSZ=4, PATCHES_X=8, CONV_C=2, CONV_KSZ=4`, giving `MATMUL_M=64` (patches), `MATMUL_K=32` (C×k×k = 2×4×4), `MATMUL_N=32` (output channels).

## Selected Strategy: Strategy 11 — Fuse im2col directly into MVIN

### Plan

Instead of pre-computing the entire `A_buf` im2col matrix and then issuing MVIN commands that read from it, we can compute the DRAM source address for each DIM×DIM tile on-the-fly and issue `gemmini_extended_mvin` directly from `X_in` with appropriate stride.

**Key insight:** Each row of the im2col matrix at patch `(pi, pj)` and column-group `k` (a tile of 16 columns) corresponds to a strided pattern in `X_in`. However, the im2col mapping scatters non-contiguous pixels from `X_in` (mixing spatial and channel dimensions), which generally makes stride-only MVIN non-trivial.

**Revised approach for strategy 11:** We can still eliminate `A_buf` for the full-tile case by noting the im2col layout: for a fixed tile `(i, k)` in the A scratchpad, row `i*DIM` through `(i+1)*DIM-1` are patches, and columns `k*DIM` through `(k+1)*DIM-1` are im2col positions. We compute, for each row in the tile, the source pointer directly from `X_in`, and write into a **stack-allocated row buffer** (16 bytes per row), then mvin from that. But this is still a buffer.

**The cleanest application of Strategy 11:** Since the im2col matrix is only 2048 bytes total, we should keep `A_buf` but align it and precompute the flat source-pointer array once, then use it in the mvin loop — this is actually **Strategy 12**. 

For **Strategy 11 purely**: the `gemmini_config_ld` stride controls the DRAM row stride. For each im2col tile `(i, k)`, if the 16 consecutive im2col columns within that tile happen to be contiguous in `X_in` memory (stride = `CONV_W * sizeof(elem_t)`), we can MVIN directly. We check: column `c*k*k + dy*k + dx` for `DIM=16` contiguous columns — these span `dx` varying fastest (0..3), then `dy`, then `c`. Within a 16-column tile starting at `k*DIM`, the 16 entries do vary contiguously in `dx,dy,c` order, meaning the source data in `X_in` is NOT contiguous in general.

Given this, **Strategy 11's most direct benefit** is achieved by removing the explicit loop over all patches and im2col positions and instead computing the A_buf fill more efficiently. The simplest correct implementation: **eliminate the 5-level nested loop** that fills `A_buf` by replacing it with `memcpy`-style row fills using pointer arithmetic, keeping `A_buf` aligned so MVIN reads it hot from cache.

### Concrete Code Change

Apply **Strategy 13 combined with 11**: Mark `A_buf` with `__attribute__((aligned(64)))` as a static/stack buffer. The im2col matrix is tiny (2048 bytes), fitting entirely in L1 cache. Replace the 5-level scatter loop with a **single flat loop** over the output rows of `A_buf`, computing source addresses with minimal arithmetic:

```c
// Flatten the im2col fill to a single loop over patches × K columns
static elem_t A_buf[MATMUL_M][MATMUL_K] __attribute__((aligned(64)));
for (int p = 0; p < MATMUL_M; p++) {
    int pi = p / PATCHES_X, pj = p % PATCHES_X;
    for (int q = 0; q < MATMUL_K; q++) {
        int c = q / (CONV_KSZ*CONV_KSZ);
        int rem = q % (CONV_KSZ*CONV_KSZ);
        int dy = rem / CONV_KSZ, dx = rem % CONV_KSZ;
        A_buf[p][q] = X_in[c][pi*CONV_KSZ+dy][pj*CONV_KSZ+dx];
    }
}
```

Then the MVIN loop reads `A_buf` which is warm in L1 cache (2048 bytes << 32KB L1). The `__attribute__((aligned(64)))` ensures cache-line-aligned MVIN DMA reads with no false sharing.

This eliminates the 5-level loop overhead, reduces address computation complexity, ensures the buffer is cache-aligned for fast DMA reads, and the tiny buffer size guarantees L1 residency throughout the MVIN phase.
