### Plan for Performance Optimization

To optimize the execution time of the weight-stationary MX matmul kernel for the $128 \times 128 \times 256$ fp4 matrix multiplication, we must focus on reducing the CPU instruction dispatch overhead and maximizing memory bus/DMA efficiency. 

#### Analysis of Bottlenecks in the Original Code:
1. **Instruction Overhead**: The original code loads matrix $A$ in small batches of 2 tiles and matrix $B$ completely unbatched (1 tile at a time). This results in $32$ DMA commands for $A$ and $64$ DMA commands for $B$, totaling $96$ separate `gemmini_extended_mvin` instructions. This induces high scalar execution latency and register pressure on the host RISC-V CPU.
2. **Sub-optimal DMA Stride and Length**: GEMMINI's DMA engine is highly optimized for wide block transfers. The hardware scratchpad parameter `MAX_BLOCK_LEN = 4` allows loading up to $4$ tiles of size $16 \times 16$ elements in a single command. The original code's small block transfers underutilize the memory bus.

#### Optimization Strategy (Aggressive DMA Batching & Complete Loop Unrolling):
1. **Contiguous K-Tile Batching for A**: We can batch the loading of matrix $A$ along the $K$ dimension by $4$ (since $K$ is contiguous). This reduces the number of $A$ `mvin` calls from $32$ to $16$.
2. **Full J-Tile Batching for B**: Since $t_j = 4$, the entire row of $B$ tiles for a given $k$ step is contiguous in DRAM. We can load all $4$ tiles ($cols = 4 \times \text{DIM}$) in a single command. This completely eliminates the inner `j` loop and reduces the B `mvin` instructions from $64$ to $16$.
3. **Complete Loop Unrolling**: By completely unrolling the loading loops (Strategy 12), we eliminate all runtime loop counters, branches, and scalar address arithmetic. The compiler can directly emit instructions with constant offsets, achieving near-zero host CPU overhead.
