An elegant and highly effective optimization strategy to reduce execution time for this MX-Gemmini FP4 kernel focuses on **Host Loop Unrolling and Address Calculation Strength-Reduction for RoCC Command Streaming**, coupled with **Dual DMA Port Parallelism via `mvin2`**.

### Optimization Strategy: Host Loop Unrolling & Dual DMA Parallelism

In the baseline code, the RISC-V host CPU performs complex 2D address calculations (including multiple multiplications and additions) inside nested loops to determine the DRAM pointer and scratchpad address for every single tile load. Since the systolic array relies on the host CPU to stream these RoCC instructions, a slow host loop can starve the Gemmini instruction queue, leading to execution stalls.

We optimize this by:
1. **Unrolling the inner loops** of both A and B matrix loads. Since $tk = 16$ (8 iterations of `k += 2` for A) and $tj = 4$ (4 iterations for B) are known constants, we can fully unroll them to eliminate loop overhead entirely.
2. **Replacing multi-dimensional pointer arithmetic with simple sequential pointer updates**, removing all multiplication operations inside the hot path.
3. **Using the dedicated `mvin2` instruction for B-matrix tiles**, which utilizes Gemmini's separate B-side DMA stream to optimize bus bandwidth.
4. **Ensuring strict programming sequence order** by moving the store/requantizer configurations to occur directly after the `mvin` sequence and right before the compute loop execution.

### Rewritten Program

```c
// AUTO-GENERATED optimized MX matmul kernel (128x128x256, fp4:e2m1).
void solution(void) {
  int ti = MATMUL_M / DIM / 2;
  int tj = MATMUL_N / DIM / 2;
  int tk = MATMUL_K / DIM;
  uint32_t ab = 0;
  uint32_t bb = BANK_NUM * BANK_ROWS - tk * tj * DIM;
  int SDST = 128;

  // 1. Configure execution with A_stride = 2 to match the batched scratchpad layout
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 2, 0, 0, false, 2, 2, 3, 0);

  // 2. Load scale factors
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // 3. MVIN A: Batched by 2 along the K dimension (cols = 2 * DIM)
  // Fully unrolled inner loop with strength-reduced pointer arithmetic
  gemmini_config_ld(MATMUL_K * sizeof(elem_t));
  for (int i = 0; i < ti; i++) {
    elem_t *a_ptr = ((elem_t*)A_in_hw) + i * DIM * MATMUL_K;
    uint32_t sp_addr = ab + i * tk * DIM;

    gemmini_extended_mvin(a_ptr,           sp_addr,           2 * DIM, DIM);
    gemmini_extended_mvin(a_ptr + 2 * DIM,  sp_addr + 2 * DIM,  2 * DIM, DIM);
    gemmini_extended_mvin(a_ptr + 4 * DIM,  sp_addr + 4 * DIM,  2 * DIM, DIM);
    gemmini_extended_mvin(a_ptr + 6 * DIM,  sp_addr + 6 * DIM,  2 * DIM, DIM);
    gemmini_extended_mvin(a_ptr + 8 * DIM,  sp_addr + 8 * DIM,  2 * DIM, DIM);
    gemmini_extended_mvin(a_ptr + 10 * DIM, sp_addr + 10 * DIM, 2 * DIM, DIM);
    gemmini_extended_mvin(a_ptr + 12 * DIM, sp_addr + 12 * DIM, 2 * DIM, DIM);
    gemmini_extended_mvin(a_ptr + 14 * DIM, sp_addr + 14 * DIM, 2 * DIM, DIM);
  }

  // 4. MVIN B: Streamed utilizing dedicated gemmini_extended_mvin2
  // Fully unrolled inner loop with strength-reduced pointer arithmetic
  gemmini_config_ld(MATMUL_N * sizeof(elem_t) / 2);
  for (int k = 0; k < tk; k++) {
    elem_t *b_ptr = ((elem_t*)B_in) + k * DIM * (MATMUL_N / 2);
    uint32_t sp_addr = bb + k * tj * DIM;

    gemmini_extended_mvin2(b_ptr,           sp_addr,           DIM, DIM);
    gemmini_extended_mvin2(b_ptr + DIM,     sp_addr + DIM,     DIM, DIM);
    gemmini_extended_mvin2(b_ptr + 2 * DIM, sp_addr + 2 * DIM, DIM, DIM);
    gemmini_extended_mvin2(b_ptr + 3 * DIM, sp_addr + 3 * DIM, DIM, DIM);
  }

  // 5. Configure store and requantizer (placed immediately before compute)
  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, ti, tj, tk, 0, 0, 1);

  // 6. Compute Weight-Stationary Matrix Multiplication
  gemmini_loop_ws_spad(ti, tj, tk, 0, 0, 0, ab, BANK_NUM * BANK_ROWS, 0, SDST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);

  // 7. Drain output BF16 elements from shared memory to DRAM
  gemmini_mx_read_smem(&C_hw[0][0], SDST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```

### How This Improves Performance

1. **Continuous Coprocessor Command Saturation:** Unrolling the inner loops for $tk$ and $tj$ eliminates all branch execution penalty on the host. More importantly, computing pointers using compile-time constants (such as `a_ptr + 2*DIM` rather than calculating `i*DIM*MATMUL_K + k*DIM` dynamically) reduces complex arithmetic instructions to single additions. This prevents the CPU from falling behind the hardware's consumption rate.
2. **Dedicated DMA Channel Execution:** By employing `gemmini_extended_mvin2` for the $B$ matrix inputs, we isolate $A$ and $B$ streams into their respective scratchpad load interfaces. This enhances bus utilization and increases overlap during the preloading phase.
3. **Adherence to State Transition Protocols:** Placing `gemmini_mxquant_config_mvout` strictly after the scratchpad data load and immediately before `gemmini_loop_ws_spad` respects Gemmini's sequential register configuration pipeline, eliminating speculative bubbles.
