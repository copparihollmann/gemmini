An elegant and highly effective optimization plan for this FP4 weight-stationary matrix multiplication is to use **Strategy 2: Loop Tiling** to maximize both scratchpad and accumulator utilization, while enabling contiguous DRAM streaming.

### Inefficiencies in the Original Code:
1. **Low Accumulator & Scratchpad Utilization:** The original code restricts the tile parameters to `ti = 4` and `tj = 4` (a 64x64 sub-matrix), but leaves them without an outer loop to compute the remaining parts of the $128 \times 128 \times 256$ matrix multiplication.
2. **DRAM Bandwidth Waste (Redundant Loads):** Since the weight matrix $B$ is constant across the entire $M$ dimension, reloading $B$ from DRAM is highly inefficient. We can fit the entire $B$ matrix ($256 \times 128$) into the scratchpad once and reuse it across multiple $A$ tile chunks.
3. **Non-Contiguous DRAM Writes:** Strided or small DRAM transfers to write back output blocks slow down execution.

### Optimization Plan:
1. **Apply Loop Tiling (`ti = 2`, `tj = 8`, `tk = 16`):**
   - By choosing `tj = 8`, the tile width covers the entire column dimension of the output matrix ($8 \times 16 = 128$ columns). 
   - This ensures that the computed outputs are completely contiguous in DRAM, allowing us to drain each $32 \times 128$ output block in a single, large, high-bandwidth contiguous DMA transfer of 4096 BF16 elements (`ti * DIM * MATMUL_N`).
   - `ti = 2, tj = 8` perfectly occupies 100% of the 256-row accumulator space (`ti * tj * DIM = 2 * 8 * 16 = 256` rows). We set `SDST = 0` to map exactly to rows `0` to `255`.
2. **Implement Outer Loops:**
   - Add an outer loop indexing `i_idx` from 0 to 3 to process the 128 rows of $A$ in 4 blocks of 32 rows.
3. **Cache Stationary Matrix $B$:**
   - Load the entire $B$ matrix once into the top of the scratchpad (`bb = 6144` down to `8192`) before starting the outer loop.
   - Load only the $A$ block chunks into the bottom of the scratchpad (`ab = 0` up to `512`) inside the loop, reducing $B$ DRAM loading bandwidth by 4×.
4. **Synchronize correctly:**
   - Offset the output scale factor pointer inside `gemmini_mxquant_config_mvout` using `scale_factors + i_idx * 128` (since each 32-row block of the output uses 128 scale factors).
   - Use `gemmini_fence()` per iteration to guarantee that shared memory data transfers finish before the next hardware loop begins.
