## Analysis of the Baseline Code

Looking at the baseline code for a 64×128×128 FP8 matmul:
- `MATMUL_M=64, MATMUL_N=128, MATMUL_K=128`
- `tiles_I=4, tiles_J=8, tiles_K=8`

The current `gemmini_mxquant_config_mvout` call uses `lut_update_granularity=1`, meaning the requantizer refreshes its output LUT after every single output tile. This is called once before `gemmini_loop_ws_spad`, but the granularity parameter controls how frequently the hardware updates the LUT *during* the fused loop execution across all `tiles_I × tiles_J = 32` output tiles.

## Selected Strategy: **Strategy 11 — Increase `lut_update_granularity`**

### Why This Strategy Applies

The format is FP8 E4M3 input with `out_mx_fmt=3` (BF16 output). BF16 is a standard floating-point format — it does **not** require a lookup table for requantization. The conversion from the internal accumulated representation to BF16 is a direct numerical cast/rounding operation, not a LUT-indexed projection. Therefore, the LUT refresh step is effectively a no-op for correctness in this BF16 output path, and the `lut_update_granularity` can safely be set to a large value to eliminate unnecessary refresh overhead entirely.

### Specific Change

In the `gemmini_mxquant_config_mvout` call, change the last argument from `1` to `tiles_I * tiles_J` (i.e., `32`, the total number of output tiles), which means the requantizer LUT refresh is triggered at most once across the entire fused loop rather than after every tile:

**Before:**
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```

**After:**
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_I * tiles_J);
```

This eliminates `(tiles_I * tiles_J - 1) = 31` unnecessary LUT refresh operations inside `gemmini_loop_ws_spad`, reducing the overhead of the fused hardware loop with no change to output correctness, since BF16 output requantization (`out_mx_fmt=3`) does not depend on the LUT content.

### Why This Is Safe

- The output format is BF16 (`out_mx_fmt=3`), which is a direct numeric format, not LUT-indexed.
- The `scale_factors` array and scale selectors are unchanged.
- The programming model sequence order is preserved exactly.
- No scratchpad layout, tile count, or address arithmetic changes.
- The single `gemmini_fence()` after `gemmini_mx_read_smem` is preserved.
