## Analysis of the Original Code

The original code loads A tiles with `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` and then immediately reuses the same stride for B tiles. Both A and B are fp8 (1 byte per element), and both have the same DRAM row stride `MATMUL_K * sizeof(elem_t)` = `MATMUL_K` bytes. So the stride is actually correct for both.

However, looking more carefully at the mvin loops:
- A tiles: pointer = `A_in + i*DIM*MATMUL_K + k*DIM` — stride between rows is `MATMUL_K` ✓
- B tiles: pointer = `B_in + j*DIM*MATMUL_K + k*DIM` — stride between rows is also `MATMUL_K` ✓

So the single `gemmini_config_ld` call covers both. No issue there.

**The real inefficiency**: The `gemmini_config_ld` is issued only once, but mvin uses port `k_MVIN` for both A and B tiles. The hardware has **three independent mvin ports** (mvin/mvin2/mvin3). By loading A via `gemmini_extended_mvin` and B via `gemmini_extended_mvin2`, they can be **overlapped** — strategy 1 (overlap data movement and compute). But more directly applicable is **strategy 10**: using separate `gemmini_config_ld` calls for A and B with the correct id, enabling the hardware to issue both DMA streams in parallel.

## Selected Strategy: Strategy 10 — Configure Separate `gemmini_config_ld` for A and B Using Different Ports (mvin vs mvin2)

### Plan

The original code uses a single `gemmini_config_ld` (which configures port id=0) for both A and B tiles, then issues all loads via `gemmini_extended_mvin`. This serializes all DMA traffic through a single port.

The fix is to:
1. Issue `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), SCALE_IDENTITY, false, /*id=*/0)` for A (port 0 / mvin).
2. Issue `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), SCALE_IDENTITY, false, /*id=*/1)` for B (port 1 / mvin2).
3. Load A tiles via `gemmini_extended_mvin(...)` (port 0).
4. Load B tiles via `gemmini_extended_mvin2(...)` (port 1).

This allows the hardware DMA engines for port 0 and port 1 to run concurrently, overlapping A and B tile fetches from DRAM into the scratchpad. Since A tiles go to the low scratchpad and B tiles go to the high scratchpad, there is no address conflict. Both strides are `MATMUL_K` bytes, which is the same value, but they are now independently configured on their respective ports. The interleaved issuing of mvin and mvin2 commands allows the hardware to pipeline both streams.

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // Configure port 0 (mvin) for A tiles
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), SCALE_IDENTITY, false, 0);
  // Configure port 1 (mvin2) for B tiles
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), SCALE_IDENTITY, false, 1);

  // Interleave A and B tile loads across two ports to overlap DMA transfers
  for (int k = 0; k < tiles_K; k++) {
    for (int i = 0; i < tiles_I; i++)
      gemmini_extended_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM),
                            a_base + (i * tiles_K + k) * DIM, DIM, DIM);
    for (int j = 0; j < tiles_J; j++)
      gemmini_extended_mvin2((void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
                             b_base + (j * tiles_K + k) * DIM, DIM, DIM);
  }

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_I * tiles_J);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```
