## Analysis of the Baseline Code

Looking at the baseline, the A and B tiles are loaded using the same `gemmini_extended_mvin` port (funct `k_MVIN`) sequentially:

```c
// A tiles loaded first, all via mvin (k_MVIN)
gemmini_config_ld(MATMUL_K * sizeof(elem_t));
for (int i = 0; i < tiles_I; i++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(...);  // k_MVIN

// Then B tiles, also via mvin (k_MVIN)
for (int j = 0; j < tiles_J; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(...);  // k_MVIN
```

Both A and B use the same DMA port (`k_MVIN`). But the hardware provides **two independent DMA ports**: `k_MVIN` and `k_MVIN2`. Loading A via `gemmini_extended_mvin` and B via `gemmini_extended_mvin2` simultaneously exploits both ports, potentially halving the total mvin latency.

## Plan: Apply Strategy 11 — Use `gemmini_extended_mvin2` for B-tile Loads

### What to change

**Interleave A and B tile loads** by issuing them concurrently using different DMA ports:
- Keep A tiles loading via `gemmini_extended_mvin` (`k_MVIN`)  
- Switch B tiles to load via `gemmini_extended_mvin2` (`k_MVIN2`)

### Specific code changes

1. **Keep `gemmini_config_ld` as-is** — it configures port 0 (mvin) stride. Since `gemmini_extended3_config_ld` with `id=1` would configure port 1 (mvin2), we need to also configure the stride for mvin2. Looking at the reference `matmul_tiled_fp4_64x64.c`, B uses a different stride formula. For fp8 both A and B have `elem_t = uint8_t` so both strides equal `MATMUL_K * sizeof(elem_t)` — the same value. We can issue `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), SCALE_IDENTITY, false, 1)` to configure mvin2's stride.

2. **Interleave the A and B mvin loops**: Instead of two separate sequential loops, issue one A-tile mvin followed immediately by a B-tile mvin2 in the same loop iteration. Since `tiles_I=4`, `tiles_J=8`, `tiles_K=8`, the loops have different trip counts. The inner K dimension is shared, so we can interleave at the `(j,k)` / `(i,k)` level.

3. **Concrete restructuring**: Issue all A mvins (via mvin) and all B mvins (via mvin2) interleaved instruction-by-instruction. The simplest correct approach is to keep two separate loops but use `gemmini_extended_mvin2` for B, which allows the hardware's two DMA engines to operate in parallel since there are no data dependencies between A and B loads.

### Resulting code structure

```c
// Configure stride for both mvin ports (same stride for fp8)
gemmini_config_ld(MATMUL_K * sizeof(elem_t));           // port 0 (A)
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t),  // port 1 (B)
    MVIN_SCALE_IDENTITY, false, 1);

// Interleave A (mvin) and B (mvin2) loads
for (int i = 0; i < tiles_I; i++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(A_ptr(i,k), a_base + (i*tiles_K+k)*DIM, DIM, DIM);

for (int j = 0; j < tiles_J; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin2(B_ptr(j,k), b_base + (j*tiles_K+k)*DIM, DIM, DIM);
```

The two loops feed two independent DMA engines, allowing the hardware to pipeline B loads while A loads proceed, reducing total data-loading latency before `gemmini_loop_ws_spad`.
