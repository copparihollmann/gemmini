## Analysis of the Original Code

Looking at the original code, I need to identify the key inefficiency to address.

The original code loads B tiles with the **same port** (`gemmini_extended_mvin`) as A tiles, sequentially:
1. Load all A tiles (loop over i, k)
2. Load all B tiles (loop over j, k)

**Strategy 8: Use `mvin2`/`mvin3` ports to parallelize A and B tile loads simultaneously**

The hardware has three independent mvin ports (`k_MVIN`, `k_MVIN2`, `k_MVIN3`). Currently, the code uses only `gemmini_extended_mvin` (port 0) for both A and B tiles, meaning all loads are sequential. By using `gemmini_extended_mvin2` for B tiles (a distinct port), the hardware can issue A and B loads concurrently, overlapping their DMA transfers.

## Plan

**Change**: Issue A tile loads via `gemmini_extended_mvin` and B tile loads via `gemmini_extended_mvin2`, interleaving them in the loop so both ports stay busy simultaneously.

**Specific changes:**
1. Set up the load stride for port 1 (mvin2) using `gemmini_extended3_config_ld` with `id=1` for B tiles, since `gemmini_config_ld` only configures port 0.
2. Restructure the mvin loops: interleave A and B tile loads so that for each k, we issue one `gemmini_extended_mvin` for an A tile and one `gemmini_extended_mvin2` for a B tile back-to-back, letting both DMA engines work in parallel.
3. The B tile stride is `MATMUL_K * sizeof(elem_t)` (same as A, since B_in is also stored in row-major with K as the inner dimension in this non-transposed layout).

**Loop restructuring**: Instead of two separate loops (all-A then all-B), interleave them: loop over `max(tiles_I, tiles_J)` and issue mvin + mvin2 pairs. To simplify, loop over `tiles_K` first and issue A and B loads for matching k-slices together.

The revised code:

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // Configure port 0 (mvin) for A tiles: stride = MATMUL_K bytes
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0);
  // Configure port 1 (mvin2) for B tiles: stride = MATMUL_K bytes
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);

  // Interleave A (port 0) and B (port 1) loads to overlap DMA transfers
  for (int k = 0; k < tiles_K; k++) {
    for (int i = 0; i < tiles_I; i++) {
      gemmini_extended_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM),
                            a_base + (i * tiles_K + k) * DIM, DIM, DIM);
    }
    for (int j = 0; j < tiles_J; j++) {
      gemmini_extended_mvin2((void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
                             b_base + (j * tiles_K + k) * DIM, DIM, DIM);
    }
  }

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```

**Why this works**: `gemmini_extended_mvin` and `gemmini_extended_mvin2` issue to distinct RoCC command queues/ports. By alternating A-port and B-port loads within the k-loop, both DMA engines are kept active simultaneously rather than draining all of port 0 before port 1 starts. This reduces total mvin latency by approximately 2× for the data-load phase.
