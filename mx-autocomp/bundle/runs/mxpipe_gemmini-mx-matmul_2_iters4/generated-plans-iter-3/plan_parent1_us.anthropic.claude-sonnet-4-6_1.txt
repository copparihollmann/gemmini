## Analysis

Looking at the original code, I need to identify which strategy offers the most direct improvement.

**Current code analysis:**
- The mvin loops use `gemmini_extended_mvin` (port 0) for A tiles and `gemmini_extended_mvin2` (port 1) for B tiles — but they are in **separate inner loops** within the same outer K loop
- A tiles are loaded in one inner loop, then B tiles in another inner loop — they are partially overlapped by being in the same K iteration, but the port assignment is correct
- The key issue: `gemmini_config_st(OUT_COLS * sizeof(out_t))` is called before `gemmini_mxquant_config_mvout`, but strategy 14 notes that `CONFIG_ST` state is **not consulted** for the smem drain path — `gemmini_loop_ws_spad` writes to `mx_smem` and results are drained via `gemmini_mx_read_smem`, completely bypassing the mvout path

**Strategy 14** directly applies: The `gemmini_config_st(OUT_COLS * sizeof(out_t))` call is unnecessary overhead because `gemmini_loop_ws_spad` writes to `mx_smem` (not to the accumulator DRAM path) and the output is drained exclusively via `gemmini_mx_read_smem`. The `CONFIG_ST` register state is irrelevant to this path.

## Plan

**Apply Strategy 14: Eliminate the unnecessary `gemmini_config_st` call.**

The `gemmini_config_st(OUT_COLS * sizeof(out_t))` instruction before `gemmini_mxquant_config_mvout` configures the output stride for the standard `MVOUT` path. However, `gemmini_loop_ws_spad` writes its BF16 results directly into `mx_smem` (the MX shared memory), and those results are subsequently drained to DRAM exclusively via `gemmini_mx_read_smem` (funct 28). The hardware loop never consults `CONFIG_ST` state for the smem drain path. Therefore, the `gemmini_config_st` call is dead code in this kernel — it wastes instruction issue cycles and any associated pipeline hazard stalls without contributing to correctness.

**Change:** Remove the line `gemmini_config_st(OUT_COLS * sizeof(out_t));` entirely. All other code remains identical.
