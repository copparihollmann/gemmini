To improve the performance of the provided matrix multiplication code, we will apply **Strategy 3**: hoisting the invariant `gemmini_extended3_config_ex` and `gemmini_flush(0)` instructions outside of the nested block loops.

### Plan

1. **Identify Loop-Invariant Instructions**: The `gemmini_flush(0)` and `gemmini_extended3_config_ex` instructions are currently executed at the beginning of every `(i0, j0)` tile iteration. The hardware configuration (like `WEIGHT_STATIONARY`, accumulator scale, transposes, and the MX formats) is completely static across the entire matrix multiplication.
2. **Hoist Outside the Loops**: Move these two instructions to the very beginning of the `solution()` function, before the `for (int i0 = 0; i0 < BLOCKS_M; i0++)` loop. 
3. **Hardware Persistence**: In the MX-Gemmini programming model, the configuration registers written by `gemmini_extended3_config_ex` persist until they are explicitly overwritten. Therefore, it is both safe and functionally correct to set this state exactly once. 

By removing these operations from the inner loop, we eliminate redundant RoCC custom instructions and reduce the overhead executed per tile, which will reduce the total latency of the kernel while producing identical bit-exact BF16 output.
