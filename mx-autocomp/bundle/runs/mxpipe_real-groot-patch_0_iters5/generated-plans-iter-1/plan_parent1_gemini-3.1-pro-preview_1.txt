To optimize the matrix multiplication and address the inefficiency of reloading weight tiles, we will apply **Strategy 2: assign B tiles to fixed high-address scratchpad region (`b_base = BANK_NUM*BANK_ROWS - ...`) to enable weight-stationary reuse across I tiles**. 

By swapping the order of the loop nest (making the `j0` loop the outer loop and the `i0` loop the inner loop), we can hoist the DRAM loads (`mvin`) of the B-matrix (weights) and its scale factors outside the inner loop. This allows the stationary B tiles in the high-address scratchpad region to be reused across all `I` dimension iterations, significantly reducing redundant memory movement and loop overhead.

### Plan:
1. **Reorder the Loop Nest**: Swap the `for (int i0 = ...)` and `for (int j0 = ...)` loops so that `j0` (iterating over `BLOCKS_N`) becomes the outer loop, and `i0` (iterating over `BLOCKS_M`) becomes the inner loop.
2. **Hoist Global Configurations**: Move `gemmini_flush(0);` and `gemmini_extended3_config_ex(...)` entirely outside of both loops, as execution formatting needs to be set only once.
3. **Hoist B-Matrix Work (Outer Loop)**: 
   - Inside the new outer `j0` loop, compute column boundaries (`ncols`) and tile limits (`tiles`, `tiles_K`).
   - Retain the calculation of the top-of-scratchpad base for B: `uint32_t b_base = BANK_NUM * BANK_ROWS - tiles * tiles_K * DIM;`.
   - Issue the `gemmini_mx_load_scales` intrinsic for `pre_B_s` (sel=1).
   - Configure the B memory stride with `gemmini_config_ld` and iterate over `tiles` and `tiles_K` to `mvin` all B blocks corresponding to the `j0` tile into the `b_base` region.
4. **Localize A-Matrix & Compute Work (Inner Loop)**:
   - Inside the `i0` inner loop, compute row boundaries (`mrows`), `a_base` (which starts at `0`), and padding variables (`pad_i`, `pad_j`).
   - Issue the `gemmini_mx_load_scales` intrinsic for `pre_A_s` (sel=0). 
   - Configure the A memory stride with `gemmini_config_ld` and `mvin` the A blocks.
   - Proceed with `gemmini_config_st`, `gemmini_mxquant_config_mvout`, and `gemmini_loop_ws_spad` exactly as they were, since both A and B have been staged appropriately.
   - Keep the hardware read sequence (`gemmini_mx_read_smem` and `gemmini_fence();`) at the end of the inner loop to drain BF16 outputs to `C_hw` before the next block iteration. 

This transformation preserves correctness since the underlying weight-stationary model expects both sets of scales to be configured before `gemmini_loop_ws_spad`, which remains logically true.
