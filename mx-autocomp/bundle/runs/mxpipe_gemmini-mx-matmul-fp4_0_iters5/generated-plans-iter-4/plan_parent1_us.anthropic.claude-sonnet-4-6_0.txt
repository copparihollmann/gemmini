## Analysis

Looking at the baseline code, the current tiling splits the problem as:
- `ti = MATMUL_M / DIM / 2 = 128/16/2 = 4`
- `tj = MATMUL_N / DIM / 2 = 128/16/2 = 4`
- `tk = MATMUL_K / DIM = 256/16 = 16`

This means A tiles occupy: `ti * tk * DIM = 4 * 16 * 16 = 1024` rows  
B tiles occupy: `tj * tk * DIM = 4 * 16 * 16 = 1024` rows  
Total: 2048 rows out of 8192 — only **25% scratchpad utilization**.

The accumulator holds `ti * tj * DIM = 4 * 4 * 16 = 256` rows — exactly at the limit but only for half of M and N.

## Selected Strategy: Strategy 14 — Use `gemmini_block_mvin` to batch up to 4 consecutive tiles per DMA command

## Plan

The baseline issues individual `gemmini_extended_mvin` calls for each tile. For A tiles, the inner loop over `k` (16 iterations) loads 16 consecutive scratchpad rows per call. Since `MAX_BLOCK_LEN=4`, we can batch 4 tiles per mvin command by using `gemmini_block_mvin` (which sets `cols = len*DIM`), reducing the total mvin instruction count by 4×.

**For A tiles:** The loop is `for i in [0,ti): for k in [0,tk)`. The A scratchpad layout is `ab + (i*tk + k)*DIM`. Within a fixed `i`, as `k` advances, addresses are consecutive: `ab + (i*tk + 0)*DIM`, `ab + (i*tk + 1)*DIM`, etc. — stride is `DIM` rows between tiles, which is exactly what block mvin expects. We can batch groups of 4 k-tiles per mvin call, reducing from `ti*tk = 4*16 = 64` calls to `ti*(tk/4) = 4*4 = 16` calls.

The DRAM stride for A is `MATMUL_K * sizeof(elem_t)` bytes per row, and the DRAM block of 4 consecutive k-tiles is at `A_in_hw + i*DIM*MATMUL_K + k*DIM` with the 4 tiles occupying 4 consecutive `DIM`-row blocks — which is valid for `gemmini_block_mvin` since `block_mvin_stride=DIM` aligns with the scratchpad layout.

**For B tiles:** The loop is `for k in [0,tk): for j in [0,tj)`. Within a fixed `k`, as `j` advances, the scratchpad addresses `bb + (k*tj + j)*DIM` are consecutive, so we can batch 4 j-tiles per call. This reduces from `tk*tj = 16*4 = 64` calls to `tk*(tj/4) = 16*1 = 16` calls.

Since `tk=16` is divisible by 4 and `tj=4` is exactly 4 (one batch per k), this works cleanly without remainder handling. The A inner-loop batches groups of 4 over `k` (16/4=4 batches per i-row), and B batches all `tj=4` j-tiles at once per k.

```c
void solution(void) {
  {
    int ti = MATMUL_M / DIM / 2, tj = MATMUL_N / DIM / 2, tk = MATMUL_K / DIM;
    uint32_t ab = 0;
    uint32_t bb = BANK_NUM * BANK_ROWS - tk * tj * DIM;
    int SDST = 128;

    gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 2, 2, 3, 0);
    gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
    gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);
    gemmini_config_st(OUT_COLS * sizeof(out_t));
    gemmini_mxquant_config_mvout((uint64_t)scale_factors, ti, tj, tk, 0, 0, 1);

    // MVIN A: batch 4 consecutive k-tiles per gemmini_block_mvin call
    // block_mvin_stride=DIM is set by gemmini_extended4_config_ld default
    gemmini_config_ld(MATMUL_K * sizeof(elem_t));
    for (int i = 0; i < ti; i++) {
      for (int k = 0; k < tk; k += MAX_BLOCK_LEN) {
        elem_t *dram_ptr = ((elem_t*)A_in_hw) + i*DIM*MATMUL_K + k*DIM;
        uint32_t sp_addr = ab + (i*tk + k)*DIM;
        gemmini_block_mvin((void*)dram_ptr, sp_addr, MAX_BLOCK_LEN);
      }
    }

    // MVIN B: batch tj=4 consecutive j-tiles per gemmini_block_mvin call (tj==MAX_BLOCK_LEN)
    gemmini_config_ld(MATMUL_N * sizeof(elem_t) / 2);
    for (int k = 0; k < tk; k++) {
      elem_t *dram_ptr = ((elem_t*)B_in) + k*DIM*(MATMUL_N/2) + 0*DIM;
      uint32_t sp_addr = bb + (k*tj + 0)*DIM;
      gemmini_block_mvin((void*)dram_ptr, sp_addr, MAX_BLOCK_LEN);
    }

    gemmini_loop_ws_spad(ti, tj, tk, 0, 0, 0, ab, BANK_NUM * BANK_ROWS, 0, SDST,
                         false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
    gemmini_mx_read_smem(&C_hw[0][0], SDST * 16, MATMUL_M * MATMUL_N);
    gemmini_fence();
  }
}
```

**Key changes:**
- A loading: 64 individual mvin → 16 block_mvin calls (4× reduction)
- B loading: 64 individual mvin → 16 block_mvin calls (4× reduction), with the j-loop collapsed since `tj=4=MAX_BLOCK_LEN` fits in one batch per k
- Total mvin instruction count drops from 128 to 32
- All addresses, strides, and memory layouts remain identical; only the batching changes
