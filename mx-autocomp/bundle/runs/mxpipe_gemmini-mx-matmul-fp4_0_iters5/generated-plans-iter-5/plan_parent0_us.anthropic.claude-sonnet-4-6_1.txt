## Analysis

Looking at the original code, I need to identify which strategy applies best.

The current code uses:
- `ti = MATMUL_M / DIM / 2` (half-sized tiles in M)
- `tj = MATMUL_N / DIM / 2` (half-sized tiles in N)
- `tk = MATMUL_K / DIM` (full K tiles)

This means `ti` and `tj` are using half the available M and N dimensions as tile counts, leaving half the scratchpad and accumulator unused. The feedback confirms "Scratchpad utilization is 0KB out of 256KB" and "Accumulator utilization is 0KB out of 64KB."

**Strategy 5: Pack A and B tiles contiguously in scratchpad to maximize `gemmini_loop_ws_spad` fused loop coverage.**

The key insight: the original code uses `ti = MATMUL_M/DIM/2` and `tj = MATMUL_N/DIM/2`, which means it only uses half the M and N tile counts. By using the full tile counts `ti = MATMUL_M/DIM` and `tj = MATMUL_N/DIM`, we can process the entire matrix in one `gemmini_loop_ws_spad` call.

Let me verify constraints:
- Full `ti = MATMUL_M/DIM = 128/16 = 8`
- Full `tj = MATMUL_N/DIM = 128/16 = 8`  
- `tk = MATMUL_K/DIM = 256/16 = 16`
- Scratchpad: `(ti*tk + tj*tk)*DIM = (8*16 + 8*16)*16 = (128+128)*16 = 4096 ≤ 8192` ✓
- Accumulator: `ti*tj*DIM = 8*8*16 = 1024 > 256` ✗

The accumulator constraint fails with full tiles. We need `ti*tj*DIM ≤ 256`, so `ti*tj ≤ 16`. With `ti=4, tj=4`: `4*4*16=256 ≤ 256` ✓, and scratchpad: `(4*16+4*16)*16=2048 ≤ 8192` ✓.

So `ti=4, tj=4, tk=16` is the maximum that fits both constraints simultaneously, meaning we process the full matmul in one pass.

## Plan

**Strategy: Pack A and B tiles contiguously in scratchpad to maximize `gemmini_loop_ws_spad` fused loop coverage (Strategy 5).**

**Changes:**
1. Change `ti = MATMUL_M / DIM / 2` → `ti = MATMUL_M / DIM` but we must respect accumulator constraint. Since `MATMUL_M=128, MATMUL_N=128, MATMUL_K=256`: `ti=8, tj=8, tk=16` violates accumulator. Use `ti=4, tj=4, tk=16` which is exactly `MATMUL_M/DIM/2 = 4` and `MATMUL_N/DIM/2 = 4` — this is actually what the code already does.

Wait — re-reading: `ti = MATMUL_M/DIM/2 = 128/16/2 = 4`, `tj = MATMUL_N/DIM/2 = 4`, `tk = 16`. Accumulator: `4*4*16=256 ✓`. Scratchpad: `(4*16+4*16)*16=2048 ✓`. The code is already fitting everything. The issue is `lut_update_granularity=1` — **Strategy 9** is the most impactful: increase it to `tk` to reduce requant overhead.

**Final Plan — Strategy 9: Increase `lut_update_granularity` to `tk` (=16).**

Change `gemmini_mxquant_config_mvout(..., 1)` to `gemmini_mxquant_config_mvout(..., tk)`. This makes the requantizer refresh its LUT only once per full matmul instead of every output tile (16× fewer refreshes), directly reducing requantization overhead with no correctness impact since all tiles share the same LUT configuration throughout the single `gemmini_loop_ws_spad` call.

```c
void solution(void) {
  {
    int ti = MATMUL_M / DIM / 2, tj = MATMUL_N / DIM / 2, tk = MATMUL_K / DIM;
    uint32_t ab = 0;
    uint32_t bb = BANK_NUM * BANK_ROWS - tk * tj * DIM;
    int SDST = 128;

    // Step 1: Configure execution with FP4 E2M1 format
    gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
        1, 1, 0, 0, false, 2, 2, 3, 0);

    // Step 2: Load scale factors for A and B
    gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
    gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

    // Step 3: (No LUT needed for FP4 E2M1 with uselut=0)

    // Step 4: MVIN tiles of A into scratchpad using block mvin (up to MAX_BLOCK_LEN=4)
    // A stride: MATMUL_K bytes per row (elem_t = uint8_t = 1 byte)
    gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0);
    for (int i = 0; i < ti; i++) {
      int k = 0;
      while (k < tk) {
        int batch = tk - k;
        if (batch > MAX_BLOCK_LEN) batch = MAX_BLOCK_LEN;
        gemmini_extended_mvin(
            (void*)(((elem_t*)A_in_hw) + i * DIM * MATMUL_K + k * DIM),
            ab + (i * tk + k) * DIM,
            DIM * batch,
            DIM);
        k += batch;
      }
    }

    // Step 4b: MVIN tiles of B into scratchpad using block mvin
    // B stride: MATMUL_N/2 bytes per row (FP4 packed, half the width)
    gemmini_extended3_config_ld(MATMUL_N * sizeof(elem_t) / 2, MVIN_SCALE_IDENTITY, false, 1);
    for (int k = 0; k < tk; k++) {
      int j = 0;
      while (j < tj) {
        int batch = tj - j;
        if (batch > MAX_BLOCK_LEN) batch = MAX_BLOCK_LEN;
        gemmini_extended_mvin2(
            (void*)(((elem_t*)B_in) + k * DIM * (MATMUL_N / 2) + j * DIM),
            bb + (k * tj + j) * DIM,
            DIM * batch,
            DIM);
        j += batch;
      }
    }

    // Step 5: Configure requantized mvout
    // lut_update_granularity increased from 1 to tk (=16):
    // the requantizer LUT now refreshes only once per full matmul rather than
    // once per output tile, reducing requant overhead by a factor of tk.
    gemmini_config_st(OUT_COLS * sizeof(out_t));
    gemmini_mxquant_config_mvout((uint64_t)scale_factors,
        ti, tj, tk,
        0, 0, tk);

    // Step 6: Compute weight-stationary tiled matmul
    gemmini_loop_ws_spad(ti, tj, tk, 0, 0, 0,
        ab, BANK_NUM * BANK_ROWS, 0, SDST,
        false, false, false, false, false,
        NO_ACTIVATION, 0, 0, false, 0x38);

    // Step 7: Drain results from mx_smem to DRAM
    gemmini_mx_read_smem(&C_hw[0][0], SDST * 16, MATMUL_M * MATMUL_N);
    gemmini_fence();
  }
}
```
