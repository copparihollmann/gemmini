## Analysis of the Current Code

Looking at the original code, the A and B mvin loops use separate `gemmini_extended_mvin` calls, loading one DIM×DIM tile per instruction. For the half-matrix sizes:
- `ti = MATMUL_M/DIM/2 = 128/16/2 = 4` (A tile rows)
- `tj = MATMUL_N/DIM/2 = 128/16/2 = 4` (B tile cols)
- `tk = MATMUL_K/DIM = 256/16 = 16` (K tiles)

The A loop issues `ti * tk = 4 * 16 = 64` individual mvin commands.
The B loop issues `tk * tj = 16 * 4 = 64` individual mvin commands.

**Strategy 11** directly addresses this: use `gemmini_block_mvin` (or equivalently, `gemmini_extended_mvin` with `cols = len * DIM`) to batch up to `MAX_BLOCK_LEN=4` consecutive row-tiles into a single DMA command, reducing instruction count by up to 4×.

## Plan: Apply Strategy 11 — Use `gemmini_block_mvin` to Batch Consecutive A-Tile Loads

### What to Change

**For A tiles:** The A loop iterates over `k` as the inner loop (consecutive k values map to consecutive scratchpad rows at `ab + (i*tk + k)*DIM`). For a fixed `i`, tiles `k=0,1,2,...,tk-1` are laid out consecutively in the scratchpad. Since `MAX_BLOCK_LEN=4`, we can batch groups of 4 consecutive k-tiles into one `gemmini_extended_mvin` call with `cols = 4*DIM = 64` and `rows = DIM`.

Instead of:
```c
for (int i = 0; i < ti; i++)
  for (int k = 0; k < tk; k++)
    gemmini_extended_mvin(..., ab + (i*tk + k)*DIM, DIM, DIM);
```

Issue one command per block of 4 k-tiles:
```c
for (int i = 0; i < ti; i++)
  for (int k = 0; k < tk; k += 4)
    gemmini_extended_mvin(A_ptr + i*DIM*MATMUL_K + k*DIM,
                          ab + (i*tk + k)*DIM,
                          4*DIM, DIM);  // batch 4 tiles per command
```

This reduces A mvin commands from 64 to 16 (4× reduction).

**For B tiles:** The B loop has `j` as inner loop for fixed `k`. The scratchpad address is `bb + (k*tj + j)*DIM`. For fixed `k`, consecutive `j` values map to consecutive scratchpad rows. Batch groups of 4 j-tiles:

```c
for (int k = 0; k < tk; k++)
  for (int j = 0; j < tj; j += 4)
    gemmini_extended_mvin(B_ptr + k*DIM*(MATMUL_N/2) + j*DIM,
                          bb + (k*tj + j)*DIM,
                          4*DIM, DIM);  // batch 4 tiles per command
```

This reduces B mvin commands from 64 to 16 (4× reduction).

Since `tj = 4` divides evenly by 4, and `tk = 16` divides evenly by 4, no remainder handling is needed.

The DRAM stride for A is `MATMUL_K * sizeof(elem_t)` (row stride in the A matrix), and `gemmini_block_mvin` uses the configured `gemmini_config_ld` stride to advance between rows — this is already set correctly. For B the stride is `MATMUL_N/2 * sizeof(elem_t)`.

The `gemmini_block_mvin` macro is defined as `gemmini_extended_mvin(dram_addr, spad_addr, (len)*DIM, DIM)`, which exactly matches this batching.

Total instruction count for mvins drops from 128 to 32, reducing dispatch overhead by 4×.
