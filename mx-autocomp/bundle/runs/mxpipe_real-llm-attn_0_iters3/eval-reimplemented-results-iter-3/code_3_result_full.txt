### What to change

**1. Swap the loop order**: Make `j0` the outer loop and `i0` the inner loop.

**2. Hoist B mvin outside the `i0` loop**: For a fixed `j0`, load all B tiles (`tiles_K × tiles_J`) into the scratchpad once, before the `i0` loop begins. B tiles sit at `b_base = BANK_NUM*BANK_ROWS - tiles_K*tiles_J*DIM` (fixed, independent of `i0`).

**3. Keep A mvin inside the `i0` loop**: A tiles differ for each `i0`, so they must still be loaded per `i0` iteration. A tiles sit at `a_base = 0`.

**4. Hoist B scale loading outside `i0`**: `B_s[g][0]` depends only on `j0`, so `memcpy` for B scales moves outside the `i0` loop. Only A scale `memcpy` stays inside `i0`.

**5. Reorder hardware init accordingly**: `gemmini_flush(0)` and `gemmini_extended3_config_ex` move outside both loops (they are format/dataflow config that doesn't change). Per the programming model sequence, `gemmini_mx_load_scales` for both A and B must precede each `gemmini_loop_ws_spad`. Since B scales change per `j0` and A scales change per `i0`, the load-scales call for B moves to the `j0` level, while A scale loading stays at `i0` level — but the **intrinsic pair** (both A and B must be called before compute) means we reload B scales at each `i0` iteration too (they're already in the staging buffer `B_s` from the `j0`-level memcpy). The B scale *memcpy* (CPU staging) is hoisted; the `gemmini_mx_load_scales` call itself stays inside `i0` per the programming model.

**6. Scratchpad capacity check**: With `tiles = BLK/DIM` for J and `tiles_K = MATMUL_K/DIM` for K, A needs `tiles * tiles_K * DIM` rows (for one i0 block) and B needs `tiles * tiles_K * DIM` rows. Total = `2 * tiles * tiles_K * DIM`. For the problem dimensions (8×512×512, BLK=typical outer block), this must stay ≤ 8192. The existing single `(i0,j0)` call already satisfies this, so hoisting B outside `i0` doesn't change the scratchpad footprint per compute call — B is still sized for one `j0` block's worth of tiles.
