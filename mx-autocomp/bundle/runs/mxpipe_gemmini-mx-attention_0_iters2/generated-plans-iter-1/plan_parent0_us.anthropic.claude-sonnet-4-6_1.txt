## Analysis

Looking at the original code, I need to identify which strategy offers the most impact.

**Current code structure:**
- Step 1: Q@K^T matmul (128×128×64), full A+B mvin → compute → read_smem
- Step 2: Softmax on host CPU (sequential, row-by-row)
- Step 3: P@V matmul (128×64×128), full A+B mvin → compute → read_smem

**Identifying the bottleneck for strategy 11:**

The softmax loop processes `ATT_S = 128` rows, each doing:
1. Unpack 128 bf16 values (inner loop over j in steps of 4)
2. Find max (same loop)
3. Compute iexp for 128 elements
4. Sum reduction
5. Compute log2 + reciprocal
6. Loop over `GROUPS_S = ATT_S/32 = 4` groups for scale quantization

Each row is processed independently with no data dependency between rows. Processing 4 rows simultaneously would improve instruction-level parallelism by interleaving independent computations (different rows have no dependencies on each other), reducing branch prediction misses and loop overhead, and enabling the compiler to use more registers productively.

## Strategy Selection: **Strategy 11 — Restructure softmax to process 4 rows simultaneously**

## Plan

The softmax loop iterates over `i = 0..ATT_S-1` (128 rows), each row is completely independent. The plan is to restructure the outer loop to step by 4 (`i += 4`), and within each iteration process 4 rows in parallel:

1. **Unpack + find max for 4 rows simultaneously**: The inner `j` loop unpacks `S1_hw[i][j/4]` through `S1_hw[i+3][j/4]` — four independent 64-bit loads and bf16 conversions interleaved, allowing out-of-order execution and reducing loop control overhead from 4 passes to 1.

2. **Compute iexp + partial sum for 4 rows simultaneously**: The `j` loop over `p[row][j] = mx_iexp(q[row][j] - mq[row])` and accumulation `sm[row] += p[row][j]` can be unrolled 4-wide across rows — the iexp calls for different rows are independent.

3. **Scale computation for 4 rows' groups**: The `g` loop over `GROUPS_S=4` groups can process all 4 rows' group-g simultaneously before moving to group g+1, keeping data hot in registers.

4. **Storage**: Declare `q[4][ATT_S]`, `p[4][ATT_S]`, `mq[4]`, `sm[4]`, `ls[4]`, `inv_sm[4]` as local arrays indexed by the 4-row lane index `r=0..3`.

This reduces loop-control overhead by 4×, improves compiler ILP visibility, and reduces branch predictor pressure — all on the scalar host CPU that has no FPU and where integer softmax is the main sequential bottleneck between the two Gemmini calls.

No changes are needed to the Gemmini configuration, mvin, or read_smem calls. The output arrays `P_scales[g][i]` and `P_q[i][j]` are written in exactly the same pattern, preserving correctness.
