## Strategy: Hoist the Integer Softmax Scalar Loop into SIMD-Width Chunks Using Precomputed Reciprocal Shifts and Eliminate Redundant bf16-Unpack Passes

### Analysis of the Bottleneck

Looking at the softmax loop (step 2), the current code has a significant inefficiency in the **inner unpack loop**:

```c
for (int j = 0; j < ATT_S; j += 4) {
    uint64_t w = S1_hw[i][j / 4];
    for (int l = 0; l < 4; l++) {
        int64_t qq = mx_ibf16_to_q((uint16_t)((w >> (l * 16)) & 0xFFFF));
        ...
    }
}
```

For each row `i`, this does **two full passes** over the 128 BF16 values:
1. **Pass 1**: Unpack all 128 values → compute `q[]` array → find `mq` (max)
2. **Pass 2**: Compute `p[j] = mx_iexp(q[j] - mq)` → accumulate `sm`
3. **Pass 3** (per group): Find `gmax`, compute scale, encode fp8

That's **3 passes** over 128 elements per row, and 128 rows → **3 × 128 × 128 = 49,152** iterations of non-trivial scalar work. The `q[]` array (128 × int64 = 1KB per row) is written and then re-read, causing cache pressure. Furthermore, the `p[]` array (another 1KB) is written and re-read for the group quantization pass.

### The New Strategy: **Single-Pass Softmax with Deferred Max Correction**

The key insight is to **fuse all three passes into one** using a two-pointer / online softmax algorithm (numerically equivalent, as used in FlashAttention), eliminating the intermediate `q[]` and `p[]` arrays entirely and reducing memory traffic by 3×.

The online softmax computes the running max and running sum in a single forward pass, storing only the *encoded fp8 values* (not full int64 intermediates). However, because the max is not known until the end, we need a correction step — but this correction can be done *per group* using only the group's already-encoded fp8 codes, which is cheap.

**Specifically:**

1. **Single forward pass** over the 128 BF16 values: maintain running `mq` (max so far) and a per-group running sum `gs[GROUPS_S]`. Store only the `mx_iexp(q[j])` values (not `q[j] - mq`, since mq isn't final yet) — or equivalently, store them relative to the current running max and rescale when the max updates. This avoids storing `q[]` and `p[]` as int64 arrays.

2. **Eliminate the `q[ATT_S]` and `p[ATT_S]` stack arrays** (each 128 × 8 = 1024 bytes). These are allocated on the stack every iteration of the outer `i` loop (128 times), causing 128 × 2KB = 256KB of stack traffic. Replacing them with a single-pass approach with only scalar running state eliminates this entirely.

3. **Fuse the group-max scan into the forward pass**: track per-group maximums `gmax[GROUPS_S]` during the same pass as the global max, avoiding a separate scan over `p[]`.

### Concrete Code Change

Replace the three-pass structure:
```c
// OLD: 3 passes, two 1KB stack arrays
int64_t q[ATT_S];   // 1KB on stack
int64_t p[ATT_S];   // 1KB on stack
// pass 1: unpack + find max
// pass 2: iexp + sum  
// pass 3: group quant
```

With a **two-pass fused approach** that eliminates `p[]` entirely and keeps `q[]` only as a compact int32 (since `q` values after `mx_ibf16_to_q` fit in int32), halving its footprint:

```c
// NEW: q stored as int32 (half the size), p[] eliminated
int32_t q[ATT_S];   // 512 bytes (was 1024)
// pass 1: unpack all, find global mq AND per-group gmax simultaneously
// pass 2: iexp, accumulate sm, directly encode fp8 using gmax
// No pass 3 needed
```

The per-group `gmax` is found during pass 1 alongside the global max, so pass 3 (the group-max scan over `p[]`) is eliminated. The `p[]` array disappears because we compute and consume each `p[j]` value inline during pass 2 without needing to store it.

### Why This Improves Performance

- **Eliminates 1KB `p[]` stack array**: removes 128 × 128 × 8 = 131,072 bytes of stack writes and reads
- **Halves `q[]` footprint** (int64→int32): `mx_ibf16_to_q` output fits in int32 since BF16 has limited range; this halves cache pressure for the q array
- **Reduces loop iterations by ~33%**: 3 passes over ATT_S=128 elements → 2 passes, saving ~5,376 iterations per row × 128 rows
- **Fuses group-max scan with global-max scan**: the inner loop body becomes slightly more work per element but eliminates an entire separate loop nest
- **Better instruction-level parallelism**: the compiler can pipeline the unpack + int32 store in pass 1 more efficiently with narrower types

This strategy is distinct from all listed strategies — it's an **algorithmic restructuring of the scalar softmax kernel** to reduce intermediate storage and loop-pass count, orthogonal to tiling, mvin batching, scale amortization, or flush elimination.
