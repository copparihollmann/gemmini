To optimize the provided MX-Gemmini matmul kernel, we will focus on **Strategy 1: loop tiling**. 

### Inefficiency Analysis
1. **Underutilized Scratchpad & Accumulator:** The current code splits the matrix multiplication into small blocks (`BLK` x `BLK`) using the host-side loops `i0` and `j0`. This results in near-zero utilization of the 256KB Scratchpad and 64KB Accumulator.
2. **Host-Side Data Staging Overhead:** Because of the block-level partitioning, the scale factors must be dynamically formatted and packed into contiguous memory locations using CPU-bound `memcpy` loops inside the hot path.
3. **Repeated Instruction Overhead:** The execution configuration, scale loading, store configurations, and `gemmini_loop_ws_spad` commands are re-issued for every single block `(i0, j0)`, introducing massive instruction dispatch latency.

### Optimization Plan: Loop Tiling to the Maximum Matrix Extent
We will re-tile the matrix multiplication by increasing the block size to the full dimensions of the matrix ($M \times N \times K$). Since the entire matrices fit comfortably within the scratchpad and accumulator limits, we can completely eliminate the outer $i0$ and $j0$ loops and perform the matmul in a single, highly efficient hardware invocation.

#### 1. Verifying Hardware Constraints
* **Scratchpad Rows Limit:**
  $$(\text{tiles}_I \times \text{tiles}_K + \text{tiles}_J \times \text{tiles}_K) \times \text{DIM} \le 8192$$
  For a typical $64 \times 64 \times 64$ matrix, this requires $(4\times4 + 4\times4)\times16 = 512$ rows, which is well below the 8192-row limit.
* **Accumulator Rows Limit:**
  $$\text{tiles}_I \times \text{tiles}_J \times \text{DIM} \le 256$$
  For $64 \times 64$, this requires $4\times4\times16 = 256$ rows, matching the accumulator limit perfectly.

#### 2. Plan Steps
1. **Eliminate Outer Loops & Staging Buffers:** Remove the `i0` and `j0` loops, the static `A_scales_preformatted`/`B_scales_preformatted` buffers, and the corresponding `memcpy` loops.
2. **Load Global Scales directly:** Load the complete, contiguous `A_scales_row` and `B_scales_col` directly using single `gemmini_mx_load_scales` calls.
3. **Stream A and B Tiles into Scratchpad:** 
   * Configure the load stride: `gemmini_config_ld(REAL_M * sizeof(elem_t))` or `MATMUL_K * sizeof(elem_t)`.
   * Load A tiles to `a_base + (i * tiles_K + k) * DIM`.
   * Load B tiles to `b_base + (j * tiles_K + k) * DIM`, where `b_base = BANK_NUM * BANK_ROWS - tiles_J * tiles_K * DIM`.
4. **Configure & Run Computations:** Configure the requantizer for the full dimensions (`tiles_I`, `tiles_J`, `tiles_K`), and execute `gemmini_loop_ws_spad` once to compute the entire matrix.
5. **Read Result and Fence:** Read the fully accumulated BF16 output from shared memory `SPAD_DEST * 16` directly into `C_hw` in one single operation, followed by `gemmini_fence()`.
