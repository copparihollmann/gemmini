## Analysis of the Current Code

The current code has a nested `(i0, j0)` loop where:
- For each `(i0, j0)` pair, **both A tiles and B tiles are loaded fresh** via mvin
- With `BLOCKS_M` × `BLOCKS_N` iterations, B tiles for a given `j0` block are loaded **`BLOCKS_M` times** — once per `i0` iteration

For this problem: `MATMUL_K = 512`, `MATMUL_N = 512`, `BLK` is some block size. The B matrix tiles for a fixed `j0` column-block don't change as `i0` varies — they're the same weight columns regardless of which A row-block we're computing. This means we're redundantly re-loading B into the scratchpad on every `i0` iteration.

## Selected Strategy: Strategy 4

**Reorder outer loops to `j0` outermost, `i0` innermost** so that B tiles for a given `j0` block are loaded once into the scratchpad and reused across all `i0` iterations.

## Concrete Plan

1. **Swap the loop order**: Make `j0` the outer loop and `i0` the inner loop.

2. **Hoist B mvin outside the `i0` loop**: Move the B tile loading (`gemmini_config_ld(MATMUL_N * sizeof(elem_t))` + the `j/k` mvin loop) to execute once per `j0` iteration, before the `i0` loop begins. Since `b_base` depends only on `tiles_K` and the number of J-tiles (which is fixed at `tiles = BLK/DIM`), it does not change with `i0`, so the B tiles remain valid in scratchpad across all `i0` iterations.

3. **Keep A mvin and scale loads inside `i0`**: A tiles change with each `i0` (different row blocks), so their mvin stays inside the inner loop. Similarly, `A_s` scale factors depend on `i0` (they index `A_scales_row[g][i0*BLK]`), so scale loading must remain inside `i0`. However, **`B_s` scale factors** only depend on `j0`, so `memcpy` for `B_s` and `gemmini_mx_load_scales` for B can be hoisted outside `i0` as well.

4. **Adjust per-iteration configuration**: `gemmini_extended3_config_ex` is stateless-safe to re-issue each `i0`, but since it doesn't change, it could also be hoisted. However, the `gemmini_flush(0)` should stay per-`(i0,j0)` invocation or be restructured — since we're reusing B in scratchpad, we should **not** flush between `i0` iterations (that would clear the scratchpad). Move `gemmini_flush` to once per `j0` block, before loading B.

5. **Scratchpad validity**: `b_base` and the B tile layout are unchanged between `i0` iterations because they depend only on `tiles_K` and `tiles` (BLK/DIM), both fixed. `a_base = 0` and A tiles occupy `tiles * tiles_K * DIM` rows starting at 0. B tiles occupy `tiles * tiles_K * DIM` rows ending at `BANK_NUM*BANK_ROWS`. These regions must not overlap — this constraint is the same as before and is unaffected by the loop reorder.

6. **Result readout**: `gemmini_mx_read_smem` + `gemmini_fence()` remain inside the `i0` loop since they drain results for each `(i0, j0)` pair before the next iteration overwrites shared memory.

This eliminates `BLOCKS_M - 1` redundant B mvin passes per `j0` block, reducing total mvin volume by approximately a factor of `BLOCKS_M` for B tiles.
