An elegant and highly effective optimization plan to address the software bottleneck in the host-side softmax execution is **Strategy 8: CLZ-Based Integer Logarithm Optimization (`mx_ilog2`)**.

### Analysis of the Inefficiency
In the provided MHA solution, the host CPU performs an integer-only Softmax approximation to avoid floating-point emulation. This involves calculating the floor of the binary logarithm ($\lfloor\log_2(x)\rfloor$) via the helper function `mx_ilog2`. 

In typical baseline implementations, `mx_ilog2` is implemented using a software loop that repeatedly shifts the input right:
```c
int mx_ilog2(uint64_t x) {
  int l = 0;
  while (x >>= 1) {
    l++;
  }
  return l;
}
```
For 64-bit integers, this loop can take up to 63 iterations. During the Softmax calculation, `mx_ilog2` is called for every row to compute:
1. `ls = mx_ilog2((uint64_t)sm);` (log2 of sum of exponents)
2. `e = mx_ilog2((uint64_t)gmax) - ls - ...;` (log2 of maximum group value)

Executing these loop iterations on a single-issue, in-order RISC-V host processor under the Spike simulator introduces severe branch overhead, instruction retirement delays, and pipeline bubbles.

---

### Optimization Plan: CLZ-Based `mx_ilog2`

We will replace the bit-shifting loop in `mx_ilog2` with a hardware-supported count-leading-zeros (CLZ) compiler built-in function (`__builtin_clzll`). 

#### 1. Mathematical Derivation
For any non-zero 64-bit unsigned integer $x$, the position of its highest set bit (which represents $\lfloor\log_2(x)\rfloor$) is directly related to the number of leading zeros:
$$\lfloor\log_2(x)\rfloor = 63 - \text{clz}(x)$$

#### 2. Modified Implementation
We will redefine the `mx_ilog2` function as follows:
```c
static inline int mx_ilog2(uint64_t x) {
  if (x == 0) return 0;
  return 63 - __builtin_clzll(x);
}
```

*Note: If `x` is 0, the original loop terminates immediately and returns `0`. The guard condition `if (x == 0) return 0;` ensures exact semantic equivalence.*

#### 3. Hardware Mapping and Impact
- **Instruction Reduction:** The original loop requires up to ~190 instructions (shifts, adds, branches) for large 64-bit values. The optimized version reduces this to a check, subtraction, and a single instruction.
- **Compiler Intrinsic:** Modern compilers (such as GCC for RISC-V) recognize `__builtin_clzll`. When compiling with the RISC-V Bitmanip (Zbb) extension, this translates directly to a single-cycle `clz` instruction. Even without Zbb, GCC generates a highly optimized branch-free instruction sequence far superior to the hand-rolled `while` loop.
- **Spike Simulation Speedup:** Since Spike simulates every retired CPU instruction, removing the loop logic directly translates to a significant drop in simulated CPU cycles for the Softmax bottleneck, without altering any of the Gemmini hardware matrix math or quantization steps.
