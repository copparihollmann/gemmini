## Analysis

Looking at the code, I need to identify which strategy offers the most impact.

**Current code structure:**
- Both matmuls use `gemmini_mxquant_config_mvout(..., lut_update_granularity=1)`
- `lut_update_granularity` G=1 means the requantizer refreshes its output LUT after every single tile
- For matmul 1: `tiles_K = ATT_D/DIM = 64/16 = 4` K-tiles per output tile
- For matmul 2: `tiles_K = ATT_S/DIM = 128/16 = 8` K-tiles per output tile
- Within a single `gemmini_loop_ws_spad` invocation, the output LUT is fixed — there's no reason to refresh it every tile

**Strategy 15** directly applies: increase `lut_update_granularity` G from 1 to `tiles_K` (or larger) for both matmuls. Within a single `gemmini_loop_ws_spad` call, the output format and LUT contents do not change, so refreshing the requantizer every tile is pure overhead with no correctness benefit.

## Plan

**Apply Strategy 15: Increase `lut_update_granularity` G in `gemmini_mxquant_config_mvout`**

**Specific changes:**

1. **In matmul 1 (Q @ K^T):** Change `gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1)` to use `lut_update_granularity = tiles_K` (= `ATT_D/DIM = 4`). Since the entire matmul is executed as a single `gemmini_loop_ws_spad` invocation, the output LUT never changes during execution. Setting G=`tiles_K` means the requantizer refreshes only once per (i,j) output tile across the K-reduction dimension, instead of after every K-slice.

2. **In matmul 2 (P @ V):** Change `gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1)` to use `lut_update_granularity = tiles_K` (= `ATT_S/DIM = 8`). Same reasoning: within one `gemmini_loop_ws_spad` call the LUT is static.

**Why this is safe:** The output format (`out_mx_fmt=3`, BF16) is set once in `gemmini_extended3_config_ex` and never changes within each matmul invocation. The LUT is not reloaded between tiles. Setting G=`tiles_K` makes the requantizer refresh at the same granularity as the K-accumulation boundary, which is the natural boundary where output tiles are actually finalized — the refresh is semantically equivalent but happens far less often.

**Concretely:** Replace both `..., 0, 0, 1)` calls with `..., 0, 0, tiles_K)` where `tiles_K` is the local variable already computed just above each call. This reduces requantizer LUT refresh overhead by a factor of `tiles_K` (4× for matmul 1, 8× for matmul 2) with zero effect on numerical output.
