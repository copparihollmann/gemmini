An elegant and highly effective way to optimize this MX-Gemmini matrix multiplication kernel is to apply the following strategy:

### **Strategy: Assign B tiles to fixed high-address scratchpad region (`b_base = BANK_NUM*BANK_ROWS - ...`) to enable weight-stationary reuse across I tiles**

### **Analysis of Inefficiencies in Baseline**
In the baseline code, the outer loop iterates over $i_0$ (M-dimension blocks) and the inner loop iterates over $j_0$ (N-dimension blocks). For every single combination of $(i_0, j_0)$, the program completely flushes the configuration, re-loads both activation scales ($A\_scales\_row$) and weight scales ($B\_scales\_col$), and re-transfers both matrix $A$ and matrix $B$ tiles from DRAM into the scratchpad. 

Because weight scales and weight tiles ($B$) do not depend on $i_0$, we can exploit **weight-stationary scratchpad reuse** by interchanging the loops so that $j_0$ becomes the outer loop and $i_0$ becomes the inner loop. By doing this:
1. Matrix $B$ tiles and their column scales can be loaded **once** per outer $j_0$ iteration.
2. Inside the inner $i_0$ loop, we only need to stream in the new $A$ tiles and row scales, reusing the already-resident $B$ tiles in the high scratchpad memory region (`b_base`) across multiple $i_0$ steps.
3. Configuration overhead (`gemmini_flush` and `gemmini_extended3_config_ex`) can be hoisted out of the loops entirely, since the execution format parameters are invariant.

---

### **Step-by-Step Optimization Plan**

1. **Hoist Invariant Setup:**
   Move `gemmini_flush(0)` and the format configuration `gemmini_extended3_config_ex(...)` to the start of the `solution()` function (alongside `gemmini_config_st`). These only need to be configured once.

2. **Interchange Loop Order:**
   Swap the loop nesting order so that the $j_0$ loop (columns of $B$) is on the outside, and the $i_0$ loop (rows of $A$) is on the inside:
   ```c
   for (int j0 = 0; j0 < BLOCKS_N; j0++) {
       // ...
       for (int i0 = 0; i0 < BLOCKS_M; i0++) {
           // ...
       }
   }
   ```

3. **Hoist B-Matrix Scaling and Loading:**
   Move the column-scale preparation (`memcpy` for `B_s`), scale-loading (`gemmini_mx_load_scales(..., 1)`), and $B$ scratchpad loading (`gemmini_extended_mvin` into `b_base`) into the outer $j_0$ loop, just before entering the $i_0$ loop. This reduces the number of DRAM reads for $B$ tiles and $B$ scales by a factor of `BLOCKS_M`.

4. **Retain A-Matrix Loading and Computation on the Inside:**
   Keep the row-scale preparation (`memcpy` for `A_s`), scale-loading (`gemmini_mx_load_scales(..., 0)`), and $A$ scratchpad loading (`gemmini_extended_mvin` into `a_base`) inside the inner $i_0$ loop. 
   Follow this immediately with the hardware computation `gemmini_loop_ws_spad(...)` and the final shared-memory read-out via `gemmini_mx_read_smem` to write back the computed $C$ results.
