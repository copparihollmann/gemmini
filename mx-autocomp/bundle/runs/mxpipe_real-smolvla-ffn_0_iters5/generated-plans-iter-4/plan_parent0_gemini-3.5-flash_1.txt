An elegant and highly effective optimization plan to improve the performance of this kernel is to apply **Strategy 1: Reduce data movement** by eliminating host-CPU scale staging and hoisting scale loads.

### Inefficiency Analysis
In the current implementation, scale factors are sliced and copied on the host CPU using `memcpy` into local buffers (`A_s` and `B_s`) before calling `gemmini_mx_load_scales` inside the `i0` and `j0` loops:
```c
for (int g = 0; g < MATMUL_K / 32; g++) {
  memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);
}
gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);
```
This is a critical bottleneck. Host-CPU data staging is extremely slow compared to the Gemmini accelerator's DMA. Additionally, because scales persist in the hardware's internal scale memories (`mx_scale_a_mem` and `mx_scale_b_mem`) until overwritten, re-loading them block-by-block inside the loops is highly redundant and wastes DRAM bandwidth.

### Optimization Plan

1. **Eliminate Host Staging Buffers and `memcpy`**: 
   Completely remove the temporary scale buffers `A_s` and `B_s` and the nested `memcpy` loops. This eliminates all scalar host-CPU overhead from the critical path.

2. **Hoist Scale Loading Outside All Loops**:
   Load the entire `A_scales_row` and `B_scales_col` matrices directly from their source DRAM locations using a single call to `gemmini_mx_load_scales` for each, placed entirely outside the outer loops:
   ```c
   gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
   gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);
   ```

3. **Simplify the Execution Loops**:
   With scale factors pre-loaded globally, the inner loop iterations no longer incur any scale-loading overhead. The hardware requantizer will automatically index into the internal scale memories during the `gemmini_loop_ws_spad` execution.
