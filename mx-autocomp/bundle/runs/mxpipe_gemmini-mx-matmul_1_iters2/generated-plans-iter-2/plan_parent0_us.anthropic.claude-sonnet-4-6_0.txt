## Analysis of the Original Code

The original code loads A and B tiles in **separate loops**:
```c
// First loop: all A tiles
for (int i = 0; i < tiles_I; i++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(A[i,k], a_base + (i*tiles_K+k)*DIM, DIM, DIM);

// Second loop: all B tiles  
for (int j = 0; j < tiles_J; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(B[j,k], b_base + (j*tiles_K+k)*DIM, DIM, DIM);
```

Additionally, `gemmini_config_ld` is called once before both loops — but since A and B have **different strides** (`MATMUL_K * sizeof(elem_t)` for row-major A vs. the same for B when using `gemmini_extended_mvin` vs `mvin2`), there's an opportunity to use the two separate mvin ports (mvin for A, mvin2 for B) with different stride configurations, and interleave them within a single loop over k to better hide DMA latency.

## Selected Strategy: #10 — Interleave A and B tile mvin calls within the same loop iteration

## Plan

**Observation:** The original code issues all A mvins sequentially, then all B mvins sequentially. The DMA engine is only kept busy with one stream at a time. By interleaving A tile loads (`gemmini_extended_mvin`, port 0) and B tile loads (`gemmini_extended_mvin2`, port 1) within the same loop body, both mvin ports can be kept busy simultaneously, hiding individual DMA latency through overlapping transfers.

**Key change:** Use `gemmini_extended_mvin` for A (port 0, id=0) and `gemmini_extended_mvin2` for B (port 1, id=1). Configure their strides independently using `gemmini_extended3_config_ld` with `id=0` for A and `id=1` for B. Then merge the two nested loops into a single loop that, for each `(k)` sweep, loads `(i,k)` A tiles and `(j,k)` B tiles together.

**Concrete steps:**

1. **Configure A stride** once before the loop using `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0)` (id=0).
2. **Configure B stride** once using `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1)` (id=1).
3. **Merge the two tile loops** into a single loop over `k`, and within that loop, issue all `i` A-tile mvins for that `k` slice followed immediately by all `j` B-tile mvins for that `k` slice:
```
for k in [0, tiles_K):
  for i in [0, tiles_I):
    gemmini_extended_mvin(A[i,k], a_base + (i*tiles_K+k)*DIM, DIM, DIM)
  for j in [0, tiles_J):
    gemmini_extended_mvin2(B[j,k], b_base + (j*tiles_K+k)*DIM, DIM, DIM)
```

This groups A and B loads for the same K-slice together, enabling the hardware to issue both port-0 and port-1 DMA requests in close temporal proximity so they can proceed in parallel, rather than waiting for all A tiles before any B tile DMA begins. The `gemmini_config_ld` call (which only configures port 0) is replaced with explicit per-id configuration calls for ports 0 and 1 respectively. All other code (config_ex, scale loads, mxquant_config_mvout, loop_ws_spad, read_smem, fence) remains unchanged.
