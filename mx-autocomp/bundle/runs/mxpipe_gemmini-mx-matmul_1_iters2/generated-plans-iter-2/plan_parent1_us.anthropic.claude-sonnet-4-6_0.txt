## Analysis

Looking at the original code, the mvin loops load A and B tiles independently, but B tiles are loaded once and reused across all I iterations in `gemmini_loop_ws_spad`. The B tiles are already loaded into the scratchpad at `b_base` and the hardware loop handles the weight-stationary computation internally. 

The key inefficiency I see relates to **mvin2 (separate port for B)**. Currently, both A and B use `gemmini_extended_mvin` (the same port). By using `gemmini_extended_mvin2` for B tiles, the hardware can overlap A and B DMA transfers, since they go through independent DMA ports.

However, looking more carefully, the more impactful strategy is **strategy 10: reuse loaded B (weight) tiles across multiple I-tile iterations without re-mvin**. But since the code already loads B only once (outside the I loop) and `gemmini_loop_ws_spad` handles the full I×J×K tiled loop, B tiles are already being reused.

The real opportunity is **strategy 2: overlap data movement and compute** — specifically using **separate mvin ports** (mvin for A, mvin2 for B) so that A and B DMA transfers can execute in parallel. Currently both use `gemmini_extended_mvin` which serializes them through a single port.

## Plan

**Strategy: Use `gemmini_extended_mvin2` for B tiles to overlap A and B loads (Strategy 2 — overlap data movement)**

**Change:** Replace `gemmini_extended_mvin` with `gemmini_extended_mvin2` for the B-tile mvin loop, and issue `gemmini_extended3_config_ld` with id=1 (for mvin2 port) before B loads. Also configure A loads with id=0.

The mvin (port 0) and mvin2 (port 1) are independent DMA channels. By issuing A loads on mvin and B loads on mvin2, both sets of DMA transfers can be in-flight simultaneously, effectively halving the data-movement latency.

The B loop should be **interleaved** with the A loop — issue A tiles on mvin, then immediately issue B tiles on mvin2 — so they overlap. Reorder: configure both load ports, then interleave A and B mvin/mvin2 calls within the k loop.

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // Configure mvin port 0 (A) with id=0
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0);
  // Configure mvin2 port 1 (B) with id=1
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);

  // Interleave A (mvin) and B (mvin2) loads to overlap DMA transfers
  #pragma GCC unroll 2
  for (int k = 0; k < tiles_K; k++) {
    #pragma GCC unroll 2
    for (int i = 0; i < tiles_I; i++)
      gemmini_extended_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM),
                            a_base + (i * tiles_K + k) * DIM, DIM, DIM);
    #pragma GCC unroll 2
    for (int j = 0; j < tiles_J; j++)
      gemmini_extended_mvin2((void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
                             b_base + (j * tiles_K + k) * DIM, DIM, DIM);
  }

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```

**Key changes:**
1. `gemmini_extended3_config_ld(..., id=0)` configures port 0 (mvin) for A tiles
2. `gemmini_extended3_config_ld(..., id=1)` configures port 1 (mvin2) for B tiles
3. The loops are restructured to outer-K, inner-I/J, so within each K-slice, A tiles (mvin port 0) and B tiles (mvin2 port 1) are issued back-to-back in the instruction stream, allowing both DMAs to be in-flight concurrently
4. B tiles use `gemmini_extended_mvin2` instead of `gemmini_extended_mvin`
