## Analysis

Looking at the code, I need to identify the key inefficiency relevant to the strategies listed.

The code has two independent Gemmini matmul operations (S1 = Q @ K^T, then O = P @ V), each preceded by `gemmini_flush(0)` and `gemmini_extended3_config_ex(...)` with **identical parameters**:

```c
gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
```

Both calls use the same dataflow, format fields, strides, and all other parameters. The second call is therefore redundant — it re-issues configuration that is already in hardware state from the first call.

Additionally, `gemmini_flush(0)` is called twice. The second `gemmini_flush` before the O = P @ V matmul is unnecessary if the first matmul and its fence have already completed (which they have — `gemmini_fence()` is called after the first `gemmini_mx_read_smem`). The flush resets hardware state and forces re-configuration overhead, but since the config parameters are identical, the second flush + re-config sequence is pure overhead.

## Plan: Simplify / Remove Unnecessary Code

**Strategy: simplify or remove unnecessary code**

The plan is:

1. **Remove the second `gemmini_flush(0)`** before the O = P @ V block. The hardware state is already clean after the `gemmini_fence()` that concludes the S1 computation. Re-flushing resets internal state unnecessarily and adds latency.

2. **Remove the second `gemmini_extended3_config_ex(...)` call** in the O = P @ V block. Since both matmuls use identical configuration (`WEIGHT_STATIONARY`, `act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`, `A_stride=1`, `C_stride=1`, no transposes), the config persists unchanged from the first call and does not need to be re-issued. Per the architecture docs: "CONFIG_EX, CONFIG_LD, and CONFIG_ST fields persist until changed; avoid redundant re-issue when format, stride, and scale are unchanged across consecutive tiles."

3. **Keep the first `gemmini_flush(0)` and first `gemmini_extended3_config_ex(...)`** as-is — these are required for correct initialization at the start of the kernel.

4. The `gemmini_config_st(...)` and `gemmini_mxquant_config_mvout(...)` calls in the second block must remain because the `j_bound` (tiles_J) and `k_bound` (tiles_K) tile counts differ between the two matmuls (ATT_S vs ATT_D for tiles_J), and `scale_factors` needs to be reconfigured for the new bounds. Similarly, the scale loads (`gemmini_mx_load_scales`) must remain since P_scales and V_scales_col differ from the first matmul's Q and KT scales.

This change eliminates two instruction-issue sequences (flush + config_ex) that do no useful work, reducing the total instruction count and the serialization stall that `gemmini_flush` introduces between the two matmul phases.
