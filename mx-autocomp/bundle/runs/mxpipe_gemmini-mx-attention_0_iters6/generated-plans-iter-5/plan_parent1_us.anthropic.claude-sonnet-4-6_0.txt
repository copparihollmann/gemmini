## Analysis

Looking at the code, the softmax section (step 2) has two passes over the `ATT_S`-element arrays:

**Pass 1:** Find max `mq` over all `q[j]`, storing all `q[j]` values in the array.
**Pass 2:** Compute `p[j] = mx_iexp(q[j] - mq)` and sum them.

This requires writing all `q[]` values to memory in pass 1, then reading them back in pass 2 — that's `ATT_S = 128` int64 reads/writes per row, for 128 rows = significant memory traffic on the `q[]` and `p[]` arrays.

Strategy 2 directly addresses this: use an online/Welford-style running max so we can fuse the two passes. However, since `mx_iexp` is applied to `(q[j] - max)`, if the max changes mid-stream we need to rescale previously computed exp values. The standard online softmax trick handles this: when `mq` is updated to `new_max`, all previous partial sums are multiplied by `mx_iexp(old_max - new_max)`.

## Plan

**Apply Strategy 2: Fuse the two softmax passes using online running-max correction.**

### Specific changes to the softmax loop (step 2):

1. **Eliminate the `q[]` array** — instead of storing all quantized BF16 values to `q[]` first, process each `q[j]` value inline as we unpack it.

2. **Maintain a running max `mq` and running sum `sm` simultaneously** in a single pass over the 4-per-word packed BF16 values from `S1_hw[i][]`.

3. **When a new maximum is found** (`qq > mq`): correct the running sum by multiplying it by `mx_iexp(mq - qq)` (the rescaling factor for the old partial sum), then store the correction factor per previously computed group's p[] values similarly. Actually, since we still need `p[j]` values for the scale quantization inner loop, we need to store them — but we can eliminate the separate `q[]` array and compute `p[j] = mx_iexp(q[j] - running_mq)` in the first pass, correcting stored `p[]` values when `mq` updates.

4. **Correction on max update**: When `mq` updates from `old_mq` to `new_mq = qq`, multiply `sm` by `mx_iexp(old_mq - new_mq)` and update all previously written `p[0..j-1]` by the same factor. Since ATT_S=128 this correction loop is at most 128 iterations but happens rarely.

5. **Result**: eliminate the `q[]` array entirely (saving 128×8 = 1KB stack), reduce the dominant memory traffic from two full passes (read q[], write p[]) to one pass (write p[] only once), and the `q[j]` values are never materialized to memory.

### Concrete code changes:

```c
// Replace:
int64_t q[ATT_S];
int64_t mq = -((int64_t)1 << 62);
for (int j = 0; j < ATT_S; j += 4) { /* fill q[] and find mq */ }
int64_t p[ATT_S];
int64_t sm = 0;
for (int j = 0; j < ATT_S; j++) { p[j] = mx_iexp(q[j] - mq); sm += p[j]; }

// With: single fused pass — no q[] array
int64_t mq = -((int64_t)1 << 62);
int64_t p[ATT_S];
int64_t sm = 0;
for (int j = 0; j < ATT_S; j += 4) {
    uint64_t w = S1_hw[i][j / 4];
    for (int l = 0; l < 4; l++) {
        int64_t qq = mx_ibf16_to_q((uint16_t)((w >> (l * 16)) & 0xFFFF));
        if (qq > mq) {
            // Rescale existing partial sum and all stored p[] values
            int64_t corr = mx_iexp(mq - qq);  // < 1 in fixed-point
            sm = (sm * corr) >> MX_FRAC;
            for (int jj = 0; jj < j + l; jj++)
                p[jj] = (p[jj] * corr) >> MX_FRAC;
            mq = qq;
        }
        int64_t pv = mx_iexp(qq - mq);
        p[j + l] = pv;
        sm += pv;
    }
}
```

The rest of the softmax body (log2, reciprocal, group scale computation, `P_scales`, `P_q`) is **unchanged** since it only reads `p[]`, `sm`, and `mq` — which are all still correctly computed. The Gemmini sections (steps 1 and 3) are also **unchanged**.
