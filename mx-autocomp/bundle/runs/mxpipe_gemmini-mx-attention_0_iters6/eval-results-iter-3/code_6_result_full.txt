## Analysis of the Current Code

Looking at the current execution timeline:

```
Phase 1: Q@KT matmul (gemmini compute)
Phase 2: gemmini_mx_read_smem + gemmini_fence()  ← blocks until DMA done
Phase 3: Softmax loop (pure scalar CPU, sequential)
Phase 4: P@V matmul setup: flush, config_ex, load_scales, mvin A, mvin B
Phase 5: P@V matmul (gemmini compute)
Phase 6: gemmini_mx_read_smem + gemmini_fence()
```

The critical observation is that **Phase 3 (softmax) and Phase 4 (P@V setup) are currently fully sequential**, even though many of Phase 4's operations don't depend on the softmax output:

- `gemmini_flush(0)` — no dependency on softmax
- `gemmini_extended3_config_ex(...)` — no dependency on softmax
- `gemmini_mx_load_scales(...V_scales_col...)` — V's scale factors exist before softmax
- `gemmini_config_ld(...)` and all **B-side (V matrix) mvin tiles** — V is read-only input, independent of P
- `gemmini_mxquant_config_mvout(...)` — configuration only

Only the **A-side (P matrix) mvin tiles** depend on softmax completing.

## The New Strategy: Hoist Gemmini P@V Setup Before the Softmax Loop

**Move all Gemmini P@V instructions that are independent of `P_q[][]` to execute before the softmax loop.** Specifically:

1. After `gemmini_fence()` in Phase 1, immediately issue:
   - `gemmini_flush(0)`
   - `gemmini_extended3_config_ex(...)` for P@V
   - `gemmini_mx_load_scales` for B (V scales) — `V_scales_col` is static
   - `gemmini_config_ld(ATT_D * sizeof(elem_t))` + all **B-side (V) mvin tiles** into the scratchpad
   
2. Then run the softmax scalar loop (Phase 3), which writes `P_q` and `P_scales`

3. After the softmax loop:
   - `gemmini_mx_load_scales` for A (P scales, now ready)
   - `gemmini_config_ld(ATT_S * sizeof(elem_t))` + all **A-side (P) mvin tiles** into the scratchpad
   - `gemmini_mxquant_config_mvout(...)`
   - `gemmini_loop_ws_spad(...)`
   - `gemmini_mx_read_smem(...)` + `gemmini_fence()`

## Why This Improves Performance

### Overlap of Scalar Work with DMA/Configuration

The Gemmini RoCC command queue is deep and the host CPU can issue instructions without stalling as long as the queue isn't full. By issuing the V-matrix mvin commands **before** the softmax loop:

- The **DMA loading of V tiles** (tiles_K × tiles_J = 8×4 = 32 tiles) executes in parallel with the scalar softmax computation
- The softmax loop processes `ATT_S=128` rows with 128 unpacks + iexp + fp8-encode per row — substantial scalar work
- During this time, Gemmini independently feeds V tiles from DRAM into the scratchpad

### Quantitative Overlap

- V matrix size: ATT_S × ATT_D = 128×64 = 8192 bytes → 32 tile mvins at 2 tiles/command = 16 mvin commands
- Softmax: 128 rows × (128 unpack + 128 iexp + 128 encode) ≈ thousands of scalar instructions
- Previously: V mvin was fully serialized after softmax; now it runs concurrently

### Correctness Preserved

- V tiles are loaded to `b_base` which is in the **top** of scratchpad — no overlap with A tiles at `a_base = 0`
- `gemmini_mx_load_scales` for A (P scales) is still issued **after** the softmax loop writes `P_scales`, respecting data dependency
- The programming model sequence is maintained: config_ex → load_scales(B) → [mvin B] → load_scales(A) → [mvin A] → mxquant_config → loop_ws_spad. Note that load_scales(A) and mvin A are issued after softmax, but config_ex and load_scales(B) are hoisted; this is valid because scale memory sel=0 (A) and sel=1 (B) are independent buffers, and sel=1 is loaded with correct data before compute begins
- `mx_loop_spad_marker` (funct 24) is still part of `gemmini_loop_ws_spad` macro and issued immediately before funct 8 — no statefulness issue
