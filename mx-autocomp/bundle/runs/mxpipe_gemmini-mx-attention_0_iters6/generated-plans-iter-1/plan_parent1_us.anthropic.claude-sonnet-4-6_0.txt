## Analysis of the Current Code

The current code performs a two-matmul attention kernel:
1. **S1 = Q @ K^T** (ATT_S × ATT_D) × (ATT_D × ATT_S) → (ATT_S × ATT_S)
2. **O = P @ V** (ATT_S × ATT_S) × (ATT_S × ATT_D) → (ATT_S × ATT_D)

The feedback states **scratchpad utilization is 0KB out of 256KB** and **accumulator utilization is 0KB out of 64KB**. This strongly indicates the current tiling uses the minimum possible tile size (one DIM×DIM tile at a time effectively), leaving massive on-chip memory unused.

## Selected Strategy: Loop Tiling

The current code already calls `gemmini_loop_ws_spad` (the fused hardware loop), so strategy 3 is already applied. Strategy 2 (amortize config_mvout) requires batching which is constrained by the single fused loop call. Strategy 4 is irrelevant since ATT_S and ATT_D are already multiples of DIM=16. **Strategy 1 (loop tiling)** is the right lever: the mvin loops load all tiles into the scratchpad before the single fused compute call. With larger matrices, fitting more tiles simultaneously into the scratchpad reduces the number of mvin + compute + read_smem invocation cycles.

## The Problem

Looking at the mvin loops, the code loads **all** A and B tiles for the entire matrix into the scratchpad in one shot, then issues one `gemmini_loop_ws_spad`. This works only if the entire matrix fits. But the constraint is:

`(tiles_I*tiles_K + tiles_J*tiles_K)*DIM ≤ 8192`

For example, if ATT_S=64, ATT_D=64: tiles_I=4, tiles_J=4, tiles_K=4 → (4×4 + 4×4)×16 = 512 ≤ 8192 ✓. The scratchpad fits fine but is severely underutilized because the tile counts are small.

The real inefficiency is that the mvin loops iterate one tile at a time with individual `gemmini_extended_mvin` calls. While the code does batch 2 tiles at a time (`bb` variable), it should maximize `bb` up to `MAX_BLOCK_LEN=4`. More importantly, the **outer tiling** (blocking over I, J, K dimensions into larger sub-problems) would let the hardware process more data per configuration overhead paid.

## The Plan

**Apply loop tiling to the mvin phase by maximizing the block size to MAX_BLOCK_LEN=4 and introducing outer tile blocks that fill the scratchpad more completely.**

Specifically:

1. **For each matmul, increase `bb` (mvin block length) to the maximum of `min(remaining_tiles, MAX_BLOCK_LEN=4)`** instead of capping at 2. This halves the number of mvin instructions for the K and J loops.

2. **Introduce outer I-blocking**: partition the `tiles_I` dimension into blocks of `BLOCK_I = floor(8192 / ((tiles_K + tiles_J*tiles_K) * DIM / DIM))` tiles, subject to the scratchpad constraint. For each I-block, load the corresponding A sub-tiles and all B tiles, then issue `gemmini_loop_ws_spad` for that sub-problem. This means B tiles are loaded once per I-block (and in the extreme case once total), while A tiles are loaded in chunks — maximizing reuse of B tiles in scratchpad.

   - For `S1 = Q @ KT`: tiles_I=ATT_S/DIM, tiles_J=ATT_S/DIM, tiles_K=ATT_D/DIM. All B tiles occupy `tiles_K*tiles_J*DIM` rows. The remaining rows hold A tiles. Compute max `BLOCK_I` such that `(BLOCK_I*tiles_K + tiles_J*tiles_K)*DIM ≤ 8192`.
   - For `O = P @ V`: similarly block over I.

3. **Within each I-block**, issue a single `gemmini_loop_ws_spad(BLOCK_I, tiles_J, tiles_K, ...)` — the fused hardware loop handles the inner I/J/K iteration, so no software loop overhead inside the block.

4. **Accumulator check**: each `gemmini_loop_ws_spad` call needs `BLOCK_I * tiles_J * DIM ≤ 256` accumulator rows. Size `BLOCK_I` to satisfy both scratchpad and accumulator constraints simultaneously.

5. **mvin uses `bb = min(remaining, 4)`** to batch up to 4 consecutive tiles per mvin command, reducing instruction count by 2× over the current cap of 2.

### Concrete changes:

**For `gemmini_loop_ws_spad`**, change the `I` argument from `tiles_I` to `block_i` (the number of I-tiles in the current block), and wrap it in a loop over I-blocks:

```
for (int ib = 0; ib < tiles_I; ib += BLOCK_I) {
    int block_i = min(tiles_I - ib, BLOCK_I);
    // mvin A tiles for rows [ib, ib+block_i)
    // mvin B tiles for all (k,j) — same every iteration if B unchanged
    // gemmini_loop_ws_spad(block_i, tiles_J, tiles_K, ...)
    // gemmini_mx_read_smem into the correct row of output buffer
}
```

B tiles are the same across all I-blocks, so they are loaded once (before the I-block loop), saving repeated B mvins.

**mvin batching**: change `bb = (tiles_K - k < 2) ? (tiles_K - k) : 2` to `bb = min(tiles_K - k, MAX_BLOCK_LEN)` (i.e., up to 4), and similarly for J batching.

This reduces:
- mvin instruction count by 2× (from max-2 batching to max-4 batching)
- Configuration overhead (config_ex, load_scales, config_st, mxquant_config_mvout) stays at one call per full matmul since B is constant across I-blocks
- The hardware loop processes larger sub-problems per invocation, reducing the ratio of setup cost to compute work
