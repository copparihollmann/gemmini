## Analysis of the Original Code

The original code performs:
1. im2col (CPU-side)
2. Load scales for A and B
3. **Sequential** mvin of all A tiles (using `gemmini_extended_mvin`)
4. **Sequential** mvin of all B tiles (using `gemmini_extended_mvin` again, same port)
5. Configure mvout, compute, read results

The key inefficiency I'm targeting: **A tiles and B tiles are loaded sequentially using the same mvin port**, meaning the hardware cannot overlap A and B tile fetches. The architecture provides **three independent mvin ports** (`mvin`, `mvin2`, `mvin3`), and using `mvin2` for B tiles allows the DMA engine to fill both scratchpad banks in parallel rather than serializing all loads through a single port.

## Selected Strategy: #12 — Use mvin2 for B-tile loads concurrently with mvin for A-tile loads

## Plan

### What to Change

**Replace `gemmini_extended_mvin` with `gemmini_extended_mvin2` for all B-tile loads**, and **interleave the A-tile and B-tile mvin loops** so that both ports are issuing commands to the DMA engine at the same time rather than one completing before the other starts.

### Detailed Steps

1. **Keep the A-tile loop using `gemmini_extended_mvin` (port 0)** — no change needed here except interleaving.

2. **Change the B-tile loop to use `gemmini_extended_mvin2` (port 1)** — replace every `gemmini_extended_mvin(...)` in the B-tile loop with `gemmini_extended_mvin2(...)`. The spad addresses and DRAM pointers are identical; only the port changes.

3. **Interleave A and B mvin commands**: Rather than issuing all A mvins then all B mvins, restructure the loop so that for each `(i, j, k)` combination (or at minimum each `k` slice), we interleave an A mvin and a B mvin. A natural interleaving is:

```
for k in tiles_K:
    for i in tiles_I:
        mvin(A[i][k] → spad_a)          // port 0
    for j in tiles_J:
        mvin2(B[j][k] → spad_b)         // port 1
```

This issues A and B commands in alternating bursts so the DMA controller can pipeline them. The inner-k structure means both A and B loads for a given K-slice are issued before moving to the next, which also improves locality.

4. **`gemmini_config_ld` only configures port 0** (mvin). Port 1 (mvin2) uses a separate config. Issue `gemmini_extended3_config_ld(..., id=0)` for A's stride and `gemmini_extended3_config_ld(..., id=1)` for B's stride before the respective loops. Both strides are `MATMUL_K * sizeof(elem_t)` in this case, so we call:
   - `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0)` for port 0 (A)
   - `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1)` for port 1 (B)

   Both strides are the same here (`MATMUL_K * sizeof(elem_t)`), but they must be configured on their respective port IDs.

5. **No other changes** — scratchpad layout, b_base, a_base, tile counts, compute call, and output read are all unchanged.

### Why This Reduces Latency

The original code serializes all A mvin commands, then all B mvin commands through a single DMA queue. With mvin + mvin2 interleaved, the hardware DMA engine can service both queues simultaneously, effectively halving the data-movement time for the load phase. Given the problem dimensions (MATMUL_M=64, MATMUL_N=32, MATMUL_K=32 based on the context), there are `tiles_I*tiles_K + tiles_J*tiles_K = 4*2 + 2*2 = 12` total tile loads, and overlapping the two ports directly reduces the critical path of the mvin phase.
