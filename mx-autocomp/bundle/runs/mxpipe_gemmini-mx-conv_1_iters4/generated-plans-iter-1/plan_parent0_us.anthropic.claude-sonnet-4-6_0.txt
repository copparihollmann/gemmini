## Analysis of the Original Code

The original code uses `gemmini_extended_mvin` (via port `k_MVIN`) for **both** A tiles and B tiles, using the same mvin port sequentially. This means all A loads happen first, then all B loads — they are serialized and use only one of the three available mvin ports.

The key observation is:
- A tiles are loaded using `gemmini_extended_mvin` (port 0 / `k_MVIN`)
- B tiles are also loaded using `gemmini_extended_mvin` (port 0 / `k_MVIN`)
- These are issued sequentially, so B loads must wait for all A loads to complete

## Selected Strategy: Overlap Data Movement (Strategy 1 — specifically using separate mvin ports for A and B)

### Plan

The hardware provides **three independent mvin ports**: `k_MVIN` (mvin), `k_MVIN2` (mvin2), and `k_MVIN3` (mvin3). The original code uses only `k_MVIN` for both A and B matrix tiles, serializing all data movement.

**The fix**: Load A tiles using `gemmini_extended_mvin` (port 1) and B tiles using `gemmini_extended_mvin2` (port 2) concurrently. The two ports are independent, so the hardware can pipeline A and B DMA transfers in parallel, cutting the effective mvin latency roughly in half.

Concretely:
1. Issue `gemmini_config_ld` once (id=0, covering both ports since stride is the same `MATMUL_K * sizeof(elem_t)`).
2. Interleave the A and B mvin loops: for each `(i, j, k)` combination, issue the A-tile mvin on port 0 and the B-tile mvin on port 1 back-to-back so the hardware overlaps them.

Actually, since both loops are already flat (not nested together), the simplest approach that maximizes overlap is to **interleave** the A and B mvin commands in a single combined loop over k (since tiles_K=2 here: K=32, DIM=16 → tiles_K=2; tiles_I=4, tiles_J=2):

- Configure port 0 (id=0) for A with `gemmini_extended3_config_ld(stride, scale, shrunk, 0)` 
- Configure port 1 (id=1) for B with `gemmini_extended3_config_ld(stride, scale, shrunk, 1)`
- Then in a single loop over all (i,k) and (j,k) pairs, alternate `gemmini_extended_mvin` and `gemmini_extended_mvin2` calls so the DMA engine sees both A and B requests in the queue simultaneously, allowing the hardware to service them in parallel.

The rewritten mvin section becomes:

```c
// Configure both ports with same stride
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0);
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);

// Interleave A (port 0) and B (port 1) loads so they overlap in the DMA queue
for (int k = 0; k < tiles_K; k++) {
    for (int i = 0; i < tiles_I; i++) {
        gemmini_extended_mvin(
            (void*)(((elem_t*)A_buf) + i * DIM * MATMUL_K + k * DIM),
            a_base + (i * tiles_K + k) * DIM, DIM, DIM);
    }
    for (int j = 0; j < tiles_J; j++) {
        gemmini_extended_mvin2(
            (void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
            b_base + (j * tiles_K + k) * DIM, DIM, DIM);
    }
}
```

By issuing mvin (port 0) and mvin2 (port 1) commands interleaved in the instruction stream, the hardware's DMA engine can process A and B transfers simultaneously. The config_ld for id=1 only affects port 1, leaving port 0 unchanged (both have the same stride here since A and B have the same K-dimension stride). This change requires no restructuring of the compute or output steps.
