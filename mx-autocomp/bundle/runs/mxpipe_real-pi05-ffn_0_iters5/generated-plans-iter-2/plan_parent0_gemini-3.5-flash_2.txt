### Optimization Plan

We will apply **Strategy 2: Host Loop Unrolling for RoCC Command Queues** to reduce the overhead of host-side loop management and keep the Gemmini command queue saturated. 

#### Target Inefficiency
In the baseline code, loading the input tiles of matrices $A$ and $B$ into the scratchpad requires nested host-side loops. For matrix $A$, the nested loops execute `tiles` $\times$ `tiles_K` times (e.g., $4 \times 32 = 128$ iterations). For matrix $B$, they also execute 128 iterations. In each iteration, the host CPU must compute DRAM addresses, perform loop increments, evaluate branch conditions, and dispatch a single `gemmini_extended_mvin` instruction. This loop overhead can stall the host CPU, preventing it from feeding the Gemmini instruction queue fast enough, causing the systolic array to idle between tile computations.

#### Optimization Steps
To eliminate this bottleneck, we will unroll the inner loop over the $K$ dimension (the `k` loop) for both the $A$ and $B$ matrix loading sequences. Since $K = 512$ and $\text{DIM} = 16$, `tiles_K` is $32$, which is perfectly divisible by a factor of $4$.

1. **Unroll Matrix A Loading Loop**:
   We will unroll the inner `k` loop by a factor of 4. Inside the loop body, we will issue 4 sequential `gemmini_extended_mvin` commands with pre-computed offsets.
   ```c
   for (int i = 0; i < tiles; i++) {
     for (int k = 0; k < tiles_K; k += 4) {
       gemmini_extended_mvin((void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
                             a_base + (i * tiles_K + k) * DIM, DIM, DIM);
       gemmini_extended_mvin((void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + (k + 1) * DIM),
                             a_base + (i * tiles_K + k + 1) * DIM, DIM, DIM);
       gemmini_extended_mvin((void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + (k + 2) * DIM),
                             a_base + (i * tiles_K + k + 2) * DIM, DIM, DIM);
       gemmini_extended_mvin((void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + (k + 3) * DIM),
                             a_base + (i * tiles_K + k + 3) * DIM, DIM, DIM);
     }
   }
   ```

2. **Unroll Matrix B Loading Loop**:
   Similarly, we will unroll the inner `k` loop of the matrix $B$ loading phase by a factor of 4.
   ```c
   for (int j = 0; j < tiles; j++) {
     for (int k = 0; k < tiles_K; k += 4) {
       gemmini_extended_mvin((void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
                             b_base + (k * tiles + j) * DIM, DIM, DIM);
       gemmini_extended_mvin((void*)((((elem_t*)B_in) + ((k + 1) * DIM) * MATMUL_N + (j0 * BLK + j * DIM))),
                             b_base + ((k + 1) * tiles + j) * DIM, DIM, DIM);
       gemmini_extended_mvin((void*)((((elem_t*)B_in) + ((k + 2) * DIM) * MATMUL_N + (j0 * BLK + j * DIM))),
                             b_base + ((k + 2) * tiles + j) * DIM, DIM, DIM);
       gemmini_extended_mvin((void*)((((elem_t*)B_in) + ((k + 3) * DIM) * MATMUL_N + (j0 * BLK + j * DIM))),
                             b_base + ((k + 3) * tiles + j) * DIM, DIM, DIM);
     }
   }
   ```

By unrolling these inner loops, we drastically reduce branch hazards, instruction cache misses, and index arithmetic overhead on the host RISC-V processor, keeping the Gemmini hardware command queue saturated.
