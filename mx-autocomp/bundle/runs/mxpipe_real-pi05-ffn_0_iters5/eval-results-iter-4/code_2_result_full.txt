Our goal is to apply **Strategy 3 (Double-buffering the output shared memory space)** to overlap the memory transfer of the completed tiles with the computation of the subsequent tiles, thereby eliminating a significant portion of the serialization overhead.

1. **Allocate Dual Buffers in `mx_smem`:**
   Each output block is of size $\text{BLK} \times \text{BLK} = 64 \times 64 = 4096$ elements of BF16.
   Since `SPAD_DEST` is addressed in rows of 16 BF16 elements, one block occupies $4096 / 16 = 256$ rows.
   We can define two non-overlapping output regions in `mx_smem`:
   * **Buffer 0:** `SPAD_DEST_0 = 0` (occupies words $0$ to $4095$)
   * **Buffer 1:** `SPAD_DEST_1 = 256` (occupies words $4096$ to $8191$)

2. **Pipeline Loop Execution:**
   Instead of immediately reading the results of iteration $t$ and fencing before proceeding to iteration $t+1$, we will:
   * Launch the compute for the current iteration $t$ using the active `SPAD_DEST` buffer.
   * Asynchronously trigger `gemmini_mx_read_smem` to drain the results of the *previous* iteration $t-1$ from the alternate buffer.
   * Call `gemmini_fence()` to allow the current compute and the previous transfer to execute concurrently.
   * Swap buffers for the next iteration.

3. **Epilogue:**
