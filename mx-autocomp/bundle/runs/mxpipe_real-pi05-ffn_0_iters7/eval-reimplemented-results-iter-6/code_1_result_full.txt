1. **Extremely High Loop Overhead & Redundant Loading:** The original code tiles the $64 \times 64 \times 64$ matrix into small blocks (`BLK=32` or similar) and loops over them. 2. **Underutilized Memories:** The scratchpad and accumulator are largely empty. For a $64 \times 64 \times 64$ problem size, the entire input and output matrices can fit simultaneously in the hardware memories:

   * **Accumulator:** The entire output $C$ ($4 \times 4$ tiles) consumes exactly $256$ rows of the $256$ available accumulator rows ($100\%$ utilization).
3. **Redundant `gemmini_flush` Calls:** Calling `gemmini_flush` in the inner loop destroys performance by invalidating state and stalling execution pipelines.

1. **Collapse Outer Loops:** Eliminate the nested block loops (`i0`, `j0`) and compute the entire $64 \times 64 \times 64$ matrix multiplication in a single unified `gemmini_loop_ws_spad` sweep.
