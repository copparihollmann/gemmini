## Analysis of the Current Code

Looking at the current solution, I need to identify the key inefficiency:

```c
// Configure port 0 (A tiles via mvin) and port 1 (B tiles via mvin2) independently
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0);
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);
```

Both ports are configured with stride `MATMUL_K * sizeof(elem_t)`. This is correct for **A** tiles (since A_in has row stride `MATMUL_K`), but it's **wrong for B tiles**.

Looking at the mvin loop:
```c
gemmini_extended_mvin2(
  (void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
  b_base + (j * tiles_K + k) * DIM,
  DIM, DIM);
```

B is indexed as `j * DIM * MATMUL_K + k * DIM`, meaning B_in has **MATMUL_K** as the column count (leading dimension). So B's DRAM row stride is also `MATMUL_K * sizeof(elem_t)`.

Wait — let me re-examine. The canonical reference (`matmul_tiled_fp8_64x64.c`) also uses `MATMUL_M` as the stride for both, but that file uses `MATMUL_M` (not `MATMUL_K`). The key insight from **strategy 11**: the stride must match the actual DRAM leading dimension of each matrix.

In the baseline (`autocomp_baseline_sol0.c`), the config uses `MATMUL_M * sizeof(elem_t)` for both A and B. In the current code, `MATMUL_K * sizeof(elem_t)` is used for both. The B matrix indexing `j * DIM * MATMUL_K + k * DIM` confirms B's leading dimension is `MATMUL_K`, so port 1's stride should be `MATMUL_K * sizeof(elem_t)` — which matches. So both strides appear consistent with the data layout used.

Now re-examining **strategy 10**: setting `b_spad_id=1` signals to the hardware loop that B tiles are reused across the I-dimension, allowing it to skip redundant B-tile preloads. Currently `b_spad_id=0` is used, which means no reuse hint is given.

## Selected Strategy: Strategy 10

**Set `b_spad_id=1` in `gemmini_loop_ws_spad`** to signal weight-stationary B-tile reuse across all I-dimension iterations.

In a weight-stationary matmul, the B tiles are the same for every `i` iteration — only the A tiles change. With `b_spad_id=0`, the hardware loop re-preloads B tiles for every (i, j, k) combination. Setting `b_spad_id=1` tells the hardware loop controller that B is already in scratchpad and can be reused, skipping redundant B preload cycles across the I dimension and reducing systolic array stall cycles.

## Plan

Change the `gemmini_loop_ws_spad` call from:
```c
gemmini_loop_ws_spad(..., 0, 0, false, 0x38);
//                        ^  ^
//                   a_spad_id=0, b_spad_id=0
```
to:
```c
gemmini_loop_ws_spad(..., 0, 1, false, 0x38);
//                        ^  ^
//                   a_spad_id=0, b_spad_id=1
```

This single change signals to the fused hardware loop that the B (weight) tiles already loaded into scratchpad at `b_base` are **stationary** and should be reused across all `tiles_I` iterations without re-preloading, eliminating the redundant B-tile preload stalls.

## Rewritten Code

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // Configure port 0 (A tiles via mvin) and port 1 (B tiles via mvin2) independently
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0);
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);

  // Interleave A (mvin, port 0) and B (mvin2, port 1) loads per k-slice
  // so both DMA engines run concurrently, hiding transfer latency
  for (int k = 0; k < tiles_K; k++) {
    for (int i = 0; i < tiles_I; i++)
      gemmini_extended_mvin(
        (void*)(((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM),
        a_base + (i * tiles_K + k) * DIM,
        DIM, DIM);
    for (int j = 0; j < tiles_J; j++)
      gemmini_extended_mvin2(
        (void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
        b_base + (j * tiles_K + k) * DIM,
        DIM, DIM);
  }

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 1, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```

The only change is `b_spad_id` from `0` to `1` in the `gemmini_loop_ws_spad` call, telling the hardware that B tiles are stationary in scratchpad and should be reused across I-dimension iterations without redundant preloads.
