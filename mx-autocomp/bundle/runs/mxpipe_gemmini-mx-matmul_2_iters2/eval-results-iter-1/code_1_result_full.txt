## Plan

### What to change

In the single call:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```

Change the last argument from `1` to `tiles_K` (or equivalently the maximum of `tiles_I`, `tiles_J`, `tiles_K`).

### Why this is safe

- `uselut=0` means the hardware never consults the LUT banks during requantization; the `lut_update_granularity` field only controls how often the hardware re-reads LUT entries between output tiles
- Since the LUT is never read for fp8→BF16 requantization, there is no correctness risk in setting G to the largest sensible value
- Setting `lut_update_granularity = tiles_K` means the requantizer performs the LUT refresh step at most once per K-dimension sweep instead of once per output tile, reducing the requantizer's internal synchronization/refresh overhead proportionally

### Concrete change

Replace:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```
with:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_K);
```

This is a one-line change. No loop restructuring, no memory layout changes, and no ordering violations — all other steps remain in the same sequence. The output is bit-exact BF16 since the LUT path is disabled entirely.
