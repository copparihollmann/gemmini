- Port 1: `gemmini_extended_mvin2` (used by `k_MVIN2`)
- Port 2: `gemmini_extended_mvin3` (used by `k_MVIN3`)

Each port has its own configuration register, set independently via `gemmini_extended3_config_ld` with the `id` parameter (0, 1, 2).

**Concrete changes:**

1. Configure port 0 (id=0) with the A stride (`MATMUL_K * sizeof(elem_t)`) using `gemmini_extended3_config_ld(stride, MVIN_SCALE_IDENTITY, false, 0)`.
2. Configure port 1 (id=1) with the B stride (`MATMUL_K * sizeof(elem_t)`) using `gemmini_extended3_config_ld(stride, MVIN_SCALE_IDENTITY, false, 1)`.
3. **Interleave** A and B mvin calls: issue an A tile mvin via `gemmini_extended_mvin` immediately followed by a B tile mvin via `gemmini_extended_mvin2`. Since these target different ports with independent command queues, the hardware can overlap their DMA transfers.
4. With `tiles_I=2, tiles_J=2, tiles_K=2`, completely unroll the interleaved sequence into 4 pairs of `(mvin, mvin2)` calls (strategy 5 naturally applies here too, but we focus on the port interleaving).

The loop body pairs each A tile with a B tile in the same instruction window:
```
mvin(A[i][k], a_spad)   // port 0
mvin2(B[j][k], b_spad)  // port 1 — can proceed concurrently
```

The B mvin loop currently uses `gemmini_extended_mvin` with the same port 0 config, which requires re-configuring the stride between loops. By using port 1 for B, both strides can be configured once upfront, and both ports fire simultaneously rather than waiting for port 0 to drain before B transfers begin. This halves the effective DMA latency for loading tiles.

The rest of the kernel (config_ex, load_scales, mxquant_config_mvout, loop_ws_spad, mx_read_smem, fence) remains unchanged and in the correct order.
