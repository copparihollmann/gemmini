## Analysis of the Original Code

The original code uses a single `gemmini_config_ld` call with stride `MATMUL_K * sizeof(elem_t)` for **both** A and B tile loads. Looking at the MVIN calls:

**A tiles** (row-major, stride should be `MATMUL_K * sizeof(elem_t)` = K bytes per row):
```c
gemmini_config_ld(MATMUL_K * sizeof(elem_t));
// A pointer arithmetic: ((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM  ✓
```

**B tiles** use the same stride setting. But B is stored with its own layout. Looking at the reference `matmul_fp8_64x64.c`, B stride should be `MATMUL_M * sizeof(elem_t)` (or `MATMUL_N * sizeof(elem_t)` depending on layout). The key issue: **A and B have different row strides**, so they need separate `gemmini_config_ld` calls.

## Selected Strategy: #13 — Use `gemmini_extended_mvin2` for B-tile loads

**Strategy 13** directly addresses an inefficiency: both A and B tiles are loaded using `gemmini_extended_mvin` (the same DMA port), serializing the transfers. By using `gemmini_extended_mvin2` for B tiles and `gemmini_extended_mvin` for A tiles, the two independent DMA ports can overlap A and B data movement.

## Plan

1. **Keep A-tile loads on port 1 (`gemmini_extended_mvin`)** with `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` (stride = K bytes, correct for A's row-major layout).

2. **Switch B-tile loads to port 2 (`gemmini_extended_mvin2`)**, preceded by a separate `gemmini_extended3_config_ld` call (or `gemmini_config_ld` with id=1 via `gemmini_extended3_config_ld(..., id=1)`) to set the correct stride for B. Looking at the reference `matmul_fp8_64x64.c`, B pointer arithmetic is `((elem_t*)B_in) + j * DIM * MATMUL_M + k * DIM`, so B's row stride is `MATMUL_M * sizeof(elem_t)`.

3. **Issue all A mvins first** (port 1), then all B mvins (port 2). Since the two ports are independent, the hardware can pipeline these transfers, overlapping the B DMA with any stall on port 1, and vice versa. This reduces the effective mvin latency for the combined A+B load phase.

4. **Use `gemmini_extended3_config_ld` with the `id` parameter** to configure port 2's stride independently from port 1. Specifically:
   - Port 0 (mvin): `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0)` — sets stride for A
   - Port 1 (mvin2): `gemmini_extended3_config_ld(MATMUL_M * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1)` — sets stride for B

5. **No changes** to the scale loading, `gemmini_mxquant_config_mvout`, `gemmini_loop_ws_spad`, `gemmini_mx_read_smem`, or `gemmini_fence` — only the mvin dispatch is changed.

The resulting structure will be:
```
gemmini_extended3_config_ex(...)
gemmini_mx_load_scales(A, 0)
gemmini_mx_load_scales(B, 1)
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), ..., id=0)  // A stride on port 0
gemmini_extended_mvin(A[0,0], spad_A[0,0], DIM, DIM)               // port 0
gemmini_extended_mvin(A[0,1], spad_A[0,1], DIM, DIM)
gemmini_extended_mvin(A[1,0], spad_A[1,0], DIM, DIM)
gemmini_extended_mvin(A[1,1], spad_A[1,1], DIM, DIM)
gemmini_extended3_config_ld(MATMUL_M * sizeof(elem_t), ..., id=1)  // B stride on port 1
gemmini_extended_mvin2(B[0,0], spad_B[0,0], DIM, DIM)              // port 1
gemmini_extended_mvin2(B[0,1], spad_B[0,1], DIM, DIM)
gemmini_extended_mvin2(B[1,0], spad_B[1,0], DIM, DIM)
gemmini_extended_mvin2(B[1,1], spad_B[1,1], DIM, DIM)
gemmini_config_st(...)
gemmini_mxquant_config_mvout(...)
gemmini_loop_ws_spad(...)
gemmini_mx_read_smem(...)
gemmini_fence()
```

The hardware will schedule both port 0 (A loads) and port 1 (B loads) concurrently once the B config and mvin2 instructions are issued, overlapping the memory transfers and reducing total mvin wall time.
