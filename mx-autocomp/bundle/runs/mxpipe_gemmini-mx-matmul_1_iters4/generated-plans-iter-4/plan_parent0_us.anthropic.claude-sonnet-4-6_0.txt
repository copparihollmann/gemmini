## Analysis of the Original Code

The original code loads all A tiles, then all B tiles sequentially before compute begins:

```c
// All A tiles loaded first
for (int i = 0; i < tiles_I; i++)
    gemmini_block_mvin(A_tile, a_base + i * tiles_K * DIM, tiles_K);

// Then all B tiles loaded
for (int j = 0; j < tiles_J; j++)
    gemmini_block_mvin(B_tile, b_base + j * tiles_K * DIM, tiles_K);
```

Both loops use `gemmini_block_mvin` (the default mvin port 0), meaning A and B DMA transfers are fully serialized. The hardware has two independent mvin ports (port 0 via `gemmini_extended_mvin`, port 1 via `gemmini_extended_mvin2`) which can operate concurrently.

## Selected Strategy: #6 — Interleave A and B mvin commands using separate mvin (port 0) and mvin2 (port 1) calls within the same loop to overlap A and B DMA transfers in hardware

## Plan

The key insight is that A tiles and B tiles are independent data — loading them on separate DMA ports allows the hardware to transfer both simultaneously, roughly halving the total DMA time for loading.

**Changes required:**

1. **Merge the two separate loops into a single loop** that issues one A-tile mvin (port 0) and one B-tile mvin (port 1) per iteration. Since `tiles_I = tiles_J` for square matrices, iterate over `max(tiles_I, tiles_J)` and guard each side. For this 64×64 problem, `tiles_I = tiles_J = tiles_K = 4`, so a single unified loop works cleanly.

2. **Replace `gemmini_block_mvin` with explicit `gemmini_extended_mvin` (port 0) for A** and **`gemmini_extended_mvin2` (port 1) for B**. Since `gemmini_block_mvin` loads `tiles_K` rows with width `tiles_K * DIM`, this is equivalent to a single mvin call with `cols = tiles_K * DIM, rows = DIM`.

3. **Keep the stride configuration correct**: A tiles are strided by `MATMUL_K * sizeof(elem_t)` bytes per row (one full row of A), B tiles by `MATMUL_K * sizeof(elem_t)` bytes per row. Both use the same stride `MATMUL_K`, so a single `gemmini_config_ld` call with `MATMUL_K * sizeof(elem_t)` covers both ports (CONFIG_LD applies to both mvin and mvin2).

4. **Scratchpad layout is unchanged**: A at `a_base + i * tiles_K * DIM`, B at `b_base + j * tiles_K * DIM` — these are the same offsets as before, ensuring correctness.

The rewritten loop becomes:

```c
gemmini_config_ld(MATMUL_K * sizeof(elem_t));
for (int ij = 0; ij < tiles_I; ij++) {
    // Port 0: A tile for row ij
    gemmini_extended_mvin(
        (void*)(((elem_t*)A_in) + ij * DIM * MATMUL_K),
        a_base + ij * tiles_K * DIM,
        tiles_K * DIM, DIM);
    // Port 1: B tile for col ij (overlaps with A DMA)
    gemmini_extended_mvin2(
        (void*)(((elem_t*)B_in) + ij * DIM * MATMUL_K),
        b_base + ij * tiles_K * DIM,
        tiles_K * DIM, DIM);
}
```

This replaces the original two sequential loops with one loop issuing paired mvin+mvin2 commands, allowing the DMA engine to overlap A and B transfers in hardware and reducing total data-movement latency before `gemmini_loop_ws_spad` can begin.
