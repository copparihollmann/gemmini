## Analysis

Looking at the original code, I can identify the key inefficiency related to strategy **#6**:

```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```

The `lut_update_granularity` is set to `1`, meaning the requantizer refreshes its output LUT after every single output tile. Since `uselut=0` in this kernel (no LUT is loaded), the requantizer still pays the overhead of LUT refresh logic on every tile boundary.

Looking at the problem:
- `tiles_I = MATMUL_M / 16`
- `tiles_J = MATMUL_N / 16`  
- `tiles_K = MATMUL_K / 16`

With `lut_update_granularity = 1`, the LUT refresh fires `tiles_I * tiles_J` times. Increasing this to `tiles_J` means it refreshes once per row of output tiles (amortized across all J tiles). Increasing it to `tiles_I * tiles_J` means it refreshes only once for the entire output, maximally amortizing the cost.

Since `uselut=0`, no LUT is actually used for dequantization, so increasing the granularity to the maximum (`tiles_I * tiles_J`) is safe — there's no LUT state that needs to be updated between tiles.

## Plan

**Apply Strategy #6: Increase `lut_update_granularity` from 1 to `tiles_I * tiles_J`.**

Change:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```
to:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_I * tiles_J);
```

This amortizes the requantizer LUT refresh overhead across the entire output tile batch rather than paying it once per tile. Since `uselut=0`, no correctness-relevant LUT state changes between tiles, making this safe.
