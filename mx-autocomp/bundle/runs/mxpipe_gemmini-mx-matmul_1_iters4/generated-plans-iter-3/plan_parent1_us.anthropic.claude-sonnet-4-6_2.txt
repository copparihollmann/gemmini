## Analysis of the Original Code

The original code loads A and B tiles using a **single mvin port** sequentially:

```c
// A tiles loaded via mvin (port 0)
for (int i = 0; i < tiles_I; i++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(...);  // port 0

// B tiles loaded via mvin (port 0) — sequential, after all A tiles
for (int j = 0; j < tiles_J; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(...);  // port 0
```

With tiles_I=2, tiles_J=2, tiles_K=2, this issues **8 mvin commands total** (4 for A, 4 for B), all serialized through port 0.

## Selected Strategy: Use `mvin2` Port to Parallelize A and B Loads

### Plan

The hardware exposes **three independent mvin ports**: `mvin` (port 0 / k_MVIN), `mvin2` (port 1 / k_MVIN2), and `mvin3` (port 2 / k_MVIN3). These ports can issue DMA transfers **concurrently** — loads issued to different ports overlap in hardware.

**Change:** Load all A tiles through `gemmini_extended_mvin` (port 0) and all B tiles through `gemmini_extended_mvin2` (port 1) **interleaved**, so both sets of transfers proceed in parallel rather than sequentially.

### Specific Changes

1. **Replace the two sequential loops** (first all A tiles, then all B tiles) with a **single interleaved sequence** that alternates `mvin` (for A) and `mvin2` (for B) calls, allowing the DMA controller to issue both streams simultaneously.

2. Since tiles_I=2, tiles_J=2, tiles_K=2 are statically known (strategy 4 is also applicable), fully **unroll** the 4+4 mvin calls into 8 straight-line instructions — 4 `gemmini_extended_mvin` calls interleaved with 4 `gemmini_extended_mvin2` calls — eliminating loop overhead and enabling the compiler/hardware to see all instructions at once.

3. A single `gemmini_config_ld` configures the stride for **both** ports (the stride register is shared), so no additional configuration instruction is needed.

4. All other steps (config_ex, load_scales, config_st, mxquant_config_mvout, loop_ws_spad, read_smem, fence) remain **unchanged** in order and semantics — only the mvin section changes.

### Why This Works

- Port 0 (mvin) and port 1 (mvin2) are independent DMA channels; they drain the DRAM→scratchpad path in parallel.
- By interleaving `mvin`/`mvin2` pairs (one A tile, one B tile per pair), both channels are kept busy simultaneously, roughly halving the effective data-movement latency for the tile-load phase.
- The scratchpad layout is unchanged: A at `a_base + (i*tiles_K+k)*DIM`, B at `b_base + (j*tiles_K+k)*DIM`, with `b_base = BANK_NUM*BANK_ROWS - tiles_K*tiles_J*DIM = 8192 - 8 = 8184`. No overlap between A (rows 0–7) and B (rows 8184–8191).
- The `gemmini_loop_ws_spad` call and all downstream operations are unaffected; the scratchpad contents are identical to the original after all mvins complete.
