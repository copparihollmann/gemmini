## Analysis of the Original Code

The original code for this 32×32×32 FP8 matmul has `tiles_I=2, tiles_J=2, tiles_K=2` — all tile counts are statically known small integers. The mvin loops:

```c
for (int i = 0; i < tiles_I; i++)      // 2 iterations
  for (int k = 0; k < tiles_K; k++)    // 2 iterations → 4 mvin calls for A
    gemmini_extended_mvin(...)

for (int j = 0; j < tiles_J; j++)      // 2 iterations
  for (int k = 0; k < tiles_K; k++)    // 2 iterations → 4 mvin calls for B
    gemmini_extended_mvin(...)
```

These loops have loop-control overhead (branch, increment, compare) for only 4 iterations each. More importantly, both loops use the same `gemmini_extended_mvin` (funct `k_MVIN`) port, serializing A and B loads through a single DMA channel when they could use separate ports (`k_MVIN` for A, `k_MVIN2` for B) to overlap loads.

## Selected Strategy: Strategy 8 — Full unroll + Strategy 1 (overlap) via separate mvin/mvin2 ports

**Strategy 8** is the most directly applicable: since all tile counts are statically known (tiles_I=2, tiles_J=2, tiles_K=2), we can fully unroll the mvin loops into straight-line code. This eliminates all loop overhead and, critically, enables **interleaving** A loads (`gemmini_extended_mvin`) and B loads (`gemmini_extended_mvin2`) to exploit the two independent DMA ports simultaneously — overlapping data movement for A and B tiles.

## Plan

1. **Remove the mvin loops entirely.** Replace the `for(i)for(k)` loop (4 A-tile mvins) and the `for(j)for(k)` loop (4 B-tile mvins) with 8 statically-computed, straight-line mvin calls.

2. **Use `gemmini_extended_mvin` for A tiles and `gemmini_extended_mvin2` for B tiles.** This is critical: mvin and mvin2 are independent DMA ports. By issuing them interleaved, the hardware can overlap the A-load and B-load DMA transfers, hiding memory latency.

3. **Interleave A and B tile loads.** Issue one A-tile mvin immediately followed by the corresponding B-tile mvin2, alternating through all 4 pairs. This maximizes overlap between the two DMA engines.

4. **Keep one `gemmini_config_ld` call** since both A and B use the same stride (`MATMUL_K * sizeof(elem_t)`). (A has row stride = K columns wide; B in this layout also uses the same stride value since `MATMUL_K == MATMUL_M == MATMUL_N == 32`.)

   Actually, re-checking: A stride is `MATMUL_K * sizeof(elem_t)` (K=32 bytes per row), and B stride is also `MATMUL_K * sizeof(elem_t)` (same layout). Both use the same stride, so one `gemmini_config_ld` suffices. If they differed we'd need `gemmini_extended3_config_ld(..., id=1)` for mvin2 — but here they match.

5. **All address arithmetic is compile-time constant** since DIM=16, tiles_I=2, tiles_J=2, tiles_K=2 are known. The compiler will fold everything to constants, eliminating all runtime address computation.

  gemmini_config_ld(MATMUL_K * sizeof(elem_t));

  // tiles_I=2, tiles_J=2, tiles_K=2: 4 A-tiles and 4 B-tiles, interleaved
  // to exploit independent DMA ports and overlap A/B transfers.

  // A tile (i=0,k=0) and B tile (j=0,k=0)

                         b_base + (0*tiles_K + 1)*DIM, DIM, DIM);

                         a_base + (1*tiles_K + 0)*DIM, DIM, DIM);
  gemmini_extended_mvin2((void*)(((elem_t*)B_in) + 1*DIM*MATMUL_K + 0*DIM),
                         b_base + (1*tiles_K + 0)*DIM, DIM, DIM);

  // A tile (i=1,k=1) and B tile (j=1,k=1)

  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
