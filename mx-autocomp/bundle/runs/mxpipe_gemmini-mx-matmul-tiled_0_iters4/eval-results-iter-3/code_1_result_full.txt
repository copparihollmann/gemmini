## Selected Strategy: #10 — Eliminate Intermediate CPU memcpy Staging Buffers

### Why This Strategy

The original code performs 4 `memcpy` calls per outer iteration: copying A rows, B rows, A scales, and B scales into staging buffers (`A_blk`, `B_blk`, `A_s`, `B_s`) before issuing DMA commands. This is a full extra data-copy round-trip through cache/DRAM. For a 256×256×512 matmul with BLK tiles, this is significant wasted memory bandwidth.

The DMA commands (`gemmini_extended_mvin`) and scale loads (`gemmini_mx_load_scales`) accept arbitrary DRAM addresses — they can be issued directly from the original arrays `A_in`, `B_in`, `A_scales_row`, `B_scales_col`.

### How to Apply the Change

**1. Eliminate `A_blk`, `B_blk`, `A_s`, `B_s` staging buffers entirely.**

**2. Issue `gemmini_extended_mvin` directly from `A_in` and `B_in`:**

Instead of:
```c
memcpy(&A_blk[r][0], &A_in[i0 * BLK + r][0], MATMUL_K);
// ... then mvin from A_blk
gemmini_extended_mvin((elem_t*)A_blk + i*DIM*MATMUL_K + k*DIM, ...)
```

Do:
```c
// mvin directly from A_in, which is row-major [MATMUL_M][MATMUL_K]
// Row i0*BLK + i*DIM, column k*DIM
gemmini_extended_mvin(&A_in[i0*BLK + i*DIM][k*DIM], a_base + (i*tiles_K + k)*DIM, DIM, DIM)
```

The stride configured via `gemmini_config_ld` must match the actual row stride of `A_in`, which is `MATMUL_K * sizeof(elem_t)`. This is the same stride as before (previously `MATMUL_K * sizeof(elem_t)` for `A_blk` since it was also `[BLK][MATMUL_K]`), so no stride reconfiguration is needed — `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` stays correct.

Similarly for B tiles, mvin directly from `&B_in[j0*BLK + j*DIM][k*DIM]`.

**3. Issue `gemmini_mx_load_scales` directly from `A_scales_row` and `B_scales_col`:**

`A_scales_row` has shape `[GK][MATMUL_M]` where `GK = MATMUL_K/32`. The original code copies `A_scales_row[g][i0*BLK .. i0*BLK+BLK-1]` into `A_s[g][0..BLK-1]` (a contiguous `[GK][BLK]` buffer) before loading. This is because the scale memory layout expected by `gemmini_mx_load_scales` requires the scales for the active block to be contiguous.

The key issue: `A_scales_row[g]` has stride `MATMUL_M` between groups, but the active slice `[g][i0*BLK]` is not contiguous across g. So we need to check whether the hardware expects contiguous layout.

Since `A_scales_row` is `[GK][MATMUL_M]`, the slice for block `i0` is scattered — `A_scales_row[g][i0*BLK]` for g=0..GK-1, with stride `MATMUL_M` between groups. The staging copy makes them contiguous in `A_s[GK][BLK]`. This staging copy **cannot be eliminated** for the scale arrays without changing the data layout, because the hardware DMA reads a contiguous byte range of `len = A_S_BYTES = GK*BLK` bytes.

Therefore: strategy #10 **fully applies to A_blk and B_blk** (the activation/weight tile copies), and **also applies to B_scales_col** if `B_scales_col` is laid out as `[GK][MATMUL_N]` with the j0 block being contiguous. For A_scales_row, if the j dimension (M) has the i0 block contiguous within each row, it still isn't contiguous across rows. The memcpy for scales cannot be removed without restructuring scale storage.

**Revised scope:** Eliminate the `A_blk` and `B_blk` memcpys (the dominant cost — `BLK * MATMUL_K` bytes each = 64×512 = 32KB per copy), while keeping the scale staging copies (much smaller: `GK * BLK = 16 * 64 = 1KB` per copy).
