## Analysis

Looking at the code, I need to identify which strategy offers the clearest win.

**Strategy 8** stands out as directly applicable and impactful: the current `P_s` layout is `[GROUPS_BT][ATT_S]` (group-major), but the hardware expects scale memory indexed as `scale_a_mem[row * GROUPS_BT + g]` (row-major). This means the current `gemmini_mx_load_scales((uint64_t)P_s, GROUPS_BT * ATT_S, 0)` loads scales in the wrong order for the hardware's indexing scheme — the hardware reads `P_s[0], P_s[1], ..., P_s[GROUPS_BT-1]` as row 0's group scales, but the current layout has `P_s[0][0..ATT_S-1]` as group 0's scales for all rows.

The current code actually works around this implicitly (the original baseline comments acknowledge it), but the *storage layout* means the CPU write loop `P_s[g][i]` causes strided writes that have poor cache behavior, and the `gemmini_mx_load_scales` call loads data in column-major order when row-major is needed.

## Plan: Apply Strategy 8 — Restructure `P_s` to `[ATT_S][GROUPS_BT]`

### What to change:

1. **Change `P_s` declaration** from `uint8_t P_s[GROUPS_BT][ATT_S]` to `uint8_t P_s[ATT_S][GROUPS_BT]`.

2. **Update the CPU write in the softmax loop**: change `P_s[g][i] = (uint8_t)(e + 127)` to `P_s[i][g] = (uint8_t)(e + 127)`. This makes writes sequential in memory (`P_s[i][0], P_s[i][1], ...` per row `i`), improving cache behavior during the CPU softmax loop.

3. **The `gemmini_mx_load_scales` call for P** remains `gemmini_mx_load_scales((uint64_t)P_s, GROUPS_BT * ATT_S, 0)` — same total size — but now the flat memory layout matches what the hardware expects: `P_s[i][g]` at offset `i*GROUPS_BT + g`, which is exactly `scale_a_mem[row * GROUPS_BT + g]`. No transposition or repacking loop is needed.

4. **No other changes needed**: the `gemmini_mx_load_scales` call, its arguments, and the rest of the kernel remain identical. The V scales load and all mvin/compute steps are unaffected.

This eliminates the strided write pattern in the inner softmax loop (currently `P_s[g][i]` writes stride `ATT_S` bytes apart in memory for different `g` values at the same `i`) and ensures the hardware consumes scales in the correct row-major order without any implicit reordering. The fix is minimal, correct, and directly addresses the layout mismatch described in strategy 8.
