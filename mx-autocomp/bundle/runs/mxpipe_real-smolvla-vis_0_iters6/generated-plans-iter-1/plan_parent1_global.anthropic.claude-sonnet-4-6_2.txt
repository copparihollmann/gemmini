## Analysis

Looking at the code, I need to identify which single strategy will have the most impact.

### Evaluating Strategy 4: Reorder outer loop to `j0` outermost, `i0` innermost

**Current structure:**
```
for i0:
  for j0:
    load A scales (for this i0 block)
    load B scales (for this j0 block)
    mvin A tiles (depends on i0)
    mvin B tiles (depends on j0)
    compute
    readout
```

In this structure, for each `(i0, j0)` pair, we reload B tiles from DRAM. B tiles only depend on `j0`, not `i0`. So B tiles are reloaded `BLOCKS_M` times unnecessarily per j0.

**With j0 outermost:**
```
for j0:
  load B scales (once per j0)
  mvin B tiles (once per j0)
  for i0:
    load A scales (per i0)
    mvin A tiles (per i0)
    compute
    readout
```

B tiles only move from DRAM to scratchpad once per j0, and are reused across all i0 iterations. This directly eliminates `(BLOCKS_M - 1) * BLOCKS_N` B mvin operations.

**Scratchpad feasibility check:** The current code already holds all A and B tiles for one (i0, j0) block simultaneously (tiles=BLK/DIM, tiles_K=K/DIM), so the scratchpad constraints are unchanged — B tiles stay loaded at `b_base` while we iterate over i0. The B scale factors also remain valid across i0 iterations since they depend only on j0.

## Plan

1. **Swap the loop order**: Make `j0` the outer loop and `i0` the inner loop.

2. **Move B-side operations outside the i0 loop**: The following are j0-dependent only and should execute once per j0:
   - `memcpy` of `B_s` scale staging
   - `gemmini_mx_load_scales` for B (sel=1)
   - `gemmini_config_ld` with B stride and the B mvin loop
   - `b_base` computation (since `tiles` and `tiles_K` are loop-invariant)

3. **Keep A-side operations inside i0**: The following remain per-(i0,j0):
   - `memcpy` of `A_s` scale staging
   - `gemmini_mx_load_scales` for A (sel=0)
   - A mvin loop
   - `gemmini_mxquant_config_mvout` (scale_factors pointer may vary with i0/j0 — keep inside)
   - `gemmini_loop_ws_spad`
   - `gemmini_mx_read_smem` + `gemmini_fence`

4. **Preserve programming model ordering**: For each i0 iteration inside j0, the sequence must still be: `config_ex` → load A scales → (B scales already loaded and valid) → mvin A → mvin B (already in spad, skip) → `mxquant_config_mvout` → `loop_ws_spad` → `read_smem` → `fence`. Since B scales were loaded before entering the i0 loop and the hardware retains them, the ordering constraint is satisfied.

5. **Issue `gemmini_flush` and `gemmini_extended3_config_ex` once** before the j0 loop since format fields are invariant across all tiles.

6. **Keep `gemmini_config_st` and `gemmini_mxquant_config_mvout` inside i0** because `scale_factors` and `pad_i` depend on i0, and the programming model requires them before each `loop_ws_spad`.
