# Optimization Plan: Hoist `gemmini_extended3_config_ex` Outside All Loops

## Strategy Selected
**Strategy 2: Hoist `gemmini_extended3_config_ex` outside all loops when MX format is invariant**

## Analysis of the Current Code

In the current code, `gemmini_extended3_config_ex` is called **inside the double loop** over `i0` (BLOCKS_M iterations) and `j0` (BLOCKS_N iterations):

```c
for (int i0 = 0; i0 < BLOCKS_M; i0++)
  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    // ...
    gemmini_flush(0);
    gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                                1, 1, 0, 0, false, 0, 0, 3, 0);
    // ...
  }
```

The MX format configuration (`WEIGHT_STATIONARY`, `act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`) **never changes** between iterations. Every call to `gemmini_extended3_config_ex` re-programs the same hardware state, wasting RoCC instruction issue cycles on every outer tile iteration.

Similarly, `gemmini_flush(0)` is called on every iteration. The flush is needed once at startup to reset hardware state, but re-flushing on every tile block is unnecessary overhead since the hardware configuration is preserved and no stale state needs clearing between tiles that use the same format.

## Proposed Change

1. **Move `gemmini_flush(0)` to before the loop nest** — it only needs to run once to initialize the accelerator.

2. **Move `gemmini_extended3_config_ex(...)` to before the loop nest** — since the format fields (`WEIGHT_STATIONARY`, `act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`), strides, and transposes are identical on every iteration, issuing this configuration once is sufficient. Per rule 6, this config must still precede all scale loads, mvins, and compute — which it will, since it runs before the loop.

The loop body then only issues the operations that genuinely vary per tile block: scale loads (since A/B scales differ per block), mvins, the compute loop, and the readout.

## Concrete Code Change

```c
// BEFORE the outer loops:
gemmini_flush(0);
gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                             1, 1, 0, 0, false, 0, 0, 3, 0);

for (int i0 = 0; i0 < BLOCKS_M; i0++) {
  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    // Remove gemmini_flush(0) and gemmini_extended3_config_ex from here
    // ... rest of loop body unchanged ...
  }
}
```

## Why This Is Correct

- The programming model sequence (rule 6) requires `gemmini_extended3_config_ex` to precede scale loads and compute — hoisting it before the loop still satisfies this ordering for every iteration.
- The format fields are **invariant** across all `(i0, j0)` tile blocks (same FP8 E4M3 input, same BF16 output, same weight-stationary dataflow), so no correctness is lost.
- Scale factors are still loaded fresh inside each iteration (correct per rule 15), since they differ per tile block.
- `gemmini_fence()` and `gemmini_mx_read_smem` remain inside the loop body, unchanged.

## Expected Benefit

With `BLOCKS_M × BLOCKS_N` outer iterations, this removes `BLOCKS_M × BLOCKS_N` redundant `gemmini_flush` + `gemmini_extended3_config_ex` instruction pairs from the critical path, reducing RoCC command overhead proportional to the number of tile blocks, directly lowering total latency.
