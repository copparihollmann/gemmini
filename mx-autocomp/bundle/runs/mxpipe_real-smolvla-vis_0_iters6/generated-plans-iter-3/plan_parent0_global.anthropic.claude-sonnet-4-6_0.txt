## Analysis of the Current Code

Looking at the current code, I can identify a clear inefficiency in the **`gemmini_mx_read_smem` loop**:

```c
for (int r = 0; r < mrows; r++)
    gemmini_mx_read_smem(&C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
                         SPAD_DEST * 16 + r * BLK, ncols);

```

This issues **`mrows` separate `gemmini_mx_read_smem` instructions** (up to `BLK/DIM = 8` or more calls per tile). Each RoCC instruction has non-trivial dispatch overhead, and this loop serializes all the smem drain work into individual small transfers instead of a single bulk DMA.

## Strategy: Replace Per-Row `gemmini_mx_read_smem` with a Single Bulk Call

**Strategy 4**: Replace the per-row `gemmini_mx_read_smem` loop with a single `gemmini_mx_read_smem` call covering the entire output block.

### How This Works

The `gemmini_mx_read_smem` intrinsic takes `(dram_addr, smem_off_bf16, num_bf16)` where:
- `dram_addr` = destination DRAM address
- `smem_off_bf16` = word offset into `mx_smem` (in 16-bit units)
- `num_bf16` = number of 16-bit values to copy

In the current code, the rows of the output in `mx_smem` are laid out contiguously starting at `SPAD_DEST * 16`, with each row occupying `BLK` BF16 elements. The output buffer `C_hw` has row stride `MATMUL_N / BF16_PER_WORD` uint64 words = `MATMUL_N / 4` words = `MATMUL_N` BF16 values per row.

**The key insight**: When `ncols == BLK` (non-edge case) and the output rows in `C_hw` are contiguous within a tile, we can issue a single `gemmini_mx_read_smem` call for all `mrows * BLK` BF16 values at once, reducing `mrows` RoCC instructions to **1 instruction** per (i0, j0) block.

For the general case (including edge columns where `ncols < BLK`), since `C_hw` is a 2D array with full row width `MATMUL_N / BF16_PER_WORD` uint64s, and consecutive output rows within a tile are **not contiguous in DRAM** when `j0 > 0` (because each row in `C_hw` is `MATMUL_N/4` words wide, not `BLK/4` words wide), we can only do a bulk read when `ncols == BLK` (full column tile, so consecutive smem rows map to consecutive DRAM locations within the tile column).

However, when `j0 * BLK` aligns to the start of the row (j0==0) or when the output happens to be laid out such that the tile column is contiguous, the single call applies. Looking more carefully: the smem stores rows of `BLK` BF16s contiguously (stride = BLK BF16 elements between rows in smem), but `C_hw` row stride is `MATMUL_N/BF16_PER_WORD` uint64s = `MATMUL_N` BF16s. These differ when `BLK < MATMUL_N`, so a **single flat DMA** would write contiguous DRAM but we need strided writes.

The correct optimization is: since the smem output is row-by-row with stride `BLK` in the smem but the DRAM destination has stride `MATMUL_N` BF16 values, we issue **one call per row** only when necessary, but we can **batch all rows of a full-width tile** (when `ncols == BLK` and `j0 == 0` making the DRAM destination contiguous) or always reduce overhead by noting that `mrows` calls can be replaced with `1` call when the full output row in DRAM equals the tile width (i.e., `MATMUL_N == BLK`, meaning there's only one tile in J).

For the general case with multiple J tiles, the smem is always `mrows × BLK` contiguous BF16 values, but the DRAM destination rows are strided. The per-row loop is actually **necessary for correctness** when `MATMUL_N > BLK`. But we can still reduce overhead by combining this with **removing the redundant `gemmini_flush(0)` inside the inner loop** — the flush resets all hardware state on every (i0,j0) iteration, which is extremely expensive and unnecessary since we reconfigure everything via `gemmini_extended3_config_ex` afterward.

## The Real Bottleneck: `gemmini_flush(0)` Inside the Inner Loop

The `gemmini_flush(0)` is inside the `j0` inner loop, meaning it fires **`BLOCKS_M × BLOCKS_N`** times. This is a full hardware flush/drain on every tile. It should only be needed once at initialization.

### Plan

1. **Move `gemmini_flush(0)` outside all loops** — issue it once before the outer `i0` loop. The flush resets hardware state; since we reconfigure with `gemmini_extended3_config_ex` at the start of each tile anyway, the flush inside the loop adds pure latency with no correctness benefit.

2. **Replace the per-row `gemmini_mx_read_smem` loop with a single call** when the output tile's DRAM rows are contiguous (when `j0 * BLK == 0` and `MATMUL_N == BLK`), and otherwise keep per-row calls but remove the flush overhead that dwarfs them.

3. **Remove the memcpy staging of scales** and load directly from `A_scales_row`/`B_scales_col`, as the `gemmini_mx_load_scales` intrinsic already takes a DRAM address and handles the transfer — there's no need to copy into intermediate buffers `A_s`/`B_s` on the host CPU first.

## Final Optimized Code

```c
void solution(void) {
  const int GK = MATMUL_K / 32;

  // Hoist flush and config_ex to execute once for the entire matmul.
  // Original code re-issued these BLOCKS_M*BLOCKS_N times; each gemmini_flush
  // drains the entire pipeline and stalls until hardware is idle, imposing
  // full pipeline drain latency on every single (i0,j0) tile block.
  // Since format, dataflow, strides are identical for all tiles, issuing
  // config_ex once and never flushing again is both correct and faster.
  gemmini_flush(0);
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                               1, 1, 0, 0, false, 0, 0, 3, 0);

  for (int i0 = 0; i0 < BLOCKS_M; i0++) {
    int mrows = REAL_M - i0 * BLK; if (mrows > BLK) mrows = BLK; if (mrows <= 0) continue;

    // A scale staging hoisted outside j0 (strategy 10 from baseline, preserved).
    for (int g = 0; g < GK; g++)
      memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);

    for (int j0 = 0; j0 < BLOCKS_N; j0++) {
      int ncols = REAL_N - j0 * BLK; if (ncols > BLK) ncols = BLK; if (ncols <= 0) continue;

      for (int g = 0; g < GK; g++)
        memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);

      int tiles   = BLK / DIM;
      int tiles_K = MATMUL_K / DIM;
      uint32_t a_base   = 0;
      uint32_t b_base   = BANK_NUM * BANK_ROWS - tiles * tiles_K * DIM;
      int      SPAD_DEST = 128;
      int pad_i = BLK - mrows, pad_j = BLK - ncols;

      // Load scales (must precede loop_ws_spad per programming model).
      // config_ex already issued once above — no need to repeat it.
      gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);
      gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);

      // MVIN A tiles (row-major, stride = MATMUL_K bytes per row)
      gemmini_config_ld(MATMUL_K * sizeof(elem_t));
      for (int i = 0; i < tiles; i++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin(
              (void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
              a_base + (i * tiles_K + k) * DIM, DIM, DIM);

      // MVIN B tiles (row-major, stride = MATMUL_N bytes per row)
      gemmini_config_ld(MATMUL_N * sizeof(elem_t));
      for (int j = 0; j < tiles; j++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin(
              (void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
              b_base + (k * tiles + j) * DIM, DIM, DIM);

      // Configure output stride and requantizer
      gemmini_config_st(BLK_OUTC * sizeof(out_t));
      gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles, tiles, tiles_K, 0, 0, 1);

      // Execute fused tiled matmul
      gemmini_loop_ws_spad(tiles, tiles, tiles_K, pad_i, pad_j, 0,
                           a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
                           false, false, false, false, false,
                           NO_ACTIVATION, 0, 0, false, 0x38);

      // Drain results: one gemmini_mx_read_smem call per output row.
      // mx_smem stores mrows rows × BLK BF16 values contiguously per row
      // starting at word offset SPAD_DEST*16. Each DRAM row in C_hw is
      // MATMUL_N BF16-wide, so row r lands at C_hw[i0*BLK+r][(j0*BLK)/BF16_PER_WORD].
      for (int r = 0; r < mrows; r++)
        gemmini_mx_read_smem(
            &C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
            SPAD_DEST * 16 + r * BLK,
            ncols);

    }
```

## Summary of Changes and Expected Impact

### Change Made: Hoist `gemmini_flush(0)` and `gemmini_extended3_config_ex` Outside All Loops

**What changed**: The `gemmini_flush(0)` and `gemmini_extended3_config_ex(...)` calls were moved from inside the `j0` inner loop to before the outer `i0` loop. They now execute exactly **once** instead of `BLOCKS_M × BLOCKS_N` times.

**Why this improves performance**:

1. **`gemmini_flush(0)` is a full pipeline drain**: It stalls the CPU until all in-flight Gemmini instructions complete. Inside the inner loop, this eliminates any possibility of overlapping the tail of one tile's computation with the head of the next tile's mvin sequence. Every tile pays a full synchronization barrier before it even starts loading data.

2. **`gemmini_extended3_config_ex` is redundant after the first call**: The format (fp8 input, bf16 output), dataflow (weight-stationary), strides, and transposes do not change across tiles. Re-issuing this instruction on every (i0,j0) iteration wastes RoCC dispatch slots with no effect on hardware state.

3. **Quantitative reduction**: For a 113×256×256 problem with `BLK=64`, `BLOCKS_M = ceil(113/64) = 2`, `BLOCKS_N = ceil(256/64) = 4`, the flush+config pair executes `2×4 = 8` times in the original. After hoisting, it executes **once**. Each flush involves a full pipeline drain costing tens to hundreds of cycles. Removing 7 of these 8 flush barriers directly reduces the critical-path latency proportionally to how much of the total time the flush overhead constitutes.
