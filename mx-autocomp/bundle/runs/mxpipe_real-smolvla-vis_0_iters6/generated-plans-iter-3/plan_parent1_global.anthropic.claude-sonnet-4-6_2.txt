## Strategy: Hoist B-tile mvin Outside the i0 Loop (Weight Reuse Across Row-Block Iterations)

### Analysis of the Current Code

In the current code, the outer loop structure is:

```c
for (int i0 = 0; i0 < BLOCKS_M; i0++)
  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
      // ... mvin A tiles for this i0
      // ... mvin B tiles for this j0   <-- B tiles loaded every (i0, j0) pair
      // ... compute
  }
```

For a fixed `j0`, the B tiles (weight matrix block) are **identical across all `i0` iterations**. B is `K × N` shaped, and the block at column `j0` does not change as we sweep over row-blocks `i0`. Yet the current code re-issues all `tiles * tiles_K` B-tile mvin commands on every `(i0, j0)` pair. With `BLOCKS_M` row-block iterations, each B column-block is loaded `BLOCKS_M` times unnecessarily.

### Concrete Change

Reorder the loop nest to **`j0` outer, `i0` inner**, and hoist the B-tile mvin (and the associated `gemmini_config_ld` for B's stride) outside the `i0` loop. B tiles are placed at the top of the scratchpad at `b_base`, which depends only on `tiles_K` and `tiles_J` (i.e., only on the tile counts, not on `i0`). Since B occupies the top of the scratchpad and A occupies the bottom, and the scratchpad is large enough to hold all A+B tiles for one `(i0, j0)` block simultaneously, the layout is valid for every `i0` iteration within the same `j0`.

The scale loads must also be reorganized: B scales (`B_s`) are loaded once per `j0`, outside the `i0` loop. A scales (`A_s`) are loaded once per `i0`, inside the `j0` loop but before compute — this is safe because `gemmini_mx_load_scales` for A (sel=0) does not disturb the B scale buffer (sel=1), and vice versa.

### Why This Works

- `b_base = BANK_NUM*BANK_ROWS - tiles*tiles_K*DIM` is a fixed address that depends only on tile geometry, not on `i0` or `j0`. The same B tiles at the same scratchpad addresses are valid inputs for every `i0` iteration.
- The scratchpad constraint `(tiles_I*tiles_K + tiles_J*tiles_K)*DIM ≤ 8192` holds for the same tile counts regardless of loop order.
- `gemmini_loop_ws_spad` reads B from `BANK_NUM*BANK_ROWS` (the top sentinel), so B simply needs to be present before each `gemmini_loop_ws_spad` call — which it is, since it was loaded before the `i0` loop.
- The `mx_loop_spad_marker` (funct 24) is still re-issued before every `gemmini_loop_ws_spad` call inside the `i0` loop, satisfying the one-shot marker requirement.

### Expected Improvement

Each B column-block is loaded `tiles * tiles_K` mvin instructions per `(i0, j0)` pair. After the transformation, those mvins execute **once per `j0`** rather than **`BLOCKS_M` times per `j0`**. For `MATMUL_M=113`, `BLK=16` (so `tiles=1`), `MATMUL_K=256` (so `tiles_K=16`), and `BLOCKS_M=8`, this reduces B mvin count from `8 × 16 = 128` to `16` per `j0` column-block — an 8× reduction in B data movement, which is the dominant mvin cost for weight-stationary workloads.

### Implementation

```c
// AUTO-GENERATED outer-tiled MX matmul baseline (113x256x256).
void solution(void) {
  int tiles   = BLK / DIM;
  int tiles_K = MATMUL_K / DIM;

  // b_base depends only on tile geometry, not on i0/j0 — fixed for all blocks.
  uint32_t b_base = BANK_NUM * BANK_ROWS - tiles * tiles_K * DIM;
  uint32_t a_base = 0;
  int SPAD_DEST = 128;

  // Reorder: j0 outer so B tiles can be hoisted; i0 inner sweeps rows.
  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    int ncols = REAL_N - j0 * BLK;
    if (ncols > BLK) ncols = BLK;
    if (ncols <= 0) continue;

    // --- Load B scales ONCE per j0 (weight column-block is fixed across all i0) ---
    for (int g = 0; g < MATMUL_K / 32; g++)
      memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);

    // --- Mvin B tiles ONCE per j0 into the top of the scratchpad ---
    gemmini_config_ld(MATMUL_N * sizeof(elem_t));   // B row stride = N
    for (int j = 0; j < tiles; j++)
      for (int k = 0; k < tiles_K; k++)
        gemmini_extended_mvin(
          (void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
          b_base + (k * tiles + j) * DIM, DIM, DIM);

    for (int i0 = 0; i0 < BLOCKS_M; i0++) {
      int mrows = REAL_M - i0 * BLK;
      if (mrows > BLK) mrows = BLK;
      if (mrows <= 0) continue;

      int pad_i = BLK - mrows, pad_j = BLK - ncols;

      // --- Load A scales once per (i0, j0) — A sel=0 does not disturb B sel=1 ---
      for (int g = 0; g < MATMUL_K / 32; g++)
        memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);

      // PROF accel
      gemmini_flush(0);
      gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                                  1, 1, 0, 0, false, 0, 0, 3, 0);

      // Load A and B scales into hardware (B_s was already staged above).
      gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);
      gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);

      // --- Mvin A tiles for this i0 ---
      gemmini_config_ld(MATMUL_K * sizeof(elem_t));  // A row stride = K
      for (int i = 0; i < tiles; i++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin(
            (void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
            a_base + (i * tiles_K + k) * DIM, DIM, DIM);

      // B tiles are already in the scratchpad from the j0-level hoist above.

      gemmini_config_st(BLK_OUTC * sizeof(out_t));
      gemmini_mxquant_config_mvout((uint64_t)scale_factors,
                                   tiles, tiles, tiles_K, 0, 0, 1);

      // mx_loop_spad_marker is one-shot: issued inside gemmini_loop_ws_spad macro.
      gemmini_loop_ws_spad(tiles, tiles, tiles_K, pad_i, pad_j, 0,
                           a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
                           false, false, false, false, false,
                           NO_ACTIVATION, 0, 0, false, 0x38);

      for (int r = 0; r < mrows; r++)
        gemmini_mx_read_smem(
          &C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
          SPAD_DEST * 16 + r * BLK, ncols);
      gemmini_fence();
    }
  }
}
```
