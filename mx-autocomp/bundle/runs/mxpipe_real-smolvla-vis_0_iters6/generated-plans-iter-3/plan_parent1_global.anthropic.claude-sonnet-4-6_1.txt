## Analysis of the Current Code

Looking at the current code, I can identify the key inefficiency relevant to the selected strategy:

**Current structure:**
```
for i0 ... for j0:
    gemmini_flush(0);
    gemmini_extended3_config_ex(...);   // ← re-issued every (i0, j0) iteration
    gemmini_mx_load_scales(...);
    mvin A tiles
    mvin B tiles
    gemmini_mxquant_config_mvout(...)
    gemmini_loop_ws_spad(...)
    gemmini_mx_read_smem(...)
    gemmini_fence();
```

**The problem:** `gemmini_extended3_config_ex` and `gemmini_flush(0)` are called inside the double loop over `(i0, j0)` blocks. The MX format fields (`WEIGHT_STATIONARY`, `act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`) **never change** across iterations — they are invariant for the entire computation. According to the architecture documentation, CONFIG_EX fields persist until changed, so re-issuing them every iteration is wasteful overhead. Similarly, `gemmini_flush(0)` resets accelerator state unnecessarily on every block.

## Plan: Hoist `gemmini_extended3_config_ex` (and `gemmini_flush`) Outside All Loops

**Strategy selected:** Strategy 2 — *Hoist `gemmini_extended3_config_ex` outside all loops when MX format is invariant.*

### Specific Changes

1. **Move `gemmini_flush(0)` to before the outer `i0` loop.** It only needs to be called once at initialization to clear stale accelerator state. Calling it per-block resets all persistent configuration unnecessarily.

2. **Move `gemmini_extended3_config_ex(...)` to immediately after the single `gemmini_flush(0)`, before the outer loop.** Since `WEIGHT_STATIONARY`, `act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0` are all constants throughout the function, this configuration is identical every iteration and does not need to be re-issued. The hardware retains it across iterations.

3. **Remove `gemmini_flush(0)` and `gemmini_extended3_config_ex(...)` from inside the loop body.** The loop body then starts directly with `gemmini_mx_load_scales(...)` (which must stay inside the loop since A_s/B_s change per block).

### Why This Is Safe

- The programming model sequence is preserved within each iteration: scales are loaded → mvin → mxquant_config → loop_ws_spad → read_smem → fence. The config_ex simply moves to a one-time setup before the first iteration.
- `gemmini_mx_load_scales` is still called per-iteration (inside the loop) because A_s/B_s are block-specific.
- No data hazard is introduced: config_ex fields are stateless from the perspective of per-block data, and the fence at the end of each iteration ensures the prior block fully completes before the next block's scales are loaded.
- The architecture explicitly states: *"CONFIG_EX, CONFIG_LD, and CONFIG_ST fields persist until changed; avoid redundant re-issue when format, stride, and scale are unchanged across consecutive tiles."*

### Pseudocode of the Change

```
// BEFORE outer loop:
gemmini_flush(0);
gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
    1, 1, 0, 0, false, 0, 0, 3, 0);

for i0 ... for j0:
    // gemmini_flush(0);              ← REMOVED
    // gemmini_extended3_config_ex    ← REMOVED
    gemmini_mx_load_scales(...A_s...);
    gemmini_mx_load_scales(...B_s...);
    mvin A tiles
    mvin B tiles
    gemmini_mxquant_config_mvout(...)
    gemmini_loop_ws_spad(...)
    gemmini_mx_read_smem(...)
    gemmini_fence();
```

This eliminates `BLOCKS_M * BLOCKS_N - 1` redundant flush+config_ex pairs, reducing instruction overhead proportionally to the number of outer blocks, with no impact on correctness.
