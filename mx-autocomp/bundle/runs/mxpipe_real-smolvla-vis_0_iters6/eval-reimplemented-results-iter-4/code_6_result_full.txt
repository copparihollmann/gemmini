## Concrete Plan

1. Move `j0` to the outer loop and `i0` to the inner loop.
2. Load B tiles for the current `j0` block **once** before the `i0` inner loop (including the scale factors for B).

4. This eliminates `BLOCKS_M - 1` redundant B mvin sequences and B scale loads per `j0` block.

- Load `A_s` (for the current `i0`) **inside** the `i0` loop — call `gemmini_mx_load_scales` for A each iteration (since A scale blocks change with `i0`).
- Per rule 6, both A and B scales must be loaded before `gemmini_loop_ws_spad`, so we must still issue both `gemmini_mx_load_scales` calls before each `loop_ws_spad`. However, the B scale data loaded at the start of the `j0` iteration is **already in `mx_scale_b_mem`** — we just need to avoid overwriting it. We can skip re-issuing B scale load each `i0` iteration by recognizing it persists in hardware state (per the architecture doc: "Scale factors persist in hardware state until overwritten").
- Therefore: issue B scale load once per `j0`, issue A scale load once per `i0`, both satisfy the ordering constraint.

**B tile mvin placement:**
- B tiles are placed at `b_base = BANK_NUM*BANK_ROWS - tiles_K*tiles_J*DIM` once per `j0` block.
- The mvin of B happens outside the `i0` loop.
- `gemmini_flush` is also moved outside the `i0` loop (issued once per `j0` block).
- `gemmini_extended3_config_ex` is moved outside the `i0` loop as well.

**A tile mvin and readout remain inside `i0` loop:**

- The memcpy of B scales is removed from the inner loop; memcpy of A scales remains.
