## Analysis

Looking at the original code, I can identify the key inefficiency targeted by **strategy 10**: the CPU-side `memcpy` loops that copy scale factors into intermediate `A_s`/`B_s` buffers:

```c
for (int g = 0; g < MATMUL_K / 32; g++) {
    memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);
    memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);
}
```

Then these buffers are passed to `gemmini_mx_load_scales`. The original `A_scales_row` and `B_scales_col` are laid out as `[GK][M]` and `[GK][N]` respectively. The needed subregion for a given `(i0, j0)` block is `A_scales_row[g][i0*BLK]` through `A_scales_row[g][i0*BLK + BLK - 1]` for each group `g`. Since the scales are stored row-major, these subregions are **not contiguous across groups** (they are strided), which is why the memcpy was introduced.

However, `gemmini_mx_load_scales` accepts a DRAM address and byte length, and the hardware/spike reads them sequentially. The staging is necessary only if the layout isn't contiguous. The memcpy exists precisely because of this non-contiguity.

## Plan: Strategy 10 — Replace memcpy scale staging with direct pointer

**The key insight**: Instead of copying the scale subregions into a contiguous buffer, we can pass `&A_scales_row[0][i0*BLK]` directly with the understanding that `gemmini_mx_load_scales` needs contiguous bytes of length `(MATMUL_K/32) * BLK`. Since `A_scales_row` is `[GK][M]` row-major, `&A_scales_row[g][i0*BLK]` for different `g` are spaced `M` bytes apart, not `BLK` bytes apart — so they are NOT contiguous when `BLK < M`.

**But wait** — examining more carefully: `A_scales_row` has shape `[GK][M]` where `M = REAL_M` (padded to `MATMUL_M`). If we pass `&A_scales_row[0][i0*BLK]`, we get `BLK` bytes, then the rest of row 0 (stride gap of `M - BLK`), then BLK bytes of row 1, etc. The spike simulator reads `len` bytes sequentially from the given address, so this would read the wrong bytes.

The correct approach is to **keep the staging buffer but avoid the memcpy by reshaping the load**: since `A_scales_row` is `[GK][MATMUL_M]` and within each group the BLK-wide column block starting at `i0*BLK` is already contiguous within that row, we can pass `&A_scales_row[0][i0*BLK]` with `len = A_S_BYTES` only if `A_scales_row` is laid out such that the relevant BLK columns of all GK groups happen to be contiguous. They aren't in general.

**Revised plan**: Transpose the scale factor layout at file scope so that `A_scales` is `[M][GK]` (row-major per-element, all K-groups for that element contiguous). Then `&A_scales_transposed[i0*BLK]` gives `BLK * GK` contiguous bytes covering all groups for the `i0` block. This requires a one-time transpose at initialization, but eliminates all per-tile memcpy overhead.

However, the golden header defines `A_scales_row` with a fixed layout. The simplest correct implementation of strategy 10 is: **allocate the staging buffers as flat arrays and observe that `A_scales_row[g]` has stride `MATMUL_M`, so `&A_scales_row[0][i0*BLK]` followed by `GK` iterations of stride `MATMUL_M` gives the needed data** — we replace the `memcpy` with a single reinterpretation by building a **column-contiguous** staging once outside the `j0` loop (reuse across `j0` since A scales don't depend on `j0`), and similarly for B scales outside the `i0` loop.

**Concrete change**:
- Hoist A scale staging outside the `j0` loop (it doesn't change with `j0`).
- Hoist B scale staging outside the `i0` loop (it doesn't change with `i0`).
- This reduces `memcpy` calls from `2 * BLOCKS_M * BLOCKS_N * GK` to `BLOCKS_M * GK + BLOCKS_N * GK` — a factor of `BLOCKS_N` and `BLOCKS_M` reduction respectively, directly proportional to the number of outer tiles.

This is the correct application of strategy 10 within the scope of reducing memcpy overhead without changing the fundamental tiling structure.
