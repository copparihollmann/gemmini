## Analysis of the Current Code

In the current implementation, `gemmini_extended3_config_ex` is called **inside the `i0 × j0` double loop**, once per block pair. For a 113×256×256 problem with `BLK=16` (tiles), this means it is re-issued on every iteration even though the MX format fields (`act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`), dataflow (`WEIGHT_STATIONARY`), strides (`A_stride=1`, `C_stride=1`), and all other config-EX fields are **completely invariant** across all iterations.

Additionally, `gemmini_flush(0)` is called inside every iteration, which resets all hardware state and forces every subsequent configuration step to re-initialize from scratch. This is unnecessary after the first iteration.

## Strategy: Hoist `gemmini_flush` and `gemmini_extended3_config_ex` Outside All Loops

### What to change

1. **Move `gemmini_flush(0)` before the `i0`/`j0` loop nest** — it only needs to be called once to initialize hardware state at the start of the kernel.

2. **Move `gemmini_extended3_config_ex(...)` before the `i0`/`j0` loop nest** — since `WEIGHT_STATIONARY`, `act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`, `A_stride=1`, `C_stride=1`, and all transpose/activation flags are constant across all `(i0, j0)` block iterations, this configuration instruction carries identical hardware state on every invocation and need only be issued once.

3. **Inside the loop, remove both calls** entirely, keeping only the data-dependent steps: `gemmini_mx_load_scales`, mvin loops, `gemmini_config_st`, `gemmini_mxquant_config_mvout`, `gemmini_loop_ws_spad`, `gemmini_mx_read_smem`, and `gemmini_fence`.

### Why this improves performance

Each `gemmini_flush(0)` + `gemmini_extended3_config_ex(...)` pair requires the hardware pipeline to drain (`flush` is a serializing operation that waits for all in-flight instructions to complete) and then re-issue a RoCC CONFIG_EX instruction. Issuing `gemmini_flush` inside the loop forces a full pipeline drain on every block iteration — this serializes the entire loop body and prevents any overlap between the tail of one block's `gemmini_mx_read_smem`/`gemmini_fence` and the setup of the next block. By hoisting both calls out:

- The pipeline drain happens exactly once at kernel entry.
- The CONFIG_EX instruction is issued exactly once; the hardware retains the format/dataflow state for all subsequent iterations without re-configuration overhead.
- The per-iteration critical path is shortened by at least two RoCC instruction round-trips plus the flush stall penalty.
