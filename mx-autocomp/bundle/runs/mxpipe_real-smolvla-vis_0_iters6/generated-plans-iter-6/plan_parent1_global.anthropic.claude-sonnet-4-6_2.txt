## Analysis

Looking at the original code, I can identify the key inefficiency related to **strategy 5: minimize `gemmini_fence` calls by deferring synchronization to after full tile batch completes**.

In the original code, `gemmini_fence()` is called **inside the inner loop** (per `i0` iteration):

```c
for (int j0 = 0; j0 < BLOCKS_N; j0++) {
  // ... B tiles loaded once ...
  for (int i0 = 0; i0 < BLOCKS_M; i0++) {
    // ... compute ...
    for (int r = 0; r < mrows; r++)
      gemmini_mx_read_smem(...);  // drain results
    gemmini_fence();  // <-- fence on EVERY i0 iteration
  }
}
```

This means for each `(j0, i0)` pair, the CPU stalls waiting for the DMA drain to complete before issuing the next iteration's instructions. This is a full pipeline stall per tile block.

## Plan: Defer `gemmini_fence()` to After the Full `i0` Loop

**Key observation:** The `gemmini_mx_read_smem` calls for iteration `i0` write to `C_hw[i0*BLK + r][...]`, which are distinct DRAM locations from all other iterations. There is no dependency between the output of one `(j0, i0)` pair and the inputs/outputs of the next `(j0, i0+1)` pair — `A_in`, `B_in`, `A_scales_row`, `B_scales_col` are read-only, and `C_hw` output rows are non-overlapping.

**The change:** Move `gemmini_fence()` to after the entire `i0` loop (still inside the `j0` loop). This allows all the `gemmini_mx_read_smem` DMA operations across all `i0` iterations to be issued back-to-back without stalling, letting the accelerator pipeline overlap the DMA drains with the setup for subsequent iterations.

**Why this is safe:** 
- Each `i0` iteration uses fresh A tiles (loaded from distinct DRAM regions) and the already-resident B tiles.
- The `gemmini_loop_ws_spad` for `i0+1` writes to `mx_smem` starting at `SPAD_DEST`, overwriting the previous result. However, the `gemmini_mx_read_smem` call for `i0` has already been **issued** (it's an asynchronous DMA command in the RoCC queue), so it will complete before the accelerator processes the next `gemmini_loop_ws_spad`. The RoCC instruction queue is ordered — commands execute in issue order — so the drain of `i0`'s results completes before `i0+1`'s compute writes new results into `mx_smem`.
- The single `gemmini_fence()` after the `i0` loop ensures all drains are visible to the host before any output is consumed.

**Concrete change:**
- Remove `gemmini_fence()` from inside the `i0` loop body.
- Place a single `gemmini_fence()` after the closing brace of the `i0` loop (but still inside the `j0` loop, since each `j0` iteration independently fills `mx_smem` and drains it).

This reduces the number of fence stalls from `BLOCKS_M * BLOCKS_N` to `BLOCKS_N`, eliminating pipeline bubbles on every inner-loop iteration.

```c
void solution(void) {
  int tiles   = BLK / DIM;
  int tiles_K = MATMUL_K / DIM;

  uint32_t b_base = BANK_NUM * BANK_ROWS - tiles * tiles_K * DIM;
  uint32_t a_base = 0;
  int SPAD_DEST = 128;

  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                              1, 1, 0, 0, false, 0, 0, 3, 0);

  gemmini_config_st(BLK_OUTC * sizeof(out_t));

  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    int ncols = REAL_N - j0 * BLK;
    if (ncols > BLK) ncols = BLK;
    if (ncols <= 0) continue;

    for (int g = 0; g < MATMUL_K / 32; g++)
      memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);

    gemmini_config_ld(MATMUL_N * sizeof(elem_t));
    for (int j = 0; j < tiles; j++)
      for (int k = 0; k < tiles_K; k++)
        gemmini_extended_mvin(
          (void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
          b_base + (k * tiles + j) * DIM, DIM, DIM);

    gemmini_config_ld(MATMUL_K * sizeof(elem_t));

    for (int i0 = 0; i0 < BLOCKS_M; i0++) {
      int mrows = REAL_M - i0 * BLK;
      if (mrows > BLK) mrows = BLK;
      if (mrows <= 0) continue;

      int pad_i = BLK - mrows, pad_j = BLK - ncols;

      for (int g = 0; g < MATMUL_K / 32; g++)
        memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);

      gemmini_flush(0);

      gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);
      gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);

      for (int i = 0; i < tiles; i++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin(
            (void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
            a_base + (i * tiles_K + k) * DIM, DIM, DIM);

      gemmini_mxquant_config_mvout((uint64_t)scale_factors,
                                   tiles, tiles, tiles_K, 0, 0, 1);

      gemmini_loop_ws_spad(tiles, tiles, tiles_K, pad_i, pad_j, 0,
                           a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
                           false, false, false, false, false,
                           NO_ACTIVATION, 0, 0, false, 0x38);

      // Issue all read_smem DMA commands without stalling between iterations
      for (int r = 0; r < mrows; r++)
        gemmini_mx_read_smem(
          &C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
          SPAD_DEST * 16 + r * BLK, ncols);

      // Fence removed from here — deferred to after the i0 loop
    }

    // Single fence after all i0 iterations: all DMA drains for this j0 block
    // complete before the host (or next j0 iteration) touches output memory.
    gemmini_fence();
  }
}
```
