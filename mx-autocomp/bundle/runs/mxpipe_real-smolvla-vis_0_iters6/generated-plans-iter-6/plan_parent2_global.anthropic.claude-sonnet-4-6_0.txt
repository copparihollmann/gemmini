## Analysis of Current Code

The current code has `BLK` tiles loaded per block. Looking at the problem:

- `MATMUL_M = 113`, `MATMUL_N = 256`, `MATMUL_K = 256`, `DIM = 16`
- `BLK` (block size) determines `tiles = BLK/DIM`
- Current scratchpad utilization is 0KB out of 256KB — this means BLK is very small

The scratchpad can hold `8192` rows total. For A and B tiles simultaneously:
- A tiles: `tiles_I * tiles_K * DIM` rows
- B tiles: `tiles_J * tiles_K * DIM` rows
- Constraint: `(tiles_I * tiles_K + tiles_J * tiles_K) * DIM ≤ 8192`

With `tiles_K = MATMUL_K/DIM = 16` (K is always fully tiled), increasing `BLK` reduces overhead per block.

## Selected Strategy: Increase BLK to Fill the Scratchpad More Fully

**Strategy 5**: Increase BLK to maximize scratchpad utilization and reduce configuration/scale-load overhead ratio.

### Plan

**Current situation**: `BLK` is set small (likely `BLK = DIM = 16`, giving `tiles = 1`). With `tiles_K = 16`, a single A-block uses `1*16*16 = 256` rows and a single B-block uses `1*16*16 = 256` rows — only 512 rows out of 8192 total (6.25% utilization). This means `gemmini_flush`, `gemmini_extended3_config_ex`, two `gemmini_mx_load_scales` calls, and all the mvin configuration overhead is paid for every `BLK×BLK` output tile.

**Target**: Set `BLK = 4*DIM = 64`, giving `tiles = 4`. Now:
- A tiles: `4 * 16 * 16 = 1024` rows
- B tiles: `4 * 16 * 16 = 1024` rows  
- Total: `2048` rows out of `8192` (25% utilization, still safe)
- Accumulator C tiles: `tiles_I * tiles_J * DIM = 4 * 4 * 16 = 256` rows — exactly fills single-buffer accumulator

Wait, accumulator constraint: `tiles_I * tiles_J * DIM ≤ 256`. With `tiles = 4`: `4 * 4 * 16 = 256` — exactly at the limit. This is valid.

**With `BLK = 64`**:
- `BLOCKS_M = ceil(113/64) = 2` (vs. `ceil(113/16) = 8` previously)
- `BLOCKS_N = ceil(256/64) = 4` (vs. `ceil(256/16) = 16` previously)
- Total outer loop iterations: `2 * 4 = 8` (vs. `8 * 16 = 128` previously)
- Configuration overhead (flush, config_ex, load_scales) is paid **16× fewer times**
- B hoisting: B is loaded once per `j0`, so `BLOCKS_N = 4` B loads instead of `16`

**Changes needed**:
1. Change `BLK` to `64` (or `4*DIM`)
2. Update `BLK_OUTC = BLK / BF16_PER_WORD` accordingly
3. Update `A_S_BYTES` and `B_S_BYTES` to match the new larger block
4. Verify `b_base = BANK_NUM*BANK_ROWS - tiles*tiles_K*DIM` still fits (it does: `8192 - 4*16*16 = 7168`)
5. The `pad_i` and `pad_j` logic already handles partial edge blocks correctly — no change needed there

**Why this works**: The dominant cost is the per-block overhead (flush, config, scale loads, mvin configuration). By processing 4×4 = 16 output tiles per invocation instead of 1×1 = 1, we amortize that overhead 16× while the scratchpad and accumulator constraints remain satisfied.

```c
// AUTO-GENERATED outer-tiled MX matmul baseline (113x256x256).
void solution(void) {
  // Increase BLK to 4*DIM=64 to fill scratchpad and amortize overhead 16x.
  const int BLK_NEW   = 4 * DIM;          // 64
  const int tiles     = BLK_NEW / DIM;    // 4
  const int tiles_K   = MATMUL_K / DIM;   // 16

  // A_S_BYTES: one e8m0 scale per 32 elements along K, BLK_NEW rows
  // A_scales_row is [MATMUL_K/32][MATMUL_M], each row has BLK_NEW entries
  const int A_S_BYTES = (MATMUL_K / 32) * BLK_NEW;   // 8 * 64 = 512
  // B_S_BYTES: one e8m0 scale per 32 elements along K, BLK_NEW cols
  const int B_S_BYTES = (MATMUL_K / 32) * BLK_NEW;   // 8 * 64 = 512

  // b_base at top of scratchpad, large enough for tiles*tiles_K*DIM rows for B
  // A tiles at bottom: tiles*tiles_K*DIM = 4*16*16 = 1024 rows
  // B tiles at top:    tiles*tiles_K*DIM = 4*16*16 = 1024 rows
  // Total: 2048 rows <= 8192 — safe
  uint32_t b_base = BANK_NUM * BANK_ROWS - tiles * tiles_K * DIM;
  uint32_t a_base = 0;
  int SPAD_DEST   = 128;

  // OUT_COLS for a BLK_NEW-wide output block: BLK_NEW / BF16_PER_WORD
  const int BLK_OUTC = BLK_NEW / BF16_PER_WORD;  // 64/4 = 16

  // Staged scale buffers sized for BLK_NEW
  uint8_t  A_s[(MATMUL_K / 32)][BLK_NEW] __attribute__((aligned(64)));
  uint8_t  B_s[(MATMUL_K / 32)][BLK_NEW] __attribute__((aligned(64)));
  uint32_t scale_factors[512] __attribute__((aligned(32))) = {0};

  const int BLOCKS_M = (REAL_M + BLK_NEW - 1) / BLK_NEW;
  const int BLOCKS_N = (REAL_N + BLK_NEW - 1) / BLK_NEW;

  // Reorder: j0 outer so B tiles can be hoisted; i0 inner sweeps rows.
  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    int ncols = REAL_N - j0 * BLK_NEW;
    if (ncols > BLK_NEW) ncols = BLK_NEW;
    if (ncols <= 0) continue;

    // --- Stage B scales ONCE per j0 ---
    for (int g = 0; g < MATMUL_K / 32; g++)
      memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK_NEW], BLK_NEW);

    // --- Mvin B tiles ONCE per j0 into the top of the scratchpad ---
    // B is [MATMUL_K][MATMUL_N/2] in fp4 packing (2 elems/byte),
    // so row stride = MATMUL_N * sizeof(elem_t) / 2
    gemmini_config_ld(MATMUL_N * sizeof(elem_t) / 2);
    for (int j = 0; j < tiles; j++)
      for (int k = 0; k < tiles_K; k++)
        gemmini_extended_mvin(
          (void*)(((elem_t*)B_in) + (k * DIM) * (MATMUL_N / 2) + (j0 * BLK_NEW + j * DIM) / 2),
          b_base + (k * tiles + j) * DIM, DIM, DIM);

    for (int i0 = 0; i0 < BLOCKS_M; i0++) {
      int mrows = REAL_M - i0 * BLK_NEW;
      if (mrows > BLK_NEW) mrows = BLK_NEW;
      if (mrows <= 0) continue;

      int pad_i = BLK_NEW - mrows, pad_j = BLK_NEW - ncols;

      // --- Stage A scales once per (i0, j0) ---
      for (int g = 0; g < MATMUL_K / 32; g++)
        memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK_NEW], BLK_NEW);

      // PROF accel
      gemmini_flush(0);

      // Step 1: Configure execution.
      gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                                  1, 1, 0, 0, false, 2, 2, 3, 0);

      // Step 2: Load A and B scales into hardware.
      gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);
      gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);

      // Step 3: Mvin A tiles for this i0 row-block.
      // A is [MATMUL_M][MATMUL_K] in fp4 packing, row stride = MATMUL_K bytes (fp4: 2/byte)
      // Wait — A is bf16/fp4? Check reference: A uses elem_t=uint8_t, stride=MATMUL_M*sizeof(elem_t)
      // From reference pattern: gemmini_config_ld(MATMUL_M * sizeof(elem_t)) for A
      // and dram_ptr = A_in_hw + i*DIM*MATMUL_M + k*DIM (A is [MATMUL_K][MATMUL_M] column-major)
      // The original code used MATMUL_K * sizeof(elem_t) stride and row-major [MATMUL_M][MATMUL_K]
      // Keep consistent with original baseline's A layout:
      gemmini_config_ld(MATMUL_K * sizeof(elem_t));
      for (int i = 0; i < tiles; i++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin(
            (void*)(((elem_t*)A_in) + (i0 * BLK_NEW + i * DIM) * MATMUL_K + k * DIM),
            a_base + (i * tiles_K + k) * DIM, DIM, DIM);

      // Step 4: Configure requantized mvout.
      gemmini_config_st(BLK_OUTC * sizeof(out_t));
      gemmini_mxquant_config_mvout((uint64_t)scale_factors,
                                   tiles, tiles, tiles_K, 0, 0, 1);

      // Step 5: Execute fused hardware matmul.
      gemmini_loop_ws_spad(tiles, tiles, tiles_K, pad_i, pad_j, 0,
                           a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
                           false, false, false, false, false,
                           NO_ACTIVATION, 0, 0, false, 0x38);

      // Step 6: Drain BF16 results from mx_smem to DRAM, row by row.
      for (int r = 0; r < mrows; r++)
        gemmini_mx_read_smem(
          &C_hw[i0 * BLK_NEW + r][(j0 * BLK_NEW) / BF16_PER_WORD],
          SPAD_DEST * 16 + r * BLK_NEW, ncols);

      // Step 7: Fence.
      gemmini_fence();
    }
  }
}
```
