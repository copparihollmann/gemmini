Looking at the code, I need to identify the bug. The key issue is in the `gemmini_mx_read_smem` call and the scale loading conventions.

Let me trace through the issues:

1. **Scale loading sel convention**: Rule 11 says sel=0 for A (activation) scales, sel=1 for B (weight) scales in `gemmini_mx_load_scales`. The code has this correct already.

2. **`gemmini_mx_read_smem` offset calculation**: The `smem_off_bf16` is in 16-bit word units. For row `r`, the offset within the tile output should be `SPAD_DEST * 16 + r * BLK` where BLK is in BF16 units. But `num_bf16` should be `ncols`, not `BLK`. This looks correct.

3. **The B matrix layout**: B is loaded with `b_base + (k * tiles + j) * DIM` but should be `b_base + (j * tiles_K + k) * DIM` based on the spec. This is a bug! The spec says B tile layout is `b_base + (j*tiles_K + k)*DIM`.

4. **`gemmini_mxquant_config_mvout` scale_dram**: The `scale_factors` pointer - this needs to be the DRAM address of per-output-block scales, but looking at the hardware description, it seems this should point to scale factors for the output quantization. For BF16 output (`out_mx_fmt=3`), this may not be needed, but the call still needs valid addresses.

5. **The `b_base` and B tile indexing**: The B DRAM pointer uses column-major indexing `(k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)` which looks correct for row-major B matrix.

The critical bug: B spad layout uses `(k * tiles + j)` but should use `(j * tiles_K + k)` per the spec.
