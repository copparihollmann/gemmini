## Analysis of the Current Code

Looking at the baseline, I notice a critical inefficiency: **the `gemmini_extended3_config_ex` call is placed inside both the `j0` and `i0` loops**, meaning it gets re-issued on every `(j0, i0)` iteration. Since the format configuration (FP8, BF16 output, weight-stationary, no transpose) is **completely fixed across all tiles**, this is pure redundant overhead — the configuration never changes between iterations.

Similarly, `gemmini_config_ld` for the B mvin (stride = `MATMUL_N * sizeof(elem_t)`) is re-issued on every `j0` iteration even though it's the same value each time (B's row stride is fixed), and `gemmini_config_ld` for the A mvin (stride = `MATMUL_K * sizeof(elem_t)`) is re-issued on every `i0` iteration even though A's stride is constant.

## Strategy: Hoist All Invariant Configuration Instructions Outside Their Loops

**What to change:**

1. Move `gemmini_extended3_config_ex(...)` to execute **once**, before the `j0` loop entirely. The format fields (`act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`), dataflow (`WEIGHT_STATIONARY`), transposes (both 0), strides (`A_stride=1`, `C_stride=1`), and `set_only_strides=false` are all loop-invariant. Per the hardware spec, config registers persist until overwritten, so issuing this once is sufficient.

2. Move `gemmini_config_ld(MATMUL_N * sizeof(elem_t))` (the B-tile stride configuration) to execute **once**, before the `j0` loop. The B matrix row stride is `MATMUL_N`, which is a compile-time constant that never changes across `j0` iterations.

3. Move `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` (the A-tile stride configuration) outside the `i0` loop but inside the `j0` loop — actually, since `MATMUL_K` is also a compile-time constant, it can be hoisted entirely before the `j0` loop as well. However, the current code issues the B-mvin config then later re-issues the A-mvin config; since `gemmini_config_ld` is stateful and B-mvin comes first in `j0`, we need to re-issue the A-mvin config before A mvins. We can hoist it to right after the B mvins complete in the `j0` body, or issue it once before the `j0` loop if B is only mvin'd at `j0` level. Since A-stride never changes, issue it once before `j0`, and re-issue just before A mvins (which is inside `i0`). But the B mvin uses a different stride — so the config must be set to B-stride before B mvins and to A-stride before A mvins. We can hoist the **B** config to once before `j0`, and hoist **A** config to once just after the B-mvin block (still inside `j0` but outside `i0`), since A's stride is invariant across `i0`.

4. Move `gemmini_config_st(BLK_OUTC * sizeof(out_t))` outside the `i0` loop (to just before the `j0` loop or just before the `i0` loop). The output stride `BLK_OUTC * sizeof(out_t)` is loop-invariant.

**Why this improves performance:**

Each RoCC instruction has non-trivial issue and serialization overhead on the Spike simulator and on real hardware (it requires a round-trip through the RoCC interface). The outer loops run `BLOCKS_N × BLOCKS_M` iterations. For the given problem (113×256×256), with `BLK` tiles, these loops execute multiple times. By eliminating redundant re-issue of 3–4 configuration instructions per iteration, we reduce the total instruction count proportionally. More importantly, `gemmini_flush(0)` is currently inside the `i0` loop — it acts as a pipeline drain. While we cannot remove it, eliminating surrounding redundant configs means each `i0` iteration issues fewer serializing instructions, allowing the hardware command queue to stay fuller with actual compute and DMA work.

## Rewritten Code

```c
void solution(void) {
  int tiles   = BLK / DIM;
  int tiles_K = MATMUL_K / DIM;

  uint32_t b_base = BANK_NUM * BANK_ROWS - tiles * tiles_K * DIM;
  uint32_t a_base = 0;
  int SPAD_DEST = 128;

  // Step 1: Configure execution ONCE — format and dataflow are loop-invariant.
  // Config registers persist until overwritten; no need to re-issue per tile.
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                              1, 1, 0, 0, false, 0, 0, 3, 0);

  // Step 4a: Configure output stride ONCE — BLK_OUTC * sizeof(out_t) is constant.
  gemmini_config_st(BLK_OUTC * sizeof(out_t));

  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    int ncols = REAL_N - j0 * BLK;
    if (ncols > BLK) ncols = BLK;
    if (ncols <= 0) continue;

    // Stage B scales ONCE per j0.
    for (int g = 0; g < MATMUL_K / 32; g++)
      memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);

    // Mvin B tiles ONCE per j0 into the top of the scratchpad.
    // Set B-stride config here (before B mvins).
    gemmini_config_ld(MATMUL_N * sizeof(elem_t));
    for (int j = 0; j < tiles; j++)
      for (int k = 0; k < tiles_K; k++)
        gemmini_extended_mvin(
          (void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
          b_base + (k * tiles + j) * DIM, DIM, DIM);

    // Hoist A-stride config to once per j0, outside the i0 loop.
    // A's row stride is MATMUL_K — constant across all i0 iterations.
    gemmini_config_ld(MATMUL_K * sizeof(elem_t));

    for (int i0 = 0; i0 < BLOCKS_M; i0++) {
      int mrows = REAL_M - i0 * BLK;
      if (mrows > BLK) mrows = BLK;
      if (mrows <= 0) continue;

      int pad_i = BLK - mrows, pad_j = BLK - ncols;

      // Stage A scales once per (i0, j0).
      for (int g = 0; g < MATMUL_K / 32; g++)
        memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);

      // PROF accel
      gemmini_flush(0);

      // Step 2: Load A and B scales into hardware.
      // config_ex already issued once above; no need to repeat it here.
      gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);
      gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);

      // Step 3: Mvin A tiles for this i0 row-block.
      // A-stride config was set above (outside i0 loop); B tiles already resident.
      // No gemmini_config_ld needed here — stride is still MATMUL_K from above.
      for (int i = 0; i < tiles; i++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin(
            (void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
            a_base + (i * tiles_K + k) * DIM, DIM, DIM);

      // Step 4b: Configure requantized mvout.
      // gemmini_config_st already issued once before j0 loop.
      gemmini_mxquant_config_mvout((uint64_t)scale_factors,
                                   tiles, tiles, tiles_K, 0, 0, 1);

      // Step 5: Execute fused hardware matmul.
      gemmini_loop_ws_spad(tiles, tiles, tiles_K, pad_i, pad_j, 0,
                           a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
                           false, false, false, false, false,
                           NO_ACTIVATION, 0, 0, false, 0x38);

      // Step 6: Drain BF16 results from mx_smem to DRAM, row by row.
      for (int r = 0; r < mrows; r++)
        gemmini_mx_read_smem(
          &C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
          SPAD_DEST * 16 + r * BLK, ncols);

      // Step 7: Fence.
      gemmini_fence();
    }
  }
}
```

**Summary of changes:** `gemmini_extended3_config_ex` and `gemmini_config_st` moved before the `j0` loop (issued once total). `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` moved from inside `i0` to between the B-mvin block and the `i0` loop within `j0` (issued once per `j0` instead of once per `i0`). The `gemmini_config_ld(MATMUL_N * sizeof(elem_t))` for B was already at `j0` level. This eliminates `BLOCKS_N * BLOCKS_M` redundant `config_ex` calls, `BLOCKS_N * BLOCKS_M` redundant `config_st` calls, and `BLOCKS_N * (BLOCKS_M - 1)` redundant `config_ld` calls — reducing total instruction count without any change to computation, memory layout, or correctness.
