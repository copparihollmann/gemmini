With `MATMUL_K=256`, `BLK=256` (guessing from context), `DIM=16`:
- `tiles_K = 256/16 = 16`
- `tiles_J = BLK/DIM` (say 16 if BLK=256)
- Scratchpad for B: `tiles_J * tiles_K * DIM = 16*16*16 = 4096` rows
- Remaining for A: `8192 - 4096 = 4096` rows → `tiles_I_max = 4096 / (tiles_K * DIM) = 4096/256 = 16`
- Accumulator: `16 * 16 * 16 = 4096 > 256` — so accumulator is the binding constraint: `tiles_I_max = 256 / (tiles_J * DIM) = 256/(16*16) = 1`

This means accumulator is tight. The fix is also to **reduce tiles_J** (the J-blocking) so that more I tiles fit. Specifically, split j0 into smaller j-blocks of size `tiles_J_inner` such that `tiles_I_max * tiles_J_inner * DIM ≤ 256`, then sweep i0 with the larger i-block for each j-inner block. This gives a **(j0_outer → j_inner → i0)** three-level nest where B is partially reused.

- Single `gemmini_loop_ws_spad(tiles_I_blk, 1, tiles_K, ...)` — fully fused
