## Analysis of the Current Code

Looking at the MVIN loops in the current code:

```c
// A tiles
for (int i = 0; i < tiles; i++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(..., DIM, DIM);  // cols=DIM=16, loads one tile at a time

// B tiles
for (int j = 0; j < tiles; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(..., DIM, DIM);  // cols=DIM=16, loads one tile at a time
```

With `tiles = BLK/DIM` and `tiles_K = MATMUL_K/DIM`, each mvin loads exactly one 16×16 tile. This means the number of mvin commands is `tiles * tiles_K` for A and `tiles * tiles_K` for B — each command has fixed overhead.

## Selected Strategy: Batch the mvin (Strategy 2)

**Reasoning:** The code issues individual `gemmini_extended_mvin` calls with `cols=DIM=16`. Each call carries instruction dispatch overhead. By batching 2 consecutive tiles per call (`cols=2*DIM=32`), we halve the number of mvin commands. The constraint `cols ≤ 48` (batch ≤ 3) is satisfied since batch=2 → cols=32.

## Plan

### For A tiles (stride = `MATMUL_K * sizeof(elem_t)`)

The inner K loop iterates over `tiles_K` indices. Consecutive k tiles in the A layout are adjacent in DRAM: `A_in + (i0*BLK + i*DIM)*MATMUL_K + k*DIM`. However, tiles at `k` and `k+1` differ by `DIM` bytes in the same row — they are contiguous in columns. But the scratchpad addresses are `a_base + (i*tiles_K + k)*DIM` — consecutive k values give consecutive scratchpad rows. So batching along k: load columns `k*DIM` and `(k+1)*DIM` together with `cols=2*DIM=32`, scratchpad address `a_base + (i*tiles_K + k)*DIM`. Iterate k in steps of 2; handle odd `tiles_K` with a final single tile.

### For B tiles (stride = `MATMUL_N * sizeof(elem_t)`)

Similarly, B tiles in the inner K loop: `B_in + k*DIM*MATMUL_N + (j0*BLK + j*DIM)`. Consecutive j tiles at fixed k differ by `DIM` bytes in DRAM columns. Scratchpad layout is `b_base + (k*tiles + j)*DIM` — consecutive j values give consecutive rows. Batch along j: cols=2*DIM=32, iterate j in steps of 2.

### Concrete changes

**A mvin loop** — batch along k (innermost):
```c
gemmini_config_ld(MATMUL_K * sizeof(elem_t));
for (int i = 0; i < tiles; i++) {
  for (int k = 0; k < tiles_K - 1; k += 2) {
    gemmini_extended_mvin(
      (void*)(((elem_t*)A_in) + (i0*BLK + i*DIM)*MATMUL_K + k*DIM),
      a_base + (i*tiles_K + k)*DIM, 2*DIM, DIM);
  }
  if (tiles_K % 2 == 1) {
    int k = tiles_K - 1;
    gemmini_extended_mvin(
      (void*)(((elem_t*)A_in) + (i0*BLK + i*DIM)*MATMUL_K + k*DIM),
      a_base + (i*tiles_K + k)*DIM, DIM, DIM);
  }
}
```

**B mvin loop** — batch along j (innermost):
```c
gemmini_config_ld(MATMUL_N * sizeof(elem_t));
for (int k = 0; k < tiles_K; k++) {
  for (int j = 0; j < tiles - 1; j += 2) {
    gemmini_extended_mvin(
      (void*)(((elem_t*)B_in) + k*DIM*MATMUL_N + (j0*BLK + j*DIM)),
      b_base + (k*tiles + j)*DIM, 2*DIM, DIM);
  }
  if (tiles % 2 == 1) {
    int j = tiles - 1;
    gemmini_extended_mvin(
      (void*)(((elem_t*)B_in) + k*DIM*MATMUL_N + (j0*BLK + j*DIM)),
      b_base + (k*tiles + j)*DIM, DIM, DIM);
  }
}
```

This halves the mvin instruction count for both A and B, reducing command dispatch overhead without changing any data, scale, or compute semantics. All other steps (config_ex, load_scales, mxquant_config_mvout, loop_ws_spad, read_smem, fence) remain identical.
