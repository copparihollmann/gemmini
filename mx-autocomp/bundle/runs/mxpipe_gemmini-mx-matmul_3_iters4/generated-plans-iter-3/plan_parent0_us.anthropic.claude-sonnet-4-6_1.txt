## Analysis of the Original Code

Looking at the original code, I can identify a clear inefficiency:

```c
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), SCALE_IDENTITY, false, 0);
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), SCALE_IDENTITY, false, 1);
```

Two `gemmini_extended3_config_ld` calls are issued with **identical parameters** (same stride `MATMUL_K * sizeof(elem_t)`, same scale `SCALE_IDENTITY`, same `shrunk=false`) — differing only in the port `id` (0 vs 1). According to **strategy 11**: the stride configuration persists across ports, and since both mvin (port 0) and mvin2 (port 1) share the same stride and scale, the second config call is redundant overhead.

Additionally, looking at strategy 12, `gemmini_config_st` and `gemmini_mxquant_config_mvout` are issued **after** all the mvin loops complete, meaning the hardware store path is configured only after the DMA is done — a configuration stall between the last mvin and `gemmini_loop_ws_spad`. Hoisting these before the mvin loops lets the hardware store path be configured while DMA is in flight.

## Plan

**Apply Strategy 11 + Strategy 12 together** (both are simplifications/reorderings that reduce stalls):

1. **Remove the second `gemmini_extended3_config_ld`** (the one with `id=1`). Since both mvin and mvin2 use the same stride (`MATMUL_K * sizeof(elem_t)`) and scale (`SCALE_IDENTITY`), the single port-0 configuration suffices — the hardware persists the stride/scale state for both ports until changed.

2. **Hoist `gemmini_config_st` and `gemmini_mxquant_config_mvout`** to before the mvin loops. This way, the store path is fully configured while the DMA engine is loading A and B tiles, eliminating a configuration stall between the last mvin command and `gemmini_loop_ws_spad`.

The sequence becomes:
- `gemmini_extended3_config_ex` (unchanged)
- `gemmini_mx_load_scales` × 2 (unchanged)
- `gemmini_extended3_config_ld` (port 0 only — port 1 inherits same stride)
- `gemmini_config_st` + `gemmini_mxquant_config_mvout` (**hoisted here**)
- mvin loops (unchanged)
- `gemmini_loop_ws_spad` (unchanged)
- `gemmini_mx_read_smem` + `gemmini_fence` (unchanged)

This preserves the mandatory programming model sequence (config_ex → load_scales → mvin → mxquant_config_mvout → loop_ws_spad → read_smem → fence) because `gemmini_mxquant_config_mvout` is only consumed by `gemmini_loop_ws_spad`, not by the mvin operations — hoisting it before the mvins does not violate ordering.

## Rewritten Code

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // Single config_ld suffices for both mvin (port 0) and mvin2 (port 1)
  // since both share the same stride and scale; port-1 inherits the config.
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), SCALE_IDENTITY, false, 0);

  // Hoist store-path configuration before mvin loops so it is ready
  // while DMA is in flight, eliminating a stall before loop_ws_spad.
  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);

  for (int k = 0; k < tiles_K; k++) {
    for (int i = 0; i < tiles_I; i++)
      gemmini_extended_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM),
                            a_base + (i * tiles_K + k) * DIM, DIM, DIM);
    for (int j = 0; j < tiles_J; j++)
      gemmini_extended_mvin2((void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
                             b_base + (j * tiles_K + k) * DIM, DIM, DIM);
  }

  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```
