## Analysis of the Original Code

Looking at the original code, I can identify the inner mvin loop structure:

```c
for (int k = 0; k < tiles_K; k++) {
    for (int i = 0; i < tiles_I; i++)
        gemmini_extended_mvin(..., a_base + (i * tiles_K + k) * DIM, DIM, DIM);
    for (int j = 0; j < tiles_J; j++)
        gemmini_extended_mvin2(..., b_base + (j * tiles_K + k) * DIM, DIM, DIM);
}
```

Each iteration recomputes `(i * tiles_K + k) * DIM` and `(j * tiles_K + k) * DIM` from scratch — these are multiply operations repeated every iteration.

## Selected Strategy: #6 — Replace per-iteration scratchpad address arithmetic with an incremented pointer variable

### Plan

**Problem:** In the inner loops, the scratchpad addresses `a_base + (i * tiles_K + k) * DIM` and `b_base + (j * tiles_K + k) * DIM` involve a multiplication per iteration. With `tiles_K=4` (K=64, DIM=16) and `tiles_I=tiles_J=4` (M=N=64), that's 16+16=32 multiplications per k-iteration, and 4 k-iterations = 128 multiplications total.

**Fix:** Instead of recomputing `(i * tiles_K + k) * DIM` each time, introduce a running `uint32_t sp_addr_a` and `uint32_t sp_addr_b` that are initialized once before the loops and incremented by `DIM` after each tile. Since the loop iterates over consecutive tiles in scratchpad address order (for fixed k, i increments by 1, so the spad address increases by `tiles_K * DIM` per i-step; for fixed i, k increments by 1, so the address increases by `DIM` per k-step), we need to carefully set the stride.

Specifically:
- In the outer `k` loop, inner `i` loop: the address `a_base + (i * tiles_K + k) * DIM` increases by `tiles_K * DIM` as `i` increments by 1 (k fixed). So initialize `sp_addr_a = a_base + k * DIM` before the `i` loop, then add `tiles_K * DIM` after each `i` iteration.
- Similarly for `j` loop: `b_base + (j * tiles_K + k) * DIM` increases by `tiles_K * DIM` as `j` increments. Initialize `sp_addr_b = b_base + k * DIM` before the `j` loop, then add `tiles_K * DIM` after each `j` iteration.
- The outer `k` increment: between k-iterations, the base shifts by `DIM`. Track a `k_offset_a` and `k_offset_b` starting at `a_base` and `b_base` respectively, incremented by `DIM` each k iteration.

This eliminates all multiplications from the inner mvin loops, replacing them with a single addition per iteration.

**DRAM pointer arithmetic** (`((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM`) similarly involves a multiply. We can replace this with a running pointer `dram_a` initialized to `A_in + k * DIM` before the `i` loop, incremented by `DIM * MATMUL_K` per `i` step, and a `k_dram_a` pointer incremented by `DIM` per `k` step. Same for B.

The resulting code eliminates multiplications from all hot inner loops, replacing them with additions only, which are cheaper on the RISC-V pipeline and reduce instruction count.
