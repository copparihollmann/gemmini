## Analysis of the Original Code

Looking at the original code, I can identify a key inefficiency in the B matrix mvin loop:

```c
for (int j = 0; j < tiles_J; j++)
    for (int k = 0; k < tiles_K; k++)
        gemmini_extended_mvin((void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
                              b_base + (j * tiles_K + k) * DIM, DIM, DIM);
```

Both A and B are loaded using `gemmini_extended_mvin` (the same port), creating **port contention** — the hardware cannot issue both A and B loads concurrently. Strategy 8 directly addresses this.

## Plan: Apply Strategy 8 — Use `gemmini_extended_mvin2` for B Tiles

**What to change:**

Replace `gemmini_extended_mvin` with `gemmini_extended_mvin2` for all B tile loads. The A tiles continue to use `gemmini_extended_mvin` (mvin port). This gives A and B independent DMA channels, so they can be in-flight simultaneously without port contention.

**Specific changes:**

1. Keep the A mvin loop exactly as-is using `gemmini_extended_mvin`.
2. Change the B mvin loop to use `gemmini_extended_mvin2` instead of `gemmini_extended_mvin`. The DRAM pointer arithmetic, scratchpad address, and loop structure remain identical.
3. Also reorder the B loop to k-outer / j-inner (strategy 7 is a prerequisite for sequential DRAM access, and it's compatible here) to match the reference pattern in `matmul_tiled_fp4_64x64.c`.

The B loop reordering changes:
- `b_base + (j * tiles_K + k) * DIM` → same formula, still correct
- DRAM pointer: `B_in + k * DIM * MATMUL_N + j * DIM` (k-outer / j-inner, row-major sequential)

**Resulting code:**

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // MVIN A tiles using mvin port (A-port)
  gemmini_config_ld(MATMUL_K * sizeof(elem_t));
  for (int i = 0; i < tiles_I; i++)
    for (int k = 0; k < tiles_K; k++)
      gemmini_extended_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM),
                            a_base + (i * tiles_K + k) * DIM, DIM, DIM);

  // MVIN B tiles using mvin2 port (B-port), k-outer/j-inner for sequential DRAM access
  for (int k = 0; k < tiles_K; k++)
    for (int j = 0; j < tiles_J; j++)
      gemmini_extended_mvin2((void*)(((elem_t*)B_in) + k * DIM * MATMUL_N + j * DIM),
                             b_base + (j * tiles_K + k) * DIM, DIM, DIM);

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);

  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```

**Why this works:** `gemmini_extended_mvin` and `gemmini_extended_mvin2` are mapped to independent DMA ports in Gemmini. Using both simultaneously allows A and B tile streams to proceed in parallel, cutting the effective mvin latency roughly in half compared to serializing both through the single mvin port. The scratchpad layout, addresses, and all correctness constraints remain unchanged.
