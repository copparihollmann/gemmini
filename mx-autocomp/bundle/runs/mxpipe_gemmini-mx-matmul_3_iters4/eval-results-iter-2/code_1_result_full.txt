Looking at the original code, I notice that `gemmini_mxquant_config_mvout` is called with `lut_update_granularity = 1`. This means the requantizer LUT refreshes after **every single output tile** during the fused hardware loop execution. With `tiles_I * tiles_J * tiles_K` total work, this causes maximum LUT refresh interruptions.

## Selected Strategy: Strategy 16

**Increase `lut_update_granularity` from 1 to `tiles_K`** to minimize requantizer LUT refresh interruptions during the fused hardware loop.

## Plan

**Why this helps:** The `lut_update_granularity` parameter G controls how often the output LUT refreshes during the requantization post-pass in `gemmini_loop_ws_spad`. With G=1, the hardware refreshes the LUT after every output tile. With G=`tiles_K`, the hardware refreshes the LUT only once per (I, J) output block — i.e., only when the accumulated K-dimension result for one output tile is complete. Since the output depends on the same A-row scales and B-column scales for all K iterations of a fixed (i, j) pair, it is correct to use the same LUT state throughout all K iterations of that tile. There is no correctness hazard because:
- The scales loaded via `gemmini_mx_load_scales` are fixed for the entire matmul
- The LUT content doesn't change between K iterations of the same (i, j) output tile
- Refreshing G=tiles_K means we refresh at the same rate as actually needed (once per completed output tile)

**Specific change:** In the `gemmini_mxquant_config_mvout` call, change the last argument from `1` to `tiles_K`:

```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors,
    tiles_I, tiles_J, tiles_K,
    0, 0, tiles_K);  // lut_update_granularity = tiles_K instead of 1
```

The `gemmini_config_st` and `gemmini_mxquant_config_mvout` are issued **after** the mvin loops complete. This means these configuration instructions sit in the issue queue behind all the mvin instructions, creating a sequential dependency: the hardware cannot commit the output configuration until all mvins drain. If the instruction queue has any depth, these configurations could instead be issued earlier — before the mvin loops — so they are already committed by the time the compute loop starts, eliminating any configuration stall at loop entry.

## Selected Strategy

**Strategy 12: Hoist `gemmini_mxquant_config_mvout` and `gemmini_config_st` to before the mvin loops so they are committed to the issue queue before compute starts, eliminating configuration stall at loop entry.**

## Plan

### What to change

Move these two instructions:
```c
gemmini_config_st(OUT_COLS * sizeof(out_t));
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```

from their current position (after both mvin loops, just before `gemmini_loop_ws_spad`) to **immediately after** the scale load instructions (after both `gemmini_mx_load_scales` calls), but **before** the `gemmini_config_ld` and mvin loops.

### Why this is valid

- `gemmini_config_st` and `gemmini_mxquant_config_mvout` configure the output path (stride and requantizer). They do not depend on the scratchpad contents and have no data dependency on the mvin instructions.
- The programming model sequence only requires that these are issued before `gemmini_loop_ws_spad`, which is still satisfied.
- The scale loads (`gemmini_mx_load_scales`) must precede `gemmini_mxquant_config_mvout` — the hoisted position is after both scale loads, so this ordering is preserved.
- `gemmini_config_ld` (which configures the mvin stride) is orthogonal to `gemmini_config_st` (which configures the mvout stride); no conflict.

### Expected benefit

By issuing these configuration instructions earlier, they enter the Gemmini instruction queue while the mvin DMA operations are executing. When `gemmini_loop_ws_spad` is finally reached, the hardware has already processed the output configuration — no stall waiting for the config to commit before compute can begin. This overlaps configuration latency with data movement latency.
