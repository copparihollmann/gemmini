## Analysis of the Original Code

The original code has the following structure:
1. im2col loop (populates `A_buf`)
2. `gemmini_extended3_config_ex`
3. `gemmini_mx_load_scales` (A and B)
4. MVIN A tiles (tiles_I=4 × tiles_K=8 = 32 mvin calls via `gemmini_extended_mvin`)
5. MVIN B tiles (tiles_J=2 × tiles_K=8 = 16 mvin calls via `gemmini_extended_mvin`)
6. `gemmini_config_st` + `gemmini_mxquant_config_mvout`
7. `gemmini_loop_ws_spad`
8. `gemmini_mx_read_smem` + `gemmini_fence`

**Key observation**: Both A and B tiles are loaded using `gemmini_extended_mvin` (port 0/funct k_MVIN). The hardware provides three independent mvin ports: `k_MVIN` (mvin), `k_MVIN2` (mvin2), and `k_MVIN3` (mvin3). By using only one port for all loads, A and B loads are serialized. Strategy 10 directly addresses this.

## Selected Strategy: Strategy 10 — Use `gemmini_extended_mvin2` for B Tile Loads

### Plan

**What to change**: Issue all B tile loads using `gemmini_extended_mvin2` instead of `gemmini_extended_mvin`. Keep A tile loads on `gemmini_extended_mvin` (port 0). This allows the hardware to process A and B loads concurrently through two separate DMA ports, effectively halving the total tile-load time since the A and B load sequences can overlap.

**Specific changes**:

1. Keep the A mvin loop exactly as-is using `gemmini_extended_mvin`.
2. Change the B mvin loop to use `gemmini_extended_mvin2` for every B tile issue. The address computation (`b_base + (j * tiles_K + k) * DIM`) and the DRAM pointer arithmetic remain identical — only the intrinsic name changes.
3. No changes to `gemmini_config_ld` are needed before the B loop: `gemmini_extended_mvin2` uses a separate config register (configured via `gemmini_extended3_config_ld(..., id=1)`). Add `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1)` before the B mvin loop to set port 1's stride to `MATMUL_K`.
4. Interleave the loops: issue all A-tile mvins first (they go to port 0's queue), then immediately issue all B-tile mvins (they go to port 1's queue). The hardware can drain both queues in parallel.
5. All other steps (config_ex, load_scales, config_st, mxquant_config_mvout, loop_ws_spad, mx_read_smem, fence) remain unchanged and in the same order.

This change is safe because: B tiles land at `b_base` (top of scratchpad) which is non-overlapping with A tiles at `a_base` (bottom); the two ports write to disjoint scratchpad regions; the `gemmini_loop_ws_spad` instruction issued afterward (which consumes both A and B tiles) implicitly synchronizes after all pending mvins complete before compute begins.
