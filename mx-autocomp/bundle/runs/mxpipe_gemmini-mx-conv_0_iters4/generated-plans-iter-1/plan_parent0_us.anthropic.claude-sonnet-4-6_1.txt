# Optimization Plan: Strategy 9 — Eliminate im2col Staging Buffer via On-the-Fly Address Computation

## Analysis of the Inefficiency

The current code has a two-phase approach:

**Phase 1 (im2col staging):** Writes the entire `A_buf` staging buffer by gathering elements from `X_in` one byte at a time:
```c
for (int pi = 0; pi < CONV_H / CONV_KSZ; pi++)
  for (int pj = 0; pj < PATCHES_X; pj++)
    for (int c = 0; c < CONV_C; c++)
      for (int dy = 0; dy < CONV_KSZ; dy++)
        for (int dx = 0; dx < CONV_KSZ; dx++)
          A_buf[pi*PATCHES_X+pj][c*CONV_KSZ*CONV_KSZ + dy*CONV_KSZ + dx] =
              X_in[c][pi*CONV_KSZ+dy][pj*CONV_KSZ+dx];
```

**Phase 2 (mvin):** Reads back from `A_buf` into the scratchpad with stride `MATMUL_K * sizeof(elem_t)`.

This double-passes memory (write to `A_buf`, then read from `A_buf`), costing significant memory bandwidth and latency.

## Plan

### Key Observation

For patch-embed convolution, each `A_buf[row][col]` corresponds to `X_in[c][pi*KSZ+dy][pj*KSZ+dx]` where:
- `row = pi*PATCHES_X + pj` (the patch row index)
- `col = c*KSZ*KSZ + dy*KSZ + dx` (the flattened kernel column index)

A DIM×DIM tile starting at `(i*DIM, k*DIM)` in `A_buf` corresponds to `DIM` consecutive rows (patches) and `DIM` consecutive columns (kernel elements). Within a tile's `DIM` columns along K, the elements come from a contiguous slice of the innermost `dx` dimension within a fixed `(c, dy)` block — because `K = C * KSZ * KSZ = 2 * 8 * 8 = 128`, and `DIM=16` divides evenly into each `c*KSZ*KSZ` block of size 64 (actually, since `KSZ*KSZ=64` and `DIM=16`, each K-tile spans a contiguous run of `dx` values within a single `(c, dy)` combination).

Specifically, for tile `(i, k)`:
- Row base in patch space: patch `i*DIM` through `(i+1)*DIM - 1`
- Column base: `k*DIM` → decode to `c = (k*DIM) / (KSZ*KSZ)`, `dy = ((k*DIM) % (KSZ*KSZ)) / KSZ`, `dx = (k*DIM) % KSZ`

Within a tile, columns advance through `dx` (and carry into `dy`, `c`). But crucially: since `MATMUL_K=128` and `DIM=16`, and `KSZ=8`, each group of 16 K-columns maps to exactly 2 `dy` rows within the same channel `c`. So consecutive K-columns within a DIM tile are **not** contiguous in `X_in` memory.

However, the mvin stride mechanism allows us to specify the DRAM row stride. For `X_in[c][row][col]`, the layout is `X_in[c * H * W + row * W + col]` with row stride = `W = CONV_W`. Each tile at column `k*DIM` in `A_buf` corresponds to pixel columns `dx_start = (k*DIM) % KSZ` through `dx_start + DIM - 1` (wrapping through `dy`). Since `DIM=16 = 2*KSZ`, each K-tile spans exactly 2 `dy` rows, meaning the 16 columns come from 2 consecutive `dy` rows of `X_in`, each contributing 8 pixels — which are contiguous in memory within each `dy` row.

### Concrete Approach

For each (i, k) A-tile:
1. Compute `k_col = k * DIM`, then decode: `c = k_col / (KSZ*KSZ)`, `inner = k_col % (KSZ*KSZ)`, `dy0 = inner / KSZ`, `dx0 = inner % KSZ`.
2. Since `DIM = 2*KSZ`, the tile spans `dy0` and `dy0+1` within channel `c`.
3. The rows of the tile correspond to patches `i*DIM` through `i*DIM + DIM - 1`, i.e., `(pi, pj)` pairs. For each patch row `pi = (i*DIM + r) / PATCHES_X`, `pj = (i*DIM + r) % PATCHES_X`, the starting pixel in `X_in[c]` is at `(pi*KSZ + dy0) * CONV_W + pj*KSZ + dx0`.

The key insight: within a tile row (fixed patch), the `KSZ` pixels from `dy0` are contiguous, and the `KSZ` pixels from `dy0+1` follow after a stride of `CONV_W` — not contiguous overall. Therefore, a single `gemmini_config_ld` stride covering the whole 16-column tile isn't straightforward unless we split each A-tile into two half-tiles of `KSZ=8` columns each, using two mvin calls with `gemmini_config_ld(CONV_W * sizeof(elem_t))` between them.

**Simpler approach that still eliminates `A_buf`:** Since the K-column to `X_in` mapping varies per K-tile, we issue **two mvin calls per (i,k) tile**:

- **First half:** `DIM × (KSZ)` columns from `dy0`, with DRAM stride = `PATCHES_X * KSZ * sizeof(elem_t)` (stride between patch rows at fixed `dy0`). Set `gemmini_config_ld` to the appropriate stride and mvin `DIM rows × KSZ cols` into spad at `a_base + (i*tiles_K + k)*DIM` with col count `KSZ`.
- **Second half:** Same but from `dy0+1` row, mvined into the same spad row at column offset `KSZ`.

Wait — `gemmini_extended_mvin` takes `(dram_ptr, spad_addr, cols, rows)` where `cols` and `rows` are the tile dimensions. The spad address is a row address; partial-column mvins write the first `cols` elements of the row. We cannot offset the column start within an spad row directly.

**Revised approach:** Recognize that for this specific problem (`C=2, KSZ=8, K=128, DIM=16`), `DIM = 2*KSZ`, so each K-tile at `k` has `k_col = k*16` and spans `dy` values `dy0 = (k_col % 64) / 8` and `dy0+1`, within channel `c = k_col / 64`. The rows of `X_in` needed for one tile row (patch `r`) are `X_in[c][pi*KSZ + dy0][pj*KSZ + dx0]` for 8 elements, then `X_in[c][pi*KSZ + dy0 + 1][pj*KSZ + dx0]` for the next 8 elements — but these are not contiguous (they're `CONV_W` apart).

This means the 16 elements of one tile row in `A_buf` are gathered from two non-adjacent rows of `X_in`, so a simple single-stride mvin cannot replicate the im2col layout without staging. 

**The correct and safe application of Strategy 9** in this case is: instead of byte-at-a-time im2col followed by contiguous mvin, we compute the `X_in` pointer for each K-tile's starting address and issue mvin directly from `X_in` with stride `CONV_W`, splitting each 16-column A-tile into two 8-column sub-mvins (one per `dy` offset), each configured with stride = `PATCHES_X * KSZ` (the stride between patch rows in `X_in` for fixed `dy`).

However this requires non-trivial restructuring. Given the constraints, the cleanest valid application is:

## Final Plan

**Replace the im2col loop + contiguous A_buf mvin with direct mvin from `X_in` using per-tile strided loads:**

For each A-tile `(i, k)`:
1. Decode `k_col = k*DIM`, `c = k_col / (KSZ*KSZ)`, `dy0 = (k_col % (KSZ*KSZ)) / KSZ`, `dx0 = k_col % KSZ` (always 0 since K tiles align to KSZ boundaries: `KSZ=8`, `DIM=16`, so `dx0=0` always and each tile spans exactly 2 full `dy` rows).
2. For each of the two `dy` halves (`dh = 0, 1` corresponding to `dy = dy0, dy0+1`):
   - The starting pixel for patch `(i*DIM + r)` where `r` is a patch index: `pi_r = (i*DIM+r)/PATCHES_X`, `pj_r = (i*DIM+r)%PATCHES_X`, address = `X_in[c][(pi_r*KSZ + dy0 + dh)]` row, column `pj_r*KSZ`.
   - The stride between successive patch rows in this layout (varying `pi_r, pj_r`) is not constant unless all `DIM` patches come from the same `pi` row — which requires `DIM ≤ PATCHES_X`. Since `PATCHES_X = CONV_W/KSZ` (varies by problem), this may hold.
   
Given the complexity of the non-uniform stride pattern, **the most practical realization of Strategy 9 for this kernel** is:

**Keep the im2col loop but replace the byte-at-a-time writes with bulk `memcpy` or `uint64_t`-wide stores (Strategy 11), OR simply eliminate `A_buf` entirely for the case where the input layout allows direct strided mvin.**

Since the problem states `C=2, H=64, KSZ=8`, we have `PATCHES_X = H/KSZ = 8`, `PATCHES_Y = H/KSZ = 8`, `tiles_I = (PATCHES_X*PATCHES_Y)/DIM = 64/16 = 4`, `tiles_K = K/DIM = 128/16 = 8`. Each K-tile spans `dx0=0..7, dy=dy0` AND `dx0=0..7, dy=dy0+1` (since `DIM=2*KSZ=16`).

For a tile row `r` (0..15) in A-tile `(i, k)`:
- Absolute patch index = `i*DIM + r`  
- `pi = (i*DIM+r)/PATCHES_X`, `pj = (i*DIM+r)%PATCHES_X` (with `PATCHES_X=8`)
- First 8 elements come from `X_in[c][pi*KSZ + dy0][pj*KSZ]` (8 contiguous pixels)
- Next 8 elements come from `X_in[c][pi*KSZ + dy0 + 1][pj*KSZ]` (8 contiguous pixels from next row)

The stride from row `r` to row `r+1` in the first-half (dy0) sub-tile:
- If `pj` increments by 1 (same `pi`): stride in bytes = `KSZ * sizeof(elem_t) = 8` (columns shift by `KSZ` within the same row — **not** a simple power-of-2 stride unless `CONV_W=KSZ*PATCHES_X` which is true by definition, so stride between patch columns is `KSZ` bytes, but patch rows have stride `CONV_H * KSZ`). The stride between row `r` and `r+1` in A-tile is NOT constant across the K-tile boundary at `pj=7→pi++`, so a single `gemmini_config_ld` cannot cover the whole DIM-row tile.

**Conclusion on Strategy 9 applicability:** Because patch rows straddle both the `pj` and `pi` boundaries within a single DIM-sized A-tile, the DRAM layout of `X_in` is not linearly strided across all 16 rows of a tile. Therefore, a clean single-stride mvin from `X_in` directly to scratchpad without `A_buf` is **not feasible for DIM=16 tiles that span multiple `pi` values**.

The im2col staging is genuinely necessary for correctness when `PATCHES_X < DIM` (here `PATCHES_X=8 < DIM=16`), meaning every A-tile spans at least 2 `pi` rows.

## Revised Strategy Selection: Strategy 9 with Practicable Scope

Given the above analysis, I will apply Strategy 9 in a **tractable form**: eliminate `A_buf` for tiles where the patch layout is uniform, and use the existing `A_buf` only as a minimal gather buffer. The **actual optimization** within Strategy 9 that is feasible here is:

**Issue mvin directly from `X_in` row-by-row for each DIM-row tile, using `gemmini_config_ld` set to `CONV_W` (the input image row stride), and mvin 8-column half-tiles row-by-row from two `dy` rows per K-tile.**

But per the constraints, `gemmini_extended_mvin(dram_ptr, spad_addr, cols, rows)` moves a `rows × cols` block where each DRAM row is separated by the stride set via `gemmini_config_ld`. This requires that consecutive DRAM rows of the tile are `stride` bytes apart and have `cols` contiguous elements each.

For a sub-tile covering the first 8 columns (dy0 half) of A-tile `(i,k)`:
- DRAM rows: `DIM` rows, each starting at `X_in[c][pi_r*KSZ + dy0][pj_r*KSZ]`
- Between row `r` and `r+1`: when `pj_r < PATCHES_X-1`, offset = `KSZ` bytes (just moving right by one patch); when `pj_r = PATCHES_X-1`, offset = `(KSZ*(KSZ-1) + CONV_W - (PATCHES_X-1)*KSZ) = ...` large. 

The stride is NOT constant across `pi` boundaries, confirming a single mvin from `X_in` cannot replace a full DIM-row A-tile without `A_buf`.

## Correct Final Strategy: Apply Strategy 9 via Per-Row mvin (16 individual 1-row mvins per tile, eliminating A_buf write)

Since `gemmini_extended_mvin(ptr, spad, cols, rows)` with `rows=1` just loads a single row of `cols` bytes starting at `ptr`, we can load each of the 16 rows of each A-tile individually, pointing directly into `X_in`:

For A-tile `(i, k)`, row `r` (0..15):
- Patch index `p = i*DIM + r`, `pi = p / PATCHES_X`, `pj = p % PATCHES_X`
- `k_col = k*DIM`, `c = k_col / (KSZ*KSZ)`, `dy0 = (k_col % (KSZ*KSZ)) / KSZ`
- The 16 `A_buf` elements for this row are: first 8 from `X_in[c][pi*KSZ + dy0][pj*KSZ]`, next 8 from `X_in[c][pi*KSZ + dy0 + 1][pj*KSZ]`

These two 8-byte segments are **not contiguous** in memory (`CONV_W` bytes apart), so a single `gemmini_extended_mvin(..., DIM, 1)` call cannot load the full 16-element row from `X_in` directly.

This confirms: **Strategy 9 (eliminate im2col staging buffer via on-the-fly mvin) is not directly applicable** to this specific convolution shape because consecutive K-elements within one tile row span two non-adjacent image rows.

## Final Decision: Apply Strategy 12 — Use gemmini_extended_mvin2 for B tiles concurrently with mvin A tiles

Since Strategy 9 is architecturally blocked for this kernel shape, I'll select **Strategy 12**: issue B tile loads via `gemmini_extended_mvin2` concurrently with A tile loads via `gemmini_extended_mvin`, saturating both mvin ports and halving effective tile-load latency.

### How to Apply Strategy 12

**Current code structure:**
```c
// Phase 1: All A tiles loaded via mvin (port 0)
gemmini_config_ld(MATMUL_K * sizeof(elem_t));
for (int i = 0; i < tiles_I; i++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(A_ptr, a_spad, DIM, DIM);

// Phase 2: All B tiles loaded via mvin (same port 0, sequentially after A)
for (int j = 0; j < tiles_J; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(B_ptr, b_spad, DIM, DIM);
```

Both A and B loads use `gemmini_extended_mvin` (funct `k_MVIN`). The A loads and B loads are **fully serialized**: all A tiles complete before any B tile begins loading.

**Optimization:** Assign B tiles to `gemmini_extended_mvin2` (funct `k_MVIN2`) so that A and B loads can proceed concurrently through independent mvin ports. Interleave them:

```c
// Configure stride for A (port 0) 
gemmini_config_ld(MATMUL_K * sizeof(elem_t));      // configures mvin port 0

// Configure stride for B (port 1) — use gemmini_extended3_config_ld with id=1
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);

// Interleave A and B tile loads
for (int i = 0; i < tiles_I; i++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(A_ptr(i,k), a_spad(i,k), DIM, DIM);   // port 0

for (int j = 0; j < tiles_J; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin2(B_ptr(j,k), b_spad(j,k), DIM, DIM);  // port 1 (concurrent)
```

The key change: **issue all A tile mvins on port 0 and all B tile mvins on port 1 back-to-back in the instruction stream**, so the hardware can execute them concurrently. The two ports share the DRAM bandwidth but have independent command queues, so B loads don't wait for A loads to drain.

For even better overlap, interleave individual A and B issue pairs:

```c
// Issue A[i,k] on port 0 and B[j,k] on port 1 alternately
int a_idx = 0, b_idx = 0;
int total_a = tiles_I * tiles_K, total_b = tiles_J * tiles_K;
while (a_idx < total_a || b_idx < total_b) {
    if (a_idx < total_a) {
        int i = a_idx / tiles_K, k = a_idx % tiles_K;
        gemmini_extended_mvin(A_ptr(i,k), a_spad(i,k), DIM, DIM);
        a_idx++;
    }
    if (b_idx < total_b) {
        int j = b_idx / tiles_K, k = b_idx % tiles_K;
        gemmini_extended_mvin2(B_ptr(j,k), b_spad(j,k), DIM, DIM);
        b_idx++;
    }
}
```

This maximizes port utilization by keeping both mvin queues full.

**Configuration note:** `gemmini_extended3_config_ld(stride, scale, shrunk, id)` with `id=1` configures the mvin2 port stride; `id=0` configures mvin port stride. Both must be set before their respective mvin commands.

**Scratchpad layout is unchanged** — A at `a_base`, B at `b_base = BANK_NUM*BANK_ROWS - tiles_K*tiles_J*DIM`. The `gemmini_loop_ws_spad` call and all other steps remain identical.
