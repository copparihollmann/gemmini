Plan: ## Strategy: Interleave A and B mvin Commands to Maximize DMA Port Utilization

### Observation

In the original code, all A tiles are loaded first (using `gemmini_extended_mvin` on port mvin), then all B tiles are loaded (also using `gemmini_extended_mvin` on the same port). This is strictly sequential: the DMA engine finishes all A loads before starting any B loads.

The hardware exposes **three independent mvin ports**: `mvin` (port 0), `mvin2` (port 1), and `mvin3` (port 2). Ports 0 and 1 (mvin and mvin2) target the scratchpad independently. When A and B loads are issued on separate ports, the DMA engine can fetch both matrices from DRAM **simultaneously**, cutting the total tile-load latency roughly in half.

### What to Change

1. Issue A-tile loads via `gemmini_extended_mvin` (port 0), configured with the A-matrix DRAM stride.
2. Issue B-tile loads via `gemmini_extended_mvin2` (port 1), configured with the B-matrix DRAM stride via a separate `gemmini_extended3_config_ld(..., id=1)` call.
3. **Interleave** the two streams: for each `(i, k)` A-tile issue, immediately follow with the corresponding `(j, k)` B-tile on port 1, so both DMA channels are active concurrently throughout the load phase.

Because `gemmini_extended3_config_ld` takes an `id` parameter (0 = mvin, 1 = mvin2), the two ports can be configured with different strides independently without interfering with each other.

### Why This Helps

The current bottleneck in the load phase is DRAM bandwidth serialized through a single DMA channel. With two independent channels active simultaneously:
- DRAM bandwidth is better utilized (two in-flight requests).
- Total load latency for tiles overlaps rather than adds.
- The compute phase (`gemmini_loop_ws_spad`) can start sooner.

          b_base + (j * tiles_K + k) * DIM,

    }
