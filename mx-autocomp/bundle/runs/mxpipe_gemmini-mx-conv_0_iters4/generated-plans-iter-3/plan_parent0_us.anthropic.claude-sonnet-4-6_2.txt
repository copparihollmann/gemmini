## Analysis

Looking at the code, the im2col loop contains:
```c
int pi = patch_idx / PATCHES_X;
int pj = patch_idx % PATCHES_X;
```

These division and modulo operations are expensive on RISC-V (no hardware divide in some configurations, or at minimum multi-cycle instructions). They are computed **inside the outer `i` loop and `li` inner loop**, meaning they execute `tiles_I * DIM = MATMUL_M` times total. For every patch, we recompute `pi` and `pj` from scratch using integer division/modulo.

**Strategy 10** is directly applicable: *precompute `pi` and `pj` outside the inner im2col loop using incremental updates instead of repeated integer division and modulo operations*.

## Plan

Instead of computing `pi = patch_idx / PATCHES_X` and `pj = patch_idx % PATCHES_X` inside the loop body, we maintain `pi` and `pj` as incrementally updated variables:

1. Before the `i` loop, initialize `pi = 0` and `pj = 0` (for `patch_idx = 0`).
2. Inside the `li` inner loop, after computing `patch_idx = i * DIM + li`, use `pi` and `pj` directly.
3. After each use, increment `pj`. When `pj` reaches `PATCHES_X`, reset `pj = 0` and increment `pi`.

This replaces `MATMUL_M` integer divisions and `MATMUL_M` modulo operations with `MATMUL_M` increments and `MATMUL_M/PATCHES_X` conditional resets — significantly cheaper on RISC-V.

The `patch_idx` variable is still needed to index `A_buf`, but can itself be maintained incrementally: start at `i * DIM` and increment by 1 each `li` iteration (or simply use `i * DIM + li` which is a multiply-add, but since `i * DIM` is loop-invariant, hoist it as `i_base = i * DIM` and then `patch_idx = i_base + li`).

The restructured im2col section becomes:

```c
int pi = 0, pj = 0;  // incremental patch coordinates, starting at patch_idx=0

for (int i = 0; i < tiles_I; i++) {
    int i_base = i * DIM;
    for (int li = 0; li < DIM; li++) {
        int patch_idx = i_base + li;
        // Use pi, pj directly — no division/modulo
        for (int c = 0; c < CONV_C; c++)
            for (int dy = 0; dy < CONV_KSZ; dy++)
                for (int dx = 0; dx < CONV_KSZ; dx++)
                    A_buf[patch_idx][c * CONV_KSZ * CONV_KSZ + dy * CONV_KSZ + dx] =
                        X_in[c][pi * CONV_KSZ + dy][pj * CONV_KSZ + dx];
        // Increment pj, wrap to next row
        pj++;
        if (pj == PATCHES_X) { pj = 0; pi++; }
    }
    // mvin tiles for this i-row (unchanged)
    for (int k = 0; k < tiles_K; k++)
        gemmini_extended_mvin(
            (void*)(((elem_t*)A_buf) + i_base * MATMUL_K + k * DIM),
            a_base + (i * tiles_K + k) * DIM, DIM, DIM);
}
```

Note: `i * DIM * MATMUL_K` is hoisted as `i_base * MATMUL_K` (with `i_base = i * DIM`), eliminating the multiply inside the mvin address calculation as a bonus.

This change is semantically equivalent because `pi` and `pj` traverse the same sequence of values as `patch_idx / PATCHES_X` and `patch_idx % PATCHES_X` respectively, just without recomputing from scratch each time.
