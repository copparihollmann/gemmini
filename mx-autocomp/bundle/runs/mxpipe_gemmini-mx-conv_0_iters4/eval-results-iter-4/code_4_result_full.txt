### Analysis of the Bottleneck

In the original code, the work for each `i`-tile is strictly sequential:
1. CPU performs im2col for tile `i` (writes `A_buf[i*DIM..(i+1)*DIM-1][0..MATMUL_K-1]`)
2. Accelerator DMAs that data from DRAM into scratchpad

These two phases serialize: the CPU stalls waiting for im2col to complete before issuing mvins, and the accelerator stalls waiting for mvins before compute. The `gemmini_loop_ws_spad` at the end consumes all A-tiles at once, but the mvin phase itself is a long sequential series of CPU-issued DMA commands interleaved with CPU scalar stores.

### The New Strategy: Double-Buffered im2col + mvin Pipeline

**Idea:** Use two alternating buffers (`A_buf[0]` and `A_buf[1]`, each holding one i-tile's worth of im2col output) so that:
- While the CPU is computing im2col for tile `i+1` into buffer `(i+1)%2`, the accelerator is simultaneously executing the mvin DMA for tile `i` from buffer `i%2`.
- This is strategy #9 from the list, applied precisely: overlap CPU im2col work with accelerator DMA.

However, in the original code, `gemmini_loop_ws_spad` requires **all** A tiles to be present in the scratchpad before it executes. So we cannot defer mvins; we must still issue all mvins before calling `gemmini_loop_ws_spad`. The overlap opportunity is between CPU im2col computation and DMA transfer of the *previous* tile.

**Concrete change:** Instead of:
```
for i:
  im2col(i → A_buf[i])   // CPU
  mvin(A_buf[i] → spad)  // accelerator DMA
```
Do:
```
im2col(0 → A_buf[0])           // CPU: prepare tile 0 (no overlap yet)
for i = 0..tiles_I-2:
  issue_mvin(A_buf[i%2])       // Accelerator: DMA tile i (non-blocking RoCC cmd)
  im2col(i+1 → A_buf[(i+1)%2])// CPU: prepare tile i+1 WHILE DMA runs
issue_mvin(A_buf[(tiles_I-1)%2]) // Accelerator: DMA last tile
```

The key insight: RoCC mvin instructions are **non-blocking** — after issuing the mvin commands for tile `i`, the CPU can immediately start computing im2col for tile `i+1` while the accelerator's DMA engine is transferring tile `i`'s data. No fence is needed between them because the scratchpad addresses don't alias (tile `i` writes to `a_base + i*tiles_K*DIM`, tile `i+1` writes to `a_base + (i+1)*tiles_K*DIM`), and `gemmini_loop_ws_spad` at the end implicitly waits for all outstanding DMAs.

### Why This Reduces Latency

The original code's mvin phase looks like:
```
[im2col i=0][mvin i=0][im2col i=1][mvin i=1]...[im2col i=N-1][mvin i=N-1]
```
Total = tiles_I × (T_im2col + T_mvin)

With double-buffering:
```
[im2col i=0][mvin i=0 ∥ im2col i=1][mvin i=1 ∥ im2col i=2]...[mvin i=N-1]
```
Total = T_im2col + tiles_I × max(T_im2col, T_mvin)

If T_im2col ≈ T_mvin, this halves the mvin phase latency. Even if one dominates, the other is hidden.

| Change | Why |
|--------|-----|
| Double-buffered `A_buf[2][DIM][MATMUL_K]` | Prevents im2col for tile `i+1` from overwriting DMA-in-flight data for tile `i` |
| Pipeline: `DO_MVIN_A(i)` then `DO_IM2COL(i+1)` in same loop iteration | Overlaps CPU scalar gather with accelerator DMA; hides whichever is shorter |
| `SPAD_DEST = tiles_I * tiles_K * DIM` | Moves output smem pointer above A region, eliminating address aliasing risk |
| `gemmini_flush(0)` at start | Clears stale accelerator state from prior kernels |
| Mvin pointer uses `A_buf[b]` base + `_k*DIM` offset | Correct: each buffer is contiguous `DIM×MATMUL_K`, so offset within buffer is `_k*DIM` elements |
