# Strategy: Fused im2col + Mvin with B-tile Reuse Across I-tiles

## Analysis of Current Code

The current code has two key inefficiencies:

1. **im2col is fully materialized before any DMA begins** — the entire `A_buf` is written to DRAM (or cache) as a separate pass, then re-read by `gemmini_extended_mvin`. This means the CPU touches all of `A_buf` twice: once to write it, once as the DMA source.

2. **B tiles are loaded redundantly** — B tiles are loaded into the scratchpad once for all I-tiles, but since all I-tiles share the same B layout (weight-stationary), the B mvin is correctly done once. However, the A mvin loop and B mvin loop are completely separated, meaning the hardware sits idle during the A mvin while B is already loaded (and vice versa).

3. **The gemmini_extended_mvin for A uses mvin port 0, and B also uses mvin port 0 sequentially** — they are not overlapped across the two available independent ports (mvin vs mvin2).

## Selected Strategy: Loop Reordering + Pipeline im2col with Mvin (Strategies 2 + 7 + 9)

The key insight is: **stream im2col row-by-row into a small DRAM-side ping-pong buffer, computing one `i`-row of A tiles at a time, and immediately issuing the mvin for that row before starting the next row's im2col**. This hides im2col CPU time behind the DMA latency of the previous row.

Additionally, **use `mvin` (port 0) for A-tiles and `mvin2` (port 1) for B-tiles**, so B loads overlap with A loads at the hardware level — though since B is loaded once up front, the main gain is from the A pipeline.

## Specific Changes

### 1. Compute im2col one i-row at a time, issue mvin immediately

Instead of:
```c
// Phase 1: full im2col into A_buf (all tiles_I * tiles_K rows)
for (all i, k, c, dy, dx) { A_buf[...][...] = ...; }

// Phase 2: all A mvins
for (i) for (k) gemmini_extended_mvin(...);

// Phase 3: all B mvins
for (j) for (k) gemmini_extended_mvin(...);
```

Do:
```c
// Load B tiles first using mvin2 (port 1)
gemmini_extended3_config_ld(..., id=1);  // config for mvin2
for (j) for (k) gemmini_extended_mvin2(B_dram, b_base + (j*tiles_K+k)*DIM, DIM, DIM);

// For each i-row: compute im2col into A_buf row i, then mvin it immediately
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), ..., id=0);  // config for mvin
for (int i = 0; i < tiles_I; i++) {
    // im2col: fill only row i (DIM output rows = one i-tile's worth of patches)
    for (int li = 0; li < DIM; li++) {
        int pi = ...; int pj = ...;
        for (int c, dy, dx) {
            A_buf[i*DIM + li][...] = X_in[c][pi*CONV_KSZ+dy][pj*CONV_KSZ+dx];
        }
    }
    // immediately mvin this i-row's tiles
    for (int k = 0; k < tiles_K; k++)
        gemmini_extended_mvin(A_buf[i*DIM] + k*DIM, a_base + (i*tiles_K+k)*DIM, DIM, DIM);
}
```

By the time `gemmini_loop_ws_spad` is issued, the DMA for the last i-row's A tiles overlaps with the tail of the im2col for that row (since mvin is non-blocking). The B tiles are already in the scratchpad and were loaded while im2col for early A rows was being computed.

### 2. Use `mvin2` for B tiles to separate port usage

Configure `gemmini_extended3_config_ld` with `id=1` before B mvins and `id=0` before A mvins. This allows the hardware to pipeline B loads on port 1 while A loads proceed on port 0 (even though in this kernel B is loaded once, separating ports avoids head-of-line blocking in the DMA queue).

### 3. Align im2col writes to DIM-row boundaries (Strategy 9)

The inner im2col loop already writes contiguous rows of `A_buf`. By processing exactly `DIM` output rows per `i` iteration, each mvin covers exactly one aligned DIM-row slab with no wasted bytes or partial tiles — matching the `DIM×DIM` tile shape exactly.

## Rewritten Code

```c
void solution(void) {
  // Tile counts
  const int tiles_I = MATMUL_M / DIM;
  const int tiles_J = MATMUL_N / DIM;
  const int tiles_K = MATMUL_K / DIM;

  // Scratchpad base addresses
  const int a_base = 0;
  const int b_base = BANK_NUM * BANK_ROWS - tiles_K * tiles_J * DIM;
  const int SPAD_DEST = 0;

  // Step 1: Configure execution (MX FP8 -> BF16)
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
      1, 1, 0, 0, false, 0, 0, 3, 0);

  // Step 2: Load scale factors
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // Step 3: Load B tiles using mvin2 (port 1) — done once, amortized over all I tiles
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);
  for (int j = 0; j < tiles_J; j++)
    for (int k = 0; k < tiles_K; k++)
      gemmini_extended_mvin2(
          (void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
          b_base + (j * tiles_K + k) * DIM, DIM, DIM);

  // Step 4: Configure mvin port 0 for A tiles
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0);

  // Step 5: Fused im2col + mvin for A, one i-row (DIM output rows) at a time
  // Each i maps to DIM consecutive patch rows in A_buf
  for (int i = 0; i < tiles_I; i++) {
    // im2col: produce DIM rows of A_buf for this i-tile
    // patch index: row = i*DIM + li in [0, MATMUL_M)
    //   patch row pi = (i*DIM + li) / PATCHES_X, patch col pj = (i*DIM + li) % PATCHES_X
    for (int li = 0; li < DIM; li++) {
      int patch_idx = i * DIM + li;
      int pi = patch_idx / PATCHES_X;
      int pj = patch_idx % PATCHES_X;
      for (int c = 0; c < CONV_C; c++)
        for (int dy = 0; dy < CONV_KSZ; dy++)
          for (int dx = 0; dx < CONV_KSZ; dx++)
            A_buf[patch_idx][c * CONV_KSZ * CONV_KSZ + dy * CONV_KSZ + dx] =
                X_in[c][pi * CONV_KSZ + dy][pj * CONV_KSZ + dx];
    }

    // Immediately mvin this i-row's tiles (port 0, non-blocking)
    // Hardware DMA for this i starts while CPU begins im2col for i+1
    for (int k = 0; k < tiles_K; k++)
      gemmini_extended_mvin(
          (void*)(((elem_t*)A_buf) + i * DIM * MATMUL_K + k * DIM),
          a_base + (i * tiles_K + k) * DIM, DIM, DIM);
  }

  // Step 6: Configure output and requantizer
  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors,
      tiles_I, tiles_J, tiles_K, 0, 0, tiles_K);

  // Step 7: Execute fused tiled matmul
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0,
      a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
      false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);

  // Step 8: Drain results
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```

## Why This Reduces Latency

| Source of savings | Mechanism |
|---|---|
| B-port separation (`mvin2`) | B DMA uses port 1; A DMA uses port 0; no head-of-line blocking between the two streams in the DMA queue |
| im2col pipelining | For i=0,1,...,N-1: im2col for row i+1 runs on CPU while DMA for row i's tiles is in flight on port 0 — CPU work is hidden behind hardware latency |
| Early B load | B tiles are fully loaded before any A tile im2col begins, so compute can start the moment the last A mvin drains |
| No extra full-array im2col materialization overhead | Only `DIM` rows of `A_buf` need to be "hot" in cache at a time, reducing cache pressure versus writing all of `A_buf` then reading it all back |

The net effect is that the im2col CPU cost (previously serial with DMA) is largely hidden behind the non-blocking mvin queue depth, reducing the critical path from `im2col_time + A_mvin_time + B_mvin_time + compute_time` toward `max(im2col_time, A_mvin_time) + B_mvin_time_hidden + compute_time`.
