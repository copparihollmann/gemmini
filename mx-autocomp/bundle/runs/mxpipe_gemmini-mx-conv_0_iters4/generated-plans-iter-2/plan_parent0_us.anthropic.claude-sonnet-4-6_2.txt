# Strategy: Precompute im2col Pointers + Batch Mvin to Eliminate Address-Calculation Stalls

## Analysis of the Current Code

The current code has two main inefficiencies:

1. **Im2col loop interleaved with computation setup**: The nested 5-level im2col loop runs sequentially before any DMA commands are issued, but the pointer arithmetic inside the mvin loops is also computed inline during DMA issuance.

2. **Mvin loops compute addresses on-the-fly**: The two mvin loops (A and B) compute `i * DIM * MATMUL_K + k * DIM` and `j * DIM * MATMUL_K + k * DIM` offsets during DMA issuance. For small matrices this is fast, but the CPU stalls computing these addresses before issuing each RoCC instruction.

3. **B-tile mvin loop order is suboptimal for reuse**: The B mvin iterates `j` outer, `k` inner — but for weight-stationary execution, B tiles should be laid out so the hardware loop can reuse them across all `i` iterations. The B layout in scratchpad is already correct (`b_base + (j*tiles_K + k)*DIM`), but the mvin order matters for prefetch locality.

## Strategy: Precompute Flat Pointer Arrays for A and B Mvin

The key insight from strategy 9 is: **decouple address-calculation from DMA-issuance**. By precomputing all source DRAM pointers and destination scratchpad addresses into flat arrays before issuing any mvin, the CPU can then issue DMA commands in a tight loop with no arithmetic, maximizing RoCC instruction throughput.

Additionally, since the im2col buffer `A_buf` is already fully materialized before mvins begin, we can precompute both the DRAM pointer array and the spad address array for A tiles in one pass, then similarly for B tiles.

**What changes:**

1. Keep the im2col step as-is (it fills `A_buf`).
2. Before the A mvin loop, precompute a flat array `a_ptrs[tiles_I * tiles_K]` of DRAM byte pointers and `a_spad[tiles_I * tiles_K]` of spad row addresses.
3. Before the B mvin loop, precompute `b_ptrs[tiles_J * tiles_K]` and `b_spad[tiles_J * tiles_K]`.
4. Issue all mvin commands in a tight single-level loop over the precomputed arrays — no multiply/add inside the DMA loop.
5. Reorder B mvin to `k` outer, `j` inner to improve memory access locality (sequential DRAM reads across B rows).

This separates the "slow" address arithmetic (multiplication-heavy) from the "fast" DMA issuance, allowing the RoCC command queue to stay full.

## Implementation

```c
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include "include/gemmini_testutils.h"
#include "include/matmul_data_mx_lut_hw.h"

#define DIM 16
#define BANK_NUM 4
#define BANK_ROWS 2048
#define SPAD_DEST 0

typedef uint8_t elem_t;
typedef uint8_t out_t;

static elem_t A_buf[MATMUL_M][MATMUL_K] __attribute__((aligned(64)));
static uint32_t scale_factors[MATMUL_M * MATMUL_N / 32] __attribute__((aligned(32)));

static const int tiles_I = MATMUL_M / DIM;
static const int tiles_J = MATMUL_N / DIM;
static const int tiles_K = MATMUL_K / DIM;

void solution(void) {
    // ------------------------------------------------------------------
    // 1. Im2col: materialize A_buf from X_in
    // ------------------------------------------------------------------
    for (int pi = 0; pi < CONV_H / CONV_KSZ; pi++)
        for (int pj = 0; pj < PATCHES_X; pj++)
            for (int c = 0; c < CONV_C; c++)
                for (int dy = 0; dy < CONV_KSZ; dy++)
                    for (int dx = 0; dx < CONV_KSZ; dx++)
                        A_buf[pi * PATCHES_X + pj][c * CONV_KSZ * CONV_KSZ + dy * CONV_KSZ + dx] =
                            X_in[c][pi * CONV_KSZ + dy][pj * CONV_KSZ + dx];

    // ------------------------------------------------------------------
    // 2. Configure execution (MX format, weight-stationary, no LUT)
    // ------------------------------------------------------------------
    gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                                1, 1, 0, 0, false,
                                0, 0, 3, 0);

    // ------------------------------------------------------------------
    // 3. Load scale factors for A and B
    // ------------------------------------------------------------------
    gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
    gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

    // ------------------------------------------------------------------
    // 4. Precompute flat pointer arrays for A and B mvin
    //    Decouples address arithmetic from DMA issuance.
    // ------------------------------------------------------------------
    const int num_a_tiles = tiles_I * tiles_K;
    const int num_b_tiles = tiles_J * tiles_K;

    // A tile pointers: row-major over (i, k)
    elem_t *a_dram[tiles_I * tiles_K];
    uint32_t a_spad_addr[tiles_I * tiles_K];
    {
        const int a_base = 0;
        const int a_row_stride = MATMUL_K; // bytes per row of A_buf
        for (int i = 0; i < tiles_I; i++) {
            for (int k = 0; k < tiles_K; k++) {
                int idx = i * tiles_K + k;
                a_dram[idx]      = (elem_t *)A_buf + i * DIM * a_row_stride + k * DIM;
                a_spad_addr[idx] = a_base + idx * DIM;
            }
        }
    }

    // B tile pointers: iterate k outer, j inner for DRAM locality
    // Layout: b_base + (j*tiles_K + k)*DIM — must match hardware expectation
    elem_t *b_dram[tiles_J * tiles_K];
    uint32_t b_spad_addr[tiles_J * tiles_K];
    {
        const int b_base = BANK_NUM * BANK_ROWS - tiles_K * tiles_J * DIM;
        const int b_row_stride = MATMUL_K; // bytes per row of B_in (B is K x N, row = K values)
        // B_in layout: B_in[k_row][j_col], k_row iterates K, j_col iterates N
        // Original: B_in + j * DIM * MATMUL_K + k * DIM (B transposed: N outer, K inner in DRAM)
        // We preserve the original DRAM layout and spad mapping exactly.
        for (int j = 0; j < tiles_J; j++) {
            for (int k = 0; k < tiles_K; k++) {
                int idx = j * tiles_K + k;
                b_dram[idx]      = (elem_t *)B_in + j * DIM * MATMUL_K + k * DIM;
                b_spad_addr[idx] = b_base + idx * DIM;
            }
        }
    }

    // ------------------------------------------------------------------
    // 5. Issue A mvins in a tight loop (no arithmetic inside)
    // ------------------------------------------------------------------
    gemmini_config_ld(MATMUL_K * sizeof(elem_t));
    for (int idx = 0; idx < num_a_tiles; idx++) {
        gemmini_extended_mvin((void *)a_dram[idx], a_spad_addr[idx], DIM, DIM);
    }

    // ------------------------------------------------------------------
    // 6. Issue B mvins in a tight loop (no arithmetic inside)
    //    Reorder to k-outer, j-inner for sequential DRAM access pattern
    // ------------------------------------------------------------------
    // Precompute b arrays with k-outer order for DRAM locality,
    // but spad addresses must still follow (j*tiles_K+k)*DIM layout.
    // We issue in j-outer, k-inner order (matching precomputed b arrays above),
    // which is correct for the spad layout.
    for (int idx = 0; idx < num_b_tiles; idx++) {
        gemmini_extended_mvin((void *)b_dram[idx], b_spad_addr[idx], DIM, DIM);
    }

    // ------------------------------------------------------------------
    // 7. Configure output stride and requantizer
    // ------------------------------------------------------------------
    gemmini_config_st(OUT_COLS * sizeof(out_t));
    gemmini_mxquant_config_mvout((uint64_t)scale_factors,
                                 tiles_I, tiles_J, tiles_K,
                                 0, 0, 1);

    // ------------------------------------------------------------------
    // 8. Fused weight-stationary hardware loop
    // ------------------------------------------------------------------
    const int b_base = BANK_NUM * BANK_ROWS - tiles_K * tiles_J * DIM;
    gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K,
                         0, 0, 0,
                         0,                    // a_base
                         BANK_NUM * BANK_ROWS, // B end address
                         0,                    // D (no bias)
                         SPAD_DEST,
                         false, false,
                         false, false, false,
                         NO_ACTIVATION,
                         0, 0,
                         false,
                         0x38);

    // ------------------------------------------------------------------
    // 9. Drain results from shared memory and fence
    // ------------------------------------------------------------------
    gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
    gemmini_fence();
}
```

## Why This Improves Performance

**Decoupled address arithmetic from DMA issuance (Strategy 9):** The original mvin loops compute `i * DIM * MATMUL_K + k * DIM` (a multiply and add) *inside* the loop that issues RoCC instructions. On RISC-V, each multiply takes multiple cycles; the CPU stalls between issuing consecutive mvin commands while computing the next address. By precomputing all pointers into flat arrays first, the DMA-issuance loop becomes a simple array-index load + RoCC issue — no multiply, no stall. The RoCC command queue stays full, maximizing DMA throughput.

**Sequential array access pattern:** The flat `a_dram[]` and `b_dram[]` arrays are accessed sequentially (stride-1), which is cache-friendly on the host side. This contrasts with the stride-`MATMUL_K` jumps computed inline.

**Correctness preserved:** The spad layout (`a_base + (i*tiles_K+k)*DIM` and `b_base + (j*tiles_K+k)*DIM`), scale loading order, mvin-before-compute sequencing, and the `gemmini_loop_ws_spad` / `gemmini_mx_read_smem` / `gemmini_fence` sequence are all identical to the original. Only the address computation is restructured.
