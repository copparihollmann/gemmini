### New Strategy: Remove the Dead `gemmini_config_st` Call

**The `gemmini_config_st` instruction is a wasted RoCC instruction issue.** In the MX path:
- Output flows: `systolic array → mx_smem → (MX_READ_SMEM) → DRAM`
- `gemmini_config_st` configures the legacy `MVOUT` path (funct 4), which writes from the accumulator to DRAM directly
- `MVOUT_SPAD` (funct 23) is documented as a no-op in Spike
- `gemmini_mx_read_smem` uses neither the config-ST stride nor the accumulator MVOUT path — it reads directly from `mx_smem` using its own `smem_off_bf16` and `num_bf16` parameters

**Removing `gemmini_config_st` eliminates one RoCC instruction dispatch**, which on the Spike simulator involves:
1. A full `ROCC_INSTRUCTION_RS1_RS2` macro expansion (register writes + custom instruction issue)
2. Spike's RoCC decode + dispatch overhead
3. A CONFIG_ST state update that is never consumed

Additionally, the `scale_factors` local buffer (2048 bytes) causes a **stack frame allocation** that touches extra cache lines. Since the buffer is never read by the host (only written by hardware), we can reduce it to the minimum required size. For `tiles_I=4, tiles_J=4, tiles_K=4`, the hardware only needs `tiles_I * tiles_J = 16` scale output slots. However, since the hardware writes to this address and the host never reads it, passing any writable aligned address (even a small one) is sufficient for correctness.

### Implementation Plan

1. **Remove `gemmini_config_st`** entirely — it configures the legacy MVOUT path which is not used in the MX `gemmini_mx_read_smem` drain path.

2. **Shrink `scale_factors`** from `uint32_t[512]` (2048 bytes) to `uint32_t[tiles_I * tiles_J]` = `uint32_t[16]` (64 bytes), reducing stack pressure and improving cache behavior. The hardware writes `tiles_I * tiles_J` output scale codes (one per output tile), so 16 entries is exactly sufficient.

**Two compounding inefficiencies are present:**

1. **Repeated multiply-add pointer arithmetic**: Every inner loop iteration recomputes `i * DIM * MATMUL_K + k * DIM` (A) and `k * DIM * MATMUL_N + j * DIM` (B) from scratch — two multiplications and two additions per mvin call, across 4×4 + 4×4 = 32 total iterations.

2. **One DMA command per tile**: With `tiles_K = 4` and `tiles_J = 4`, the B loop issues 16 individual `gemmini_extended_mvin` calls. With `MAX_BLOCK_LEN = 4`, consecutive tiles in the same row of the k-loop (varying j) can be batched into a single `gemmini_block_mvin` command, reducing DMA command count by up to 4×.

## Strategy: Hoist Pointer Arithmetic + Use `gemmini_block_mvin`

**For A tiles**: The inner loop over k iterates `tiles_K = 4` times. For a fixed `i`, the DRAM addresses `A_in + i*DIM*MATMUL_K + k*DIM` are separated by `DIM` bytes (contiguous in k), and the scratchpad addresses `a_base + (i*tiles_K + k)*DIM` are also contiguous. Since `tiles_K = 4 = MAX_BLOCK_LEN`, the entire inner k-loop for a given `i` collapses into a **single** `gemmini_block_mvin(dram_ptr, sp_addr, tiles_K)` call, reducing 16 mvin commands to 4 (one per i-tile).

**For B tiles**: The inner loop over k for a fixed j is **not** contiguous in DRAM (stride is `MATMUL_N` between k-rows). However, the j-dimension for a fixed k **is** contiguous: `B_in + k*DIM*MATMUL_N + j*DIM` increments by `DIM` as j increases. The scratchpad slots `b_base + (k*tiles_J + j)*DIM` are also contiguous in j. So we swap the loop order to outer-k, inner-j, and batch the j-loop with `gemmini_block_mvin(..., tiles_J)` — reducing 16 mvin commands to 4 (one per k-tile).

**Pointer hoisting**: The base address for row `i` of A is `A_in + i*DIM*MATMUL_K`, computed once before the k-loop. For B, the base for row `k` is `B_in + k*DIM*MATMUL_N`, computed once per k iteration. All inner-loop multiplications are eliminated.

This reduces total DMA command count from 32 to 8 (4 for A + 4 for B), and eliminates ~48 multiply operations from the hot setup path.
