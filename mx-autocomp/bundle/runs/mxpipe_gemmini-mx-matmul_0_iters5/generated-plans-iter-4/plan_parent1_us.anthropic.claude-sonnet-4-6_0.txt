## Analysis of the Current Code

The current code issues all A mvins first (using port 0 via `gemmini_block_mvin`), then all B mvins (also using port 0 via `gemmini_block_mvin`/`gemmini_config_ld`). This is sequential: the DMA port is idle while waiting for one batch to complete before the next starts. Both A and B use `gemmini_extended_mvin` (port 0/k_MVIN), so there's no parallelism between A and B data movement.

## Selected Strategy: Strategy 11 — Interleave A mvin (port 0) and B mvin2 (port 1)

### Plan

The key insight is that `gemmini_extended_mvin` (k_MVIN, port 0) and `gemmini_extended_mvin2` (k_MVIN2, port 1) are **independent DMA ports** that can operate simultaneously. Currently, all A tiles are loaded via port 0, then all B tiles are loaded via port 0 — both ports are never active at the same time.

The fix is to interleave A and B mvin instructions tile-by-tile so that for each tile index, we issue one A mvin (port 0) immediately followed by one B mvin2 (port 1), allowing both DMA engines to overlap their transfers.

### Concrete Changes

1. **Use `gemmini_extended_mvin2`** for B tiles instead of `gemmini_extended_mvin` (which is what `gemmini_block_mvin` uses).

2. **Merge the A and B loading loops** into a single interleaved loop. Since there are `tiles_I = 4` A row-groups and `tiles_K = 4` B k-groups, we can iterate over `max(tiles_I, tiles_K)` steps and issue one A mvin + one B mvin2 per step.

3. **Configure both load strides before the interleaved loop**: use `gemmini_extended3_config_ld` (id=0) for A stride and `gemmini_extended3_config_ld` (id=1) for B stride, or more practically, configure LD for port 0 (A), issue A mvin, configure LD for port 1 (B), issue B mvin2 — but since `gemmini_config_ld` only sets port 0's stride while `gemmini_extended3_config_ld(..., id=1)` sets port 1's stride independently, we can set both strides once before the loop.

4. **The loop structure**: iterate `i` from 0 to `tiles_I-1` and `k` from 0 to `tiles_K-1` simultaneously. Since `tiles_I == tiles_K == 4` for 64×64 matrices, a single loop variable suffices. For each iteration index `t`, issue:
   - `gemmini_extended_mvin` for A tile at row `t` (using the pre-configured A stride on port 0)
   - `gemmini_extended_mvin2` for B tile at k-index `t` (using the pre-configured B stride on port 1)

   When `tiles_I != tiles_K`, handle the remainder tiles after the shared loop.

5. **Stride configuration**: Use `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0)` for port 0 (A) and `gemmini_extended3_config_ld(MATMUL_N * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1)` for port 1 (B) — both issued once before the interleaved loop, eliminating the stride re-configuration between the two separate loops.

The rest of the code (`gemmini_mxquant_config_mvout`, `gemmini_loop_ws_spad`, `gemmini_mx_read_smem`, `gemmini_fence`) remains unchanged. This change reduces the effective data-movement latency by approximately 2× since both DMA ports are kept busy simultaneously rather than sequentially.
