## Analysis of the Current Code

Looking at the current code, I need to identify which strategy applies most directly.

The current code already:
- Uses `gemmini_loop_ws_spad` (strategy 5 ✓)
- Hoists `gemmini_extended3_config_ex` outside loops (strategy 4 ✓)
- Uses block_mvin for batching (strategy 1 partially ✓)
- No LUT needed for fp8 (strategy 6 N/A)

**Key inefficiency I see:** The `lut_update_granularity` parameter in `gemmini_mxquant_config_mvout` is set to `1`, which means the requantizer refreshes its output LUT after **every single tile**. This is the maximum possible refresh rate and causes maximum overhead during the requantization post-pass.

**Strategy 6 is not applicable** (no LUT, uselut=0). The most impactful applicable strategy is **strategy 1 (reduce data movement)** — specifically, increasing `lut_update_granularity` to reduce the number of requantizer LUT refresh operations during `gemmini_loop_ws_spad`.

Wait — re-reading more carefully, `lut_update_granularity` G controls how often the **output LUT refreshes during quantization**, not a separate load. Larger G = fewer refreshes = faster.

For an fp8→BF16 output (out_fmt=3, BF16), the largest safe granularity is `tiles_J` (refresh once per output row of tiles, i.e., once per I×K sweep), or even `tiles_I * tiles_J` for the entire output.

## Plan: Increase `lut_update_granularity` (Strategy 1 — Reduce Data Movement)

**The change:** In `gemmini_mxquant_config_mvout`, change `lut_update_granularity` from `1` to `tiles_I * tiles_J * tiles_K` (or the total number of output tiles), so the requantizer LUT refreshes only once for the entire matmul instead of after every tile.

**Rationale:** With `lut_update_granularity=1`, the requantizer re-computes/refreshes its internal LUT state after every output tile, adding overhead proportional to `tiles_I * tiles_J * tiles_K`. Since the output format is fixed BF16 (out_fmt=3) and the scale factors are uniform (loaded once before the loop), the LUT content is invariant across all tiles — refreshing it repeatedly is pure waste. Setting G = `tiles_I * tiles_J` (the total output tiles in one pass) eliminates this redundant work entirely while remaining correct because the LUT content does not change between tiles.

**Specific code change:**

```c
// Before:
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);

// After:
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_I * tiles_J);
```

No other changes are needed. The rest of the kernel (mvin layout, loop_ws_spad arguments, read_smem, fence) remains identical.

**Full rewritten solution:**

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  gemmini_config_ld(MATMUL_K * sizeof(elem_t));
  for (int i = 0; i < tiles_I; i++) {
    elem_t *dram_ptr = ((elem_t*)A_in) + i * DIM * MATMUL_K;
    uint32_t sp_addr = a_base + (i * tiles_K) * DIM;
    gemmini_block_mvin((void*)dram_ptr, sp_addr, tiles_K);
  }

  gemmini_config_ld(MATMUL_N * sizeof(elem_t));
  for (int k = 0; k < tiles_K; k++) {
    elem_t *dram_ptr = ((elem_t*)B_in) + (k * DIM) * MATMUL_N;
    uint32_t sp_addr = b_base + (k * tiles_J) * DIM;
    gemmini_block_mvin((void*)dram_ptr, sp_addr, tiles_J);
  }

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_I * tiles_J);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```
