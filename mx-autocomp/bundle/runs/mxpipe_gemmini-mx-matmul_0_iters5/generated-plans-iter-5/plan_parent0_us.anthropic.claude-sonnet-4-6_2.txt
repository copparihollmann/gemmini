## Analysis of the Current Code

The current code has latency 92. Looking at the structure:

1. `gemmini_extended3_config_ex` — one call
2. `gemmini_mx_load_scales` — two calls (A and B scales loaded once, which is already optimal for this size)
3. MVIN A: 4 `gemmini_block_mvin` calls (one per i-tile, each batching tiles_K=4 k-tiles)
4. MVIN B: 4 `gemmini_block_mvin` calls (one per k-tile, each batching tiles_J=4 j-tiles)
5. `gemmini_config_st` + `gemmini_mxquant_config_mvout`
6. `gemmini_loop_ws_spad`
7. `gemmini_mx_read_smem` + `gemmini_fence`

## New Strategy: Use `gemmini_extended_mvin2` for B Tiles to Overlap A and B DMA Transfers on Separate Ports

The key insight is that A tile loads (port 1, `gemmini_extended_mvin`) and B tile loads (port 2, `gemmini_extended_mvin2`) are **separate DMA channels** that can operate concurrently. In the current code, all A mvins complete before any B mvin begins — they are serialized. By interleaving A and B mvin commands (issuing A loads via `mvin` and B loads via `mvin2`), the hardware can overlap their transfer latencies, effectively halving the total mvin time.

Additionally, the current B tile DRAM layout (for fixed j, tiles across k are *not* contiguous — `b_base + (j*tiles_K + k)*DIM` is indexed j-outer, k-inner in the reference, but the code loops k-outer, j-inner placing j-contiguous tiles per k) means `gemmini_block_mvin` correctly batches j-tiles per k-row. However, `gemmini_block_mvin` uses `mvin` (port 1), not `mvin2` (port 2). Switching B to use `mvin2` frees port 1 exclusively for A loads, enabling true concurrent DMA.

The strategy: **interleave the A and B mvin loops** — for each i/k pair, issue an A tile load via `gemmini_extended_mvin`, and for each k, issue a B tile load via `gemmini_extended_mvin2`. Since `mvin` and `mvin2` are independent ports, the hardware issues both DMA requests and can transfer them in parallel.

For this 64×64×64 problem (tiles_I=4, tiles_J=4, tiles_K=4), we can fuse the loops: iterate k from 0 to tiles_K-1, and within each k, issue all i-row A tiles via `mvin` and the full j-row B block via `mvin2`. This maximally overlaps A and B transfers.

Note: `gemmini_config_ld` configures the stride for `mvin` (port 0/1). For `mvin2` we need `gemmini_extended3_config_ld` with `id=1` to configure port 2's stride separately, since both strides happen to be the same (64 bytes = MATMUL_K = MATMUL_N), so a single config suffices for both ports.

## Implementation

```c
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include "include/gemmini_testutils.h"
#include "include/matmul_fp8_64x64.h"

void solution(void) {
    // Tile counts
    const int tiles_I = MATMUL_M / DIM;  // 4
    const int tiles_J = MATMUL_N / DIM;  // 4
    const int tiles_K = MATMUL_K / DIM;  // 4

    // Scratchpad layout
    const uint32_t a_base    = 0;
    const uint32_t b_base    = BANK_NUM * BANK_ROWS - tiles_K * tiles_J * DIM;
    const uint32_t SPAD_DEST = 0;

    // -----------------------------------------------------------------------
    // 1. Configure execution (fp8 e4m3 inputs, BF16 output, weight-stationary)
    // -----------------------------------------------------------------------
    gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
        /*C_stride*/1, /*A_stride*/1,
        /*A_transpose*/0, /*B_transpose*/0,
        /*set_only_strides*/false,
        /*act_mx_fmt*/0, /*wgt_mx_fmt*/0, /*out_mx_fmt*/3, /*uselut*/0);

    // -----------------------------------------------------------------------
    // 2. Load scale factors (A: sel=0, B: sel=1)
    // -----------------------------------------------------------------------
    gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
    gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

    // -----------------------------------------------------------------------
    // 3. Configure stride for mvin port 0 (A tiles, stride = MATMUL_K bytes)
    //    and mvin port 1 (B tiles, same stride = MATMUL_N bytes = MATMUL_K).
    //    Both strides are identical (64 bytes), so configure both ports once.
    // -----------------------------------------------------------------------
    // Configure port 0 (mvin) stride for A
    gemmini_config_ld(MATMUL_K * sizeof(elem_t));
    // Configure port 1 (mvin2) stride for B — same stride value
    gemmini_extended3_config_ld(MATMUL_N * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);

    // -----------------------------------------------------------------------
    // 4. Interleaved MVIN A (port 0) and B (port 1):
    //    Outer loop over k-tiles. For each k:
    //      - Issue all i-row A tiles via mvin (port 0): tiles_I commands
    //      - Issue all j-col B tiles via mvin2 (port 1): 1 block command
    //    This allows the hardware to overlap A and B DMA transfers.
    //
    //    A tile (i,k): DRAM = A_ptr + i*DIM*MATMUL_K + k*DIM
    //                  SPAD = a_base + (i*tiles_K + k)*DIM
    //
    //    B tile (k, all j): DRAM = B_ptr + k*DIM*MATMUL_N  (j-tiles contiguous)
    //                       SPAD = b_base + k*tiles_J*DIM
    //    tiles_J=4 == MAX_BLOCK_LEN → single block covers all j-tiles per k.
    // -----------------------------------------------------------------------
    {
        const elem_t *A_ptr = (const elem_t *)A_in;
        const elem_t *B_ptr = (const elem_t *)B_in;

        for (int k = 0; k < tiles_K; k++) {
            // Issue A tile loads for all i-rows at this k via port 0 (mvin)
            for (int i = 0; i < tiles_I; i++) {
                const void *a_dram = (const void *)(A_ptr + (i * DIM) * MATMUL_K + k * DIM);
                uint32_t    a_sp   = a_base + (i * tiles_K + k) * DIM;
                gemmini_extended_mvin(a_dram, a_sp, DIM, DIM);
            }
            // Issue B tile load for all j-cols at this k via port 1 (mvin2)
            // tiles_J=4 contiguous j-tiles fit in one block mvin2 command
            const void *b_dram = (const void *)(B_ptr + (k * DIM) * MATMUL_N);
            uint32_t    b_sp   = b_base + k * tiles_J * DIM;
            // Issue tiles_J DIM-wide tiles as a single wide mvin2
            gemmini_extended_mvin2(b_dram, b_sp, tiles_J * DIM, DIM);
        }
    }

    // -----------------------------------------------------------------------
    // 5. Configure output store and requantizer
    // -----------------------------------------------------------------------
    gemmini_config_st(OUT_COLS * sizeof(out_t));
    gemmini_mxquant_config_mvout((uint64_t)scale_factors,
        tiles_I, tiles_J, tiles_K,
        /*scale_act_sel*/0, /*scale_w_sel*/0,
        /*lut_update_granularity*/1);

    // -----------------------------------------------------------------------
    // 6. Execute fused weight-stationary tiled matmul
    // -----------------------------------------------------------------------
    gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0,
        a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
        false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);

    // -----------------------------------------------------------------------
    // 7. Drain BF16 results from shared memory to DRAM, then fence
    // -----------------------------------------------------------------------
    gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
    gemmini_fence();
}
```

## Why This Improves Performance

**The core improvement** is splitting A and B loads onto separate DMA ports (`mvin` vs `mvin2`) and interleaving them per k-iteration:

1. **Concurrent DMA**: Port 0 (`mvin`) handles A tiles and Port 1 (`mvin2`) handles B tiles independently. When issued in close succession, the hardware queues both DMA requests and transfers them in parallel, overlapping memory bandwidth for A and B simultaneously rather than sequentially.

2. **Better instruction interleaving**: By looping over k and issuing A mvins followed immediately by the B mvin2 for the same k, the hardware sees a pattern of alternating port-0 and port-1 requests. This fills both DMA queues early, maximizing sustained bandwidth.

3. **Reduced total transfer latency**: Previously, all 4 A block-mvins completed before the 4 B block-mvins started. With interleaving, after the first k-iteration's A+B commands are issued, both transfers proceed concurrently, effectively hiding B transfer latency behind A transfer latency (and vice versa).

4. **Same scratchpad layout and correctness**: The tile placement (`a_base`, `b_base`, indexing) is unchanged, preserving all correctness constraints. The `gemmini_extended_mvin2` call with `cols=tiles_J*DIM=64, rows=DIM` correctly loads one row-group of DIM rows spanning all j-tiles, equivalent to the prior `gemmini_block_mvin` but on port 1.
