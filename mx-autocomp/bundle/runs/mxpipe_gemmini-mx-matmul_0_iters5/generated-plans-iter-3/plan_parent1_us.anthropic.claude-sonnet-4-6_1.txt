## Analysis

Looking at the current code, the MVIN operations for A and B tiles are sequential:
1. First, all A tiles are loaded (4 block_mvin commands, one per i-tile)
2. Then, all B tiles are loaded (4 block_mvin commands, one per k-tile)

These two phases are completely independent — A and B tiles go to different scratchpad regions and neither depends on the other. The hardware provides three independent mvin ports (`k_MVIN`, `k_MVIN2`, `k_MVIN3`) that can issue overlapping DMA transfers. Currently, only `k_MVIN` (via `gemmini_extended_mvin` / `gemmini_block_mvin`) is used for both A and B, serializing them.

## Selected Strategy

**Strategy 8: Use `mvin2`/`mvin3` ports to parallelize A and B tile loads into scratchpad simultaneously.**

## Plan

The key insight is that `gemmini_config_ld` configures the stride for port 0 (`k_MVIN`), but `gemmini_extended_mvin2` uses port 1 and `gemmini_extended_mvin3` uses port 2. Each port can be configured independently using `gemmini_extended3_config_ld` with the `id` parameter (0, 1, 2 for ports 0, 1, 2 respectively).

### Concrete Changes

1. **Configure port 0 (id=0) for A tiles** with stride `MATMUL_K * sizeof(elem_t)` and **configure port 1 (id=1) for B tiles** with stride `MATMUL_N * sizeof(elem_t)` — both configurations issued upfront before any mvin.

2. **Interleave A and B mvin commands**: Instead of loading all A tiles first then all B tiles, issue an A tile load (`gemmini_block_mvin` on port 0) followed immediately by a B tile load (`gemmini_extended_mvin2` on port 1) within the same loop iteration. Since `tiles_I == tiles_K == 4`, we can pair them: for iteration `t = 0..3`, issue A tile for `i=t` (all k) on port 0 and B tile for `k=t` (all j) on port 1.

3. The loop structure becomes a single loop over `t = 0..tiles_I` (= `tiles_K` = 4), issuing one `gemmini_block_mvin` (port 0, A tiles for row-group `t`) and one `gemmini_extended_mvin2` (port 1, B tiles for k-group `t`) per iteration. The hardware can pipeline these two DMA streams concurrently.

4. Apply `#pragma GCC unroll 4` to eliminate loop overhead since the count is a compile-time constant (this combines strategy 9 opportunistically, but the core change is port parallelism).

This reduces the effective mvin latency from ~8 serialized DMA commands to ~4 overlapping pairs, potentially halving the data-movement phase before compute begins.

### Correctness Verification
- A tiles still land at `a_base + (i*tiles_K + k)*DIM` — block_mvin with `tiles_K=4` fills all k slots for a given i ✓  
- B tiles still land at `b_base + (k*tiles_J + 0)*DIM` — block_mvin2 with `tiles_J=4` fills all j slots for a given k ✓  
- Port 1 (mvin2) uses `k_MVIN2` funct code, which is independent of port 0; the stride for port 1 is set via `gemmini_extended3_config_ld(..., id=1)` ✓  
- The programming model order is preserved: config_ex → load_scales → mvin (both ports) → mxquant_config_mvout → loop_ws_spad → read_smem → fence ✓
