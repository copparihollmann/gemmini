## Analysis of the Current Code

The baseline code processes only **half the M dimension** (`ti = MATMUL_M/DIM/2 = 4`) and **half the N dimension** (`tj = MATMUL_N/DIM/2 = 4`), meaning it only computes a quarter of the full output matrix in a single pass. The scratchpad utilization report confirms "0KB out of 256KB" — the tile sizes are far too small relative to the available scratchpad capacity.

Let me check the scratchpad constraints for the full matrix:
- `MATMUL_M = 128`, `MATMUL_N = 128`, `MATMUL_K = 256`, `DIM = 16`
- Full tiles: `tiles_I = 8`, `tiles_J = 8`, `tiles_K = 16`
- A footprint: `tiles_I * tiles_K * DIM = 8 * 16 * 16 = 2048` rows
- B footprint: `tiles_J * tiles_K * DIM = 8 * 16 * 16 = 2048` rows
- Total: `4096` rows ≤ `8192` ✓
- C accumulator: `tiles_I * tiles_J * DIM = 8 * 8 * 16 = 1024` rows — **exceeds** 256 rows ✗

So the full I×J cannot fit in the accumulator. But the MX path uses `gemmini_loop_ws_spad` which outputs to `mx_smem`, not the accumulator. The accumulator constraint doesn't apply here. The smem constraint is what matters, and the hardware handles tiling internally.

## Selected Strategy: **Strategy 3 — Try New Parameter Values**

Specifically: increase `ti` and `tj` to use the **full** `tiles_I` and `tiles_J` (all 8×8 output tiles) in a single `gemmini_loop_ws_spad` call, eliminating the artificial halving that was causing only a quarter of the matrix to be computed per invocation (and presumably requiring two more calls elsewhere, or simply under-utilizing the hardware).

## Plan

### Problem Identified
The baseline sets `ti = MATMUL_M/DIM/2 = 4` and `tj = MATMUL_N/DIM/2 = 4`, processing only one quarter of the output tiles per loop invocation. This means:
1. Only half the A rows and half the B columns are loaded/computed per pass
2. The B scratchpad base is sized for `tk*tj*DIM = 16*4*16 = 1024` rows of B tiles, leaving huge scratchpad headroom unused
3. The single `gemmini_loop_ws_spad` call does 4× less work than the hardware can handle in one shot

### Fix
Change `ti = MATMUL_M/DIM` (full 8 I-tiles) and `tj = MATMUL_N/DIM` (full 8 J-tiles), and adjust `bb`, mvin loops, and `gemmini_mxquant_config_mvout` bounds accordingly.

**Scratchpad check with full tiles:**
- A: `ti * tk * DIM = 8 * 16 * 16 = 2048` rows
- B: `tj * tk * DIM = 8 * 16 * 16 = 2048` rows  
- Total: `4096 ≤ 8192` ✓
- `bb = BANK_NUM*BANK_ROWS - tk*tj*DIM = 8192 - 16*8*16 = 8192 - 2048 = 6144` — no overlap with A (A uses rows 0–2047) ✓

The A mvin loop must cover all `ti=8` I-tiles. The B mvin loop must cover all `tj=8` J-tiles. The `gemmini_mxquant_config_mvout` `i_bound` and `j_bound` parameters must be updated to `ti=8` and `tj=8`. The `gemmini_mx_read_smem` call already uses `MATMUL_M * MATMUL_N` which is the full output, so no change there.

This change eliminates the artificial loop splitting and processes the entire 128×128×256 matmul in a single hardware loop invocation, maximizing utilization of both the scratchpad and the fused hardware loop engine.

```c
void solution(void) {
  {
    int ti = MATMUL_M / DIM, tj = MATMUL_N / DIM, tk = MATMUL_K / DIM;
    uint32_t ab = 0;
    uint32_t bb = BANK_NUM * BANK_ROWS - tk * tj * DIM;
    int SDST = 128;
    gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 1, 1, 3, 1);
    gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
    gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);
    gemmini_mx_load_lut((uint64_t)B_lut_p, 1, 0);
    gemmini_mx_load_lut((uint64_t)A_lut_p, 1, 1);
    gemmini_config_ld(MATMUL_K * sizeof(elem_t));
    for (int i = 0; i < ti; i++)
      for (int k = 0; k < tk; k++)
        gemmini_extended_mvin((void*)(((elem_t*)A_in_hw) + i*DIM*MATMUL_K + k*DIM), ab + (i*tk + k)*DIM, DIM, DIM);
    gemmini_config_ld(MATMUL_N * sizeof(elem_t) / 2);
    for (int k = 0; k < tk; k++)
      for (int j = 0; j < tj; j++)
        gemmini_extended_mvin((void*)(((elem_t*)B_in) + k*DIM*(MATMUL_N/2) + j*DIM), bb + (k*tj + j)*DIM, DIM, DIM);
    gemmini_config_st(OUT_COLS * sizeof(out_t));
    gemmini_mxquant_config_mvout((uint64_t)scale_factors, ti, tj, tk, 0, 0, 9);
    gemmini_loop_ws_spad(ti, tj, tk, 0, 0, 0, ab, BANK_NUM * BANK_ROWS, 0, SDST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
    gemmini_mx_read_smem(&C_hw[0][0], SDST * 16, MATMUL_M * MATMUL_N);
    gemmini_fence();
  }
}
```
