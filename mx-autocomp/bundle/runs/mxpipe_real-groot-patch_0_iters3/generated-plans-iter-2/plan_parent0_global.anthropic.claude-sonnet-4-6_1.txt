## Analysis of the Current Code

The current code issues `gemmini_extended3_config_ex`, `gemmini_config_ld` (for A stride), and `gemmini_config_ld` (for B stride) **inside the outer `i0`/`j0` loop** on every iteration. These configurations are completely invariant across all iterations:

- `gemmini_extended3_config_ex`: dataflow, MX format fields, strides — never change
- `gemmini_config_ld(MATMUL_K * sizeof(elem_t))`: A's DRAM row stride is always `MATMUL_K` bytes
- `gemmini_config_ld(MATMUL_N * sizeof(elem_t))`: B's DRAM row stride is always `MATMUL_N` bytes

Additionally, `gemmini_flush(0)` is called every loop iteration, which is unnecessary after the first call.

## Selected Strategy

**Strategy 3: Hoist `gemmini_extended3_config_ex` and both `gemmini_config_ld` calls (for A and B strides) outside all loops since format, dataflow, and strides are invariant for the entire kernel invocation.**

## Plan

1. **Move `gemmini_flush(0)` to before the outer loop** — flush once at the start, not once per block pair.

2. **Move `gemmini_extended3_config_ex(...)` to before the outer `i0`/`j0` loop** — the dataflow (WEIGHT_STATIONARY), all MX format fields (act=0, wgt=0, out=3), strides (A_stride=1, C_stride=1), transposes (both false), uselut=0, and ACC_SCALE_IDENTITY never change across any block. This single call currently pays instruction dispatch cost on every `(i0, j0)` pair.

3. **Hoist the first `gemmini_config_ld(MATMUL_K * sizeof(elem_t))`** (the A-tile stride configuration) to before the outer loop. The A matrix DRAM row stride is always `MATMUL_K` bytes regardless of which block is being processed.

4. **Between A mvin and B mvin, issue `gemmini_config_ld(MATMUL_N * sizeof(elem_t))`** only once before the loop, and inside the loop body only the B mvin loop runs (no re-issue of config_ld for B). However, since A and B use different strides and the config is shared, the A config must be re-issued before A mvins and B config before B mvins **within** each iteration — BUT the stride values themselves are constant, so we can hoist them as: issue `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` once before the loop for A, and add `gemmini_config_ld(MATMUL_N * sizeof(elem_t))` once before the B mvin loop at the top of the kernel (outside `i0`/`j0`). Since the loop body alternates between A-mvin (needs K-stride) and B-mvin (needs N-stride), we still need to switch strides inside the loop body — but the config_ld instructions themselves still need to appear in the right order relative to the mvins. The key insight is: both stride values are loop-invariant constants, so the pair of `gemmini_config_ld` calls must remain in sequence before their respective mvin groups inside the loop body, **but `gemmini_extended3_config_ex` and `gemmini_flush` can be fully hoisted out**.

In summary, the concrete changes are:

- Remove `gemmini_flush(0)` from inside the loop; place it once before the `i0` loop.
- Remove `gemmini_extended3_config_ex(...)` from inside the loop; place it once before the `i0` loop (after the flush).
- Keep both `gemmini_config_ld` calls inside the loop body in their existing positions (they must precede their respective mvin groups and alternate between K-stride and N-stride), but note they are now the only remaining per-iteration configuration overhead — this is unavoidable since A and B need different strides within the same loop iteration.

This eliminates one `gemmini_extended3_config_ex` dispatch and one `gemmini_flush` per `(i0, j0)` block pair across `BLOCKS_M × BLOCKS_N` iterations, reducing total instruction overhead proportionally.
