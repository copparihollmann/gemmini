## Analysis

Looking at the current code, I can identify the key inefficiency targeted by **strategy 2: reuse loaded B (weight) tiles across multiple I-tile iterations without re-mvin**.

Currently, the loop structure is:
```
for i0 in BLOCKS_M:
  for j0 in BLOCKS_N:
    mvin A tiles for (i0, all k)
    mvin B tiles for (all k, j0)
    compute
    readout
```

For each `(i0, j0)` pair, B tiles are loaded fresh. But if we restructure to loop `j0` in the outer loop and `i0` in the inner loop, the B tiles for a given `j0` can be loaded **once** and reused across all `i0` iterations. This is classic weight-stationary reuse.

## Plan

**Swap the loop order so `j0` is outer and `i0` is inner.** For each `j0`:

1. Load B tiles for that `j0` block **once** (outside the `i0` loop) into the fixed high-address scratchpad region (`b_base = BANK_NUM*BANK_ROWS - tiles_K*tiles*DIM`, where `tiles = BLK/DIM`).

2. Inside the `i0` loop, only re-load A tiles (which change per `i0`) and re-load A/B scale factors (which differ per `(i0, j0)` block).

3. Keep `gemmini_flush(0)` and `gemmini_extended3_config_ex` outside both loops (they are loop-invariant — format fields, dataflow, and strides don't change).

4. Also hoist `gemmini_config_ld` for B outside the `i0` loop (it only needs to be issued once per `j0` since the B stride is constant), and only re-issue `gemmini_config_ld` for A inside the `i0` loop.

**Concrete changes:**

- Move `gemmini_flush(0)` and `gemmini_extended3_config_ex(...)` before the outer `j0` loop.
- Make `j0` the outer loop.
- Before the `i0` loop (but inside `j0`): compute `b_base`, issue `gemmini_config_ld(MATMUL_N * sizeof(elem_t))`, and mvin all B tiles for this `j0`.
- Inside the `i0` loop: copy A/B scales, call `gemmini_mx_load_scales` for both A and B (scales differ per block), issue `gemmini_config_ld(MATMUL_K * sizeof(elem_t))`, mvin A tiles, then configure mvout, run `gemmini_loop_ws_spad`, readout, and fence.

**Scratchpad capacity check:** `tiles = BLK/DIM`, `tiles_K = MATMUL_K/DIM`. With BLK=64, DIM=16 → `tiles=4`; MATMUL_K=512, DIM=16 → `tiles_K=32`. A tiles: `tiles_I * tiles_K * DIM = 4*32*16 = 2048` rows. B tiles: `tiles_J * tiles_K * DIM = 4*32*16 = 2048` rows. Total = 4096 rows ≤ 8192. ✓ B reuse across `i0` iterations (up to `BLOCKS_M = ceil(41/64) = 1`) is valid.

Note: since REAL_M=41 means BLOCKS_M=1, the B-reuse benefit is most pronounced when BLOCKS_M > 1 in general, but the restructuring is still correct and eliminates the redundant B mvins when the same `j0` would be paired with multiple `i0` blocks.
