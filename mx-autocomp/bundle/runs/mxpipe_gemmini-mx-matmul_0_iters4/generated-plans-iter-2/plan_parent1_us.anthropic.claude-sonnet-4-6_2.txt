## Analysis of the Current Code

Looking at the original code, I need to identify the key inefficiency to address with a single strategy.

The DRAM strides and pointer arithmetic for B tiles are suspicious:

```c
gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);
// ...
(void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
```

The B matrix is stored as `B_in[MATMUL_K][MATMUL_N]` (K rows × N columns, row-major). So a row of B has width `MATMUL_N` elements, not `MATMUL_K`. The DRAM stride for `gemmini_config_ld` should be `MATMUL_N * sizeof(elem_t)` (the number of bytes to advance by one row in DRAM), but the code sets it to `MATMUL_K * sizeof(elem_t)`.

Similarly, the pointer for B tile `(k, j)` should be:
- Row `k * DIM` of B (each row is `MATMUL_N` wide), plus column offset `j * DIM`
- = `B_in + k * DIM * MATMUL_N + j * DIM`

But the code computes `j * DIM * MATMUL_K + k * DIM`, which swaps the roles of j/k and uses the wrong row width.

**This is Strategy 10**: fix DRAM stride for B tiles to `MATMUL_N * sizeof(elem_t)` and fix the pointer arithmetic.

## Plan

**Strategy: Fix DRAM stride for B tiles to `MATMUL_N * sizeof(elem_t)` and correct the B tile pointer arithmetic (Strategy 10)**

### Changes:

1. **Change port 1 config stride** from `MATMUL_K * sizeof(elem_t)` to `MATMUL_N * sizeof(elem_t)`, so the DMA engine correctly steps by one full B row (N bytes wide) between mvin rows.

2. **Fix the B tile DRAM pointer**: The tile at k-index `k`, j-index `j` starts at row `k * DIM` of B (each row is `MATMUL_N` elements wide), offset by column `j * DIM`:
   - Correct: `((elem_t*)B_in) + k * DIM * MATMUL_N + j * DIM`
   - Wrong (current): `((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM`

3. Keep the loop structure (outer `k`, inner `j`) unchanged, as it already matches the correct `b_base + (j * tiles_K + k) * DIM` scratchpad addressing.
