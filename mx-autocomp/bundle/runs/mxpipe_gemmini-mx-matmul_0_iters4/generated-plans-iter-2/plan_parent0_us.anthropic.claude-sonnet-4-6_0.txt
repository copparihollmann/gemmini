## Analysis

Looking at the original code, I need to identify the key inefficiency to target with a single strategy.

The original code uses `lut_update_granularity = 1` in `gemmini_mxquant_config_mvout`:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```

However, `uselut = 0` in `gemmini_extended3_config_ex`, so LUTs are not being used here. The granularity parameter controls how often the requantizer refreshes its LUT during the hardware loop — but with no LUT in use, there's still overhead from the granularity setting driving unnecessary internal refresh checks.

Looking more carefully at the problem: the `lut_update_granularity` controls refresh frequency during the fused hardware loop. Setting it to `1` means refreshes happen at the finest granularity (every single tile). Setting it to a larger value like `tiles_J` or `tiles_I` reduces this overhead significantly.

**Strategy 12**: Use `lut_update_granularity > 1` in `gemmini_mxquant_config_mvout`.

## Plan

The fix is to change `lut_update_granularity` from `1` to a larger value. Since `uselut=0` (no LUT-based dequantization is used), the output quantization parameters are uniform across all tiles — there is no correctness reason to refresh the LUT at every tile. Setting the granularity to `tiles_J` means the requantizer updates once per row-of-tiles rather than once per individual tile, reducing the per-tile overhead in the hardware loop significantly.

Given `MATMUL_N` and the tile structure, `tiles_J = MATMUL_N / DIM`. Setting `lut_update_granularity = tiles_J` amortizes requantizer LUT refresh across an entire row sweep of J-tiles, which is the maximum sensible granularity along the J dimension without skipping updates across different I rows (which might have different scale factors).

The change is minimal and targeted:

```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_J);
```

This single-line change reduces the number of requantizer LUT refresh events during `gemmini_loop_ws_spad` by a factor of `tiles_J`, lowering the per-tile overhead in the fused hardware loop while preserving bit-exact correctness since no LUT is actually used for format conversion.

void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  gemmini_config_ld(MATMUL_K * sizeof(elem_t));
  for (int i = 0; i < tiles_I; i++)
    gemmini_block_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K),
                       a_base + i * tiles_K * DIM, tiles_K);
  for (int j = 0; j < tiles_J; j++)
    gemmini_block_mvin((void*)(((elem_t*)B_in) + j * DIM * MATMUL_K),
                       b_base + j * tiles_K * DIM, tiles_K);

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_J);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
