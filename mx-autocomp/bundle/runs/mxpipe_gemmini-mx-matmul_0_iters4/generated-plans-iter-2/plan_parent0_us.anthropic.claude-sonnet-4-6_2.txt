## Strategy: Split Large `tiles_K` mvin Calls to Respect `MAX_BLOCK_LEN=4`

### Analysis of the Original Code

The original code uses `gemmini_block_mvin` to load entire rows of A and B tiles in a single call:

```c
gemmini_block_mvin(..., tiles_K);  // tiles_K tiles at once
```

`gemmini_block_mvin` expands to `gemmini_extended_mvin(..., tiles_K * DIM, DIM)` — it passes `tiles_K * DIM` as the `cols` field. However, the hardware DMA has a hard limit of **`MAX_BLOCK_LEN = 4`** consecutive DIM-row tiles per single mvin command (derived from `MAX_BYTES=64`, `elem_t=1 byte`, `DIM=16`: `64/(16×1)=4`).

When `tiles_K > 4`, the single `gemmini_block_mvin` call silently truncates the DMA transfer — only the first `MAX_BLOCK_LEN * DIM = 64` columns are loaded, and the remaining tile data is never written to the scratchpad. The systolic array then computes over garbage/stale data for those K-tiles, producing **silently incorrect results** and causing the accelerator to potentially stall or misbehave.

For the given problem, `MATMUL_K` could be large enough that `tiles_K = MATMUL_K / DIM > 4`, triggering this silent truncation.

### The New Strategy: Guard `gemmini_block_mvin` Against `MAX_BLOCK_LEN=4`

Replace each single `gemmini_block_mvin(..., tiles_K)` call with a loop that issues multiple mvin commands of at most `MAX_BLOCK_LEN=4` tiles each. This corresponds directly to **strategy 9** from the list.

### How It Improves Performance

- **Correctness is restored**: All K-dimension tiles are actually loaded into the scratchpad. Without this fix, partial loads mean the matmul computes wrong results, and any downstream comparison would fail — the kernel cannot be considered "fast" if it produces wrong answers.
- **Performance**: Once all data is correctly present in the scratchpad, the systolic array utilizes all K-accumulation tiles, achieving full arithmetic intensity. Previously, truncated loads meant the compute phase was doing partial (wrong) work; now all `tiles_K` reductions execute correctly.
- **No added overhead for small K**: When `tiles_K ≤ 4`, the loop body executes exactly once, identical to the original. The guard is zero-cost in the common small-K case.

### Concrete Code Change

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
      1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  gemmini_config_ld(MATMUL_K * sizeof(elem_t));

  // Load A tiles: split into chunks of at most MAX_BLOCK_LEN=4
  for (int i = 0; i < tiles_I; i++) {
    int k = 0;
    while (k < tiles_K) {
      int chunk = tiles_K - k;
      if (chunk > MAX_BLOCK_LEN) chunk = MAX_BLOCK_LEN;
      gemmini_block_mvin(
          (void*)(((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM),
          a_base + (i * tiles_K + k) * DIM,
          chunk);
      k += chunk;
    }
  }

  // Load B tiles: split into chunks of at most MAX_BLOCK_LEN=4
  for (int j = 0; j < tiles_J; j++) {
    int k = 0;
    while (k < tiles_K) {
      int chunk = tiles_K - k;
      if (chunk > MAX_BLOCK_LEN) chunk = MAX_BLOCK_LEN;
      gemmini_block_mvin(
          (void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + k * DIM),
          b_base + (j * tiles_K + k) * DIM,
          chunk);
      k += chunk;
    }
  }

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors,
      tiles_I, tiles_J, tiles_K, 0, 0, 1);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0,
      a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
      false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```

### Key Correctness Notes

- The DRAM pointer for each chunk advances by `k * DIM` elements (since `elem_t = uint8_t`, stride is `k * DIM` bytes), correctly offsetting into the row-major A and B arrays.
- The scratchpad address for each chunk advances by `chunk * DIM` rows, matching the tile layout formula `a_base + (i*tiles_K + k)*DIM` and `b_base + (j*tiles_K + k)*DIM`.
- The `b_base` placement (`BANK_NUM*BANK_ROWS - tiles_K*tiles_J*DIM`) is unchanged, preserving the top-of-scratchpad B layout and guaranteeing no overlap with A tiles.
- All other steps (scale loading, config, loop, read_smem, fence) remain in the mandated ordering.
