### Problem in the Original Code

The original code:
1. Issues all A mvins via `gemmini_block_mvin` (uses `k_MVIN` port)
2. Then issues all B mvins via `gemmini_block_mvin` (also uses `k_MVIN` port)

Both sets use the same DMA port (`k_MVIN`), so they execute sequentially. The B tile loads cannot begin until all A tile loads finish.

### How to Fix It

The hardware has two independent DMA ports:
- `k_MVIN` (via `gemmini_extended_mvin`) — for A tiles
- `k_MVIN2` (via `gemmini_extended_mvin2`) — for B tiles

These ports operate independently. By interleaving A and B mvin instructions — issuing one A-tile mvin immediately followed by one B-tile mvin, then repeating — the hardware can execute both DMA transfers concurrently, effectively halving the data movement time.

### Concrete Changes

1. **Replace `gemmini_block_mvin` calls with `gemmini_extended_mvin` (A) and `gemmini_extended_mvin2` (B)** — this assigns each to its own independent DMA port.

2. **Separate the `gemmini_config_ld` for A and B** — A and B have different DRAM strides (`MATMUL_K` bytes for A vs `MATMUL_K` bytes for B, but they need separate config since `gemmini_config_ld` uses id=0 for mvin and id=1 for mvin2). 3. **Interleave the A and B tile loads** in a single loop that iterates over all tiles, issuing one A-mvin then one B-mvin per iteration so both DMA engines stay busy simultaneously.

4. **Fix the B-tile scratchpad indexing** to match the required layout: `b_base + (j*tiles_K + k)*DIM` (per strategy 11 / rule 12).
