Looking at the baseline code, the B matrix is loaded with nested loops:

```c
for (int j = 0; j < tiles_J; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(..., b_base + (j * tiles_K + k) * DIM, DIM, DIM);
```

For a 64×64×64 matrix with DIM=16: `tiles_I=4`, `tiles_J=4`, `tiles_K=4`. Each mvin issues a single 16-row DMA command. For B, that's 4×4=16 mvin commands, each loading DIM=16 consecutive rows — but each issued as a separate command.

## Selected Strategy: Strategy 12 — Use `gemmini_block_mvin` to coalesce multiple contiguous row tiles

## Plan

**Observation:** When loading B tiles, the inner loop iterates over `k` from 0 to `tiles_K-1`. For a fixed `j`, the B tiles at `b_base + (j*tiles_K + 0)*DIM`, `b_base + (j*tiles_K + 1)*DIM`, ..., `b_base + (j*tiles_K + (tiles_K-1))*DIM` are **contiguous in scratchpad** (consecutive DIM-row blocks). Similarly, their DRAM sources `B_in + j*DIM*MATMUL_K + k*DIM` are contiguous along the K dimension.

**Constraint check:** `MAX_BLOCK_LEN=4` allows up to 4 consecutive DIM-row tiles per single mvin command. Since `tiles_K=4`, all K-tiles for a fixed `j` can be coalesced into a single `gemmini_block_mvin` call with `len=tiles_K=4`.

**Change for B loading:**  
Replace the inner-k loop over individual `gemmini_extended_mvin` calls with a single `gemmini_block_mvin(dram_ptr, spad_addr, tiles_K)` per `j`. This issues one mvin command per `j` row instead of `tiles_K` commands, reducing B mvin command count from `tiles_J * tiles_K = 16` down to `tiles_J = 4`.

**Change for A loading:**  
Similarly, for a fixed `i`, the A tiles at `a_base + (i*tiles_K + k)*DIM` for k=0..tiles_K-1 are contiguous in scratchpad, and the DRAM sources `A_in + i*DIM*MATMUL_K + k*DIM` are also contiguous along K. Replace the inner-k loop with `gemmini_block_mvin(dram_ptr, spad_addr, tiles_K)` per `i`, reducing A mvin commands from `tiles_I * tiles_K = 16` to `tiles_I = 4`.

**Stride check:** `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` sets the DRAM row stride to `MATMUL_K` bytes. For A: the matrix is row-major with `MATMUL_K` columns, so consecutive DIM rows of one tile column are separated by `MATMUL_K` bytes — correct. For B: the matrix is stored with `MATMUL_K` columns and the k-tiles are adjacent in memory along a row — correct.

**`gemmini_block_mvin` definition:** `gemmini_block_mvin(dram_addr, spad_addr, len)` expands to `gemmini_extended_mvin(dram_addr, spad_addr, (len)*DIM, DIM)`, which sets cols=`len*DIM` and rows=`DIM`, transferring `len` contiguous DIM-wide tiles in one command.

**Result:** Total mvin commands drop from 32 to 8, directly reducing instruction-issue overhead and potentially allowing better overlap with compute in the hardware pipeline.
