## Analysis of the Original Code

The original code uses `lut_update_granularity = 1` in `gemmini_mxquant_config_mvout`:

```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```

This means the requantizer LUT refreshes after every single output tile, which incurs maximum refresh overhead during the fused hardware loop execution.

## Selected Strategy: #6 — Increase `lut_update_granularity`

### Why This Applies

The `lut_update_granularity` parameter `G` in `gemmini_mxquant_config_mvout` controls how frequently the output LUT is refreshed during requantization. With `G=1`, the LUT refreshes for every output tile. Since this kernel uses FP8 (`out_mx_fmt=3` → BF16 output, `uselut=0`), there are no LUTs loaded, but the granularity parameter still governs internal requantizer refresh scheduling.

Looking at the reference patterns:
- `matmul_tiled_fp8_64x64.c` and `matmul_tiled_fp8_64x64_requant.c` both use `lut_update_granularity=1`
- `matmul_ws_mx_generic.c` uses `QUANT_LUT_UPDATE_GRANULARITY=1` but explicitly notes the LUT-path
- The architecture docs state: "larger G = fewer refreshes = faster"

For a kernel where `uselut=0` and the weight format is invariant across all output tiles, the LUT never actually changes, so the requantizer refresh is pure overhead. Setting `G = tiles_J` means the LUT refreshes once per row of I-tiles (once per J sweep), and setting `G = tiles_I * tiles_J` means it refreshes only once for the entire matmul — the maximum amortization.

### The Plan

Change the `lut_update_granularity` argument in `gemmini_mxquant_config_mvout` from `1` to `tiles_I * tiles_J`. Since `uselut=0` and the output format (`out_mx_fmt=3` = BF16) is fixed and homogeneous across all output tiles, the requantizer LUT content is identical for every tile. Setting `G = tiles_I * tiles_J` eliminates all intermediate refresh overhead, reducing the number of requantizer LUT refresh events from `tiles_I * tiles_J` down to `1` for the entire matmul computation.

No other changes are required. The function signature, memory layout, scratchpad addressing, scale loading, mvin loops, loop_ws_spad arguments, and smem readback all remain identical.

## Rewritten Code

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  gemmini_config_ld(MATMUL_K * sizeof(elem_t));
  for (int i = 0; i < tiles_I; i++)
    gemmini_block_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K),
                       a_base + i * tiles_K * DIM, tiles_K);
  for (int j = 0; j < tiles_J; j++)
    gemmini_block_mvin((void*)(((elem_t*)B_in) + j * DIM * MATMUL_K),
                       b_base + j * tiles_K * DIM, tiles_K);

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_I * tiles_J);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       0, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], 0, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```
