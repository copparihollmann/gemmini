## Analysis of the Original Code

Looking at the original code, I can identify a key inefficiency:

```c
gemmini_config_ld(MATMUL_K * sizeof(elem_t));
for (int i = 0; i < tiles_I; i++)
    gemmini_block_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K),
                       a_base + i * tiles_K * DIM, tiles_K);
for (int j = 0; j < tiles_J; j++)
    gemmini_block_mvin((void*)(((elem_t*)B_in) + j * DIM * MATMUL_K),
                       b_base + j * tiles_K * DIM, tiles_K);
```

**Problem:** A tiles are loaded via `mvin` (port 0) and B tiles are loaded sequentially after — both using the same `gemmini_config_ld` stride. This is purely sequential: B loading doesn't begin until all A loading finishes. Moreover, `gemmini_block_mvin` issues one command per `tiles_K` rows, but when `tiles_K > MAX_BLOCK_LEN=4`, it silently loads too many rows in one command (hardware DMA block-length violation).

## Strategy: Use `mvin2` Port to Parallelize A and B Loads + Split Oversized Blocks

**Selected Strategy: Use `mvin2`/`mvin3` ports to parallelize A and B tile loads simultaneously (strategy 5), combined with splitting oversized `gemmini_block_mvin` calls into chunks of ≤ MAX_BLOCK_LEN=4 tiles (strategy 7).**

### How This Improves Performance

For this problem, `MATMUL_K` determines `tiles_K`. The A matrix has row stride `MATMUL_K * sizeof(elem_t)` and the B matrix also has row stride `MATMUL_K * sizeof(elem_t)`. They share the same stride, but `mvin` and `mvin2` have **independent configuration registers** — each port maintains its own stride setting via separate `CONFIG_LD` commands (id=0 for mvin, id=1 for mvin2).

By interleaving `mvin` (A tiles) and `mvin2` (B tiles) commands:
1. The hardware can pipeline/overlap DMA transfers for A and B simultaneously, since they use different scratchpad regions and different DMA ports.
2. We eliminate the sequential dependency between A-load completion and B-load start.
3. We correctly split any block larger than `MAX_BLOCK_LEN=4` into chunks to avoid DMA corruption.

The key insight: A tiles go to the **bottom** of the scratchpad (`a_base`), B tiles go to the **top** (`b_base`). These are non-overlapping regions, so concurrent DMA into both is safe.

### Implementation Plan

1. Configure port 0 (`mvin`, id=0) with A's stride using `gemmini_extended3_config_ld(stride, MVIN_SCALE_IDENTITY, false, 0)`.
2. Configure port 1 (`mvin2`, id=1) with B's stride using `gemmini_extended3_config_ld(stride, MVIN_SCALE_IDENTITY, false, 1)`.
3. Interleave `gemmini_extended_mvin` and `gemmini_extended_mvin2` calls per tile, chunked at MAX_BLOCK_LEN=4.

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
      1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  // Configure both mvin ports with the same stride (MATMUL_K bytes per row)
  // Port 0 (mvin)  → A tiles
  // Port 1 (mvin2) → B tiles
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0);
  gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);

  // Interleave A and B tile loads across ports 0 and 1 simultaneously.
  // Both loops emit commands without waiting; the hardware DMA engine
  // processes mvin and mvin2 queues in parallel.
  // Chunk size is capped at MAX_BLOCK_LEN=4 to avoid DMA block-length violations.

  const int CHUNK = MAX_BLOCK_LEN; // 4

  // Emit all A tile mvins (port 0) and B tile mvins (port 1) interleaved.
  // We iterate over the larger of tiles_I / tiles_J and issue both when available.
  int max_tiles = (tiles_I > tiles_J) ? tiles_I : tiles_J;

  for (int idx = 0; idx < max_tiles; idx++) {
    // Issue A mvin for tile row `idx` if still in range
    if (idx < tiles_I) {
      elem_t *a_dram = (elem_t*)A_in + idx * DIM * MATMUL_K;
      uint32_t a_sp  = a_base + idx * tiles_K * DIM;
      // Split into chunks of at most CHUNK tiles along K
      for (int k = 0; k < tiles_K; k += CHUNK) {
        int blk = (tiles_K - k < CHUNK) ? (tiles_K - k) : CHUNK;
        gemmini_extended_mvin(
            (void*)(a_dram + k * DIM),
            a_sp + k * DIM,
            blk * DIM, DIM);
      }
    }
    // Issue B mvin2 for tile col `idx` if still in range
    if (idx < tiles_J) {
      elem_t *b_dram = (elem_t*)B_in + idx * DIM * MATMUL_K;
      uint32_t b_sp  = b_base + idx * tiles_K * DIM;
      for (int k = 0; k < tiles_K; k += CHUNK) {
        int blk = (tiles_K - k < CHUNK) ? (tiles_K - k) : CHUNK;
        gemmini_extended_mvin2(
            (void*)(b_dram + k * DIM),
            b_sp + k * DIM,
            blk * DIM, DIM);
      }
    }
  }

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors,
      tiles_I, tiles_J, tiles_K, 0, 0, 1);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0,
      a_base, BANK_NUM * BANK_ROWS, 0,
      0, false, false, false, false, false,
      NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], 0, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```

### Why This Is Better

- **Parallelism:** By interleaving `mvin` and `mvin2` commands in a single loop, we keep both DMA ports busy simultaneously. The A scratchpad region (rows 0…`a_base+tiles_I*tiles_K*DIM-1`) and B scratchpad region (rows `b_base`…8191) are completely disjoint, so there is no bank conflict between the two streams.
- **Correctness of block sizes:** Each `gemmini_extended_mvin/mvin2` call now moves at most `CHUNK * DIM = 4 * 16 = 64` columns worth of data — exactly `MAX_BLOCK_LEN * DIM` — which respects the hardware's `MAX_BLOCK_LEN=4` DMA limit. The original `gemmini_block_mvin(ptr, sp, tiles_K)` would issue a single command for all `tiles_K` rows, which silently corrupts data when `tiles_K > 4`.
- **No extra fences added:** We rely on the hardware command queue to serialize loads before the `gemmini_loop_ws_spad` compute command naturally, since all commands go through the same in-order issue queue. The single fence at the end (after `gemmini_mx_read_smem`) is preserved as required.
