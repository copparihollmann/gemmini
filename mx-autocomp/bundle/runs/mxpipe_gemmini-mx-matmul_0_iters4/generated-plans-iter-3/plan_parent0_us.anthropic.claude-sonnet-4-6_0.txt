## Analysis of the Original Code

The original code uses `SPAD_DEST = 128` and reads smem with offset `SPAD_DEST * 16 = 2048`. Looking at the code:

```c
int SPAD_DEST = 128;
// ...
gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
```

## Applying Strategy 7: Set `SPAD_DEST = 0`

**Strategy:** Set `SPAD_DEST = 0` and reduce the smem word offset to `0` in `gemmini_mx_read_smem` when no scratchpad/accumulator aliasing conflict exists.

**Analysis of aliasing conflicts:**

- A tiles occupy: `a_base + (i*tiles_K + k)*DIM` starting at 0, up to `tiles_I * tiles_K * DIM` rows
- B tiles occupy: top of scratchpad at `b_base = BANK_NUM*BANK_ROWS - tiles_K*tiles_J*DIM`
- `SPAD_DEST` is the C output destination address in smem — it is in `mx_smem`, **not** in the scratchpad address space

The `SPAD_DEST` parameter in `gemmini_loop_ws_spad` specifies where in `mx_smem` the BF16 results are written. It is not a scratchpad address — it is an offset into the separate `mx_smem` memory. Therefore, there is **no aliasing conflict** between `SPAD_DEST = 0` and the A/B tiles in the scratchpad.

**Plan:**

1. Change `SPAD_DEST` from `128` to `0`
2. Change the `gemmini_mx_read_smem` call to use `SPAD_DEST * 16 = 0` as the smem word offset

This eliminates the address offset arithmetic overhead (`SPAD_DEST * 16 = 2048` word offset) and allows the hardware to write results starting at smem word 0 rather than word 2048, reducing the read-back address computation and potentially improving smem access locality for the drain operation.

The `smem_start_addr` computation in the reference pattern (`((uint64_t *)SMEM) + SPAD_DEST * 2`) also becomes simpler, though in the Spike path this is handled by `gemmini_mx_read_smem` directly.

## Rewritten Code

```c
void solution(void) {
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

  gemmini_config_ld(MATMUL_K * sizeof(elem_t));
  for (int i = 0; i < tiles_I; i++)
    gemmini_block_mvin((void*)(((elem_t*)A_in) + i * DIM * MATMUL_K),
                       a_base + i * tiles_K * DIM, tiles_K);
  for (int j = 0; j < tiles_J; j++)
    gemmini_block_mvin((void*)(((elem_t*)B_in) + j * DIM * MATMUL_K),
                       b_base + j * tiles_K * DIM, tiles_K);

  gemmini_config_st(OUT_COLS * sizeof(out_t));
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
  gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                       0, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
  gemmini_mx_read_smem(&C_hw[0][0], 0, MATMUL_M * MATMUL_N);
  gemmini_fence();
}
```

**Change summary:** `SPAD_DEST` changed from `128` to `0` in `gemmini_loop_ws_spad` (4th argument from end before the transpose flags), and the smem word offset in `gemmini_mx_read_smem` changed from `SPAD_DEST * 16 = 2048` to `0`. All other logic is identical.
