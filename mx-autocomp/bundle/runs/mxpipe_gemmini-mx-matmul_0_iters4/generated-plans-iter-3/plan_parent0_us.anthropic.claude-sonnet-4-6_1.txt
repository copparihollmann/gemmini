## Analysis of the Original Code

The original code loads A tiles using `gemmini_block_mvin` with a loop over `tiles_I`, and B tiles similarly with a loop over `tiles_J`. Let me examine the strides:

- **A tiles**: Each row of A in DRAM is `MATMUL_K` bytes wide. The `gemmini_config_ld` is set to `MATMUL_K * sizeof(elem_t)`. For tile `i`, the DRAM pointer is `A_in + i * DIM * MATMUL_K`, and `tiles_K` consecutive k-tiles are loaded via `gemmini_block_mvin(..., tiles_K)`. This is correct.

- **B tiles**: B is stored as `B_in[MATMUL_K][MATMUL_N]` — each row is `MATMUL_N` bytes wide (not `MATMUL_K`). But the code reuses the same `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` for B's mvin. This is **wrong** — B's DRAM row stride is `MATMUL_N`, not `MATMUL_K`.

## Selected Strategy: Strategy 11

**Reconfigure `gemmini_config_ld` stride separately for A and B tiles when A and B have different DRAM row strides.**

## Plan

The original code calls `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` once and then uses it for both A and B `block_mvin` calls. However:

- A is laid out as `A_in[MATMUL_M][MATMUL_K]` → row stride = `MATMUL_K` bytes ✓
- B is laid out as `B_in[MATMUL_K][MATMUL_N]` → row stride = `MATMUL_N` bytes ✗

The B mvin is using the wrong stride (`MATMUL_K` instead of `MATMUL_N`), which means `gemmini_block_mvin` fetches B rows from incorrect DRAM offsets. The fix is to:

1. Keep `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` before the A mvin loop (correct for A).
2. Add a second `gemmini_config_ld(MATMUL_N * sizeof(elem_t))` before the B mvin loop to set the correct row stride for B.

This is a correctness fix that also eliminates the stride misconfiguration, ensuring the hardware fetches the right B data without needing workarounds or extra copies. The rest of the code (mvin addressing, `gemmini_loop_ws_spad`, etc.) remains unchanged.
