To improve the performance of the FP6 microscaling (MX) matrix multiplication kernel, we will apply **Strategy 1: Reduce data movement** by batching DMA transfer commands using the maximum block length supported by the Gemmini hardware (`MAX_BLOCK_LEN = 4`).

### Inefficiency in Baseline Code
In the baseline implementation, every $16 \times 16$ tile of $A$ and $B$ is loaded from DRAM into the scratchpad via an individual `gemmini_extended_mvin` call. For a tile configuration of `ti = 4`, `tj = 4`, and `tk = 16`, this results in:
- $4 \times 16 = 64$ individual `mvin` calls for matrix $A$.
- $16 \times 4 = 64$ individual `mvin` calls for matrix $B$.

Each instruction issue introduces significant host-side synchronization and RoCC command queue overhead, leading to high latency.

### Optimization Strategy
Since the memory layouts of $A$ and $B$ are row-major and contiguous along the inner dimensions in DRAM, we can group multiple adjacent $16 \times 16$ tiles and load them with a single `mvin` instruction:
1. **For Matrix $A$:** The K-dimension contains `tk = 16` tiles. Since `MAX_BLOCK_LEN = 4`, we can load chunks of 4 contiguous tiles along the K-dimension at once. This reduces the number of `mvin` commands for $A$ from 64 to 16.
2. **For Matrix $B$:** The J-dimension contains `tj = 4` tiles. We can load all 4 tiles along the J-dimension contiguously in a single `mvin` command. This reduces the number of `mvin` commands for $B$ from 64 to 16.

By batching these transfers, we preserve the exact scratchpad memory layout required by the hardware loop while reducing the total number of issued instructions from 128 to 32, significantly improving performance.
