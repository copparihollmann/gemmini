## Analysis

Looking at the current code, the key inefficiency is in the mvin loop structure:

```c
for (int k = 0; k < tiles_K; k++) {
    // A tiles for all i-rows at this k-slice → port 1 (k_MVIN)
    for (int i = 0; i < tiles_I; i++)
        gemmini_extended_mvin(...A..., a_base + (i * tiles_K + k) * DIM, DIM, DIM);
    // B tiles for all j-columns at this k-slice → port 2 (k_MVIN2)
    for (int j = 0; j < tiles_J; j++)
        gemmini_extended_mvin2(...B..., b_base + (j * tiles_K + k) * DIM, DIM, DIM);
}
```

**The B tiles are being loaded once per K-slice**, which is already correct behavior since `gemmini_loop_ws_spad` is a single fused hardware call. However, the im2col loop writes `A_buf` entirely before any DMA begins. **Strategy 13** applies: tile the im2col loop over K-blocks so that each block of `A_buf` rows (for a given k-slice) is written to memory and immediately DMA'd, allowing the CPU im2col work for the next block to overlap with Gemmini DMA for the current block, keeping the written data hot in L1 cache.

## Plan: Strategy 13 — Tile the im2col loop over K to pipeline CPU writes with Gemmini DMA

**Current structure:**
1. Complete ALL of im2col (writes entire `A_buf[PATCHES][K]`) — touches all of A_buf
2. Then start all DMA mvins

**Problem:** The full `A_buf` is large (e.g., 64×64 = 4096 bytes for fp8), and by the time DMA starts for late K-slices, the early-K data may have been evicted from L1. More importantly, the CPU sits idle during DMA and DMA sits idle during im2col — they are fully serialized.

**New structure:** Merge the im2col k-block loop with the mvin k-block loop:

```
for k in 0..tiles_K:
    # CPU: compute im2col for this k-block (c, dy, dx range)
    for i in 0..tiles_I:
        for (c, dy, dx) in k-block:
            A_buf[i*DIM .. (i+1)*DIM][k_col_start .. k_col_end] = ...
    # DMA: immediately mvin A tiles for this k-block (data still hot in L1)
    for i in 0..tiles_I:
        gemmini_extended_mvin(A_buf + ..., a_base + (i*tiles_K+k)*DIM, DIM, DIM)
    # DMA: mvin B tiles for this k-block on port 2 (overlaps next im2col iteration)
    for j in 0..tiles_J:
        gemmini_extended_mvin2(B_in + ..., b_base + (j*tiles_K+k)*DIM, DIM, DIM)
```

Each K-block's A data is DMA'd immediately after being written, while it's still hot in L1/L2 cache. The B mvin on port 2 overlaps with the next iteration's im2col CPU work.

**Concrete changes:**
1. Restructure the im2col nested loops to iterate over `k`-blocks (each k-block corresponds to one `tiles_K` slice: `c*CONV_KSZ*CONV_KSZ + dy*CONV_KSZ + dx` maps to a column range `[k*DIM, (k+1)*DIM)`).
2. Inside each k-block, compute im2col for all `i` patch rows and exactly the columns in that k-block.
3. Immediately follow with `gemmini_extended_mvin` for all `i` tiles of that k-block (port 0).
4. Follow with `gemmini_extended_mvin2` for all `j` tiles of that k-block (port 1), which can overlap with the next iteration's im2col.
5. The rest of the sequence (config_st, mxquant_config_mvout, loop_ws_spad, mx_read_smem, fence) is unchanged.

This requires computing the mapping from flat column index `col = k*DIM + offset` back to `(c, dy, dx)` to know which input pixels to copy in each k-block.

Here is the rewritten code:

```c
void solution(void) {
    // Tile the im2col + mvin together over K-blocks:
    // Each k-block covers DIM columns of A_buf, corresponding to a range of (c, dy, dx).
    // We compute im2col for that k-block and immediately DMA it, keeping data hot in cache.

    // Configure port 0 (mvin, id=0) for A tiles
    gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 0);
    // Configure port 1 (mvin2, id=1) for B tiles
    gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);

    // Process each K-block: im2col then immediate mvin
    for (int k = 0; k < tiles_K; k++) {
        int col_start = k * DIM;
        // Compute im2col for this k-block: columns [col_start, col_start+DIM)
        // col = c * CONV_KSZ * CONV_KSZ + dy * CONV_KSZ + dx
        for (int col = col_start; col < col_start + DIM; col++) {
            int tmp = col;
            int dx = tmp % CONV_KSZ; tmp /= CONV_KSZ;
            int dy = tmp % CONV_KSZ; tmp /= CONV_KSZ;
            int c  = tmp;
            for (int pi = 0; pi < CONV_H / CONV_KSZ; pi++)
                for (int pj = 0; pj < PATCHES_X; pj++)
                    A_buf[pi * PATCHES_X + pj][col] =
                        X_in[c][pi * CONV_KSZ + dy][pj * CONV_KSZ + dx];
        }

        // Immediately DMA the A tiles for this k-block (data still hot in cache)
        for (int i = 0; i < tiles_I; i++)
            gemmini_extended_mvin(
                (void*)(((elem_t*)A_buf) + i * DIM * MATMUL_K + col_start),
                a_base + (i * tiles_K + k) * DIM, DIM, DIM);

        // DMA B tiles for this k-block on port 2 (overlaps with next im2col block)
        for (int j = 0; j < tiles_J; j++)
            gemmini_extended_mvin2(
                (void*)(((elem_t*)B_in) + j * DIM * MATMUL_K + col_start),
                b_base + (j * tiles_K + k) * DIM, DIM, DIM);
    }

    gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);
    gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
    gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);

    gemmini_config_st(OUT_COLS * sizeof(out_t));
    gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
    gemmini_loop_ws_spad(tiles_I, tiles_J, tiles_K, 0, 0, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                         SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
    gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
    gemmini_fence();
}
```
