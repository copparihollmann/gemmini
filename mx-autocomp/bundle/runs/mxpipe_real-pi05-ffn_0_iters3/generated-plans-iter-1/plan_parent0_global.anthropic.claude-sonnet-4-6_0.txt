## Analysis of the Current Code

Looking at the code, I need to identify which strategy applies best.

**Examining the current `gemmini_mxquant_config_mvout` call:**

```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles, tiles, tiles_K, 0, 0, 1);
```

The last argument is `lut_update_granularity = 1`, meaning the output LUT is refreshed **every K-step** during the requantization post-pass. Since this is an FP8 path (`act_mx_fmt=0, wgt_mx_fmt=0`), the output LUT is invariant across the entire K reduction for a given (i,j) output tile — it doesn't change as we accumulate across K. Refreshing it every K-step wastes cycles.

**Strategy 3 directly applies:** raise `lut_update_granularity` so the LUT refreshes once per output (i,j) tile — i.e., set it to `tiles_K` instead of `1`.

## Plan: Apply Strategy 3 — Raise `lut_update_granularity`

### What to change

In the `gemmini_mxquant_config_mvout` call, change the `lut_update_granularity` argument from `1` to `tiles_K`:

**Before:**
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles, tiles, tiles_K, 0, 0, 1);
```

**After:**
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles, tiles, tiles_K, 0, 0, tiles_K);
```

### Rationale

- `tiles_K = MATMUL_K / DIM = 512 / 16 = 32` for this problem.
- With `lut_update_granularity = 1`, the requantizer refreshes the output LUT **32 times** per (i,j) output tile (once per K-step).
- The output LUT encodes the BF16 quantization projection for a given output tile. This projection depends only on the output (i,j) position, not on which K-slice is being accumulated — so the LUT is identical across all `tiles_K` K-steps for a fixed (i,j).
- Setting `lut_update_granularity = tiles_K = 32` tells the hardware to refresh the LUT only **once per (i,j) tile** (every `tiles_K` steps), reducing the number of LUT refreshes by a factor of 32.
- This is semantically equivalent: the same LUT value is used throughout, just reloaded 32× less often.
- The outer loop iterates over `tiles × tiles = (BLK/DIM)² = 16×16 = 256` output tiles per block, and the block loop runs `BLOCKS_M × BLOCKS_N` times. Multiplied out, this saves 31 LUT refresh operations per output tile across the entire computation.
- No change to correctness: the BF16 output requantization result is identical since the LUT content is invariant across K.
