## Analysis of the Current Code

The current code iterates over `(i0, j0)` block pairs. For each pair, it:
1. Flushes Gemmini
2. Loads A and B scales (per-block)
3. MVINs all A tiles for block `i0`
4. MVINs all B tiles for block `j0`
5. Runs `gemmini_loop_ws_spad`
6. Reads results

**Key inefficiency**: For a fixed `j0`, as `i0` iterates through all M-blocks, the B tiles (weight tiles for `j0`) are re-mvin'd from DRAM every single iteration of `i0`. The B tiles don't change across `i0` — only A tiles and output destination change. This means B tiles are loaded `BLOCKS_M` times unnecessarily.

## Selected Strategy: Reuse Loaded B (Weight) Tiles Across Multiple I-tile Iterations

### Plan

**Restructure the loop nest to `(j0, i0)` instead of `(i0, j0)`, and load B tiles only once per `j0` outer iteration.**

Specifically:

1. **Swap loop order**: Make `j0` the outer loop and `i0` the inner loop. This groups all I-block iterations that share the same B column block together.

2. **Hoist B mvin outside the `i0` loop**: Since B tiles for a given `j0` are identical across all `i0` iterations, perform `gemmini_config_ld` for B and all `gemmini_extended_mvin` calls for B tiles **once per `j0`**, before the inner `i0` loop begins.

3. **Move `gemmini_flush` and B-scale loading outside the `i0` loop**: `gemmini_flush(0)` and `gemmini_mx_load_scales` for B can be hoisted to the `j0` scope. A-scales still need to be loaded per `i0` (since they differ per row block), but B-scales are constant for a given `j0`.

4. **Keep A mvin and compute inside `i0`**: A tiles change per `i0`, so `gemmini_config_ld` for A, A mvin, `gemmini_loop_ws_spad`, `gemmini_mx_read_smem`, and `gemmini_fence` remain in the inner `i0` loop. A-scale loading also stays in the inner loop.

5. **Scratchpad layout verification**: With `tiles = BLK/DIM` and `tiles_K = MATMUL_K/DIM`, B occupies `tiles_K * tiles * DIM` rows at the top of the scratchpad, and A occupies `tiles * tiles_K * DIM` rows starting at `a_base = 0`. Total = `2 * tiles * tiles_K * DIM` rows — unchanged from before, so no constraint violations.

6. **Re-issue `gemmini_loop_ws_spad` per `i0`**: The fused loop must be re-issued each `i0` iteration (since `mx_loop_spad_marker` is one-shot and A data/scales change), but B is already in the scratchpad and doesn't need to be reloaded.

This eliminates `BLOCKS_M - 1` redundant B mvin sequences per `j0` block, reducing total DRAM traffic and mvin instruction count by approximately `(BLOCKS_M - 1)/BLOCKS_M * 50%` of the data movement cost (since A and B are equal size per block-pair).
