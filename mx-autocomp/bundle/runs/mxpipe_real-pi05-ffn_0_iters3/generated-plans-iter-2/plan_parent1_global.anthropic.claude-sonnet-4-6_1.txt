## Analysis of the Current Code

The current code has an **outer loop over (i0, j0)**, meaning for each `(i0, j0)` pair:
1. It loads A scales for `i0`'s rows
2. It loads B scales for `j0`'s columns  
3. It mvins **all A tiles** for the current `i0` block
4. It mvins **all B tiles** for the current `j0` block
5. It computes and reads out results

**The critical inefficiency**: For a fixed `j0`, B tiles are re-loaded from DRAM on **every** `i0` iteration. If there are `BLOCKS_M` row blocks, each B tile block is loaded `BLOCKS_M` times total. Since the hardware is weight-stationary and B tiles don't change across row iterations, this is `(BLOCKS_M - 1) × B_mvin_cost` of wasted DMA bandwidth.

## Strategy: Reorder Outer Loop to (j0, i0) — Weight-Stationary B Reuse Across M

This directly applies **strategy 5**: reorder the outer loops to `(j0, i0)` so that B tiles for a fixed `j0` column block are mvin'd **once** and reused across all `i0` row iterations.

### How It Works

**Current order `(i0, j0)`**:
- For `i0=0, j0=0`: mvin B[j0=0], compute
- For `i0=0, j0=1`: mvin B[j0=1], compute
- For `i0=1, j0=0`: mvin B[j0=0] **again**, compute  ← redundant
- For `i0=1, j0=1`: mvin B[j0=1] **again**, compute  ← redundant

**New order `(j0, i0)`**:
- For `j0=0, i0=0`: mvin B[j0=0] **once**, compute
- For `j0=0, i0=1`: **skip B mvin**, reuse B in scratchpad, compute
- For `j0=1, i0=0`: mvin B[j0=1] **once**, compute
- For `j0=1, i0=1`: **skip B mvin**, reuse B in scratchpad, compute

B tiles occupy `tiles_K * tiles_J * DIM` rows at the top of the scratchpad. Since A tiles change per `i0` but B tiles stay fixed for the entire inner `i0` loop, we only reload A scales + A tiles on each `i0` iteration while B scales + B tiles are loaded once per `j0`.

### Constraint Check

The scratchpad must hold all A and B tiles simultaneously:
- A tiles: `tiles_I * tiles_K * DIM` rows = `(BLK/16) * (MATMUL_K/16) * 16` rows
- B tiles: `tiles_J * tiles_K * DIM` rows = `(BLK/16) * (MATMUL_K/16) * 16` rows
- Total must be ≤ 8192 rows

This constraint is identical to the original — the reordering doesn't change scratchpad requirements since we still only hold one (i0, j0) pair's tiles at a time. The B layout at `b_base` is unchanged.

### Code Changes

```c
void solution(void) {
  for (int j0 = 0; j0 < BLOCKS_N; j0++) {           // ← outer loop is now j0
    int ncols = REAL_N - j0 * BLK;
    if (ncols > BLK) ncols = BLK;
    if (ncols <= 0) continue;

    int tiles   = BLK / DIM;
    int tiles_K = MATMUL_K / DIM;
    uint32_t b_base = BANK_NUM * BANK_ROWS - tiles * tiles_K * DIM;

    // --- Load B scales ONCE per j0 ---
    for (int g = 0; g < MATMUL_K / 32; g++)
      memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);

    // --- Mvin B tiles ONCE per j0 ---
    gemmini_config_ld(MATMUL_N * sizeof(elem_t));
    for (int j = 0; j < tiles; j++)
      for (int k = 0; k < tiles_K; k++)
        gemmini_extended_mvin(
          (void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
          b_base + (k * tiles + j) * DIM, DIM, DIM);

    for (int i0 = 0; i0 < BLOCKS_M; i0++) {          // ← inner loop is now i0
      int mrows = REAL_M - i0 * BLK;
      if (mrows > BLK) mrows = BLK;
      if (mrows <= 0) continue;

      int pad_i = BLK - mrows, pad_j = BLK - ncols;
      uint32_t a_base = 0;
      int SPAD_DEST = 128;

      // --- Load A scales per (i0, j0) ---
      for (int g = 0; g < MATMUL_K / 32; g++)
        memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);

      gemmini_flush(0);

      // Step 1: configure
      gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                                   1, 1, 0, 0, false, 0, 0, 3, 0);

      // Step 2: load scales — A changes per i0, B is already correct
      // but gemmini_mx_load_scales must be called for BOTH before compute
      gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);
      gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);

      // Step 4: mvin A tiles (B already in scratchpad from outer j0 load)
      gemmini_config_ld(MATMUL_K * sizeof(elem_t));
      for (int i = 0; i < tiles; i++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin(
            (void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
            a_base + (i * tiles_K + k) * DIM, DIM, DIM);

      // Step 5: configure output
      gemmini_config_st(BLK_OUTC * sizeof(out_t));
      gemmini_mxquant_config_mvout((uint64_t)scale_factors,
                                    tiles, tiles, tiles_K, 0, 0, tiles_K);

      // Step 6: compute
      gemmini_loop_ws_spad(tiles, tiles, tiles_K, pad_i, pad_j, 0,
                            a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
                            false, false, false, false, false,
                            NO_ACTIVATION, 0, 0, false, 0x38);

      // Step 7: drain results
      for (int r = 0; r < mrows; r++)
        gemmini_mx_read_smem(
          &C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
          SPAD_DEST * 16 + r * BLK, ncols);
      gemmini_fence();
    }
    // B tiles remain valid in scratchpad for the entire j0 block;
    // they are naturally overwritten when j0 advances to the next iteration.
  }
}
```

### Why This Reduces Latency

- **B mvin cost saved**: Each B mvin block costs `tiles * tiles_K` DMA commands. In the original `(i0, j0)` order this is paid `BLOCKS_M × BLOCKS_N` times. With `(j0, i0)` order it is paid only `BLOCKS_N` times — a factor of `BLOCKS_M` reduction in B DMA commands.
- **B scale memcpy saved**: The `memcpy` for `B_s` (a CPU-side operation noted in the profiler) similarly drops from `BLOCKS_M × BLOCKS_N` to `BLOCKS_N` iterations.
- **Correctness preserved**: The `gemmini_mx_load_scales` calls for **both** A and B still precede every `gemmini_loop_ws_spad`, satisfying the programming model sequence requirement. B scale data in `B_s` is valid for all `i0` iterations within a given `j0` since `B_s` is only overwritten at the top of the `j0` loop. The scratchpad B tile layout (`b_base`) is identical to the original, so no addressing rules are violated.
