## Analysis of the Current Code

Looking at the current code, I can identify the key inefficiency targeted by **Strategy 4**: `gemmini_flush(0)` is called **inside the double-nested `(i0, j0)` loop**, meaning it executes once per output block tile. For a matrix of size `REAL_M × REAL_N` with block size `BLK`, this is `BLOCKS_M × BLOCKS_N` flush operations total.

`gemmini_flush` resets hardware state and incurs a **full pipeline drain** on every call. This is extremely expensive and completely unnecessary after the first call — the hardware state (format, dataflow, scales) is re-configured at the start of each block iteration anyway via `gemmini_extended3_config_ex` and `gemmini_mx_load_scales`. There is no reason to flush on every iteration.

## Plan: Hoist `gemmini_flush` Outside All Tile Loops

**Specific change:** Move the single call to `gemmini_flush(0)` from inside the `(i0, j0)` double loop to **before** the outermost `i0` loop begins — i.e., call it exactly once at the top of the `solution()` function.

**Why this is safe:** The purpose of `gemmini_flush` is to drain the pipeline and reset stale hardware state before a fresh computation begins. The subsequent calls to `gemmini_extended3_config_ex`, `gemmini_mx_load_scales`, `gemmini_config_ld`, `gemmini_config_st`, and `gemmini_mxquant_config_mvout` at the start of each block iteration already fully re-establish all required hardware configuration. The flush does not need to be repeated — calling it `BLOCKS_M × BLOCKS_N` times instead of once pays the pipeline drain cost unnecessarily on every single block.

**The change:**
- Remove `gemmini_flush(0)` from inside the `(i0, j0)` loop body.
- Add `gemmini_flush(0)` once, before the `for (int i0 = 0; ...)` loop.

This eliminates `(BLOCKS_M × BLOCKS_N - 1)` redundant pipeline drain operations while preserving full semantic correctness — the single flush before the first tile ensures clean hardware state, and the per-tile reconfiguration instructions handle all state setup for each subsequent tile.
