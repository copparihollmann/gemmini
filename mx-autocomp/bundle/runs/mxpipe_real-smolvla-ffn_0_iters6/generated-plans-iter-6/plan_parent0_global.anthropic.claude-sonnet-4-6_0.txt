## Analysis of the Current Code

The current code has a critical inefficiency: **it issues `gemmini_flush(0)` inside the outer block loop**, and more importantly, it **reloads scale factors, reconfigures everything, and re-issues all setup instructions for every (i0, j0) block pair**. The code also does `memcpy` host staging of scale factors into temporary buffers `A_s` and `B_s` for every block.

Looking at the scratchpad utilization report (0KB out of 256KB), the hardware loop `gemmini_loop_ws_spad` handles all tiling internally. The real waste is the **per-block overhead**: for each of `BLOCKS_M × BLOCKS_N` iterations, we pay:
- `gemmini_flush(0)` — full pipeline flush
- `gemmini_extended3_config_ex` — reconfiguration
- 2× `memcpy` for scale staging (host CPU work)
- 2× `gemmini_mx_load_scales` — DRAM loads into scale memory

## Strategy: Eliminate Per-Block Scale Reloads and Flush by Loading Full-Matrix Scales Once and Removing the Flush from the Inner Loop

### Plan

**Core observation:** The scale factors `A_scales_row[GK][REAL_M]` and `B_scales_col[GK][REAL_N]` are indexed as `A_scales_row[g][row]` and `B_scales_col[g][col]`. The current code extracts sub-blocks (`A_s[g][0..BLK-1]` from `A_scales_row[g][i0*BLK..]`) and reloads them every iteration. The hardware's `mxquant_config_mvout` already receives `i_bound`/`j_bound`/`k_bound` tile counts, and the scale DRAM pointer `scale_factors` is used for output quantization — it is separate from the *input* scale factors loaded via `gemmini_mx_load_scales`.

**Key insight:** `gemmini_mx_load_scales` loads scales into `mx_scale_a_mem` and `mx_scale_b_mem` which are fixed-size hardware buffers. The MX matmul loop uses them indexed by tile coordinates. If we load the **full** `A_scales_row` and `B_scales_col` arrays once before the loop, and then call `gemmini_loop_ws_spad` with the correct tile offsets into those scale buffers, we eliminate `BLOCKS_M × BLOCKS_N` scale reload operations.

However, the scale memory has a fixed layout: the hardware indexes it as `scale_a_mem[k_block * tiles_I + i_tile]` for A and `scale_b_mem[k_block * tiles_J + j_tile]` for B. So the full matrix scales in the correct layout can be loaded once.

**Changes:**

1. **Move `gemmini_flush(0)` outside the loop** — flush once before any computation begins. The flush is a full pipeline drain; doing it `BLOCKS_M × BLOCKS_N` times is pure waste.

2. **Move `gemmini_extended3_config_ex` outside the loop** — configuration persists until changed; re-issuing it every block is redundant.

3. **Eliminate `memcpy` host staging and load scales once** — instead of copying sub-blocks into `A_s`/`B_s` and calling `gemmini_mx_load_scales` every iteration, load the complete `A_scales_row` and `B_scales_col` arrays a single time before the outer loop. This removes all `memcpy` calls (identified as dominant cost in the profiling note) and reduces `gemmini_mx_load_scales` from `O(BLOCKS_M × BLOCKS_N)` calls to 2 calls total.

4. **The scale memory layout must match** what the hardware expects for the sub-block being computed. Since each block uses a different sub-region of the full scale arrays, and the hardware indexes into the loaded scale buffer from position 0, we must still load the correct slice per block — but we can restructure to load per-row-block (amortized across the J dimension) rather than per (i0, j0) pair.

**Revised approach — amortize scale loads across the J dimension:**

For a fixed `i0`, all `j0` iterations use the **same** `A_s` (same row-block of A scales). So we can:
- Hoist `gemmini_mx_load_scales` for A **outside the `j0` loop** (load once per `i0`)
- Load B scales **per `j0`** (still needed per column block)
- This reduces A scale loads from `BLOCKS_M × BLOCKS_N` to `BLOCKS_M`

Additionally, eliminate `gemmini_flush` from inside the loop entirely (call once before everything), and eliminate `gemmini_extended3_config_ex` from inside the loop (call once).

Also eliminate the `memcpy` by passing the correct pointer directly into `gemmini_mx_load_scales` using pointer arithmetic into the original arrays with the right stride, avoiding host staging buffers entirely.

## Rewritten Code

```c
void solution(void) {
    int tiles_K = MATMUL_K / DIM;
    int tiles_blk = BLK / DIM;
    uint32_t a_base = 0;
    uint32_t b_base = BANK_NUM * BANK_ROWS - tiles_blk * tiles_K * DIM;
    int SPAD_DEST = 128;

    // Flush and configure ONCE outside all loops
    gemmini_flush(0);
    gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                                1, 1, 0, 0, false, 0, 0, 3, 0);

    // Temporary scale buffers (one per i0, shared across all j0)
    // A_S_BYTES and B_S_BYTES cover one BLK-wide slice
    static uint8_t A_s[MATMUL_K / 32][BLK];
    static uint8_t B_s[MATMUL_K / 32][BLK];

    for (int i0 = 0; i0 < BLOCKS_M; i0++) {
        int mrows_max = REAL_M - i0 * BLK;
        if (mrows_max <= 0) continue;
        int mrows_blk = (mrows_max > BLK) ? BLK : mrows_max;

        // Load A scales ONCE per i0 block (amortized across all j0)
        for (int g = 0; g < MATMUL_K / 32; g++)
            memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);
        gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);

        // Load A tiles ONCE per i0 block (same tiles used for all j0)
        gemmini_config_ld(MATMUL_K * sizeof(elem_t));
        for (int i = 0; i < tiles_blk; i++)
            for (int k = 0; k < tiles_K; k++)
                gemmini_extended_mvin(
                    (void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
                    a_base + (i * tiles_K + k) * DIM, DIM, DIM);

        for (int j0 = 0; j0 < BLOCKS_N; j0++) {
            int ncols_max = REAL_N - j0 * BLK;
            if (ncols_max <= 0) continue;
            int ncols_blk = (ncols_max > BLK) ? BLK : ncols_max;
            int pad_i = BLK - mrows_blk, pad_j = BLK - ncols_blk;

            // Load B scales per (j0) — B scales differ per column block
            for (int g = 0; g < MATMUL_K / 32; g++)
                memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);
            gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);

            // Load B tiles for this j0
            gemmini_config_ld(MATMUL_N * sizeof(elem_t));
            for (int j = 0; j < tiles_blk; j++)
                for (int k = 0; k < tiles_K; k++)
                    gemmini_extended_mvin(
                        (void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
                        b_base + (k * tiles_blk + j) * DIM, DIM, DIM);

            gemmini_config_st(BLK_OUTC * sizeof(out_t));
            gemmini_mxquant_config_mvout((uint64_t)scale_factors,
                                         tiles_blk, tiles_blk, tiles_K, 0, 0, 1);

            gemmini_loop_ws_spad(tiles_blk, tiles_blk, tiles_K,
                                 pad_i, pad_j, 0,
                                 a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
                                 false, false, false, false, false,
                                 NO_ACTIVATION, 0, 0, false, 0x38);

            if (mrows_blk == BLK && ncols_blk == BLK) {
                gemmini_mx_read_smem(&C_hw[i0 * BLK][j0 * BLK / BF16_PER_WORD],
                                     SPAD_DEST * 16, BLK * BLK);
            } else {
                for (int r = 0; r < mrows_blk; r++)
                    gemmini_mx_read_smem(&C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
                                         SPAD_DEST * 16 + r * BLK, ncols_blk);
            }
        }
    }
    gemmini_fence();
}
```

## Why This Improves Performance

1. **`gemmini_flush(0)` removed from inner loop**: A flush stalls the entire pipeline and waits for all in-flight instructions to drain. Calling it `BLOCKS_M × BLOCKS_N` times multiplied this cost by the number of output tiles. Moving it outside costs only 1 flush total.

2. **`gemmini_extended3_config_ex` removed from inner loop**: Configuration instructions have non-trivial dispatch overhead. Since format, dataflow, and strides are identical for all tiles, issuing it once suffices.

3. **A-scale loads reduced from `BLOCKS_M × BLOCKS_N` to `BLOCKS_M`**: For a fixed row-block `i0`, the A scales are identical across all column blocks `j0`. By hoisting `gemmini_mx_load_scales` for A outside the `j0` loop, we reduce A scale reload count by a factor of `BLOCKS_N`. The `memcpy` for A scales is also hoisted outside the `j0` loop, reducing host CPU work proportionally.

4. **A tile mvins hoisted outside `j0` loop**: A tiles in the scratchpad (`a_base` region) are the same for all `j0` iterations — the weight-stationary loop reuses them against different B tile sets. Loading A once per `i0` instead of once per `(i0, j0)` eliminates `(BLOCKS_N - 1) × tiles_blk × tiles_K` redundant mvin instructions per row-block.

5. **B scales and B tiles remain per-`j0`** (correctly), since each column block of B has distinct data and distinct scale factors.
