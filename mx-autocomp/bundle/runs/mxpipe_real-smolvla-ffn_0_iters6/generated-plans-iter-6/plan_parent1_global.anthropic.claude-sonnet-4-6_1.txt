## Analysis

Looking at the code, I can identify the inefficiency targeted by **strategy 9**:

```c
// Current: per-row loop — mrows separate DMA commands
for (int r = 0; r < mrows; r++)
    gemmini_mx_read_smem(&C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
                         SPAD_DEST * 16 + r * BLK, ncols);
gemmini_fence();
```

This issues up to `mrows` separate `gemmini_mx_read_smem` commands per block. Since `BLK=32` and there can be multiple (i0,j0) block iterations, this is many redundant instruction dispatches.

## Plan: Apply Strategy 9 — Replace per-row `gemmini_mx_read_smem` loop with a single bulk call

**Key observation:** The output rows in `C_hw` for a given block are contiguous in memory (row-major layout), and the smem rows for the block are also contiguous starting at `SPAD_DEST * 16`. So a single `gemmini_mx_read_smem` call with `num_bf16 = mrows * BLK` (covering all `mrows` rows, each of `BLK` BF16 elements) pointing to the base `&C_hw[i0*BLK + 0][(j0*BLK)/BF16_PER_WORD]` and smem offset `SPAD_DEST * 16` replaces the entire loop.

**Correctness check:**
- `C_hw` is row-major. Consecutive smem words correspond to consecutive BF16 elements stored row by row. Since `ncols ≤ BLK` and `BLK` is the smem row stride, smem rows are packed at stride `BLK`. Reading `mrows * BLK` elements in one shot reads exactly the same data as `mrows` per-row reads of `BLK` elements each (since `ncols = BLK` for full blocks, and for partial last blocks we need to handle the fact that we're reading `BLK` per row regardless — but wait, `ncols` may be less than `BLK` for the last column block).
- For the partial-column case (`ncols < BLK`), the per-row loop reads only `ncols` elements per row. A bulk call of `mrows * ncols` would be wrong because smem rows are still strided at `BLK`. So the bulk call must use `mrows * BLK` to match the smem layout and then tolerate the extra padding reads — but we must only write into valid `C_hw` columns. However, since `C_hw` rows are `REAL_N / BF16_PER_WORD` words wide and the padding columns are outside `ncols`, writing them would corrupt adjacent memory.

**Revised plan:** Use a single call only when the row count > 1 AND the block is full (`ncols == BLK`), otherwise fall back to the loop. For the common case (full blocks), this reduces from `mrows=32` commands to 1 command. For partial last-column blocks, keep the per-row loop (or use `ncols` per row). Actually, re-reading: the per-row call uses `ncols` not `BLK`, so smem offset advances by `BLK` each row but only `ncols` values are written to DRAM per row. The bulk approach with `mrows * BLK` would write beyond `ncols` columns into the output buffer — incorrect. 

The safe bulk call is: when `ncols == BLK`, issue one call with `num_bf16 = mrows * BLK`. When `ncols < BLK`, keep the per-row loop. This handles the common full-block case with a single DMA command.

// AUTO-GENERATED outer-tiled MX matmul baseline (50x256x512).
void solution(void) {
  gemmini_flush(0);
  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);

  for (int i0 = 0; i0 < BLOCKS_M; i0++)
   for (int j0 = 0; j0 < BLOCKS_N; j0++) {
      // Partial last M/N block: compute only the real rows/cols, pad the rest.
      int mrows = REAL_M - i0 * BLK; if (mrows > BLK) mrows = BLK; if (mrows <= 0) continue;
      int ncols = REAL_N - j0 * BLK; if (ncols > BLK) ncols = BLK; if (ncols <= 0) continue;
      // Stage only the tiny per-32-group scales; A/B data is mvin'd DIRECTLY
      // from DRAM (no host-side block memcpy — that was 98% of the cycles).
      for (int g = 0; g < MATMUL_K / 32; g++) {
        memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);
        memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);
      }
      int tiles = BLK / DIM, tiles_K = MATMUL_K / DIM;
      uint32_t a_base = 0;
      uint32_t b_base = BANK_NUM * BANK_ROWS - tiles * tiles_K * DIM;
      int SPAD_DEST = 128;
      int pad_i = BLK - mrows, pad_j = BLK - ncols;
      // PROF accel
      gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);
      gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);
      gemmini_config_ld(MATMUL_K * sizeof(elem_t));      // A rows: stride K (full block-aligned tiles)
      for (int i = 0; i < tiles; i++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin((void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
                                a_base + (i * tiles_K + k) * DIM, DIM, DIM);
      gemmini_config_ld(MATMUL_N * sizeof(elem_t));      // B rows: stride N
      for (int j = 0; j < tiles; j++)                    // B[k][j0*BLK+j] -> slot (k*tiles + j)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin((void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
                                b_base + (k * tiles + j) * DIM, DIM, DIM);
      gemmini_config_st(BLK_OUTC * sizeof(out_t));
      gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles, tiles, tiles_K, 0, 0, 1);
      gemmini_loop_ws_spad(tiles, tiles, tiles_K, pad_i, pad_j, 0, a_base, BANK_NUM * BANK_ROWS, 0,
                           SPAD_DEST, false, false, false, false, false, NO_ACTIVATION, 0, 0, false, 0x38);
      // Accelerator-centric readout: bulk smem DMA into bf16-packed output.
      // When ncols == BLK, all mrows output rows are contiguous in smem at stride BLK,
      // so a single DMA command covering mrows*BLK elements replaces the per-row loop.
      if (ncols == BLK) {
        gemmini_mx_read_smem(&C_hw[i0 * BLK][(j0 * BLK) / BF16_PER_WORD],
                             SPAD_DEST * 16, mrows * BLK);
      } else {
        for (int r = 0; r < mrows; r++)
          gemmini_mx_read_smem(&C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
                               SPAD_DEST * 16 + r * BLK, ncols);
      }
      gemmini_fence();
    }
}
