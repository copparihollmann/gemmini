## Analysis

Looking at the current code, I need to identify which strategy offers the most impact.

The current code uses `lut_update_granularity=1` in `gemmini_mxquant_config_mvout`. According to strategy 6, this means the requantizer LUT refreshes after **every single tile**, which is maximally expensive. With `tiles_I * tiles_J` total output tiles, setting `lut_update_granularity = tiles_I * tiles_J` (or its maximum valid value) means the LUT refreshes only **once** for the entire computation, dramatically reducing requantizer overhead.

## Plan: Apply Strategy 6 — Increase `lut_update_granularity`

### Current Code (Step 5):
```c
gemmini_mxquant_config_mvout(
    (uint64_t)scale_factors,
    /*i_bound*/tiles_I, /*j_bound*/tiles_J, /*k_bound*/tiles_K,
    /*scale_act_sel*/0, /*scale_w_sel*/0,
    /*lut_update_granularity*/1);  // ← refreshes LUT every tile
```

### Problem:
With `lut_update_granularity=1`, the requantizer reloads/refreshes its LUT after every single output tile produced by `gemmini_loop_ws_spad`. For a `tiles_I × tiles_J` output grid, this causes `tiles_I * tiles_J` LUT refresh operations. Each refresh is overhead that could be amortized.

### Fix:
Since we're using FP8 E4M3 input with BF16 output (`out_mx_fmt=3`), the output requantizer LUT does not change between tiles — the same scale and format apply uniformly across all output tiles. Therefore, it is safe to set `lut_update_granularity = tiles_I * tiles_J`, which tells the hardware to refresh the LUT only once at the start of the entire output tile batch, eliminating all intermediate refresh overhead.

The `lut_update_granularity` field is 16-bit (RS2[15:0] per the `MXQUANT_CONFIG_MVOUT` encoding), so the maximum representable value is 65535. With the problem dimensions, `tiles_I * tiles_J` will fit within 16 bits.

### Specific Change:
In the `gemmini_mxquant_config_mvout` call, change `lut_update_granularity` from `1` to `tiles_I * tiles_J`:

```c
gemmini_mxquant_config_mvout(
    (uint64_t)scale_factors,
    /*i_bound*/tiles_I, /*j_bound*/tiles_J, /*k_bound*/tiles_K,
    /*scale_act_sel*/0, /*scale_w_sel*/0,
    /*lut_update_granularity*/tiles_I * tiles_J);  // ← refresh LUT only once
```

No other changes are needed. The rest of the sequence (config_ex, load_scales, mvin, loop_ws_spad, read_smem, fence) remains identical and in the correct order.

### Why This Is Safe:
- The output format is BF16 (`out_mx_fmt=3`), and the same requantization parameters apply uniformly to all `tiles_I * tiles_J` output tiles.
- Scale factors are already loaded once before compute (not per-tile), so the LUT state is consistent throughout the entire `gemmini_loop_ws_spad` execution.
- This change is purely a performance hint to the requantizer controlling refresh frequency — it does not alter what data is computed or stored.
