To optimize the performance of the MX-Gemmini FP8 matmul kernel, we will focus on **Strategy 1: Reduce Data Movement** by eliminating CPU-side data staging for scale factors.

### Inefficiency Analysis
The original code performs CPU-side transposition and staging of scale factors into static arrays `A_scales_T` and `B_scales_T` using `memcpy` inside nested loops before executing the hardware matrix multiplication:
```c
  for (int i0 = 0; i0 < BLOCKS_M; i0++) {
    for (int g = 0; g < GK; g++) {
      memcpy(&A_scales_T[i0][g * BLK], &A_scales_row[g][i0 * BLK], BLK);
    }
  }
```
This host-side data staging is a dominant bottle-neck. Since the scale factor memory in Gemmini streams bytes from DRAM and writes them sequentially, we can bypass CPU-side buffering entirely. 

### Optimization Plan
1. **Eliminate Staging Buffers**: Remove the `A_scales_T` and `B_scales_T` static arrays and their initialization `memcpy` loops.
2. **Direct Scale Streaming**: Replace the single block-level `gemmini_mx_load_scales` calls with a loop over the scale groups (`g = 0` to `GK - 1`).
3. **Multi-Segment DMA Loads**: Issue `gemmini_mx_load_scales` directly from the original DRAM addresses:
   - For B-scales (weights): `&B_scales_col[g][j0 * BLK]`
   - For A-scales (activations): `&A_scales_row[g][i0 * BLK]`
   This leverages the sequential auto-incrementing write pointer of Gemmini's scale memory to assemble the non-contiguous blocks directly in hardware, resulting in zero CPU overhead and zero redundant DRAM-to-DRAM copies.
