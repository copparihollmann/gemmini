### Optimization Plan

Our goal is to reduce the execution latency of the weight-stationary tiled matrix multiplication kernel. Currently, the scale factor loads are performed redundantly inside the innermost tile loops, causing excessive DRAM-to-SRAM transfer overhead. We will apply **Strategy 3: batch scale factor loads with `gemmini_mx_load_scales` once per K-dimension sweep, not per tile**.

#### Analysis of Inefficiency
In the current implementation:
```c
for (int j0 = 0; j0 < BLOCKS_N; j0++) {
  ...
  for (int i0 = 0; i0 < BLOCKS_M; i0++) {
    ...
    // Load A and B scales
    gemmini_mx_load_scales((uint64_t)A_scales_T[i0], A_S_BYTES, 0);
    gemmini_mx_load_scales((uint64_t)B_scales_T[j0], B_S_BYTES, 1);
```
The B-side scale factors (`B_scales_T[j0]`) are loaded inside the inner loop over `i0`. Because the weight columns (indexed by `j0`) are invariant across different row blocks (`i0`), reloading them in every iteration of the `i0` loop is highly redundant. This causes `BLOCKS_M` times more DRAM scale memory load instructions than necessary.

#### Specific Changes
We will hoist the loading of the B scale factors out of the inner `i0` loop into the outer `j0` loop:

1. Locate the `gemmini_mx_load_scales((uint64_t)B_scales_T[j0], B_S_BYTES, 1);` call.
2. Move this call to the outer loop scope (inside `for (int j0 = ...)` but before the `for (int i0 = ...)` loop starts).
3. Leave the activation scales (`A_scales_T[i0]`) load inside the inner loop since they vary with `i0`.

This change reduces the scale load frequency of the weight matrix by a factor of `BLOCKS_M`, significantly minimizing DRAM bandwidth bottlenecks and lowering execution time while maintaining full numerical correctness.
