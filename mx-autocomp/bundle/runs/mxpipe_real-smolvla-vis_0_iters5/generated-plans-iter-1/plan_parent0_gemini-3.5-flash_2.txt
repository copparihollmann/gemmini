### Chosen Strategy
**Strategy 4: Hoist or eliminate `gemmini_flush(0)` from the hot loop**

---

### Inefficiency Analysis
In the original `solution()` kernel, `gemmini_flush(0)` is invoked inside the nested outer loops over `i0` and `j0`. 

Each call to `gemmini_flush(0)` initiates a hardware pipeline flush, resetting internal control registers, stalling subsequent instructions, and potentially invalidating TLB and cache state. Because this occurs on every single outer tile iteration (for every $BLK \times BLK$ block), it introduces significant execution overhead and prevents overlapping or pipeline optimization of consecutive tiled workloads. This flushing is only strictly necessary once at the beginning of the entire matrix multiplication workload to clean the system state before execution.

---

### Optimization Plan
1. **Identify the Target:** Locate the `gemmini_flush(0);` instruction inside the nested loops:
   ```c
   for (int i0 = 0; i0 < BLOCKS_M; i0++) {
       for (int j0 = 0; j0 < BLOCKS_N; j0++) {
           ...
           gemmini_flush(0); // <--- Inefficient location
           gemmini_extended3_config_ex(...);
           ...
       }
   }
   ```
2. **Hoist the Instruction:** Move `gemmini_flush(0);` to the very top of the `solution(void)` function so that it runs exactly once during the program initialization phase.
3. **Preserve Surrounding Logic:** Keep all other configuration commands (`gemmini_extended3_config_ex`, scale loadings, `mvin` loops, compute execution, and shared memory reads) inside the nested loops intact to ensure exact semantic correctness and execution flow.
