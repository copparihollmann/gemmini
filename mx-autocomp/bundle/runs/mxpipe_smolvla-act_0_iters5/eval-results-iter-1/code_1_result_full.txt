Looking at the original code, I can identify the key inefficiency targeted by **strategy 11**:

Inside the double loop over `i0` and `j0`, the code does:
```c
for (int g = 0; g < MATMUL_K / 32; g++) {
    memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);
    memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);
}
```
This copies a sub-array of scales into staging buffers `A_s` and `B_s` before passing them to `gemmini_mx_load_scales`. This CPU-side memcpy is entirely unnecessary because `gemmini_mx_load_scales` just takes a DRAM address and byte length — we can pass a pointer directly into the original `A_scales_row` and `B_scales_col` arrays at the correct offset, eliminating all host-side data movement for scales.

## Plan: Apply Strategy 11

**What to change:**

1. **Remove the `A_s` and `B_s` staging buffers** (and their associated `memcpy` loops entirely). These exist solely to create a contiguous sub-array for each (i0, j0) block, but direct pointer arithmetic into the source arrays achieves the same thing.

2. **Replace `gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0)`** with a direct pointer into `A_scales_row`: the sub-array for block `i0` starts at `&A_scales_row[0][i0 * BLK]`. Since `A_scales_row` is laid out as `[MATMUL_K/32][MATMUL_M]`, the stride between rows is `MATMUL_M` bytes, so the data for a single i0-block is **not** contiguous across `g` groups. However, `gemmini_mx_load_scales` loads `len` bytes from a flat address — so we must pass each group row separately, or verify the layout.

   The original `A_scales_row` has shape `[GK][M]` (row-major), so `A_scales_row[g][i0*BLK]` gives the correct pointer per-group. The `A_s` buffer was concatenating these into a flat `[GK][BLK]` layout. Since `gemmini_mx_load_scales` reads `A_S_BYTES = (MATMUL_K/32)*BLK` bytes flat, and the original `A_scales_row[g]` rows are each `MATMUL_M` bytes wide (not `BLK`), the staging was needed to repack the sub-columns.

   **However**: if `i0==0` and there's only one block (i.e., `BLK==MATMUL_M`), or if `MATMUL_M==BLK`, we can pass directly. For the general case where `BLK < MATMUL_M`, the memcpy is doing column-extraction repacking. In that case, we can eliminate the staging by **issuing one `gemmini_mx_load_scales` call per K-group** with a direct pointer, rather than one call for the whole repacked buffer.

3. **Specifically**: replace the `memcpy` loop + single `gemmini_mx_load_scales` call with a loop over `g` that calls `gemmini_mx_load_scales` directly with `&A_scales_row[g][i0 * BLK]` (length `BLK`) and similarly for B. This eliminates all CPU memcpy work while keeping the same scales loaded into hardware. The total bytes loaded per `gemmini_mx_load_scales` call is `BLK` instead of `(MATMUL_K/32)*BLK`, but the same total data is transferred — just in `MATMUL_K/32` separate calls instead of one, with zero CPU copying.

4. **Remove** `A_s`, `B_s`, `A_S_BYTES`, `B_S_BYTES` from the code entirely.

This is a pure CPU-side optimization: it eliminates the `(MATMUL_K/32) * 2` memcpy calls per outer iteration (each copying `BLK` bytes) which the profiler identified as consuming ~98% of CPU cycles.
