## Analysis of the Current Code

The current code has **BLK separate `gemmini_mx_read_smem` calls** per output block (one per row):

```c
for (int r = 0; r < BLK; r++)
    gemmini_mx_read_smem(&C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
                         SPAD_DEST * 16 + r * BLK, BLK);
```

This issues `BLK` separate RoCC instructions with small transfers, each with instruction dispatch overhead. Strategy 12 directly addresses this.

## Selected Strategy: #12 — Batch all `gemmini_mx_read_smem` calls into a single call

### Plan

**Observation:** The current code issues `BLK` separate `gemmini_mx_read_smem` calls, each reading `BLK` BF16 values (one row at a time) from `mx_smem` into non-contiguous rows of `C_hw`. This works because each output row `r` maps to `smem_off = SPAD_DEST*16 + r*BLK` and DRAM destination `&C_hw[i0*BLK + r][(j0*BLK)/BF16_PER_WORD]`.

**Key insight:** The `mx_smem` stores all `BLK × BLK` BF16 values contiguously starting at `SPAD_DEST*16`. The DRAM output `C_hw` is row-major, so `C_hw[i0*BLK + r][(j0*BLK)/BF16_PER_WORD]` for `r = 0..BLK-1` are **also contiguous in memory** (each row has `MATMUL_N/BF16_PER_WORD` words, but the block columns `j0*BLK/BF16_PER_WORD` through `(j0*BLK + BLK - 1)/BF16_PER_WORD` are contiguous within a row, and rows are laid out sequentially).

**Problem with naïve single call:** `C_hw` rows have stride `MATMUL_N/BF16_PER_WORD` words (the full output width), so rows of the output block are **not contiguous** in DRAM unless `BLK == MATMUL_N`. The per-row loop is needed to handle this non-contiguous DRAM layout.

**However:** Looking at the code, `gemmini_mx_read_smem` takes a flat DRAM address and copies `num_bf16` contiguous BF16 words from smem to DRAM sequentially. The smem layout for the block is `BLK × BLK` contiguous BF16 values. If we allocate a **temporary contiguous staging buffer** of size `BLK × BLK` BF16 values (i.e., `BLK * BLK / BF16_PER_WORD` uint64 words), we can:

1. Issue **one** `gemmini_mx_read_smem` call into the staging buffer (one RoCC instruction, one DMA transfer of `BLK*BLK` BF16 values).
2. After `gemmini_fence()`, copy from the staging buffer into `C_hw` on the CPU (a simple scatter with `BLK` `memcpy` calls of `BLK/BF16_PER_WORD` words each).

But this reintroduces CPU staging. A better approach: observe that `gemmini_mx_read_smem` can write directly to any DRAM address. Since `C_hw[i0*BLK]` starts at a known address and `C_hw` rows are `MATMUL_N/BF16_PER_WORD` uint64 words apart, we **cannot** avoid the per-row calls unless rows are contiguous.

**Correct single-call approach:** When `j0 == 0` and `BLK == MATMUL_N`, rows are contiguous and one call suffices. In general, the per-row loop is necessary for correctness. But we can **replace `BLK` RoCC instructions with a single RoCC instruction** by using a **contiguous scratch output buffer** declared as a local or static array, issuing one `gemmini_mx_read_smem` into it, then scattering rows into `C_hw` with `memcpy`.

**Concrete change:**

- Declare `static out_t block_out[BLK][BLK / BF16_PER_WORD]` (a flat `BLK × BLK` BF16 staging area).
- Replace the `BLK`-iteration `gemmini_mx_read_smem` loop with:
  ```c
  gemmini_mx_read_smem(&block_out[0][0], SPAD_DEST * 16, BLK * BLK);
  gemmini_fence();
  for (int r = 0; r < BLK; r++)
      memcpy(&C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
             &block_out[r][0],
             (BLK / BF16_PER_WORD) * sizeof(out_t));
  ```
- This reduces `BLK` RoCC instructions to **1**, trading RoCC dispatch overhead for a CPU `memcpy` scatter (which is much cheaper than RoCC instruction overhead × BLK).
- Also move `gemmini_flush(0)` outside the `i0`/`j0` loop (strategy 11 — directly applicable and trivially correct since flush only needs to happen once before the entire computation, not once per block).

The dominant saving is reducing RoCC instruction count from `BLK` to `1` per output block, eliminating `BLK - 1` RoCC round-trips per `(i0, j0)` pair.
