## Strategy: Increase Tile Size to Maximize Scratchpad Utilization and Amortize Fixed Overhead

### Analysis of the Current Code

The current code processes the 128×320×320 matmul using blocks of size `BLK` (presumably 32, given the 32-group structure). For each `(i0, j0)` block pair, it:
1. Issues `gemmini_flush(0)` (hardware reset — very expensive)
2. Calls `gemmini_extended3_config_ex`
3. Loads A and B scales
4. MVINs A tiles (`tiles × tiles_K = 2 × 20 = 40` mvin calls) and B tiles (another 40)
5. Issues `gemmini_loop_ws_spad`
6. Issues per-row `gemmini_mx_read_smem` calls

The scratchpad utilization is reported as **0KB out of 256KB** — this is because `BLK=32` tiles fit trivially. With `MATMUL_K=320`, `tiles_K=20`, `BLK=32` (tiles=2):
- A tiles: `2 × 20 × 16 = 640` rows
- B tiles: `2 × 20 × 16 = 640` rows
- Total: 1280 rows out of 8192 — only **15.6% utilization**

The accumulator holds `tiles_I × tiles_J × DIM = 2 × 2 × 16 = 64` rows out of 256 — only **25%**.

The dominant inefficiency is **per-block fixed overhead amortized over too few compute tiles**. Each invocation of the outer loop pays for `gemmini_flush`, config, two scale loads, 80 mvin commands, loop setup, and smem readout — but only executes `2×2×20 = 80` 16×16 MACs worth of work.

### Proposed Strategy: Increase BLK to Process Larger Tiles per Accelerator Invocation

**The core idea:** Increase the effective tile size processed per hardware invocation by setting `BLK` to a larger value — specifically, expand to process `BLK = 64` (tiles_I = tiles_J = 4) per invocation. This:

1. **Amortizes fixed overhead** (flush, config, scale loads) over 4× more compute
2. **Increases scratchpad utilization**: With `BLK=64`, tiles=4, tiles_K=20:
   - A: `4 × 20 × 16 = 1280` rows
   - B: `4 × 20 × 16 = 1280` rows
   - Total: 2560 rows — still within 8192 ✓
3. **Accumulator**: `4 × 4 × 16 = 256` rows — exactly fits in 256 ✓
4. **Reduces total loop iterations**: `(128/64)² = 4` outer iterations instead of `(128/32)² = 16`

The constraint check for `BLK=64` with `MATMUL_M=MATMUL_N=128`, `MATMUL_K=320`:
- `tiles_I = tiles_J = 64/16 = 4`, `tiles_K = 320/16 = 20`
- Scratchpad: `(4×20 + 4×20) × 16 = 2560 ≤ 8192` ✓
- Accumulator: `4 × 4 × 16 = 256 ≤ 256` ✓ (exactly saturates single-buffer)
- Scale bytes: `A_S_BYTES` and `B_S_BYTES` scale proportionally with `BLK`

### How This Differs from Listed Strategies

This is not simply "hoisting config outside loops" (strategy 6/10) or "reusing B tiles" (strategy 11). It is **increasing the granularity of the hardware invocation itself** — making each `gemmini_loop_ws_spad` call cover a 64×64×320 subproblem instead of 32×32×320. This directly reduces the number of times all fixed-cost operations (flush, config, scale load, smem drain) execute, from 16 to 4 iterations, while fully saturating the accumulator.

### Implementation

```c
#include <stdint.h>
#include <string.h>
#include "include/gemmini_testutils.h"
#include "include/matmul_data_mx.h"

#define DIM 16
#define ADDR_LEN 32
#define BF16_PER_WORD 4
#define BANK_NUM 4
#define BANK_ROWS 2048

// Use BLK=64 to saturate accumulator and amortize per-invocation overhead
#define BLK 64

typedef uint8_t elem_t;
typedef uint8_t out_t;

// tiles within one BLK-sized block
#define TILES   (BLK / DIM)           // = 4
#define TILES_K (MATMUL_K / DIM)      // = 20

// Scale-factor byte counts for one BLK-wide block
// A_scales_row[MATMUL_K/32][MATMUL_M]: BLK rows of A per block
// B_scales_col[MATMUL_K/32][MATMUL_N]: BLK cols of B per block
#define GK       (MATMUL_K / 32)
#define A_S_BYTES (GK * BLK)          // bytes for BLK A-side rows
#define B_S_BYTES (GK * BLK)          // bytes for BLK B-side cols
#define BLK_OUTC  (BLK / BF16_PER_WORD)

#define BLOCKS_M (MATMUL_M / BLK)     // = 2
#define BLOCKS_N (MATMUL_N / BLK)     // = 2

// Staging buffers for scale factors (one block's worth)
static uint8_t A_s[GK][BLK];
static uint8_t B_s[GK][BLK];

// Output scale factors (not used for fp8/BF16 path but required by API)
static uint8_t scale_factors[MATMUL_M * (MATMUL_N / 32)];

void solution(void) {
  // Scratchpad layout for BLK=64, TILES=4, TILES_K=20:
  //   A: a_base=0, rows = TILES*TILES_K*DIM = 4*20*16 = 1280
  //   B: b_base = 8192 - TILES*TILES_K*DIM = 8192 - 1280 = 6912
  //   No overlap: A ends at 1280, B starts at 6912 ✓
  //   Accumulator: TILES*TILES*DIM = 4*4*16 = 256 rows (exactly full) ✓

  uint32_t a_base  = 0;
  uint32_t b_base  = BANK_NUM * BANK_ROWS - TILES * TILES_K * DIM;
  int      SPAD_DEST = 128;

  // One-time hardware initialization — hoisted outside all loops
  gemmini_flush(0);
  gemmini_extended3_config_ex(
    WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
    /*C_stride*/1, /*A_stride*/1,
    /*A_transpose*/0, /*B_transpose*/0,
    /*set_only_strides*/false,
    /*act_mx_fmt*/0, /*wgt_mx_fmt*/0, /*out_mx_fmt*/3, /*uselut*/0);

  // Output stride configured once (BLK_OUTC packed BF16 words per row)
  gemmini_config_st(BLK_OUTC * sizeof(out_t));

  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    // --- Hoist B-side data movement outside i0 loop ---
    // B tiles and B scales are independent of i0; load once per j0.

    // Stage B scale factors for this j0 block
    for (int g = 0; g < GK; g++)
      memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);

    // MVIN B tiles: B_in[k*DIM .. (k+1)*DIM-1][j0*BLK .. j0*BLK+BLK-1]
    // B row stride = MATMUL_N bytes (fp8: 1 byte/elem, full row width)
    gemmini_config_ld(MATMUL_N * sizeof(elem_t));
    for (int j = 0; j < TILES; j++)
      for (int k = 0; k < TILES_K; k++)
        gemmini_extended_mvin(
          (void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
          b_base + (k * TILES + j) * DIM,
          DIM, DIM);

    for (int i0 = 0; i0 < BLOCKS_M; i0++) {
      // Stage A scale factors for this (i0, j0) block
      for (int g = 0; g < GK; g++)
        memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);

      // Load both sets of scale factors
      // A scales: sel=0, B scales: sel=1
      gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0);
      gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);

      // MVIN A tiles: A_in[i0*BLK+i*DIM .. ][k*DIM .. ]
      // A row stride = MATMUL_K bytes (full K-dimension row width)
      gemmini_config_ld(MATMUL_K * sizeof(elem_t));
      for (int i = 0; i < TILES; i++)
        for (int k = 0; k < TILES_K; k++)
          gemmini_extended_mvin(
            (void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
            a_base + (i * TILES_K + k) * DIM,
            DIM, DIM);

      // Configure requantizer mvout bounds
      gemmini_mxquant_config_mvout(
        (uint64_t)scale_factors,
        TILES, TILES, TILES_K,
        /*scale_act_sel*/0, /*scale_w_sel*/0,
        /*lut_update_granularity*/1);

      // Execute fused tiled matmul: 4×4×20 tiles of 16×16 MACs
      gemmini_loop_ws_spad(
        TILES, TILES, TILES_K,
        0, 0, 0,
        a_base, BANK_NUM * BANK_ROWS,
        0, SPAD_DEST,
        false, false,
        false, false, false,
        NO_ACTIVATION, 0, 0, false,
        0x38);

      // Drain BF16 results: one bulk DMA for the entire BLK×BLK region
      // smem layout: SPAD_DEST*16 is word offset; BLK*BLK BF16 values total
      gemmini_mx_read_smem(
        &C_hw[i0 * BLK][(j0 * BLK) / BF16_PER_WORD],
        SPAD_DEST * 16,
        BLK * BLK);
      gemmini_fence();
    }
  }
}
```

### Why This Improves Performance

| Metric | BLK=32 (original) | BLK=64 (proposed) |
|--------|-------------------|-------------------|
| Outer loop iterations | 16 | 4 |
| `gemmini_flush` calls | 16 | 1 (hoisted) |
| `gemmini_extended3_config_ex` calls | 16 | 1 (hoisted) |
| `gemmini_mx_load_scales` call pairs | 16 | 4 (A only; B hoisted) |
| Total mvin commands | 16×80 = 1280 | 4×(80+80)=640† |
| `gemmini_loop_ws_spad` invocations | 16 | 4 |
| `gemmini_fence` calls | 16×32 (per-row) → 16 (after bulk) | 4 |
| Scratchpad utilization | ~15.6% | ~31.3% |
| Accumulator utilization | ~25% | **100%** |

†B mvins are now hoisted to 2 j0 iterations × 80 = 160; A mvins: 4 total × 80 = 320; total 480 — 2.7× fewer than original.

The key gains are: (1) **4× reduction in fixed-overhead operations** (flush/config/scale load/smem drain), (2) **accumulator fully saturated** so each hardware loop invocation does maximum useful work before draining, and (3) **B-tile mvins hoisted** outside the i0 loop, eliminating redundant reloads of the same B data across i0 iterations for the same j0 column block.
