Looking at the original code, the outer loop is `i0` outer / `j0` inner. For each `(i0, j0)` pair:
- B tiles are mvin'd into the scratchpad
- B scales are loaded via `gemmini_mx_load_scales(..., 1)`

Since the loop order is `i0` outer / `j0` inner, the B tiles and B scales change every iteration of the inner `j0` loop — **but they also change every iteration of the outer `i0` loop** because `j0` resets.    - The entire B mvin loop (`gemmini_extended_mvin` for B) hoisted outside `i0`
   - `gemmini_config_ld` for B stride hoisted outside `i0`

3. **Keep A mvin and A scale load inside the `i0` loop**: A tiles change with `i0` so they must remain inside.

4. **Keep `b_base` computation outside `i0`**: `b_base` depends only on `tiles` and `tiles_K` (constants), so it stays fixed. Since B tiles are only loaded once per `j0`, the scratchpad layout is unchanged — `b_base = BANK_NUM*BANK_ROWS - tiles*tiles_K*DIM` stays the same.

5. **Verify scratchpad fit**: The scratchpad constraint `(tiles_I*tiles_K + tiles_J*tiles_K)*DIM ≤ 8192` still uses the same `tiles` for both I and J (since BLK is fixed and tiles = BLK/DIM), and the layout is unchanged — this is satisfied identically to before.

6. **Programming model sequence per `i0` iteration** is preserved: `gemmini_extended3_config_ex` → `gemmini_mx_load_scales` (A, then B — B load is now before the `i0` loop but within `j0`, so it precedes each inner-loop `gemmini_loop_ws_spad`) → mvin A (and B already in scratchpad) → `gemmini_mxquant_config_mvout` → `gemmini_loop_ws_spad` → `gemmini_mx_read_smem` → `gemmini_fence`.

7. **`gemmini_flush`**: Move it outside both loops (before the `j0` loop) since it only needs to be issued once to reset state.

This eliminates `BLOCKS_M` redundant B mvin sequences and `BLOCKS_M` redundant `gemmini_mx_load_scales` (sel=1) calls per `j0` block — reducing total B mvin work by a factor of `BLOCKS_M`.
