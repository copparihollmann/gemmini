An elegant and highly effective optimization plan to improve the latency of the MHA kernel is to apply **Strategy 1: cache reused data in local memory instead of reloading from main memory** by reordering the computation loops.

### Analysis of Inefficiencies in the Baseline
In the baseline implementation, the outer loop iterates over each attention head $h$ sequentially (`for (int h = 0; h < ATT_H; h++)`). Within each iteration, the code:
1. Loads $K^T$ (`KT_in` and `KT_sc`) from DRAM to compute $S1 = Q \times K^T$.
2. Performs the softmax on the host.
3. Loads $V$ (`V_in` and `V_sc`) from DRAM to compute $O = P \times V$.

Because $H > H_{kv}$ (specifically, $H=4$ and $H_{kv}=2$), multiple attention heads share the same key-value head ($kv = h / 2$). In the baseline, `KT_in` and `V_in` (as well as their scales `KT_sc` and `V_sc`) are repeatedly evicted and reloaded from DRAM for every single head $h$. Since the scratchpad B-region is overwritten between Step 1 and Step 3 within the same head iteration, we cannot cache them across steps without reordering.

---

### Optimization Plan: Loop Reordering and Scratchpad Caching

Since there are no loop-carried dependencies between different attention heads, we can reorder the execution to group heads sharing the same `kv` index. This allows us to load the key and value matrices into the scratchpad **exactly once per `kv` group**, rather than once per head $h$.

#### Step-by-Step Implementation Plan:

1. **Allocate Head-Private Temporary Buffers**:
   To avoid overwriting the intermediate outputs $S1$, $P_q$, and $P_{\text{scales}}$ when processing heads out of order, define head-private arrays on the stack:
   ```c
   uint64_t S1_hw_h[ATT_H][ATT_S][ATT_S / 4];
   elem_t P_q_h[ATT_H][ATT_S][ATT_S];
   uint8_t P_scales_h[ATT_H][GROUPS_S][ATT_S];
   ```
   These buffers are small (totaling $\approx 48\text{ KB}$) and easily fit within the host memory.

2. **Restructure the Outer Loop**:
   Iterate over each KV head `kv` from $0$ to $ATT\_HKV - 1$. For each `kv` group, determine the range of corresponding query heads `h` (from `h_start` to `h_end`).

3. **Stage 1: Batch $Q \times K^T$ Computations**:
   * Load the shared scale factor `KT_sc` into the scale register (`sel=1`) once.
   * Load the shared key matrix `KT_in` into the top of the scratchpad (`b_base`) once.
   * Iterate $h$ from `h_start` to `h_end`:
     * Load `Q_sc[h]` to `sel=0` and `Q_in[h]` to `a_base`.
     * Execute `gemmini_loop_ws_spad` with `skips = 0x38` (skipping the B load from DRAM since $K^T$ is already cached in the scratchpad).
     * Drain the result to `S1_hw_h[h]`.

4. **Stage 2: Run Softmax**:
   * For each head $h$ in the `kv` group, execute the CPU-side softmax algorithm on `S1_hw_h[h]` to produce `P_q_h[h]` and `P_scales_h[h]`.

5. **Stage 3: Batch $P \times V$ Computations**:
   * Load the shared scale factor `V_sc` into the scale register (`sel=1`) once.
   * Load the shared value matrix `V_in` into the top of the scratchpad (`b_base`) once.
   * Iterate $h$ from `h_start` to `h_end`:
     * Load `P_scales_h[h]` to `sel=0` and `P_q_h[h]` to `a_base`.
     * Execute `gemmini_loop_ws_spad` with `skips = 0x38` (skipping the B load from DRAM since $V$ is already cached in the scratchpad).
     * Drain the final result directly to the corresponding head slice in `O_hw[h]`.

### Expected Impact
* **DRAM Bandwidth Reduction**: Reduces the total volume of $K^T$ and $V$ coordinate data read from DRAM by $2\times$.
* **Scale Loading Latency**: Reduces the scale-factor loading overhead via `gemmini_mx_load_scales` for `KT_sc` and `V_sc` by $2\times$.
* **Systolic Array Efficiency**: By reusing B tiles already present in the scratchpad across consecutive systolic array invocations, we maximize compute-to-load overlap and greatly reduce execution latency.
