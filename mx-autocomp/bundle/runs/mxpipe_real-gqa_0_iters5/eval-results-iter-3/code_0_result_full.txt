### Optimization Strategy: Grouped-Query KV Cache Hoisting

In the original implementation, the outermost loop iterates over each query head `h` (`0` to `ATT_H - 1`). Within each iteration, the Key tensor ($K^T$) and Value tensor ($V$) (along with their scale factors) are loaded from DRAM into the scratchpad. However, in GQA, multiple query heads share the same Key/Value heads ($H / H_{kv} = 4 / 2 = 2$ query heads per KV head).

Instead of redundantly reloading $K^T$ and $V$ for every query head, we can restructure the outer loop nest to group execution by `kv` head first:
1. **Dram-to-Scratchpad Savings ($2\times$ reduction)**: For each `kv` group, we load $K^T$ into the top of the scratchpad (`b_base`) *exactly once*. We then perform the $Q @ K^T$ matrix multiplication for all query heads $h$ in that group, completely bypassing the software `gemmini_extended_mvin` calls for $K^T$ on subsequent query heads.
2. **Scale Factor Load Savings ($2\times$ reduction)**: We load the Key scale factors (`KT_sc`) and Value scale factors (`V_sc`) using `gemmini_mx_load_scales` only once per `kv` group.
3. **Decoupled Softmax and Projection**: Since $K^T$ and $V$ share the same physical scratchpad space at `b_base` (due to hardware constraint Rule 12), we decouple the attention computation into two phases per KV group. First, we compute $S1$ and run the Softmax for all query heads in the KV group, storing intermediate $P_q$ and $P_{scales}$ into local head-specific buffers. Then, we overwrite `b_base` once with $V$ and compute $O = P @ V$ for all heads in the group. 

This eliminates redundant DRAM accesses, mitigates host CPU instruction overhead, and significantly boosts performance on Spike.
