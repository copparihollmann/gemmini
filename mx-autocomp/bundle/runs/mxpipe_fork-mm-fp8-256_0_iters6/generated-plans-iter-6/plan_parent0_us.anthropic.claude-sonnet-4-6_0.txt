## Analysis

Looking at the original code, I need to identify which strategy applies best.

**Current situation:**
- `SPAD_DEST = 0` — results written to accumulator address 0
- `tiles_I = MATMUL_M/DIM`, `tiles_J = MATMUL_N/DIM`, `tiles_K = MATMUL_K/DIM`
- Single `gemmini_loop_ws_spad` call covering all I×J×K tiles
- The accumulator constraint: `tiles_I * tiles_J * DIM ≤ 256` rows

The feedback says scratchpad and accumulator utilization are both 0KB — this means the hardware's fused loop is doing all the work internally, and the single-call approach is fine IF the accumulator doesn't overflow. But the key insight from strategy 13 is about `lut_update_granularity`.

**Current code uses `lut_update_granularity = 1`** in `gemmini_mxquant_config_mvout`. This means the requantizer refreshes the output LUT for every single tile during the K-reduction. Since the output quantization LUT is invariant across K-reduction tiles (it doesn't change based on which K slice we're computing), we can set `lut_update_granularity = tiles_K` to reduce LUT refresh overhead from per-K-tile to once per output tile (i,j).

**Strategy 13: Increase `lut_update_granularity` to `tiles_K`**

This directly reduces the number of requantizer LUT refresh operations from `tiles_I * tiles_J * tiles_K` to `tiles_I * tiles_J` — a `tiles_K`-fold reduction in requantizer overhead. The output LUT is invariant across the K dimension since it only depends on the output quantization parameters (which are fixed for a given output block), not on which partial sum we're accumulating.

## Plan

**Change `lut_update_granularity` from `1` to `tiles_K`** in the `gemmini_mxquant_config_mvout` call.

Specifically:
```c
// Before:
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);

// After:
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_K);
```

This sets G = `tiles_K`, meaning the requantizer LUT only refreshes once at the start of each output tile (i,j) rather than once per K-step. Since we're using FP8 with `uselut=0` and `out_mx_fmt=3` (BF16 output), and there are no per-K LUT updates needed (the output LUT is fixed for the entire computation), this is safe and correct.

```c
void solution(void) {

  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);

#ifdef SPIKE_SIM
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);
#else
  load_scale_factors((volatile uint64_t *) GEMMINI_SF_MEM_A, (uint8_t *) &A_scales_row, MATMUL_M, MATMUL_K);
  load_scale_factors((volatile uint64_t *) GEMMINI_SF_MEM_B, (uint8_t *) &B_scales_col, MATMUL_N, MATMUL_K);
#endif

  // ---- MVIN A: batch up to MAX_BLOCK_LEN=4 consecutive K-tiles per row i ----
  gemmini_config_ld(MATMUL_K * sizeof(elem_t));

  for (int i = 0; i < tiles_I; i++) {
    for (int k = 0; k < tiles_K; k += MAX_BLOCK_LEN) {
      int batch = (tiles_K - k < MAX_BLOCK_LEN) ? (tiles_K - k) : MAX_BLOCK_LEN;
      elem_t *dram_ptr = ((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM;
      uint32_t sp_addr = a_base + (i * tiles_K + k) * DIM;
      gemmini_extended_mvin((void *) dram_ptr, sp_addr, batch * DIM, DIM);
    }
  }

  // ---- MVIN B: batch up to MAX_BLOCK_LEN=4 consecutive J-tiles per K-row k ----
  gemmini_config_ld(MATMUL_N * sizeof(elem_t));

  for (int k = 0; k < tiles_K; k++) {
    for (int j = 0; j < tiles_J; j += MAX_BLOCK_LEN) {
      int batch = (tiles_J - j < MAX_BLOCK_LEN) ? (tiles_J - j) : MAX_BLOCK_LEN;
      elem_t *dram_ptr = ((elem_t*)B_in) + k * DIM * MATMUL_N + j * DIM;
      uint32_t sp_addr = b_base + (k * tiles_J + j) * DIM;
      gemmini_extended_mvin((void *) dram_ptr, sp_addr, batch * DIM, DIM);
    }
  }

  int SPAD_DEST = 0;

  gemmini_config_st(DIM * sizeof(elem_t));
  // Increase lut_update_granularity from 1 to tiles_K: the output LUT is invariant
  // across the K-reduction dimension, so refreshing it once per output (i,j) tile
  // (every tiles_K steps) rather than every K-step reduces requantizer overhead
  // by a factor of tiles_K with no loss of correctness.
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_K);

  // ---- Compute ----
  gemmini_loop_ws_spad(
      tiles_I, tiles_J, tiles_K,
      0, 0, 0,
      a_base,
      BANK_NUM * BANK_ROWS,
      0,
      SPAD_DEST,
      false, false,
      false, false, false,
      NO_ACTIVATION,
      0, 0,
      false,
      0x38);

  gemmini_fence();

#ifdef SPIKE_SIM
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
#else
  printf("Moving out:\n");
  for (int i = 0; i < tiles_J*tiles_I*2; i++) {
      gemmini_mvout((void*)((uint64_t*) C_hw + i*2*DIM), SPAD_DEST + i*DIM);
  }
  gemmini_fence();
#endif

}
```
