## Analysis

The current code loads A and B tiles using a single DMA port (`gemmini_block_mvin` for both A and B, both using `k_MVIN`). This means A and B loads are serialized — the hardware processes them sequentially through one port.

**Strategy 11: Load B tiles using `gemmini_extended_mvin2` (the dedicated second DMA port) while A tiles use `gemmini_extended_mvin`, enabling hardware-parallel dual-port DMA for A and B simultaneously.**

## Plan

The key inefficiency is that A and B tiles are loaded sequentially through the same DMA port. The hardware has two independent DMA ports:
- Port 1: `k_MVIN` / `gemmini_extended_mvin` / `gemmini_block_mvin` — for A tiles
- Port 2: `k_MVIN2` / `gemmini_extended_mvin2` — for B tiles

By interleaving A and B mvin commands, the hardware can overlap the two DMA transfers in parallel, cutting data movement time roughly in half.

**Concrete changes:**

1. Configure the LD stride for port 1 (A) using `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` — unchanged.
2. Configure the LD stride for port 2 (B) using `gemmini_extended3_config_ld(MATMUL_N * sizeof(elem_t), SCALE_IDENTITY, false, 1)` — this sets id=1 for mvin2.
3. Instead of two separate loop nests (first all A, then all B), interleave them: for each `(i, k)` A-tile batch, immediately follow with the corresponding `(k, j)` B-tile batch, issuing A via `gemmini_block_mvin` (port 1) and B via `gemmini_extended_mvin2` (port 2). The hardware can then overlap the two DMA streams.
4. Since `gemmini_config_ld` sets the stride for port 0 and `gemmini_extended3_config_ld(..., id=1)` sets port 1 independently, both can be configured once before the combined loop without conflict.
5. The iteration structure: loop over `k`, and within each `k`, issue `i`-batched A tiles and `j`-batched B tiles, interleaving port-1 and port-2 commands.

This requires no changes to the compute or output path — only the mvin loop structure changes.

```c
void solution(void) {

  gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0);

#ifdef SPIKE_SIM
  gemmini_mx_load_scales((uint64_t)&A_scales_row, sizeof(A_scales_row), 0);
  gemmini_mx_load_scales((uint64_t)&B_scales_col, sizeof(B_scales_col), 1);
#else
  load_scale_factors((volatile uint64_t *) GEMMINI_SF_MEM_A, (uint8_t *) &A_scales_row, MATMUL_M, MATMUL_K);
  load_scale_factors((volatile uint64_t *) GEMMINI_SF_MEM_B, (uint8_t *) &B_scales_col, MATMUL_N, MATMUL_K);
#endif

  // Configure port 0 (mvin) for A: row stride = MATMUL_K bytes
  gemmini_config_ld(MATMUL_K * sizeof(elem_t));
  // Configure port 1 (mvin2) for B: row stride = MATMUL_N bytes, id=1
  gemmini_extended3_config_ld(MATMUL_N * sizeof(elem_t), MVIN_SCALE_IDENTITY, false, 1);

  // Interleave A (port 0) and B (port 1) mvin commands so hardware can
  // overlap the two DMA streams in parallel.
  for (int k = 0; k < tiles_K; k++) {
    // Issue all i-row A-tile batches for this k slice via port 0
    for (int i = 0; i < tiles_I; i += MAX_BLOCK_LEN) {
      // A tiles are NOT contiguous across i for fixed k, so batch size=1 per i
      // (consecutive k-tiles for fixed i are contiguous; here we fix k and vary i)
      elem_t *dram_ptr_a = ((elem_t*)A_in) + i * DIM * MATMUL_K + k * DIM;
      uint32_t sp_addr_a = a_base + (i * tiles_K + k) * DIM;
      gemmini_extended_mvin((void*)dram_ptr_a, sp_addr_a, DIM, DIM);
    }
    // Issue all j-col B-tile batches for this k slice via port 1
    for (int j = 0; j < tiles_J; j += MAX_BLOCK_LEN) {
      int batch = (tiles_J - j < MAX_BLOCK_LEN) ? (tiles_J - j) : MAX_BLOCK_LEN;
      elem_t *dram_ptr_b = ((elem_t*)B_in) + k * DIM * MATMUL_N + j * DIM;
      uint32_t sp_addr_b = b_base + (k * tiles_J + j) * DIM;
      // Use mvin2 (port 1) for B tiles
      gemmini_extended_mvin2((void*)dram_ptr_b, sp_addr_b, batch * DIM, DIM);
    }
  }

  // SPAD_DEST = 128 avoids aliasing with a_base = 0 region
  int SPAD_DEST = 128;

  gemmini_config_st(OUT_COLS * sizeof(out_t));

  // lut_update_granularity = tiles_K: refresh LUT only once per (i,j) output
  // tile pair, amortizing requantizer overhead across the full K reduction
  gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_K);

  // ---- Compute ----
  gemmini_loop_ws_spad(
      tiles_I, tiles_J, tiles_K,
      0, 0, 0,
      a_base,
      BANK_NUM * BANK_ROWS,
      0,
      SPAD_DEST,
      false, false,
      false, false, false,
      NO_ACTIVATION,
      0, 0,
      false,
      0x38);

  gemmini_fence();

#ifdef SPIKE_SIM
  gemmini_mx_read_smem(&C_hw[0][0], SPAD_DEST * 16, MATMUL_M * MATMUL_N);
#else
  printf("Moving out:\n");
  for (int i = 0; i < tiles_J*tiles_I*2; i++) {
      gemmini_mvout((void*)((uint64_t*) C_hw + i*2*DIM), SPAD_DEST + i*DIM);
  }
  gemmini_fence();
#endif

  gemmini_fence();
}
```

**Key changes:**
- Added `gemmini_extended3_config_ld(..., id=1)` to configure the B DMA port (port 1) with the correct stride before the combined loop.
- Restructured the two separate A/B loop nests into a single `k`-outer loop that interleaves port-0 A commands and port-1 B commands for each k-slice, allowing the hardware DMA controller to overlap them.
- B tiles are now loaded via `gemmini_extended_mvin2` (port 1) instead of `gemmini_block_mvin` (port 0), with `batch * DIM` cols to match the block-mvin behavior.
- A tiles still use port 0 (`gemmini_extended_mvin`); batching across `i` for fixed `k` is not possible since rows are not contiguous in DRAM for that access pattern, so each is issued individually (same effective bandwidth as before but now overlapped with B).
