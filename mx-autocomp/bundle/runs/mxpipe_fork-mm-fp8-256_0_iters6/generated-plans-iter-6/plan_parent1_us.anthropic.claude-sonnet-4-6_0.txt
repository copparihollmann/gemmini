## Analysis

Looking at the original code, I can identify the following structure:

1. **MVIN A loop**: Uses `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` with stride `MATMUL_K`, loading A tiles with `gemmini_block_mvin` (via mvin port 0)
2. **MVIN B loop**: Uses a **separate** `gemmini_config_ld(MATMUL_N * sizeof(elem_t))` with stride `MATMUL_N`, loading B tiles with `gemmini_block_mvin` (via mvin port 0)

The two phases are **sequential** — all A tiles are loaded, then all B tiles are loaded. This serializes the DMA traffic and leaves one port idle while the other is busy.

## Selected Strategy: #8 — Interleave per-tile A and B mvins within a unified loop

### Plan

**Key insight**: The hardware has two independent DMA ports — `mvin` (port 0, via `gemmini_extended_mvin`) and `mvin2` (port 1, via `gemmini_extended_mvin2`). These can issue concurrently. By interleaving A and B loads in a unified loop and routing them to different ports, we allow A and B DMA transfers to overlap in time.

**Concrete changes:**

1. **Issue `gemmini_config_ld` once for each port before the unified loop** (this also applies strategy #9). Port 0 (mvin) gets stride `MATMUL_K * sizeof(elem_t)` for A; port 1 (mvin2) gets stride `MATMUL_N * sizeof(elem_t)` for B. Use `gemmini_extended3_config_ld(stride, MVIN_SCALE_IDENTITY, false, 0)` with `id=0` and `id=1` respectively to configure each port independently.

2. **Replace the two separate MVIN loops with a single unified loop** over `(i, k)` and `(k, j)` tile pairs. Within each iteration, issue `gemmini_extended_mvin` (port 0) for the A tile `(i, k)` immediately followed by `gemmini_extended_mvin2` (port 1) for the corresponding B tile. Since tiles_I == tiles_J and tiles_K is shared, we can iterate over `k` in the outer loop and issue one A tile and one B tile per iteration.

   Specifically: loop over `k` (0..tiles_K), and for each `k`, loop over the i/j dimension, issuing `mvin` for `A[i][k]` and `mvin2` for `B[k][j]` back-to-back. This maximizes memory-level parallelism: the DMA controller can pipeline the two port requests simultaneously.

3. **Preserve scratchpad addresses exactly**: A at `a_base + (i*tiles_K + k)*DIM`, B at `b_base + (k*tiles_J + j)*DIM` — unchanged from original.

4. **Remove the batching (`gemmini_block_mvin`)** for simplicity of interleaving, or keep batching on each port independently if the loop structure allows it (tiles_I == tiles_J == 4 for a 64×64 matrix with DIM=16, so batch=4 fits exactly in one call per k-row).

The result is that for each `k`-slice, port 0 starts loading A tiles while port 1 simultaneously starts loading B tiles, cutting the effective DMA time roughly in half and better hiding memory latency before the compute phase.
