## Analysis

Looking at the original code, I can identify the key inefficiency targeted by **strategy 11**: both A and B tile loads use `gemmini_extended_mvin` (the same DMA port). This means A and B DMA transfers are serialized — the hardware cannot overlap them.

The architecture doc explicitly states:
> "Three independent mvin ports (mvin/mvin2/mvin3) can overlap A, B, and D loads with each other and with compute"

And strategy 11 says:
> "use `gemmini_extended_mvin2` for B-tile loads (the dedicated B-port) while using `gemmini_extended_mvin` for A-tile loads, enabling the hardware to overlap A and B DMA transfers into the scratchpad concurrently"

## Plan

**Change B-tile loads from `gemmini_extended_mvin` to `gemmini_extended_mvin2`.**

Specifically:

1. The A-tile loop already uses `gemmini_extended_mvin` with `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` — keep this unchanged.

2. For B-tile loads, the original code reconfigures with `gemmini_config_ld(MATMUL_N * sizeof(elem_t))` and calls `gemmini_extended_mvin`. 

3. Change the B-tile configuration to use `gemmini_extended3_config_ld(..., id=1)` (port 1, which corresponds to `mvin2`) with the same stride `MATMUL_N * sizeof(elem_t)`, then replace all `gemmini_extended_mvin(dram_ptr, sp_addr, batch * DIM, DIM)` calls in the B loop with `gemmini_extended_mvin2(dram_ptr, sp_addr, batch * DIM, DIM)`.

4. The stride configuration for port 0 (A) and port 1 (B) are independent — `gemmini_extended3_config_ld` with `id=0` configures port 0 (used by `mvin`), and `id=1` configures port 1 (used by `mvin2`). Both can be set before issuing any mvin commands, or interleaved — but since the A and B loops are separate, we configure port 0 before the A loop and port 1 before the B loop.

5. The net effect: the hardware's DMA scheduler can now issue A and B transfers concurrently since they use independent ports, reducing the total data-movement latency.

The B-tile scratchpad addressing (`b_base`, `b_base + (k*tiles_J + j)*DIM`) and all other logic remain identical.
