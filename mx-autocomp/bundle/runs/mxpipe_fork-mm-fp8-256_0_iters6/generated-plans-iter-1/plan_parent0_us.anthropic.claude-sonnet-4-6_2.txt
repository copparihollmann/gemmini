## Selected Strategy: #11 — Eliminate the premature `gemmini_fence()` before `gemmini_mx_read_smem` on the SPIKE path

### Why This Applies

In the SPIKE_SIM path, the code currently does:
```c
gemmini_loop_ws_spad(...);
gemmini_fence();                                    // <-- premature fence
// ...
gemmini_mx_read_smem(&C_hw[0][0], ...);           // then reads
```

The `gemmini_fence()` is a **full memory barrier** that stalls the host CPU until all in-flight accelerator operations complete. Placing it *between* `gemmini_loop_ws_spad` and `gemmini_mx_read_smem` forces the pipeline to drain completely before the read command is even issued. This adds unnecessary stall cycles because `gemmini_mx_read_smem` itself already enforces ordering — the hardware processes instructions in-order, so `MX_READ_SMEM` will naturally execute after `LOOP_WS` completes without needing an explicit fence in between.

The fence that **is required** (by Rule 9) belongs *after* `gemmini_mx_read_smem`, before the host CPU reads `C_hw` from DRAM. That fence is currently missing on the SPIKE path.

### Plan

1. **Remove** the `gemmini_fence()` call that appears between `gemmini_loop_ws_spad` and the `#ifdef SPIKE_SIM` block.
2. **Add** `gemmini_fence()` *after* `gemmini_mx_read_smem` on the SPIKE path, so the host CPU correctly waits for the DMA drain to complete before consuming `C_hw`.
3. The non-SPIKE path already has its own `gemmini_fence()` after the mvout loop — leave that unchanged.

This removes one full pipeline stall and moves the necessary fence to the correct position, reducing latency by eliminating the idle cycles between the loop completion and the smem read command being issued.
