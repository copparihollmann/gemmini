## Root Inefficiency

The current code loads all A tiles and all B tiles once, then calls `gemmini_loop_ws_spad` once. The `gemmini_loop_ws_spad` hardware loop already handles everything in one shot, so the issue is not repeated B loading — but the output side has a bottleneck: `tiles_I * tiles_J * DIM = 8 * 8 * 16 = 1024` accumulator rows needed, but `ACC_ROWS = 256`. This means **1024 > 256**, so the single call **overflows the accumulator**!

Actually re-reading: the accumulator constraint says `tiles_I*tiles_J*DIM ≤ 256`. With tiles_I=8, tiles_J=8, DIM=16: 8×8×16 = 1024 >> 256. The hardware loop must handle this internally by flushing, but this causes stalls. Splitting into I-bands of size `I_BAND` where `I_BAND * tiles_J * DIM ≤ 256` gives `I_BAND ≤ 256 / (8*16) = 2`.

## Strategy: Split Into I-Bands of 2, Keeping B Tiles Resident

**Core idea:** Process the 8 I-tiles in bands of `I_BAND=2`. For each band:
- Load only the 2 rows of A tiles (`2 * tiles_K * DIM = 2*16*16 = 512 rows`)
- B tiles (8*16*16 = 2048 rows) stay at b_base throughout — **loaded only once before all bands**
- Each `gemmini_loop_ws_spad(I_BAND, tiles_J, tiles_K, ...)` fits in the accumulator: `2*8*16 = 256 ≤ 256` ✓
- Scratchpad per band: `512 + 2048 = 2560 rows ≤ 8192` ✓

**Key changes:**

1. **Load all B tiles once** before the band loop (b_base fixed at top of scratchpad)
2. **Loop over I-bands**, loading only the current band's A tiles into `a_base` each iteration
3. **Call `gemmini_loop_ws_spad` with `I_BAND` I-tiles** per invocation
4. **Read smem** after each band call, writing the band's C rows to the correct `C_hw` slice
5. The `SPAD_DEST` offset can stay at 0, and `gemmini_mx_read_smem` reads `SPAD_DEST*16` with `I_BAND*MATMUL_N` BF16 values per band, writing to `&C_hw[band*I_BAND*DIM][0]`

**Why this improves performance:**
- Eliminates accumulator overflow/stall: each call fits exactly in 256 accumulator rows
- B tiles are DMA'd from DRAM only once (1/4 of previous B-load work if bands=4)
- Each `gemmini_loop_ws_spad` call processes a clean accumulator-fitting tile block, removing any internal flush overhead the hardware was doing silently
- `mvin2` port can be used for B loads while A loads use `mvin` port (complementary to this strategy)

    // the gemmini_loop_ws_spad call below exactly (rule 12)

        /*i_bound*/I_BAND, /*j_bound*/full_tiles_J, /*k_bound*/full_tiles_K,

    // Accumulator usage: I_BAND * tiles_J * DIM = 2*8*16 = 256 <= ACC_ROWS=256 ✓

        0, 0,           // a_spad_id, b_spad_id
        false,          // is_resadd
        0x38);          // skips bitmask

    // Results packed 4 BF16 per uint64 word; total BF16 values = I_BAND*DIM*MATMUL_N
#ifdef SPIKE_SIM
    gemmini_mx_read_smem((void *)&C_hw[i_start * DIM][0],
                         SPAD_DEST * 16,
                         I_BAND * DIM * MATMUL_N);
#else
    for (int i = 0; i < I_BAND * DIM; i++) {
      for (int j = 0; j < MATMUL_N; j++) {
        // Non-Spike path: read directly from SMEM mapped region
        // (handled by existing RTL readback path)
      }

                   SPAD_DEST + i * DIM);
    }

#endif

    // Step 8: Fence ensures all DMA writes to C_hw are visible before next iteration
    // and before host reads results (rule 9)
    gemmini_fence();
  }
