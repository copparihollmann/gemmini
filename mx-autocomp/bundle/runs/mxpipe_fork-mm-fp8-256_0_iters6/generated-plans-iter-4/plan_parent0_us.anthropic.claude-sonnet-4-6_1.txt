## Analysis

Looking at the original code, I can identify a clear inefficiency related to **strategy 9**: A tiles are loaded using `gemmini_extended_mvin` (the `mvin` port) and B tiles are loaded sequentially after A tiles complete, using `gemmini_block_mvin` (also the `mvin` port via `gemmini_config_ld`). This means A and B loads are serialized — B loading cannot begin until all A loading finishes.

The hardware has **three independent mvin ports**: `mvin` (funct k_MVIN), `mvin2` (funct k_MVIN2), and `mvin3` (funct k_MVIN3). Using `mvin` for A and `mvin2` for B, each with their own separate `gemmini_extended3_config_ld` configuration (via `id=0` for mvin and `id=1` for mvin2), allows the DMA engine to issue A and B tile transfers **concurrently**, overlapping the two memory streams.

## Plan

**Strategy 9: Use `mvin2` port for B tile loads while using `mvin` port for A tile loads with separate config per port.**

### Specific changes:

1. **Configure port 0 (mvin) for A tiles**: Use `gemmini_extended3_config_ld(MATMUL_K * sizeof(elem_t), SCALE_IDENTITY, false, 0)` with `id=0` to configure the stride for A's DRAM layout.

2. **Configure port 1 (mvin2) for B tiles**: Use `gemmini_extended3_config_ld(MATMUL_N * sizeof(elem_t), SCALE_IDENTITY, false, 1)` with `id=1` to configure the stride for B's DRAM layout.

3. **Interleave A and B mvin commands**: Issue A tile loads via `gemmini_extended_mvin(...)` and B tile loads via `gemmini_extended_mvin2(...)` in an interleaved fashion. The hardware DMA controller can then pipeline both streams simultaneously. The interleaving loop visits tiles in a combined schedule — iterate over the outer tile indices and issue an A tile command immediately followed by the corresponding B tile command (or the next scheduled B tile) so both ports stay busy.

4. **No change to the B scratchpad layout rule**: B base and indexing remain `b_base = BANK_NUM*BANK_ROWS - tiles_K*tiles_J*DIM` and `b_base + (k*tiles_J + j)*DIM`. The B block-mvin batching (`MAX_BLOCK_LEN=4`) applies to the `mvin2` port via `gemmini_block_mvin2` equivalent — issue `gemmini_extended_mvin2(dram_ptr, sp_addr, batch*DIM, DIM)` for each batch.

5. **Remove the old sequential separation**: Delete the current two-phase structure (all A mvins, then all B mvins) and replace it with a single interleaved loop that issues A and B loads together, relying on port independence for overlap.

6. The `gemmini_config_ld` (which configures port 0 only) and the separate port-1 config are issued once each before the interleaved loop begins — no per-tile config re-issue needed since stride is invariant across all tiles.

This change directly reduces the effective mvin latency from `latency(A) + latency(B)` to approximately `max(latency(A), latency(B))`, since both DMA ports operate concurrently.
