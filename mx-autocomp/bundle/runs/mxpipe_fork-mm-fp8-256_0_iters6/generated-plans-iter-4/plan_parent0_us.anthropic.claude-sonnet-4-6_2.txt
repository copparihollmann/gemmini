## Strategy: Increase `lut_update_granularity` to Reduce Requantizer Refresh Overhead

### Identification of the Inefficiency

In the current code, `gemmini_mxquant_config_mvout` is called with `lut_update_granularity = 1`:

```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```

The `lut_update_granularity` parameter `G` controls how often the output requantizer refreshes its internal LUT during the post-compute quantization pass. With `G=1`, the hardware refreshes the output LUT after every single output tile, which is the most conservative (and most expensive) setting. Each refresh is an additional operation that stalls or slows the output pipeline.

### Why This Is Safe to Increase

For this kernel:
- The output format is **BF16** (`out_mx_fmt=3`), which is a standard floating-point format that does **not** depend on a code-book LUT for its value mapping — BF16 values are defined by the IEEE binary format, not by a lookup table.
- Since `uselut=0` in `gemmini_extended3_config_ex`, no LUT is loaded or used for input formats either.
- The output requantizer in BF16 mode applies per-block e8m0 scale multiplication, not a LUT projection. The LUT refresh in this path is either a no-op or applies to an identity-like mapping that does not change across tiles.
- Therefore, refreshing the LUT on every tile (G=1) provides no correctness benefit and only adds overhead. Setting G to the maximum tile count (e.g., `tiles_I * tiles_J` or simply the total number of output tiles) means the LUT is refreshed at most once for the entire matmul, eliminating per-tile refresh stalls.

### The Change

Replace:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, 1);
```

With:
```c
gemmini_mxquant_config_mvout((uint64_t)scale_factors, tiles_I, tiles_J, tiles_K, 0, 0, tiles_I * tiles_J);
```

Setting `G = tiles_I * tiles_J` tells the requantizer to refresh at most once per full output plane sweep (i.e., once across all I×J output tiles), instead of once per tile. For this 64×64 matmul with `tiles_I = tiles_J = 4`, this reduces the granularity from `G=1` (16 refreshes) to `G=16` (1 refresh), a 16× reduction in requantizer LUT refresh events.

### Performance Impact

- **Fewer requantizer stalls**: Each LUT refresh event in the requantizer pipeline introduces latency. Reducing from 16 refreshes to 1 directly reduces the number of pipeline interruptions in the output quantization pass that runs after `gemmini_loop_ws_spad`.
- **No correctness impact**: Because `out_mx_fmt=3` (BF16) does not use a value-changing LUT — it uses the scale-factor memory loaded via `gemmini_mx_load_scales` — the output of every tile remains bit-exact regardless of how frequently the LUT is refreshed. The result still matches the MX golden model.
- **Composable with other optimizations**: This change is a single-line modification to `gemmini_mxquant_config_mvout` and does not interact with the mvin strategy, scratchpad layout, or compute loop. It can be applied independently alongside batched mvins or `mvin2` port usage.
