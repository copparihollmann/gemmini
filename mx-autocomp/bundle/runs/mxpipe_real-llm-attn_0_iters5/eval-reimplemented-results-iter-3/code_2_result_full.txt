#### Inefficiency Analysis
The original code uses a small tiling factor (`BLK`) that forces the matrix multiplication to be split into multiple blocks (`BLOCKS_M` and `BLOCKS_N`). This introduces several major performance overheads:
1. **CPU Host Staging Overhead:** It requires copying slices of scale factors from the global scale arrays (`A_scales_row` and `B_scales_col`) into temporary host buffers (`A_s` and `B_s`) via `memcpy` before loading them.
2. **Redundant Hardware Scaling Loads:** The scales are repeatedly loaded into Gemmini's scale memory inside the nested loop structure.
3. **Underutilization:** The scratchpad and accumulator are heavily underutilized (0KB out of 256KB/64KB).

#### Optimization Steps
1. **Eliminate Outer Loops:** Since the entire $64 \times 64$ matrix easily fits within the 256KB scratchpad and 64KB accumulator, we can scale the tile sizes up to the full matrix dimensions (`MATMUL_M`, `MATMUL_N`, `MATMUL_K`). This completely eliminates the outer loop overhead.
