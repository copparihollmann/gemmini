An elegant way to optimize the performance of the provided Gemmini kernel is by implementing **Strategy 1: Ping-pong accumulator destinations (SPAD_DEST)**.

### Plan

1. **Analyze the Loop Structure**:
   The inner loop iterates over column blocks `j0` (`BLOCKS_N`). In the baseline code, each iteration writes its results to the same shared memory location, `SPAD_DEST = 128`, and immediately stalls the CPU with a `gemmini_fence()` to wait for the data to be read into DRAM via `gemmini_mx_read_smem()`. This prevents any overlap between the computation of the next column block and the memory drain of the current block.

2. **Define Double-Buffer Zones**:
   To prevent overwriting active accumulator data, we can define two disjoint zones in `mx_smem`.
   - Zone 0 starting at `128`
   - Zone 1 starting at `128 + tiles * tiles * DIM` (dynamically sized based on the actual tile counts to prevent any overlap).

3. **Ping-Pong the Destinations**:
   In each iteration of the `j0` loop, compute the destination `current_spad_dest` based on the loop index parity:
   ```c
   int current_spad_dest = (j0 % 2 == 0) ? 128 : (128 + tiles * tiles * DIM);
   ```

4. **Pipelined Synchronization**:
   - Remove the immediate `gemmini_fence()` from the end of the `j0` loop. This allows `gemmini_mx_read_smem()` to execute asynchronously while the CPU continues to issue scale loads, MVINs, and the next `gemmini_loop_ws_spad` compute using the alternate `SPAD_DEST` buffer.
   - Insert a conditional `gemmini_fence()` at the beginning of the `j0` loop (only when `j0 >= 2`). This ensures that before we reuse a `SPAD_DEST` buffer, any outstanding read from two iterations ago has completed.
   - Insert a final `gemmini_fence()` after the `j0` loop terminates to guarantee all remaining asynchronous read operations are complete before moving to the next row block or returning.
