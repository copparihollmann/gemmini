### Optimization Plan

Our goal is to apply **Strategy 2: Multi-channel load stride configuration** to eliminate the redundant configuration of load strides inside the nested loops.

#### Inefficiencies in the original code:
In the original kernel, `gemmini_config_ld` is called twice inside the `j0` loop:
1. Once with stride `MATMUL_K * sizeof(elem_t)` before loading matrix $A$.
2. Once with stride `MATMUL_N * sizeof(elem_t)` before loading matrix $B$.

Since Gemmini supports multiple load channels (IDs), we can configure the load strides for different channels once outside the loops and then dispatch the memory loads to those respective channels. This completely removes the configuration overhead from the inner compute loops.

#### Steps to implement the optimization:
1. **Configure Load Channels Outside the Loops**:
   We will configure Load ID `0` for matrix $A$ and Load ID `1` for matrix $B$ before entering the loops:
   - Configure Load ID `0` with stride `MATMUL_K * sizeof(elem_t)` using `gemmini_extended3_config_ld`.
   - Configure Load ID `1` with stride `MATMUL_N * sizeof(elem_t)` using `gemmini_extended3_config_ld`.

2. **Remove Inner-loop Reconfigurations**:
   Delete both `gemmini_config_ld(...)` calls inside the `j0` loop.

3. **Utilize Multi-channel Loads**:
   - Keep matrix $A$ loads mapped to `gemmini_extended_mvin` (which implicitly uses Load ID `0`).
   - Change matrix $B$ loads to use `gemmini_extended_mvin2` (which uses Load ID `1`).

This eliminates the configuration overhead of swapping strides in every iteration of the outer block loops.
