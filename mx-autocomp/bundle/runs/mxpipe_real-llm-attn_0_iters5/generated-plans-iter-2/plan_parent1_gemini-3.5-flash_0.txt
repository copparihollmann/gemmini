An elegant and highly effective optimization plan is to apply **Strategy 1: eliminate redundant computation** (which includes redundant memory transfers and configuration overheads).

### Inefficiency Analysis
In the baseline code, several operations are executed repeatedly inside the inner `j0` loop, despite their operands or parameters being invariant across the `j0` dimension:
1. **Activation (A) Matrix Loading**: Matrix `A_in` only depends on the row block index `i0`. However, the code re-loads the same tile of `A` from DRAM into the scratchpad for every single iteration of the column block index `j0`. This introduces massive, redundant DRAM-to-scratchpad transfer overhead.
2. **Activation Scale Factor Loading**: Similarly, `A_scales_row` only depends on `i0` but is copied via `memcpy` and loaded via `gemmini_mx_load_scales(..., 0)` on every `j0` step.
3. **Redundant Configurations and Flushes**: Both `gemmini_extended3_config_ex` and `gemmini_flush(0)` are executed inside the inner loop, incurring unnecessary processor-accelerator round-trips.

Because the scratchpad is large enough (256KB) to hold the current block of `A` and `B` simultaneously without overlap (using the top-down/bottom-up layout), we can load `A` and its scales **once** per `i0` iteration and reuse them across all `j0` iterations.

---

### Optimization Plan

1. **Hoist Static Setup**:
   - Move `gemmini_extended3_config_ex` to the very beginning of `solution()`, before any loops, as the execution configuration is invariant.
   - Move `gemmini_flush(0)` to the beginning of the function.

2. **Hoist Activation Tile and Scale Loading**:
   - Move the copying of row scales to `A_s` and the corresponding scale-load `gemmini_mx_load_scales(..., 0)` from the `j0` loop up to the `i0` loop.
   - Configure the load stride for `A` using `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` once in the `i0` loop.
   - Move the nested loops that perform `gemmini_extended_mvin` for `A_in` out of the `j0` loop and place them directly in the `i0` loop.

3. **Retain Column-Dependent Loading in the Inner Loop**:
   - Keep the column scale loading (`B_scales_col` -> `B_s` -> `gemmini_mx_load_scales(..., 1)`) and weight tile loading (`B_in` -> scratchpad) inside the `j0` loop, as they vary with `j0`.

4. **Preserve Computations and Writebacks**:
   - Execute the WS matmul loop `gemmini_loop_ws_spad` with `skips = 0x38` inside the `j0` loop. Since both `A` and `B` are preloaded in non-overlapping scratchpad regions, the hardware will correctly compute the results and write them back.

This optimization eliminates $(BLOCKS\_N - 1) \times \text{size}(A)$ DRAM accesses per row-block, greatly reducing latency and maximizing the utilization of the scratchpad.
