An elegant and highly effective optimization plan to improve the execution time of the matrix multiplication kernel is to apply **Strategy 2: reuse loaded B (weight) tiles across multiple I-tile iterations without re-mvin**.

### Inefficiency Analysis
In the original kernel, the outer loop iterates over the rows of $A$ (`i0`), and the inner loop iterates over the columns of $B$ (`j0`). Because $B$ is loaded inside the inner loop, the same $B$ (weight) tiles are transferred from DRAM to the scratchpad over and over again for every single row block $i0$. Since weight-stationary dataflow is configured (`WEIGHT_STATIONARY`), reloading $B$ on every $i0$ iteration incurs massive redundant DRAM bandwidth overhead, which is the primary bottleneck on this accelerator.

### Optimization Plan

1. **Loop Nest Reordering**: 
   Swap the loop order of $M$-blocks (`i0`) and $N$-blocks (`j0`) so that `j0` becomes the outer loop and `i0` becomes the inner loop.
   
2. **Hoist B Tile MVIN**:
   * For any given `j0` column block, the weights ($B$ tiles) are constant. Hoist the initialization and `gemmini_extended_mvin` of $B$ tiles out of the inner `i0` loop and place them directly under the outer `j0` loop.
   * This ensures $B$ tiles are copied from DRAM to the top of the scratchpad (`b_base`) exactly **once** per `j0` iteration, rather than `BLOCKS_M` times.
   
3. **Preserve Inner Loop Execution & Sequence**:
   * The inner `i0` loop will now focus entirely on streaming the activation tiles of $A$ and performing the systolic compute.
   * To satisfy the strict programming model sequence, inside the inner loop we will:
     1. Configure execution format via `gemmini_extended3_config_ex`.
     2. Load scale factors for both A and B using `gemmini_mx_load_scales`. (The B scale factors `B_s` are loaded once to scale memory to satisfy hardware sequence requirements, which has negligible latency compared to tile memory loads).
     3. Load $A$ tiles into the low scratchpad region (`a_base = 0`).
     4. Program the requantizer and bounds via `gemmini_config_st` + `gemmini_mxquant_config_mvout`.
     5. Execute the fused compute loop via `gemmini_loop_ws_spad`. Since $B$ tiles still reside safely at `b_base` (unmodified by $A$ loads or compute), the array correctly computes using the pre-loaded weight tiles.
     6. Drain outputs to DRAM and sync with `gemmini_mx_read_smem` + `gemmini_fence()`.

This strategy dramatically reduces the DRAM transfer volume for $B$ (by a factor of `BLOCKS_M`), directly tackling the performance bottleneck without altering numerical correctness.
