### Optimization Plan

We will apply **Strategy 5: Elimination of gemmini_flush Inside Loops** to address the major performance bottleneck in the original code.

#### 1. Inefficiency Analysis
In the original kernel, `gemmini_flush(0)` is invoked in the innermost loop (`j0` loop) on every tile evaluation:
```c
for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    ...
    gemmini_flush(0);
    gemmini_extended3_config_ex(...);
    ...
}
```
`gemmini_flush(0)` flushes the coprocessor's TLBs and state, which drains the hardware execution pipelines, destroys the pipelined execution overlap between the host CPU and the Gemmini coprocessor, and incurs a significant latency penalty. Since memory coherency and execution ordering are already guaranteed by `gemmini_fence()` and RoCC instruction queuing, calling `gemmini_flush` inside the loops is completely redundant and catastrophically slow.

#### 2. Optimization Steps
- **Move the Flush Operation:** Remove the `gemmini_flush(0)` call from inside the nested `j0` loop.
- **Perform Initial Flush:** Place a single `gemmini_flush(0)` at the very beginning of the `solution()` function before entering the loops. This ensures the coprocessor TLB is warmed up/cleared once at start-up without penalizing iterative runtime.
- **Maintain Execution Semantics:** Keep the rest of the loop structure, memory staging, DMA transfers, scale loads, computations, and synchronization structures exactly the same to guarantee bit-exact correctness.

By eliminating this redundant flush, we allow Gemmini's DMA engine and compute units to run back-to-back in a pipelined fashion, dramatically reducing the execution latency.
