An elegant and highly effective optimization plan to address the performance bottlenecks in the current code is to apply **Strategy 9: Direct scale factor DMA from DRAM**. 

### Inefficiency Analysis
In the original code, the CPU performs nested `memcpy` operations inside the execution loops to stage scale factors into the temporary buffers `A_s` and `B_s`. This is because the original scale-factor matrices (`A_scales_row` and `B_scales_col`) are stored in a layout where the values for a specific block tile are non-contiguous. 

This host-side data staging introduces several severe inefficiencies:
1. **CPU Overhead**: The CPU spends significant cycles copying small chunks of memory (`BLK` bytes) in nested loops, stalling the Gemmini accelerator.
2. **Redundant Scale Loads**: The A-scale factors (which only depend on `i0`) are loaded into Gemmini's scale memory inside the inner `j0` loop. This wastes DRAM bandwidth by reloading the exact same scale factors `BLOCKS_N` times.
3. **No DMA Pipelining**: We are unable to utilize the fast on-chip DMA engine for zero-copy scale transfers.

### Optimization Plan: Direct Scale Factor DMA

To eliminate host staging completely, we will restructure the scale-factor matrices in DRAM so that the scale factors for any given tile are completely contiguous. This enables direct zero-copy DMA streaming via `gemmini_mx_load_scales`.

1. **Pre-arrange Scale Matrices (Offline/Initialization Structuring)**:
   We will define restructured scale arrays:
   - `A_scales_row_structured[BLOCKS_M][MATMUL_K / 32][BLK]`
   - `B_scales_col_structured[BLOCKS_N][MATMUL_K / 32][BLK]`
   At the start of the function (simulating offline compiler/initialization time), we will copy the scale factors from the default non-contiguous layout into these restructured contiguous layouts.

2. **Direct DMA Transfers**:
   - For A scales: Pass the direct DRAM address `&A_scales_row_structured[i0]` to `gemmini_mx_load_scales` with `sel = 0`.
   - For B scales: Pass the direct DRAM address `&B_scales_col_structured[j0]` to `gemmini_mx_load_scales` with `sel = 1`.

3. **Hoist A-Scale DMA Loading**:
   Since the restructured A-scale factors only depend on `i0`, we can hoist the `gemmini_mx_load_scales` call for A out of the `j0` loop entirely. It will run exactly once per `i0` iteration. Since the A-scale and B-scale memories are independent in the hardware, loading B-scales inside the `j0` loop will not overwrite the loaded A-scales.

This strategy completely eliminates the host `memcpy` overhead inside the execution loops, reduces DRAM scale traffic by `BLOCKS_N` times, and allows the hardware to run at maximum compute utilization.
