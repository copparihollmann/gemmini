An elegant and highly effective strategy to optimize this kernel is **Global Tiling to Eliminate CPU Scale Staging and Maximize On-Chip Resource Utilization**.

### Why the Original Code is Inefficient
1. **CPU Data Staging Bottleneck:** The original code slices the scale factors (`A_scales_row` and `B_scales_col`) inside the nested `i0` and `j0` loops using CPU-side `memcpy` operations into temporary arrays (`A_s` and `B_s`). This forces the host CPU to perform redundant memory copies, stalling the Gemmini accelerator.
2. **Underutilized Hardware Resources:** The diagnostics report 0KB utilization for both the scratchpad and accumulator. By processing small block sizes (`BLK`), the systolic array spends more time waiting for configuration, scale/LUT reloads, and dram-to-scratchpad transfers than performing actual matrix multiplication.

---

### The Proposed Strategy: Global Tiling
Instead of dividing the problem into small, CPU-managed blocks, we can scale up the tiling parameters to process the entire matrix dimensions (`REAL_M`, `REAL_N`, `MATMUL_K`) in a single fused hardware loop, or use the largest possible block size (`BLK`) that fully utilizes the scratchpad and accumulator. 

This brings two massive performance advantages:
1. **Direct Scale Loads:** The scale factors can be streamed directly from their original DRAM locations (`A_scales_row` and `B_scales_col`) into Gemmini’s scale-factor memory via `gemmini_mx_load_scales` without any CPU staging or `memcpy` overhead.
2. **Maximized SRAM Utilization:** Processing larger matrices directly on-chip keeps the systolic array continuously fed, maximizing the occupancy of the 256KB scratchpad and 64KB accumulator.

---

### How to Modify the Code

1. **Calculate the Maximum Allowed Tile Counts:**
   First, determine if the entire matrix fits on-chip. The hardware constraints are:
   $$\text{Scratchpad Row Limit: } (\text{tiles}_I \times \text{tiles}_K + \text{tiles}_J \times \text{tiles}_K) \times 16 \le 8192$$
   $$\text{Accumulator Row Limit: } \text{tiles}_I \times \text{tiles}_J \times 16 \le 256$$
   If the total problem size satisfies these limits, remove the outer loops `i0` and `j0` entirely.

2. **Load Scales Directly from DRAM:**
   Remove the CPU `memcpy` loops and temporary buffers `A_s` and `B_s`. Issue the scale loads directly using the original global matrices:
   ```c
   gemmini_mx_load_scales((uint64_t)A_scales_row, sizeof(A_scales_row), 0);
   gemmini_mx_load_scales((uint64_t)B_scales_col, sizeof(B_scales_col), 1);
   ```

3. **Configure and Run the Fused Loop globally:**
   Set `tiles_I = REAL_M / DIM`, `tiles_J = REAL_N / DIM`, and `tiles_K = MATMUL_K / DIM`.
   Perform strided MVINs directly from `A_in` and `B_in` using their global strides to populate the scratchpad:
   * **A layout:** `a_base + (i * tiles_K + k) * DIM`
   * **B layout:** `b_base + (k * tiles_J + j) * DIM` (where `b_base = 8192 - tiles_K * tiles_J * DIM`)

4. **Requantize and Drain Once:**
   Configure `gemmini_mxquant_config_mvout` and trigger the compute using the global tile parameters. Once complete, drain the entire output from the shared memory word offset to `C_hw` in one sequence, followed by a single `gemmini_fence()`.
