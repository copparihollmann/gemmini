### Optimization Plan: Eliminate Host-Side Scale Factor Buffering (Strategy 5)

#### 1. Analysis of the Inefficiency
In the baseline code, the host CPU performs redundant `memcpy` operations to copy slices of the scale factor matrices `A_scales_row` and `B_scales_col` into temporary stack-allocated buffers `A_s` and `B_s` on every iteration of the outer loops:
```c
// A scales only depend on i0: copy once per i0, reuse across all j0.
for (int g = 0; g < MATMUL_K / 32; g++)
  memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK);

...

// B scales depend on j0: copy once per (i0,j0).
for (int g = 0; g < MATMUL_K / 32; g++)
  memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK);
```
These temporary buffers are then loaded into the Gemmini scale-factor SRAM using `gemmini_mx_load_scales`. Because host-to-scratchpad/SRAM data transfer on this architecture is managed via explicit DMA, we can completely bypass the CPU-driven `memcpy` staging step. Operating the host CPU to tile and copy memory blocks is highly inefficient and acts as a major bottleneck.

#### 2. Proposed Changes
We will eliminate the host-side arrays `A_s` and `B_s` along with their corresponding `memcpy` loops. Instead, we will configure the Gemmini DMA engine to stream scale factors directly from their original strided positions in DRAM:

1. **Calculate Direct DRAM Addresses:** 
   - The starting address for the activation (A) scale block of the current row-block $i_0$ is `(uint64_t)&A_scales_row[0][i0 * BLK]`.
   - The starting address for the weight (B) scale block of the current column-block $j_0$ is `(uint64_t)&B_scales_col[0][j0 * BLK]`.

2. **Redirect scale loading:** 
   - Replace the load for A scales with:
     ```c
     gemmini_mx_load_scales((uint64_t)&A_scales_row[0][i0 * BLK], BLK, 0);
     ```
   - Replace the load for B scales with:
     ```c
     gemmini_mx_load_scales((uint64_t)&B_scales_col[0][j0 * BLK], BLK, 1);
     ```
     *(Note: If the scale factors consist of multiple quantization groups along K, i.e., `MATMUL_GK > 1`, and the sub-blocks are layout-contiguous or can be loaded sequentially, we adjust the length parameter to `BLK * MATMUL_GK` accordingly.)*

By pointing `gemmini_mx_load_scales` directly to the source DRAM slices, we leverage the hardware's fast DMA capabilities and completely eliminate CPU staging overhead.
