An elegant and highly effective way to optimize this kernel is to apply **Strategy 1: Loop Tiling** (specifically, scaling up the tile sizes to maximize scratchpad and accumulator utilization while completely eliminating host-side scale factor staging).

### Inefficiency Analysis
1. **Underutilized Scratchpad & Accumulator:** The baseline code processes very small blocks (`BLK`), leading to 0% utilization of the 256KB scratchpad and 64KB accumulator.
2. **Dominant Host Staging Overhead:** Copying scale factors via host-CPU `memcpy` (`A_s` and `B_s`) is extremely slow and dominates execution. Because the blocks are so small, scale factors must be constantly packed and loaded.
3. **Frequent Re-configuration:** Hardware configurations (`gemmini_extended3_config_ex`, `gemmini_config_ld`, `gemmini_config_st`) are repeatedly executed inside the outer loops, adding control-flow overhead.

### Optimization Plan: Loop Tiling (Strategy 1)
We will increase the tiling dimensions to the maximum possible size that safely fits within the Gemmini hardware constraints. By processing the entire matrix (or the largest possible tiles) in one go:
1. **Maximize Memory Utilization:** We will calculate the tile counts `tiles_I = MATMUL_M / DIM`, `tiles_J = MATMUL_N / DIM`, and `tiles_K = MATMUL_K / DIM`. This utilizes the scratchpad up to the limit: `(tiles_I * tiles_K + tiles_J * tiles_K) * DIM <= 8192` rows, and accumulator limit: `tiles_I * tiles_J * DIM <= 256` rows.
2. **Eliminate Host Staging (`memcpy`):** Since we tile over the entire dimensions directly, the scale factors in DRAM (`A_scales_row` and `B_scales_col`) are already contiguous and block-aligned. We can load them directly via `gemmini_mx_load_scales` without any host-side staging into temporary buffers `A_s` and `B_s`.
3. **Minimize Instruction Overhead:** The nested loops for `i0` and `j0` are eliminated. Hardware configurations are executed once per large tile rather than repeatedly for tiny blocks.
