An elegant and highly effective optimization strategy for this code is to **compile the Gemmini instruction-configuration sequences into non-inlined functions**.

### The Strategy: Out-of-Line Configuration Helpers

The baseline code repeatedly issues config macros (`gemmini_extended3_config_ex`, `gemmini_config_ld`, `gemmini_config_st`, and `gemmini_mxquant_config_mvout`) inside the outer loops. Because these macros expand into complex inline assembly instructions with a large number of inputs, they create severe **register pressure** and **instruction-cache (I-cache) thrashing** on the RISC-V host processor. 

By encapsulating these configuration sequences into standalone, non-inlined helper functions (using `__attribute__((noinline))`), we can:
1. **Reduce Host Register Spilling**: Prevent the compiler from spilling loop induction variables (such as `i0`, `j0`, `r`, `g`, etc.) to the stack.
2. **Improve Host I-Cache Locality**: Shrink the footprint of the hot matmul loop in `solution` so it fits entirely within the host's L1 instruction cache.
3. **Amortize Call Overhead**: Since configuration happens once per block (not per tile), the small overhead of a function call is completely negligible compared to the execution cycles of the hardware matmul.

---

### Implementation Plan

1. **Define Non-Inlined Helpers**:
   Create three specialized helper functions marked `__attribute__((noinline))` to isolate the inline assembly expansions:
   * `config_gemmini_ex()`: Wraps `gemmini_extended3_config_ex` to set up formats and dataflow.
   * `config_gemmini_ld_stride(stride)`: Wraps `gemmini_config_ld` to set up load strides.
   * `config_gemmini_st_quant(out_stride, scale_dram, tiles_I, tiles_J, tiles_K)`: Wraps both `gemmini_config_st` and `gemmini_mxquant_config_mvout` to configure output write-back parameters.

2. **Refactor the `solution` Loop**:
   Replace the inline macro call sites inside the `solution()` function with calls to these helper functions. Ensure the exact programming sequence is maintained:
   $$\text{Config EX} \rightarrow \text{Load Scales} \rightarrow \text{Config LD} \rightarrow \text{MVIN} \rightarrow \text{Config ST/Quant} \rightarrow \text{Compute Loop} \rightarrow \text{Read SMEM} \rightarrow \text{Fence}$$

3. **Verify Constraints**:
   Keep all block dimensions, scale loading, scratchpad indexing (`a_base`, `b_base`), accumulator limits, and the terminal `gemmini_fence()` exactly as specified to ensure bit-exact output equivalence on the Spike simulator.
