Plan: ### Optimization Plan

We will apply **Strategy 6: Consolidate scale factor arrays to minimize `gemmini_mx_load_scales` call count across tiled loop iterations**.

#### Analysis of Inefficiencies
In the baseline implementation, both the activation scale factors (`A_scales_row`) and weight scale factors (`B_scales_col`) are copied via host `memcpy` into staging buffers (`A_s` and `B_s`) and loaded into Gemmini's scale memory via `gemmini_mx_load_scales` inside the innermost tiling loop over `j0` (representing columns of $B$).
- **Redundant Copies & Loads of A Scales**: The activation scale factors `A_scales_row` solely depend on the row block index `i0`. Re-staging and reloading them inside the `j0` loop for every column block of $B$ is highly redundant and consumes excessive host CPU cycles and coprocessor load bandwidth.

#### Optimization Strategy
1. **Hoist Activation Scale Staging and Loading**: Move the `memcpy` of `A_s` and its corresponding `gemmini_mx_load_scales(..., 0)` call outside the `j0` loop into the outer `i0` loop. Since these scales persist in Gemmini's internal scale memory until overwritten, we only load them once per row block.
2. **Move Persistent Configurations**: Hoist `gemmini_flush(0)` and `gemmini_extended3_config_ex` to the start of the function, since execution configurations and formats are static across all tiles.
