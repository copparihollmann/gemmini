### Optimization Strategy: Chunked-K Accumulation with Maximized Accumulator Tiling

1. **Why the Baseline is Inefficient:**
   The baseline uses a small tile block size `BLK`, which fails to utilize the capacity of the accumulator (using 0KB out of 64KB) and scratchpad. This leads to a massive number of outer loop iterations (`i0`, `j0`), incurring high host-side CPU overhead and redundant scale factor DRAM transfers.

2. **The New Strategy (Chunked-K Accumulation):**
   * **Maximize `BLK` to 64:** We increase the block size `BLK` to 64, which corresponds to `tiles_I = 4` and `tiles_J = 4`. This fully utilizes the maximum capacity of the accumulator ($4 \times 4 \times 16 = 256$ rows, or exactly 100% of the 256 accumulator rows).
   * **Chunking K-dimension:** Because a large `BLK=64` along with the full $K$-dimension would overflow the scratchpad memory, we split the $K$-dimension into manageable chunks (e.g., `chunk_K_tiles = 16`, representing 256 elements along $K$).

      gemmini_fence();
