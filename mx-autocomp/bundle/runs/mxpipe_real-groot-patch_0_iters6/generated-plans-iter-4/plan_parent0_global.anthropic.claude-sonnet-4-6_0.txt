## Analysis

Looking at the code, the key inefficiency I'll target is **strategy 6**: eliminate the static `pre_A_s` / `pre_B_s` pre-staging arrays and the associated `memcpy` work, passing `A_scales_row` / `B_scales_col` directly to `gemmini_mx_load_scales`.

### Understanding the Current Layout

The hardware `gemmini_mx_load_scales` expects a **contiguous** block of bytes: for A, it needs `[GK][BLK]` bytes (GK scale groups, each with BLK=32 scale values for the row-block). For B, similarly `[GK][BLK]`.

The golden data layout is:
- `A_scales_row[g][i]` — indexed as `A_scales_row[g][i0*BLK + local_i]`
- `B_scales_col[g][j]` — indexed as `B_scales_col[g][j0*BLK + local_j]`

The current code pre-stages into `pre_A_s[i0][g][0..BLK-1]` to make the data contiguous per block, but this costs O(BLOCKS_M × GK × BLK + BLOCKS_N × GK × BLK) memcpy work upfront.

### Can We Eliminate Pre-Staging?

The question is whether `A_scales_row[g][i0*BLK]` is already contiguous in memory for `g=0..GK-1`. The layout `A_scales_row[GK][M]` stores `GK` rows each of length `M`. For block `i0`, we need elements at column offsets `i0*BLK .. i0*BLK+BLK-1` across all `GK` rows — these are **strided**, not contiguous.

So the pre-staging cannot be fully eliminated without hardware scatter support. However, we **can** eliminate the upfront O(all-blocks) pre-staging and instead do the per-block restride **inline** in the i0/j0 loop, only staging the one block needed per iteration, using a single small stack-local buffer rather than large static arrays. This removes the O(BLOCKS_M×GK×BLK + BLOCKS_N×GK×BLK) upfront memcpy cost and eliminates the large static memory.

But strategy 5 is also highly applicable: **hoist A scale loading out of the j0 loop** since A scales only change when i0 changes. Combined with strategy 6's spirit (minimal staging), this means:

### Plan: Apply Strategy 6 — Eliminate Static Pre-Staging Arrays

**Specific changes:**

1. **Remove `static uint8_t pre_A_s[BLOCKS_M][GK][BLK]` and `pre_B_s[BLOCKS_N][GK][BLK]`** — these are large static arrays that require the full upfront O(total_blocks × GK × BLK) memcpy pass before any compute begins.

2. **Replace with two small stack/local buffers** `uint8_t cur_A_s[GK][BLK]` and `uint8_t cur_B_s[GK][BLK]` — sized for exactly one block at a time.

3. **Move the restride into the loop**: fill `cur_A_s` once per i0 iteration (hoisted outside j0), fill `cur_B_s` once per j0 iteration. This does the same work but deferred to when needed, and never requires allocating memory for all blocks simultaneously.

4. **Apply strategy 5 simultaneously**: the `gemmini_mx_load_scales` for A is hoisted to the i0 loop since A scales are fixed across all j0 for a given i0. This eliminates `BLOCKS_N - 1` redundant A-scale loads per i0 row-block.

This reduces the upfront memcpy from `O(BLOCKS_M*GK*BLK + BLOCKS_N*GK*BLK)` to zero (the work is deferred and amortized), eliminates the large static arrays, and reduces scale-load instructions by hoisting A out of the j0 loop.

```c
void solution(void) {
  const int GK = MATMUL_K / 32;

  // Small per-block staging buffers (stack, one block at a time)
  uint8_t cur_A_s[GK * BLK];   // [g * BLK + local_i]
  uint8_t cur_B_s[GK * BLK];   // [g * BLK + local_j]

  static uint32_t scale_factors[BLK * BLK / 32] __attribute__((aligned(32))) = {0};

  for (int i0 = 0; i0 < BLOCKS_M; i0++) {
    int mrows = REAL_M - i0 * BLK; if (mrows > BLK) mrows = BLK; if (mrows <= 0) continue;

    // Restride A scales for this i0 block — done once per i0, amortized over all j0
    for (int g = 0; g < GK; g++)
      memcpy(&cur_A_s[g * BLK], &A_scales_row[g][i0 * BLK], BLK);

    for (int j0 = 0; j0 < BLOCKS_N; j0++) {
      int ncols = REAL_N - j0 * BLK; if (ncols > BLK) ncols = BLK; if (ncols <= 0) continue;

      // Restride B scales for this j0 block
      for (int g = 0; g < GK; g++)
        memcpy(&cur_B_s[g * BLK], &B_scales_col[g][j0 * BLK], BLK);

      int tiles = BLK / DIM, tiles_K = MATMUL_K / DIM;
      uint32_t a_base = 0;
      uint32_t b_base = BANK_NUM * BANK_ROWS - tiles * tiles_K * DIM;
      int SPAD_DEST = 128;
      int pad_i = BLK - mrows, pad_j = BLK - ncols;

      gemmini_flush(0);
      gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY,
                                  1, 1, 0, 0, false, 0, 0, 3, 0);

      // A scales: loaded once per (i0, j0) pair but cur_A_s is already
      // prepared outside the j0 loop for this i0 block.
      // B scales: loaded fresh each j0 from cur_B_s.
      gemmini_mx_load_scales((uint64_t)cur_A_s, A_S_BYTES, 0);
      gemmini_mx_load_scales((uint64_t)cur_B_s, B_S_BYTES, 1);

      gemmini_config_ld(MATMUL_K * sizeof(elem_t));
      for (int i = 0; i < tiles; i++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin(
            (void*)(((elem_t*)A_in) + (i0 * BLK + i * DIM) * MATMUL_K + k * DIM),
            a_base + (i * tiles_K + k) * DIM, DIM, DIM);

      gemmini_config_ld(MATMUL_N * sizeof(elem_t));
      for (int j = 0; j < tiles; j++)
        for (int k = 0; k < tiles_K; k++)
          gemmini_extended_mvin(
            (void*)(((elem_t*)B_in) + (k * DIM) * MATMUL_N + (j0 * BLK + j * DIM)),
            b_base + (k * tiles + j) * DIM, DIM, DIM);

      gemmini_config_st(BLK_OUTC * sizeof(out_t));
      gemmini_mxquant_config_mvout((uint64_t)scale_factors,
                                   tiles, tiles, tiles_K, 0, 0, 1);
      gemmini_loop_ws_spad(tiles, tiles, tiles_K, pad_i, pad_j, 0,
                           a_base, BANK_NUM * BANK_ROWS, 0, SPAD_DEST,
                           false, false, false, false, false,
                           NO_ACTIVATION, 0, 0, false, 0x38);

      for (int r = 0; r < mrows; r++)
        gemmini_mx_read_smem(&C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
                             SPAD_DEST * 16 + r * BLK, ncols);
      gemmini_fence();
    }
  }
}
```

Wait — I need to reconsider strategy 5 more carefully. The `gemmini_mx_load_scales` for A **can** be hoisted out of the j0 loop because the same `cur_A_s[i0]` is used for all j0. But the programming model requires: `config_ex → load_scales_A → load_scales_B → mvin → mxquant_config → loop_ws_spad`. The A scale load must precede B scale load and compute, but it can be issued once before the j0 loop.

However, `gemmini_flush(0)` and `gemmini_extended3_config_ex` are inside the j0 loop. If we hoist A-scale loading, we must ensure config_ex still precedes it. The cleanest approach: hoist both the A-scale restride **and** the `gemmini_mx_load_scales(A)` call to immediately after `gemmini_extended3_config_ex` at i0 level, but `gemmini_extended3_config_ex` must stay per-iteration (due to flush). This creates a sequencing conflict.

To properly apply strategy 5, restructure so `config_ex` is issued once at i0 level (hoisted), then A-scale load once, then j0 inner loop handles B-scale + mvin + compute. The `gemmini_flush` can remain inside or be moved.

## Final Plan

**Strategy applied: 6 (eliminate static pre-staging arrays) + 5 (hoist A-scale load outside j0 loop)**

### Changes:

1. **Remove large static `pre_A_s[BLOCKS_M][GK][BLK]` and `pre_B_s[BLOCKS_N][GK][BLK]`** and the upfront double-nested `memcpy` loops that populate them.

2. **Introduce two small local buffers** `cur_A_s[GK*BLK]` and `cur_B_s[GK*BLK]` on the stack (or as `static` to avoid stack overflow if GK×BLK is large).

3. **Hoist A-scale restride and `gemmini_mx_load_scales(..., 0)` outside the j0 loop** (strategy 5): since `cur_A_s` only changes when i0 changes, fill it and load it once per i0, before the j0 loop begins.

4. **B-scale restride and `gemmini_mx_load_scales(..., 1)` stay inside the j0 loop** since B scales change every j0.

5. **Move `gemmini_flush` and `gemmini_extended3_config_ex` to the i0 level** (before the A-scale load) so the programming model order is satisfied: `config_ex → load_A_scales` happens at i0 entry, then per j0: `load_B_scales → mvin → mxquant_config → loop_ws_spad → read_smem → fence`.
