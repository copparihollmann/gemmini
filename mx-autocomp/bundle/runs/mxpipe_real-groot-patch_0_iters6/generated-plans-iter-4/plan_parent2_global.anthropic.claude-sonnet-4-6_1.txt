## Analysis of the Current Code

The current code has a J/K loop ordering for B tiles:
```c
for (int j = 0; j < tiles; j++)
  for (int k = 0; k < tiles_K; k++)
    gemmini_extended_mvin(..., b_base + (k * tiles + j) * DIM, ...);
```

The outer I/J/K loop nest iterates as `for i0 → for j0`, meaning for each (i0, j0) pair, all B tiles for that (i0, j0) block are loaded fresh. The B tiles loaded for (i0=0, j0=0) are discarded before (i0=1, j0=0) even though the B block at j0=0 is **identical** for all i0 values. This means B tiles are reloaded `BLOCKS_M` times unnecessarily — a significant waste since B is weight-stationary.

## Selected Strategy: Strategy 2 — Reorder I/J/K Loop Nest to Maximize Weight-Stationary B-Tile Reuse

### Plan

**Reorder the outer loop nest from `for i0 → for j0` to `for j0 → for i0`.**

In weight-stationary mode, the B (weight) matrix tiles are fixed across all I (activation row) iterations. By making j0 the outermost loop and i0 the inner loop:

1. B tiles for block `j0` are loaded **once** into the scratchpad
2. All `BLOCKS_M` activation blocks (i0 = 0..BLOCKS_M-1) are processed against the same B tiles
3. Only A tiles and scales change per i0 iteration; B tiles and B scales remain resident

### Concrete Changes

**1. Swap the loop order:**
```c
for (int j0 = 0; j0 < BLOCKS_N; j0++) {
  // compute ncols, load B scales and B tiles ONCE here
  for (int i0 = 0; i0 < BLOCKS_M; i0++) {
    // compute mrows, load A scales and A tiles per i0
  }
}
```

**2. Hoist B-tile mvin and B-scale loading out of the i0 loop:**
- `B_s` scales: `memcpy(&B_s[g][0], &B_scales_col[g][j0 * BLK], BLK)` moves to the j0 loop body, executed once per j0.
- `gemmini_config_ld(MATMUL_N * sizeof(elem_t))` and the B-tile mvin loop move to the j0 level.
- `b_base` is constant given `tiles` and `tiles_K` (which don't change), so it can be computed once.

**3. Keep A-tile mvin and A-scale loading inside the i0 loop:**
- `A_s` scales: `memcpy(&A_s[g][0], &A_scales_row[g][i0 * BLK], BLK)` stays per i0.
- `gemmini_config_ld(MATMUL_K * sizeof(elem_t))` and the A-tile mvin loop stay per i0.

**4. Handle `gemmini_flush` and `gemmini_extended3_config_ex` placement:**
- `gemmini_flush(0)` must only be called once (or at least not per-i0 since it resets all state). Move it outside both loops (or keep it at the j0 level but note it resets B-resident tiles). Since flush invalidates scratchpad state, it must be called before B tiles are loaded — place it at the start of the j0 loop **before** B mvin.
- `gemmini_extended3_config_ex` also moves to j0 level (format doesn't change across iterations).

**5. `gemmini_mx_load_scales` must load both A and B before each `gemmini_loop_ws_spad`** (per the programming model sequence and rule 15). So per i0:
  - Load A scales via `gemmini_mx_load_scales((uint64_t)A_s, A_S_BYTES, 0)`
  - Load B scales via `gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1)` — B_s is already filled (hoisted), so this is just the intrinsic call (no memcpy overhead), amortizing the memcpy cost across BLOCKS_M iterations.

**6. `ncols`, `pad_j`, and `BLK_OUTC` are constant for a given j0** — compute them once at the j0 level. `mrows`, `pad_i` vary per i0 — keep them inside.

### Expected Benefit

Currently, for BLOCKS_M outer iterations per j0: each (i0, j0) pair does a full B memcpy + B mvin. After reordering:
- B memcpy: reduced from `BLOCKS_M × BLOCKS_N` to `BLOCKS_N` calls (saving `(BLOCKS_M-1) × BLOCKS_N` memcpy calls)
- B mvin instructions: reduced from `BLOCKS_M × BLOCKS_N × tiles × tiles_K` to `BLOCKS_N × tiles × tiles_K` total B mvin instructions
- The `gemmini_flush` cost is also paid only `BLOCKS_N` times instead of `BLOCKS_M × BLOCKS_N` times

For a 41×512×512 problem with BLK-sized blocks, BLOCKS_M ≈ 3 (ceil(41/BLK)), so this eliminates approximately 2/3 of all B data movement and flush overhead.
