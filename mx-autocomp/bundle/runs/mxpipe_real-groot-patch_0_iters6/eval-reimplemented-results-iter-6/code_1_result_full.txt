Since B scales persist from `j0`-level load, we only call `gemmini_mx_load_scales` for A inside `i0`.

Wait — per rule 15: scales must be loaded before each `gemmini_loop_ws_spad`. B scales loaded at `j0` level are still valid for all subsequent `i0` invocations (same B block, same scales). A scales must be reloaded per `i0`. This is correct.

The programming model sequence per `(i0, j0)` compute call becomes:
- B loaded (mvin + scale) at `j0` level (once)
- Per `i0`: load A scales → mvin A → config_mvout → loop_ws_spad → read_smem → fence ✓

This reduces total `gemmini_mx_load_scales(B)` calls from `BLOCKS_M * BLOCKS_N` to `BLOCKS_N`, and total B mvin instructions from `BLOCKS_M * BLOCKS_N * tiles * tiles_K` to `BLOCKS_N * tiles * tiles_K`. With `BLOCKS_M = ceil(41/64) = 1` and `BLOCKS_N = ceil(512/64) = 8`, the savings are modest for this problem size, but the structure is correct for larger M.

More impactfully: **eliminate `gemmini_flush` from inside the loop** — it was called `BLOCKS_M * BLOCKS_N` times, flushing the pipeline every iteration. Move it outside.
