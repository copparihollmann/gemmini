## Analysis

Looking at the original code, I identify the key inefficiency targeted by **Strategy 3**: B tiles are reloaded for every `(i0, j0)` block pair, even though in a weight-stationary dataflow, the same B block (weight) is reused across all `i0` (row) tiles for a fixed `j0` (column) tile.

Currently the outer loop is `for i0: for j0:`, meaning B is loaded `BLOCKS_M` times per unique `j0`. By swapping to `for j0: for i0:`, the B tiles for a given `j0` can be loaded **once** into the fixed high-address scratchpad region and reused across all `i0` iterations. Similarly, the B scales only need to be loaded once per `j0`.

## Plan: Weight-Stationary B Reuse (Strategy 3)

### What to change:

1. **Swap the outer loop order** from `for i0: for j0:` to `for j0: for i0:`. This makes `j0` the outermost loop so B stays fixed while `i0` varies.

2. **Hoist B mvin and B scale loading outside the inner `i0` loop**: For each `j0`, load `pre_B_s[j0]` scales and mvin B tiles into scratchpad once. These B tiles sit at `b_base = BANK_NUM*BANK_ROWS - tiles*tiles_K*DIM` (fixed top of scratchpad) and remain valid for all `i0` iterations.

3. **Keep A mvin and A scale loading inside the inner `i0` loop**: A changes with each `i0`, so it must still be loaded per `i0` iteration. A tiles go at `a_base = 0` (bottom of scratchpad).

4. **Move `gemmini_extended3_config_ex` and `gemmini_config_ld` for B outside the `i0` loop** (but keep them inside `j0`): The config only needs to be set once per `j0` block since format doesn't change. The `gemmini_config_ld` for B (stride = `MATMUL_N * sizeof(elem_t)`) is set once per `j0` before the B mvin loop.

5. **Inside the `i0` loop**: load A scales, mvin A tiles (reconfiguring `gemmini_config_ld` to `MATMUL_K * sizeof(elem_t)` first), then issue `gemmini_mxquant_config_mvout`, `gemmini_loop_ws_spad`, `gemmini_mx_read_smem`, and `gemmini_fence()`.

6. **Maintain programming model order within each `i0` iteration**: The sequence must be `config_ex → load_scales(A) → load_scales(B)` — but B scales are already loaded at the `j0` level. To satisfy the rule that both A and B scales must be loaded before `loop_ws_spad`, we load A scales inside `i0` (sel=0) and rely on the already-loaded B scales (sel=1) persisting in hardware state since they haven't been overwritten. This is valid per the architecture doc: "Persist in hardware state until overwritten."

7. **Result**: B is loaded `BLOCKS_N` times total instead of `BLOCKS_M * BLOCKS_N` times, reducing mvin traffic by a factor of `BLOCKS_M`. The `gemmini_flush` also moves outside the `i0` loop (to once per `j0`), reducing flush overhead.

The scratchpad layout remains valid: A tiles at `a_base=0` occupy `tiles_I_single * tiles_K * DIM` rows (where `tiles_I_single = tiles = BLK/DIM`), and B tiles at the top occupy `tiles * tiles_K * DIM` rows. Constraint: `(tiles*tiles_K + tiles*tiles_K)*DIM ≤ 8192` — with `tiles=4, tiles_K=32`: `(4*32 + 4*32)*16 = 4096 ≤ 8192`. ✓
