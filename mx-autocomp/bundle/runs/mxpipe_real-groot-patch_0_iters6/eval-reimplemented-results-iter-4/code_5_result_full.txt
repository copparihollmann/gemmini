2. It flushes Gemmini
3. It re-issues `gemmini_extended3_config_ex`
4. It **re-mvins all B tiles** for every `i0` iteration — even though B tiles for a given `j0` column block are identical across all `i0` row blocks
5. It calls per-row `gemmini_mx_read_smem`

The key inefficiency: **B tiles for column block `j0` are loaded `BLOCKS_M` times** (once per `i0`). For a 41×512×512 problem, this is enormous waste.

### The Plan: Restructure to `j0`-outer, `i0`-inner Loop with B Tile Reuse

**However**, we must respect the programming model ordering constraint: `gemmini_extended3_config_ex → load_scales → mvin → mxquant_config_mvout → loop_ws_spad → read_smem → fence`. 1. **Outer loop: `j0`** — mvin B tiles once into the scratchpad top region
2. **Inner loop: `i0`** — for each row block, only mvin A tiles (much smaller), reload scales (A and B scales are block-specific but B scales for same `j0` change per `i0` too — wait, B scales are indexed `B_scales_col[g][j0*BLK]` which is j0-only, so **B scales are constant across i0 for a fixed j0**)
3. Reload only A scales per `i0`, B scales once per `j0`
4. Skip re-mvin of B tiles in the inner `i0` loop

- `A_s[g][0..BLK]` ← `A_scales_row[g][i0*BLK]` — changes per `i0` ✓ must reload
- `B_s[g][0..BLK]` ← `B_scales_col[g][j0*BLK]` — **fixed for all `i0` at same `j0`** ✓ load once

**Scratchpad layout with B reuse:**
- B tiles: `b_base = BANK_NUM*BANK_ROWS - tiles_K * tiles_J_block * DIM` (top, fixed for j0 outer loop)
  - `tiles_J_block = BLK/DIM`, `tiles_K = MATMUL_K/DIM`
  - B region: `tiles_K * tiles_J_block * DIM` rows
- A tiles: `a_base = 0`, A region: `tiles_I_block * tiles_K * DIM` rows
  - `tiles_I_block = BLK/DIM` → `(BLK/DIM)*tiles_K*DIM = BLK*tiles_K` rows

**Scratchpad feasibility check** (BLK=32, tiles_K=512/16=32, tiles_J_block=tiles_I_block=2):
- A: `2 * 32 * 16 = 1024` rows
- B: `32 * 2 * 16 = 1024` rows
- Total: 2048 rows << 8192 ✓

    gemmini_flush(0);

### Why This Is Faster

1. **B tile mvin reduction**: In the original code, B tiles are mvin'd `BLOCKS_M × BLOCKS_N` times total. In the new code, B tiles are mvin'd only `BLOCKS_N` times — a **`BLOCKS_M`-fold reduction** in B mvin instructions. For 41 rows and `BLOCKS_M = ceil(41/32) = 2`, this halves the B mvin count. For larger M, the saving scales linearly.

2. **Config/flush amortization**: `gemmini_flush(0)` is issued once instead of `BLOCKS_M × BLOCKS_N` times. The config_ex is still re-issued per `(i0, j0)` pair (required by the programming model), but the flush overhead is eliminated.

3. **Bulk smem read**: Replaces `mrows` individual `gemmini_mx_read_smem` calls (one per row, up to 32 calls) with a single call covering `mrows * ncols` BF16 elements. This reduces instruction-issue overhead from O(mrows) to O(1) per output block.

4. **Correctness preserved**: B tile data in the scratchpad is not modified between the outer mvin and the inner compute loops. Scale factors are re-staged correctly per `(i0, j0)` pair. The programming model order is maintained within each `i0` iteration: `config_ex → load_scales (A, B) → mvin_A → mxquant_config → loop_ws_spad → read_smem → fence`.
