## Analysis

The original code calls `gemmini_flush(0)` inside the per-tile outer loop (every `(i0, j0)` iteration). According to the architecture documentation and strategy 6, `gemmini_flush` drains the **entire pipeline** and dominates per-tile overhead when called every iteration. This is clearly wasteful — the flush is needed once at kernel entry to reset hardware state, but subsequent iterations don't need it because the accelerator state (format, dataflow) is being explicitly reconfigured anyway via `gemmini_extended3_config_ex`.

## Plan: Eliminate `gemmini_flush` from the Per-Tile Inner Loop (Strategy 6)

### What to change

1. **Move `gemmini_flush(0)` out of the `for (i0) for (j0)` loop** — call it exactly once before the loop begins.

2. **Remove `gemmini_flush(0)` from inside the loop body** — it currently appears at the top of every `(i0, j0)` iteration, stalling the pipeline completely each time.

### Why this is correct

- `gemmini_flush` is needed once to drain any residual pipeline state at kernel entry (e.g., stale instructions from a previous kernel). After that single flush, the hardware is in a clean state.
- Each subsequent `(i0, j0)` iteration calls `gemmini_extended3_config_ex` to reconfigure the accelerator, then issues its own `gemmini_fence()` after `gemmini_mx_read_smem`. The fence already ensures all accelerator work from the prior tile completes before the next tile's loads begin — there is no need for a full pipeline drain.
- The programming model sequence is preserved: config → load_scales → mvin → mxquant_config_mvout → loop_ws_spad → read_smem → fence. The flush is not part of the required per-tile sequence.
- No tile reorders or data dependencies are changed; semantic equivalence is maintained.

### Specific code change

**Before (inside the loop):**
```c
for (int i0 = 0; i0 < BLOCKS_M; i0++)
  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    ...
    // PROF accel
    gemmini_flush(0);                          // ← called every tile iteration
    gemmini_extended3_config_ex(...);
    ...
  }
```

**After (moved before the loop):**
```c
gemmini_flush(0);                              // ← called once at kernel entry
for (int i0 = 0; i0 < BLOCKS_M; i0++)
  for (int j0 = 0; j0 < BLOCKS_N; j0++) {
    ...
    // PROF accel
    gemmini_extended3_config_ex(...);          // ← flush removed from here
    ...
  }
```

This eliminates `BLOCKS_M * BLOCKS_N - 1` unnecessary full pipeline stalls, each of which previously serialized all in-flight accelerator operations before any useful work could begin for the next tile.
