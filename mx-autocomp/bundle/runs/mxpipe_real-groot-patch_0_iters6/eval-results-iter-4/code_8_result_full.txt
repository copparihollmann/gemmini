The profiler flagged 2 `memcpy` calls per `(i0, j0)` iteration as a dominant cost. Looking at the original code: it copies `BLK` bytes per group into `A_s[g][0]`, making `A_s` a contiguous `[MATMUL_K/32][BLK]` array, then loads `A_S_BYTES = (MATMUL_K/32)*BLK` bytes in one call. The source `A_scales_row[g][i0*BLK]` is not contiguous across groups (there's a stride in the second dimension), so we cannot eliminate the staging entirely without changing the scale data layout.

**Instead**, we eliminate the **B-side memcpy** by hoisting B scale loading outside the i0 loop, and only do A-side staging (which is unavoidable given the layout) inside the i0 loop.

    // B data is constant across all i0 iterations for this j0.

    gemmini_fence();

      gemmini_mx_load_scales((uint64_t)B_s, B_S_BYTES, 1);

      gemmini_config_ld(MATMUL_K * sizeof(elem_t));
      for (int i = 0; i < tiles; i++)

            a_base + (i * tiles_K + k) * DIM, DIM, DIM);

    }

## Why This Improves Performance

| Cost | Original | Optimized |
|------|----------|-----------|
| B-tile mvin calls | `BLOCKS_M × BLOCKS_N × tiles × tiles_K` | `BLOCKS_N × tiles × tiles_K` (÷ BLOCKS_M) |
| B memcpy calls | `BLOCKS_M × BLOCKS_N × (K/32)` | `BLOCKS_N × (K/32)` (÷ BLOCKS_M) |
| A memcpy calls | `BLOCKS_M × BLOCKS_N × (K/32)` | unchanged |
| A-tile mvin calls | `BLOCKS_M × BLOCKS_N × tiles × tiles_K` | unchanged |

For the 41×512×512 problem with `BLOCKS_M=2`, this halves B-tile DMA traffic and halves B-scale memcpy overhead. For larger M dimensions (more BLOCKS_M), the savings scale linearly.
