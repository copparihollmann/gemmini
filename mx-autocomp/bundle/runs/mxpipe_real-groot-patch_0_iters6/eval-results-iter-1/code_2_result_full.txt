**Key inefficiencies:**

1. **`gemmini_extended3_config_ex` is called `BLOCKS_M × BLOCKS_N` times** but the MX format (`act_mx_fmt=0, wgt_mx_fmt=0, out_mx_fmt=3, uselut=0`) is **invariant across all tiles**. 2. **`gemmini_flush(0)` is called `BLOCKS_M × BLOCKS_N` times**. A flush is only needed once at initialization; repeated flushes inside the tile loop add unnecessary synchronization overhead.

3. **The loop order is `i0` (M-block) outer, `j0` (N-block) inner**. In weight-stationary mode, the B matrix is stationary — a given `j0` B-block (weight tile column block) is reused across **all `i0` iterations**. With the current `i0`-outer/`j0`-inner ordering, the B-tile for a given `j0` is only used once before we move to the next `j0`, which means we **reload B scales and B tiles every iteration of `j0` within each `i0`**. 

   If we **swap to `j0`-outer / `i0`-inner**, then for a fixed `j0`, we loop over all `i0` values. The B-block (columns `j0*BLK` to `(j0+1)*BLK`) and its scale factors **do not change across the inner `i0` loop**. This means:
   - `B_s` (B scale factors for this `j0` block) is the **same for all `i0`** — we load it once per `j0` instead of once per `(i0, j0)` pair.
   - The B tiles themselves are mvin'd once per `j0` (into the scratchpad) and reused across all `i0` iterations (though note: since scratchpad must hold all tiles simultaneously, we still re-load per invocation — but with `j0` outer we can see that B-scale loading and B-data loading amortize over the `i0` loop).

4. **Scale memcpy overhead**: The `memcpy` for `A_s` and `B_s` copies scale factors from the global arrays into staging buffers. With `j0`-outer ordering, **`B_s` only needs to be staged once per `j0` block** (not once per `(i0,j0)` pair).

### Strategy 2: Hoist `gemmini_extended3_config_ex` outside all loops
