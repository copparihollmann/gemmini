## Analysis of the Current Code

The current code calls `gemmini_extended3_config_ex` **inside the outer `i0 × j0` loop**, once per block pair. Since the MX format fields (`act_mx_fmt=0`, `wgt_mx_fmt=0`, `out_mx_fmt=3`, `uselut=0`) and dataflow (`WEIGHT_STATIONARY`) never change across any iteration, this is a redundant re-issue on every loop iteration.

## Selected Strategy: Hoist `gemmini_extended3_config_ex` Outside All Loops

### Why This Is Applicable

- `gemmini_extended3_config_ex` configures static hardware state: dataflow, MX format encoding, strides, transposes, and activation function.
- In the current code, the call `gemmini_extended3_config_ex(WEIGHT_STATIONARY, 0, 0, ACC_SCALE_IDENTITY, 1, 1, 0, 0, false, 0, 0, 3, 0)` is issued unconditionally on every `(i0, j0)` block iteration — up to `BLOCKS_M × BLOCKS_N` times.
- None of the arguments change between iterations: the format is always FP8→BF16 (`act_mx_fmt=0, wgt_mx_fmt=0, out_mx_fmt=3`), `uselut=0`, strides are always `1`, no transposes, no activation.
- `gemmini_flush(0)` is also inside the loop but only needs to be called once at startup to reset the accelerator state.

### Specific Changes

1. **Move `gemmini_flush(0)` to before the outer `i0` loop** — it only needs to be issued once to initialize the accelerator.
2. **Move `gemmini_extended3_config_ex(...)` to immediately after `gemmini_flush(0)`, before the outer `i0` loop** — the configuration is invariant across all `(i0, j0)` tile pairs, so issuing it once is sufficient and correct per the programming model (config persists until changed).

### What Remains Inside the Loop

Everything else stays in place: `gemmini_mx_load_scales` (must be per-block since scales differ per `i0`/`j0`), the mvin loops, `gemmini_mxquant_config_mvout`, `gemmini_loop_ws_spad`, `gemmini_mx_read_smem`, and `gemmini_fence()`. The programming model sequence is preserved: config_ex (once, before all blocks) → load_scales (per block, before compute) → mvin → mxquant_config_mvout → loop_ws_spad → read_smem → fence.

### Expected Benefit

Eliminates `BLOCKS_M × BLOCKS_N - 1` redundant `gemmini_extended3_config_ex` instructions and the same number of `gemmini_flush` calls. Each flush and config_ex instruction carries non-trivial overhead (fence-like pipeline drain for flush; RoCC instruction dispatch for config_ex). Hoisting them out reduces total instruction count proportionally to the number of tile blocks.
