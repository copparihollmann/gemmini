## Analysis of the Current Code

The current code has **2 memcpy calls per (i0, j0) block iteration** to copy scale factors from `A_scales_row[g][i0*BLK...]` and `B_scales_col[g][j0*BLK...]` into intermediate buffers `A_s` and `B_s`. These memcpy operations happen on the CPU host every block iteration, and the feedback explicitly flags this as CPU staging overhead.

## Selected Strategy: #4 — Eliminate A_s/B_s intermediate buffers

### Why this strategy applies

The scale arrays `A_scales_row[GK][M]` and `B_scales_col[GK][N]` are already in DRAM in row-major layout. `gemmini_mx_load_scales(dram_addr, len, sel)` streams `len` bytes from `dram_addr` into scale memory. The question is whether the hardware expects a contiguous block of `tiles * (BLK / GK)` bytes or the specific strided layout.

Looking at the current code: for each of the `MATMUL_K/32` groups `g`, it copies `BLK` bytes from `A_scales_row[g][i0*BLK]` into `A_s[g][0]`. The result is that `A_s` is a contiguous 2D array `[GK][BLK]`, loaded as a flat `A_S_BYTES = (MATMUL_K/32) * BLK` byte block.

The source `A_scales_row[g][i0*BLK]` has stride `M` (full matrix width) between groups, but the destination `A_s` has stride `BLK`. So the copy is **restriding** the scale data — the scale memory does not have the same layout as a direct contiguous read from `A_scales_row`.

### Optimization Plan

**Pre-compute contiguous scale staging buffers once at initialization time** (or as static allocations), instead of memcpy-ing every block iteration:

1. **Declare static/global pre-transposed scale buffers** sized `[MATMUL_K/32][BLK_MAX]` for both A and B, covering the maximum block size.

2. **At the start of `solution()` (once, before the loop)**, pre-copy the *entire* scale layout for all blocks into pre-staged flat arrays organized as `pre_A_scales[i0][g*BLK ... (g+1)*BLK]` and similarly for B. This is a one-time O(total_scale_data) cost rather than a per-block cost.

3. **Replace the per-iteration inner `g` loop memcpy** with a single pointer lookup into the pre-staged array — no copying, just passing the pre-staged address directly to `gemmini_mx_load_scales`.

Concretely:

- Before the `i0/j0` loop, allocate (statically or as local arrays) `pre_A_s[BLOCKS_M][GK][BLK]` and `pre_B_s[BLOCKS_N][GK][BLK]` and fill them once with the restride:
  ```c
  for (int i0 = 0; i0 < BLOCKS_M; i0++)
    for (int g = 0; g < GK; g++)
      memcpy(&pre_A_s[i0][g][0], &A_scales_row[g][i0*BLK], BLK);
  for (int j0 = 0; j0 < BLOCKS_N; j0++)
    for (int g = 0; g < GK; g++)
      memcpy(&pre_B_s[j0][g][0], &B_scales_col[g][j0*BLK], BLK);
  ```

- Inside the `i0/j0` loop, replace the memcpy block with:
  ```c
  // No per-iteration memcpy — use pre-staged pointers directly
  gemmini_mx_load_scales((uint64_t)pre_A_s[i0], A_S_BYTES, 0);
  gemmini_mx_load_scales((uint64_t)pre_B_s[j0], B_S_BYTES, 1);
  ```

This amortizes the restriding CPU work across all `BLOCKS_M * BLOCKS_N` iterations (each block pair reuses the pre-staged data), reducing the per-iteration CPU cost from `2 * GK` memcpy calls to zero memcpy calls. The total memcpy work is now `BLOCKS_M * GK + BLOCKS_N * GK` instead of `BLOCKS_M * BLOCKS_N * 2 * GK`, which for non-trivial block counts is a significant reduction.
