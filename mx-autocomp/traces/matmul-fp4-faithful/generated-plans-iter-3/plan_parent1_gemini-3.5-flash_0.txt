An elegant and highly effective optimization plan to improve the performance of this MX-matmul kernel is **Strategy 1: Loop Reordering and Restructuring**. 

### Analysis of Inefficiencies in Baseline
1. **Incomplete Coverage & Output Alignment**: The baseline code only computes a single partial block of size `ti = MATMUL_M / DIM / 2` and `tj = MATMUL_N / DIM / 2`. To compute the complete $128 \times 128 \times 256$ matrix, we must cover all tiles while respecting the accumulator size constraint of $\le 256$ rows.
2. **Redundant DRAM Loads**: In a weight-stationary dataflow, the weight matrix $B$ is stationary. In the baseline, $B$ is loaded inside the same scope as $A$. By restructuring the loops, we can hoist the loading of $B$ entirely out of the outer block loop over the $M$ dimension, loading $B$ exactly once and reusing it for all blocks of $A$.
3. **Contiguous Output Stores**: Choosing $t_i = 2$ and $t_j = 8$ (full $N$ width) fits the accumulator exactly ($2 \times 8 \times 16 = 256$ rows) and ensures that each computed block of output is fully contiguous in DRAM, matching the layout of `C_hw` and avoiding complex strided write-backs.

---

### Optimization Plan

1. **Outer-Loop Tiling**:
   - Set $t_i = 2$, $t_j = 8$ (full width), and $t_k = 16$.
   - Loop over the $M$ dimension with `block_i` from `0` to `3` (since $\frac{\text{MATMUL\_M}}{t_i \times \text{DIM}} = \frac{128}{32} = 4$ blocks).

2. **Hoist Weight Loads ($B$)**:
   - Before entering the `block_i` loop, load the entire $B$ matrix into the scratchpad once at address `bb`. Since $B$ is shared across all blocks along the $M$ dimension, we completely amortize the DRAM transfer of weights.

3. **Restructured Block Loop**:
   - Inside the `block_i` loop:
     - Load the corresponding $A$ tiles from DRAM at the correct offset: `((elem_t*)A_in_hw) + (block_i * ti * DIM) * MATMUL_K + k * DIM`.
     - Update the requantization config `gemmini_mxquant_config_mvout` with the correct pointer to `scale_factors` offset for the current row: `scale_factors + (block_i * ti * DIM) * (MATMUL_K / 32)`.
     - Execute the fused hardware loop `gemmini_loop_ws_spad`.
     - Drain the computed results from shared memory (`mx_smem`) to the contiguous block of DRAM starting at `&C_hw[block_i * ti * DIM][0]`.
     - Issue `gemmini_fence()` at the end of each iteration to prevent RAW (read-after-write) hazards on `mx_smem` before the next block's compute begins.

This plan perfectly adheres to the hardware constraints, obeys the programming sequence, and drastically reduces execution latency.
