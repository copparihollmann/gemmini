## Analysis

The current code has a per-row `gemmini_mx_read_smem` loop:

```c
for (int r = 0; r < mrows; r++)
    gemmini_mx_read_smem(&C_hw[i0 * BLK + r][(j0 * BLK) / BF16_PER_WORD],
                         SPAD_DEST * 16 + r * BLK, ncols);
```

This issues `mrows` separate `gemmini_mx_read_smem` instructions (up to `BLK` = 32 or similar per output tile). Each instruction is a separate RoCC command with overhead.

## Strategy: Replace per-row loop with single bulk `gemmini_mx_read_smem`

**Strategy 4**: Replace per-row `gemmini_mx_read_smem` loop with a single bulk call.

## Plan

**Condition for bulk read**: The smem layout after `gemmini_loop_ws_spad` stores results row-major starting at `SPAD_DEST * 16`, with row stride = `BLK` (the tile width in BF16 elements). The DRAM output buffer `C_hw[i0*BLK + r][(j0*BLK)/BF16_PER_WORD]` advances by `OUT_COLS` uint64 words (= `MATMUL_N / BF16_PER_WORD` words) per row in DRAM, but in smem each row is `BLK` BF16 elements wide.

For the **full-block case** (`mrows == BLK` and `ncols == BLK`): smem is contiguous for all `mrows * ncols` elements starting at `SPAD_DEST * 16`, and DRAM destination row `r` is `&C_hw[i0*BLK + r][(j0*BLK)/BF16_PER_WORD]`. However, if DRAM rows are not contiguous (stride = `OUT_COLS` words ≠ `BLK/BF16_PER_WORD` words when `BLK < MATMUL_N`), a single bulk read cannot span multiple rows correctly.

**Key insight**: `gemmini_mx_read_smem` with `num_bf16 = mrows * ncols` reads `mrows * ncols` contiguous BF16 values from smem into a **contiguous** DRAM region. The smem is indeed contiguous (row stride = `BLK`, total = `mrows * BLK` words with padding). We can read the entire `mrows * BLK` smem block into a **temporary contiguous staging buffer**, then do a single strided copy to `C_hw` — but that reintroduces CPU work.

**Better approach**: Since `ncols` may equal `BLK` and the smem block is `mrows` rows × `BLK` BF16 elements (contiguous), issue a **single** `gemmini_mx_read_smem` with `num_bf16 = mrows * BLK` into a contiguous output buffer when `ncols == BLK` (full N block), and for partial blocks keep the per-row loop. When `ncols == BLK`, the entire block output `C_hw[i0*BLK][j0*BLK/BF16_PER_WORD]` ... `C_hw[i0*BLK + mrows - 1][...]` is contiguous in DRAM **only if** `C_hw` row stride equals `BLK/BF16_PER_WORD` — i.e., only if `MATMUL_N == BLK`. Otherwise it is not contiguous.

**Correct general approach**: Replace the per-row loop with a single bulk `gemmini_mx_read_smem` call reading `mrows * ncols` BF16 values from smem into a **local contiguous scratch buffer**, then memcpy each row from that buffer to `C_hw`. But the instruction count reduction is the goal.

**Simplest correct approach** matching Strategy 4 exactly: When `ncols == BLK` (full-width output tile), the smem contains `mrows * BLK` contiguous BF16s. Issue one `gemmini_mx_read_smem` writing into a contiguous `out_buf[mrows * BLK/BF16_PER_WORD]` uint64 array, then copy rows to `C_hw`. For partial `ncols`, keep the row loop (already just 1–2 rows typically). This reduces instruction count from `mrows` to 1 for the common full-block case.

**Actual simplest approach**: Read the full smem block (`mrows * BLK` BF16s) as one call into an aligned intermediate buffer, then scatter rows to `C_hw`. This always issues exactly 1 `gemmini_mx_read_smem` regardless of `mrows`, reducing from up to 32 instructions to 1, at the cost of a small CPU memcpy (which is much cheaper than RoCC instruction overhead × mrows).

The concrete change:

```c
// Before (mrows instructions):
for (int r = 0; r < mrows; r++)
    gemmini_mx_read_smem(&C_hw[i0*BLK+r][(j0*BLK)/BF16_PER_WORD],
                         SPAD_DEST*16 + r*BLK, ncols);
gemmini_fence();

// After (1 instruction + small CPU scatter):
static uint64_t smem_buf[BLK * BLK / BF16_PER_WORD] __attribute__((aligned(64)));
gemmini_mx_read_smem((uint64_t)smem_buf, SPAD_DEST * 16, mrows * BLK);
gemmini_fence();
for (int r = 0; r < mrows; r++)
    memcpy(&C_hw[i0*BLK+r][(j0*BLK)/BF16_PER_WORD],
           &smem_buf[r * (BLK / BF16_PER_WORD)],
           (ncols / BF16_PER_WORD) * sizeof(uint64_t));
```

This reads `mrows * BLK` BF16s (full smem rows including any right-padding) into a contiguous buffer, then CPU-copies only the valid `ncols` elements per row to the output. The `gemmini_fence()` moves before the CPU scatter (still after `gemmini_mx_read_smem`, satisfying Rule 9). The smem always has `BLK`-wide rows, so reading `mrows * BLK` is always valid and contiguous. Instruction count drops from `mrows` RoCC calls to 1, with the scatter being cheap DRAM-to-DRAM CPU memcpy.
